# Техническое задание для Claude Code

## Проект: портал, автообновление и система обратной связи для X-Piratez / OpenXcomEx

Ты работаешь над существующим игровым проектом и связанным с ним HD-модом. Не начинай с переписывания проекта и не выбирай технологии вслепую. Сначала исследуй репозиторий, текущий сайт, сборку игры, формат мода, размещение файлов, существующие API и инфраструктуру. Затем предложи реалистичный план и реализуй систему по этапам.

Главная цель: создать единый официальный контур распространения обновлений, восстановления файлов, сообщений об ошибках, предложений, документации и публичного roadmap. Пользователь должен установить один небольшой Windows-лаунчер, после чего он сможет проверять и устанавливать обновления игры/мода, восстанавливать пропавшие или повреждённые файлы, запускать игру и отправлять сообщения разработчикам.

Рабочие названия компонентов можно изменить после аудита:

- `Launcher` — Windows-лаунчер и updater;
- `GameIntegration` — минимальные изменения OpenXcomEx для F8 и crash-маркера;
- `Portal` — публичный сайт и кабинет пользователя;
- `Admin` — административная часть;
- `API` — серверное API;
- `ReleaseBuilder` — подготовка manifest и пакетов обновления.

## 1. Обязательный порядок начала работы

До написания основного кода:

1. Изучи весь репозиторий и составь краткую карту проекта: язык и версия OpenXcomEx, способ сборки, структура мода, текущий сайт, БД, хостинг, CI/CD, существующая авторизация.
2. Найди все `README`, build-скрипты, конфигурации, схемы БД и deployment-файлы. Не выводи секреты и не копируй их в логи.
3. Установи, какие части уже существуют и могут быть переиспользованы.
4. Зафиксируй неизвестные данные в `docs/OPEN_QUESTIONS.md`. Задавай мне вопрос только тогда, когда без ответа нельзя безопасно продолжать. Для остального используй разумные настройки по умолчанию и вынеси их в конфигурацию.
5. Создай `docs/ARCHITECTURE.md`, `docs/IMPLEMENTATION_PLAN.md` и список рисков.
6. Разбей реализацию на независимые этапы. После каждого этапа проект должен собираться и запускаться.
7. Не делай массовый рефакторинг существующей игры ради этой функции. Интеграция с движком должна быть минимальной и изолированной.

Если сайт уже написан и его стек пригоден, расширяй его. Если сайта или backend нет, предпочтительная базовая архитектура: ASP.NET Core/.NET 8 LTS для API и админки, PostgreSQL для данных, S3-совместимое object storage для вложений и релизов, отдельный Windows launcher на C#/.NET 8. Это рекомендация, а не приказ: после аудита обоснуй окончательный выбор.

## 2. Автообновление игры, `.exe` и мода

### 2.1 Общая модель

Обновлением занимается отдельный launcher/updater. Запущенный игровой `.exe` не должен пытаться перезаписать сам себя.

Лаунчер должен:

- запускаться на Windows 10/11 без Linux и WSL;
- определять каталог игры, текущую версию лаунчера, OpenXcomEx и мода;
- получать с сайта подписанный manifest выбранного канала обновлений;
- поддерживать как минимум каналы `stable` и `test`, по умолчанию `stable`;
- сравнивать файлы по пути, размеру и SHA-256;
- скачивать только новые, изменённые или отсутствующие файлы;
- иметь отдельную кнопку **«Проверить/восстановить файлы»**;
- показывать общий размер, прогресс, скорость, текущий файл и понятную ошибку;
- уметь докачивать после разрыва соединения через временные `.part`-файлы;
- проверять хэш каждого скачанного файла до установки;
- устанавливать обновление атомарно: staging → проверка → замена;
- создавать резервную копию заменяемых критических файлов и поддерживать откат последнего обновления;
- не удалять пользовательские сейвы, настройки, скриншоты и иные данные, если они явно не включены в безопасную миграцию;
- не заменять изменённые пользователем файлы молча: manifest должен различать управляемые файлы и пользовательские файлы;
- блокировать обновление, пока игра запущена;
- вести локальный лог обновления без токенов, паролей и персональных данных;
- после успешной проверки запускать игру из лаунчера.

### 2.2 Обновление самого лаунчера

Самообновление реализуй через маленький bootstrapper либо второй updater-процесс:

1. launcher скачивает новую версию во временный каталог;
2. проверяет подпись и SHA-256;
3. запускает bootstrapper и закрывается;
4. bootstrapper заменяет файлы launcher атомарно;
5. при ошибке восстанавливает предыдущую версию;
6. запускает обновлённый launcher.

Никогда не исполняй файл, если его хэш или цифровая подпись не прошли проверку.

### 2.3 Manifest и релизы

Создай документированную схему manifest с версионированием. Manifest должен содержать минимум:

- версию схемы;
- ID и версию релиза;
- канал;
- минимально допустимую версию launcher;
- changelog;
- список файлов: относительный нормализованный путь, размер, SHA-256, URL/ключ объекта, тип компонента;
- признак обязательного обновления только для случаев несовместимости или критической уязвимости;
- список управляемых удалений;
- дату публикации;
- криптографическую подпись manifest.

Используй асимметричную подпись, например Ed25519. Закрытый ключ существует только в защищённом release/CI окружении. В launcher хранится только открытый ключ. Не доверяй одному HTTPS и не храни секрет подписи в клиенте.

Защити updater от path traversal: никакой путь из manifest не может выйти за разрешённый каталог, быть абсолютным, UNC-путём или содержать опасные сегменты. Ограничь размер загрузок и проверь свободное место на диске.

### 2.4 Публикация релиза

Сделай отдельный инструмент или CI-задачу `ReleaseBuilder`, которая:

1. принимает подготовленный каталог версии;
2. считает размеры и SHA-256;
3. создаёт manifest;
4. подписывает manifest;
5. загружает файлы/пакеты в object storage/CDN;
6. публикует релиз сначала как draft;
7. после подтверждения делает его доступным выбранному каналу;
8. умеет пометить релиз отозванным и переключить канал на предыдущую стабильную версию.

## 3. F8: скриншот, пауза и форма сообщения

При нажатии F8 во время игры должна происходить следующая последовательность:

1. Снять скриншот текущего кадра без интерфейса формы отчёта.
2. Сразу поставить игру на настоящую паузу: игровое время, AI, таймеры и ввод в игровой мир не продолжаются.
3. Открыть поверх игры модальное окно обратной связи. Игра остаётся открыта.
4. Предзаполнить технические данные: версия игры, мода и launcher, ОС, режим экрана, текущий экран/состояние игры, timestamp и идентификатор сессии. Не собирать лишние персональные данные.
5. Предложить тип обращения: `Баг`, `Графика`, `Предложение`, `Баланс`, `Перевод`, `Другое`.
6. Поля формы: короткий заголовок, описание, шаги воспроизведения, ожидаемый и фактический результат.
7. Скриншот прикреплён и показан в preview; пользователь может удалить его перед отправкой.
8. Дополнительно и только с явного согласия можно приложить последний лог и выбранный сейв. Рядом показать имя и размер каждого файла.
9. Кнопки: `Отправить`, `Сохранить как черновик`, `Отмена`.
10. После закрытия формы корректно вернуть прежнее состояние паузы: если игра уже была на паузе, она должна остаться на паузе; иначе продолжиться.

Предпочтительно встроить обработку F8 в event loop игры. Глобальный системный hotkey или отдельный overlay допустим только как документированный fallback, если исходный код игры невозможно изменить. Не перехватывай F8 вне запущенной игры.

Если интернет недоступен, сохрани обращение локально в очередь и предложи повторную отправку позже. Исключи дублирование с помощью client-generated UUID/idempotency key.

## 4. Отчёт после краша

Реализуй безопасное обнаружение аварийного завершения:

- при штатном запуске создаётся session marker;
- при штатном завершении marker закрывается/удаляется;
- при следующем старте launcher видит незакрытую сессию и предлагает отправить crash report;
- не считать крашем обычное принудительное завершение во время обновления или известное штатное закрытие;
- по возможности приложить crash dump, последний лог, версии компонентов и время сбоя;
- перед отправкой показать пользователю список файлов, их размеры и возможность снять любую галочку;
- отправка только после явного согласия; никаких фоновых автоматических загрузок;
- добавить поле комментария: что пользователь делал перед сбоем;
- после успеха показать номер тикета;
- при отсутствии сети сохранить пакет локально и повторить позже;
- реализовать ротацию локальных логов и crash-файлов, чтобы каталог не рос бесконечно.

Перед загрузкой сделай редактирование/очистку логов: по возможности убирай токены, cookies, email, имя Windows-пользователя и абсолютные домашние пути. Сейвы считать потенциально приватными данными.

- инструкции по установке, обновлению, восстановлению и удалению;
- база новых функций и изменений;

- графические утилиты;

- статус сервисов и известные проблемы, если это не создаёт лишнюю сложность.

### 5.1 Веб-форма тикета

Форма должна работать для гостя и зарегистрированного пользователя. Поля и категории согласуй с F8-формой. Разреши приложить:

- изображения PNG/JPG/WebP;
- текстовые логи;
- сейвы только разрешённых расширений;
- при необходимости ZIP, но архив нельзя распаковывать небезопасно и нельзя исполнять его содержимое.

Обязательны:

- ограничения расширений, MIME, magic bytes, размера и количества файлов;
- безопасные сгенерированные имена объектов;
- антивирусная проверка/карантин вложений;
- rate limit, защита от спама и CSRF;
- хранение вложений вне web-root;
- signed URL с коротким сроком жизни для доступа администраторов;
- запрет на выполнение загруженных файлов;
- политика хранения и удаления данных;
- согласие пользователя на отправку логов/сейвов.

После создания тикета показать номер и секретную ссылку для гостя либо добавить тикет в кабинет зарегистрированного пользователя. Не раскрывать приватные вложения публично.

### 5.2 Состояния и работа с тикетом

Минимальные состояния:

`new` → `triaged` → `in_progress` → `needs_info` → `resolved` → `closed`, а также `duplicate` и `rejected`.

Тикет должен иметь:

- номер, автора/гостя, категорию, заголовок, описание;
- версию игры/мода/launcher;
- вложения;
- ответственного и административную специализацию;
- приоритет и статус;
- внутренние заметки, невидимые пользователю;
- публичную переписку;
- историю изменений/audit log;
- ссылку на дубликат;
- даты создания и обновления.

## 6. Пользователи, роли и права

Нужны четыре уровня доступа:

1. `Guest` — незарегистрированный посетитель: публичные страницы, утилиты, создание тикета с защитой от спама, просмотр только своего тикета по секретной ссылке.
2. `User` — зарегистрированный пользователь: кабинет, свои тикеты, подписка на обновления тикета, управление своими данными.
3. `Admin` — обработка тикетов только в разрешённых направлениях.
4. `SuperAdmin` — полный доступ, роли, администраторы, релизы, настройки, roadmap, Telegram, аудит.

Для `Admin` добавь специализации/permissions, а не отдельные жёстко прошитые роли:

- `tickets.code` — баги движка и кода;
- `tickets.graphics` — графика;
- `tickets.balance`;
- `tickets.translation`;
- `tickets.general`;
- при необходимости `docs.edit` и `roadmap.edit`.

Администратор видит и меняет только разрешённые категории. SuperAdmin может назначать несколько специализаций. Проверка прав обязательна на сервере для каждого endpoint, а не только через скрытие кнопок в UI.

Требования к авторизации:

- безопасное хэширование паролей Argon2id или проверенный механизм выбранного фреймворка;
- подтверждение email и восстановление пароля, если email используется;
- MFA/TOTP как минимум для SuperAdmin, желательно для всех администраторов;
- защищённые HttpOnly/Secure/SameSite cookies либо корректный token flow;
- rate limit на вход;
- журнал административных действий;
- отсутствие открытой регистрации администраторов;
- первый SuperAdmin создаётся только через безопасную CLI/миграцию/переменную развёртывания, не через публичную страницу.

## 7. Telegram-уведомления

При создании нового тикета отправляй в настроенный Telegram-канал/группу короткое уведомление без скриншота, сейва, лога и полного текста обращения.

Допустимый состав сообщения:

- номер тикета;
- категория;
- короткий заголовок, безопасно обрезанный по длине;
- версия игры/мода;
- время;
- ссылка на тикет в админке.

Не отправляй персональные данные, email, IP, подробное описание и вложения. Telegram Bot Token хранится только как server-side secret. Уведомление отправляется фоновой очередью с retry/backoff и не должно отменять создание тикета при недоступности Telegram. Защити Markdown/HTML-разметку от инъекций.

Сделай настройку соответствия категории тикета Telegram topic/thread и/или группе администраторов. Например, `code` направляется ответственным за код, `graphics` — графическим администраторам. Управление маршрутизацией доступно только SuperAdmin.

## 8. Графические утилиты на сайте

Создай отдельный раздел с инструментами для проверки игровых изображений. Где возможно, обработка должна происходить локально в браузере через Canvas/WebAssembly без загрузки картинок на сервер.

Минимальный набор:

1. Сравнение двух картинок side-by-side.
2. Интерактивный before/after slider.
3. Наложение с регулировкой прозрачности.
4. Blink/переключение A/B с регулируемой скоростью.
5. Pixel-diff и тепловая карта различий.
6. Проверка ширины, высоты, формата, цветовой модели и наличия alpha.
7. Просмотр на светлом, тёмном и шахматном фоне.
8. Масштабирование nearest-neighbor и smooth, zoom и pan.
9. Для sprite sheets: задаваемые размер кадра, количество колонок/строк, отступы и просмотр отдельных кадров.
10. Экспорт diff/preview, если это можно сделать полностью локально.

Поставь разумные ограничения на разрешение и объём памяти, показывай понятную ошибку и не замораживай страницу на больших файлах; тяжёлые операции вынеси в Web Worker.

## 10. Roadmap

Публичный roadmap должен показывать:

- направления/этапы;
- короткое описание;
- статус `planned`, `in_progress`, `blocked`, `done`;
- процент выполнения от 0 до 100;
- планируемую версию или период без обещания точной даты;
- выполненные пункты и ближайшие планы;
- дату последнего обновления.

Процент не вычисляй по числу закрытых тикетов автоматически. Он задаётся ответственным либо считается по весам подзадач. В админке нужна проверка диапазона 0–100 и журнал изменений. Пользователям нельзя редактировать roadmap.

Все ссылки редактирует только SuperAdmin и они должны проходить allowlist допустимых HTTPS-доменов.

Если разрешение на использование имени, материалов или ссылки Dioxine не подтверждено, пометь это как блокирующий организационный вопрос, а не придумывай реквизиты.

## 12. API и модель данных

После аудита спроектируй версионированное API, например `/api/v1`. Необязательно строго повторять следующие имена, но должны быть эквивалентные сущности:

- `User`, `Role`, `Permission`, `AdminSpecialization`;
- `Ticket`, `TicketMessage`, `TicketAttachment`, `TicketHistory`;
- `GameSession`, `CrashReport`;
- `Release`, `ReleaseChannel`, `ReleaseFile`, `ReleaseManifest`;
- `DocumentationArticle`;
- `RoadmapItem`, `RoadmapHistory`;
- `DonationTarget`;
- `TelegramRoute`, `NotificationJob`;
- `AuditLog`.

Публичный manifest и release-файлы должны быть доступны без пользовательской авторизации, но с rate limit/CDN и обязательной проверкой подписи на клиенте. Административные операции — только по RBAC.

Для загрузок используй потоковую передачу, ограничения размера и object storage; не загружай большой сейв целиком в память. Поддержи idempotency для создания тикета и crash report. Ответ API при ошибке должен быть машинно читаемым и не раскрывать stack trace.

## 13. Безопасность и приватность

Обязательно учти:

- OWASP ASVS/Top 10 для web-части;
- HTTPS-only в production;
- строгую валидацию на сервере;
- CSP, HSTS, CSRF и безопасные cookies;
- parameterized queries/ORM без SQL-инъекций;
- защиту от IDOR: пользователь не может открыть чужой тикет перебором номера;
- безопасную обработку архивов и защиту от zip-slip/zip-bomb;
- секреты только в secret storage/environment, не в git;
- backup БД и object storage, проверяемое восстановление;
- audit log для ролей, релизов, настроек и удаления данных;
- удаление/анонимизацию данных пользователя по запросу, насколько это совместимо с диагностикой;
- понятный срок хранения логов, сейвов и crash dumps;
- Sentry/телеметрию подключать только с явным решением и без скрытого сбора данных.

Никакой удалённый manifest не должен позволять запуск произвольных команд, PowerShell/скриптов или запись за пределами каталогов компонентов. Миграции должны быть заранее определены и подписаны вместе с релизом; произвольные команды с сервера запрещены.

## 14. Наблюдаемость и эксплуатация

Добавь:

- структурированные server-side логи без секретов;
- health/readiness endpoints без раскрытия деталей;
- метрики ошибок API, загрузок, очереди Telegram и обновлений;
- correlation ID между launcher, API и тикетом;
- фоновые задания с retry/backoff и dead-letter состоянием;
- резервное копирование и документированный restore test;
- отдельные конфигурации development/staging/production;
- миграции БД и способ безопасного rollback;
- страницу админки со статусом очередей и последними ошибками без показа секретов.

## 15. Тестирование

Нужны автоматические и ручные тесты минимум для следующих случаев:

### Launcher/updater

- чистая установка;
- отсутствие одного файла;
- повреждённый файл с тем же размером;
- оборванная загрузка и resume;
- недостаточно места;
- игра запущена во время обновления;
- неверная подпись manifest;
- неверный SHA-256 файла;
- попытка path traversal;
- откат после сбоя в середине установки;
- самообновление launcher;
- сохранность сейвов и настроек.

### F8/crash

- F8 в разных экранах и режимах fullscreen/windowed;
- игра уже была на паузе;
- отмена формы;
- отправка без сети и повтор;
- большие/неразрешённые вложения;
- нормальное завершение не считается crash;
- аварийное завершение распознаётся при следующем запуске;
- пользователь отказался отправлять данные.

### Сайт/API

- Guest/User/Admin/SuperAdmin и запреты между ролями;
- Admin code не видит/не меняет graphics, если у него нет разрешения;
- пользователь не читает чужой тикет или вложение;
- Telegram получает только сокращённое безопасное сообщение;
- malicious filename, MIME spoofing, zip-slip, XSS в заголовке;
- rate limit и повтор запроса с тем же idempotency key;
- roadmap 0/100 и неверные значения;
- публикация/отзыв релиза.

Сделай smoke test и краткий ручной чек-лист для каждого релиза.

## 16. Этапы реализации

Реализуй в таком порядке, если аудит не выявит веской причины изменить его:

### Этап 0 — аудит и проектирование

Карта существующего проекта, архитектура, threat model, схема данных, API contract, макеты основных экранов и план миграций.

### Этап 1 — минимально полезный updater

Manifest, ReleaseBuilder, проверка подписи, launcher, проверка/докачка файлов, безопасная установка, запуск игры, базовый экран релизов на сайте.

### Этап 2 — тикеты на сайте

Форма гостя/пользователя, вложения, кабинет, API, базовая админка, RBAC, маршрутизация code/graphics, Telegram.

### Этап 3 — интеграция F8

Скриншот, пауза, форма, очередь offline, лог/сейв с согласием, номер созданного тикета.

### Этап 4 — crash reporting

Session marker, предложение после следующего запуска, redaction, очередь и crash ticket.

### Этап 5 — документация, roadmap, донаты и графические утилиты

Публичные разделы и полный набор browser-side инструментов.

### Этап 6 — укрепление production

Нагрузочные и security-тесты, backup/restore, мониторинг, подпись релизов, CI/CD, runbooks.

## 17. Definition of Done

Задача считается законченной не по наличию экранов, а когда:

- новый пользователь скачивает один launcher с сайта, устанавливает/указывает папку и получает рабочую актуальную версию;
- launcher исправляет удалённый или повреждённый файл и не трогает сейвы;
- поддельный manifest или файл гарантированно отклоняется;
- F8 делает правильный скриншот, ставит игру на паузу и создаёт тикет либо offline-черновик;
- после реального краша при следующем запуске появляется добровольное предложение отправить диагностический пакет;
- тикет с сайта и из игры попадает в одну систему;
- Telegram получает только краткое уведомление без вложений и подробностей;
- code/graphics администраторы ограничены своими permissions, SuperAdmin управляет всей системой;
- публично доступны инструкции, changelog, roadmap, донаты и launcher;
- графические инструменты работают без обязательной загрузки изображений на сервер;
- есть автоматические тесты критических сценариев, миграции, backup/restore инструкция и deployment/runbook;
- в репозитории нет секретов, временных файлов, дампов пользователей и приватных вложений.

## 18. Формат твоей работы и отчёта

Работай автономно, но не скрывай архитектурные решения. Перед первым большим изменением выдай:

1. что найдено в репозитории;
2. что уже существует;
3. предлагаемую архитектуру;
4. список рисков и блокеров;
5. план файлов и миграций;
6. порядок этапов с приблизительной сложностью, без выдуманных сроков.

Во время реализации:

- делай небольшие логические коммиты;
- не коммить секреты, пользовательские логи, сейвы и бинарные вложения;
- не ломай существующую сборку;
- после каждого этапа запускай доступные тесты и сборку;
- документируй новые environment variables в `.env.example` без значений секретов;
- при изменении API обновляй OpenAPI и клиентов;
- не отмечай задачу выполненной, если тесты не запускались; явно сообщай, что проверено, а что проверить не удалось.

В конце каждого этапа дай короткий отчёт:

- реализовано;
- изменённые компоненты;
- команды сборки/запуска;
- результаты тестов;
- известные ограничения;
- следующий этап.
