# HD art pipeline (этап 5)

Путь от оригинального спрайта до HD-пака, который движок подхватывает из `hd/<набор>/<кадр>.png`:

```
PCK/TAB  --extract_pck.py-->  лист original.png (+ original_x4, mask_x4, layout.json)
                                       |
                                       v  gen_hd.py (SDXL img2img + ControlNet tile/canny, на 5090)
                              лист painted_x8.png -> painted_x4.png
                                       |
                                       v  build_pack.py (режет лист на кадры, альфа из оригинала)
                              <мод>/hd/TERRAIN/CULTIVAT.PCK/0.png ... 36.png
```

Все листы имеют одинаковую раскладку (сетка кадров с полями по 4 px вокруг каждого), поэтому
нарисованный лист режется точно так же, как собирался, а поля не дают соседям «протекать» друг в друга.

## Установка (один раз, PowerShell из E:\OpenXCom)

```powershell
powershell -ExecutionPolicy Bypass -File tools\hdart\setup_gen.ps1
```

Ставит venv в `tools\hdart\.venv`, torch для CUDA 12.8 (RTX 50xx), diffusers, и в конце скачивает
модели (~12 ГБ: Juggernaut XL v9 — дообученный SDXL, VAE fp16-fix, ControlNet tile и canny) в **`E:\models`** (другая папка:
`-Models D:\что-то`). `gen_hd.py` берёт модели оттуда же (`--models <папка>` или переменная `HD_MODELS`);
`gen_hd.py --download-only` докачивает недостающее.

## Первый прогон: ферма

```powershell
py -3 tools\hdart\extract_pck.py --data bin\UFO --out hdart_sheets --sets TERRAIN/CULTIVAT.PCK
tools\hdart\.venv\Scripts\python.exe tools\hdart\gen_hd.py --sheets hdart_sheets --set CULTIVAT.PCK --test
```

`--test` рисует один кусок листа (6 кадров, 20 шагов) — проверка, что всё работает; результат в
`hdart_sheets\CULTIVAT.PCK\crops\crop_00.png`. Подбор силы перерисовки:

```powershell
tools\hdart\.venv\Scripts\python.exe tools\hdart\gen_hd.py --sheets hdart_sheets --set CULTIVAT.PCK --sweep 0.7,0.8,0.9
```

пишет `crops\sweep.png`: оригинал | вход модели | результат при каждой силе — выбираем на глаз и
запускаем полный прогон с `--strength <выбранная>` (37 кадров, 8 кусков, на 5090 около минуты).
`--sweep tile=0.3,0.6` перебирает любой другой параметр (`strength`, `tile`, `tile-blur`, `canny`, `refine`,
`cfg`, `gen-scale`, `init`), `--frame 9` — смотреть на кусок с кадром 9 (дерево) вместо первого.
`--matrix --frame 9` рисует один кадр всеми вариациями из списка `MATRIX` в скрипте (веса, размытие,
второй проход, масштаб 16) в `crops\matrix.png` с подписями — быстрый способ понять, что помогает. Потом:

```powershell
py -3 tools\hdart\build_pack.py --sheets hdart_sheets --set CULTIVAT.PCK --hd hdart_sheets\CULTIVAT.PCK\painted_x4.png --mod user\mods\hd --pack-path TERRAIN
```

и в игре: масштаб 4, режим HD-спрайтов 1 или 2, Новая битва → террейн «Ферма» (или любой бой на ферме).

Кадры двух сортов. **Земля** (полы и проходимые объекты, заполняющие ромб пола — посевы, цветы;
`extract_pck.py` берёт это из MCD террейна и пишет в `layout.json`) размножается по изометрической
сетке на всю клетку: модель видит сплошное поле и рисует ландшафт, а не «грядку с бордюром» на фоне —
именно так первый полный прогон превратил траву и рожь в клумбы и заборы. **Объекты** (деревья, стены,
изгороди) рисуются по одному на клетке, фон вокруг — растянутые цвета самого спрайта. Земля с землёй и
объекты с объектами рисуются парами, у каждого сорта свой промпт.

Модель не знает, что нарисовано на конкретном тайле (рожь у неё выходила оранжевыми початками, яблоки
с яблони пропадали), поэтому есть **подсказки по кадрам**: словарь `HINTS` в `gen_hd.py` (для CULTIVAT
заполнен: «ripe golden wheat field», «apple tree with red apples»…) и/или файл `hints.json` рядом с
листами набора (`{"4": "ripe golden wheat field", ...}`); кадры с одинаковой подсказкой рисуются вместе.
`--no-hints` — без них. `--frame 4,8,9` в `--sweep`/`--matrix` — несколько кадров строками, а
`--sweep base=stabilityai/stable-diffusion-xl-base-1.0,RunDiffusion/Juggernaut-XL-v9` сравнивает чекпойнты.

Рисуется в два прохода: первый (`--strength`) придумывает картинку по мягкому входу — формы и цвета
держит размытая подсказка tile, но выходит «пластилин»; второй (`--refine`, 0.45) перерисовывает
результат первого с резкими подсказками — так появляются фактура и детали (`--refine 0` — один проход;
в `crops\sweep_080_pass1.png` лежит результат первого прохода).

Ручки `gen_hd.py`: `--strength` (0.6 — подкрасить, 0.8 — по умолчанию, перерисовать, 0.9 — придумать
заново; ниже 0.7 модель оставляет мыло), `--refine` (сила второго прохода), `--tile`/`--canny` (веса ControlNet: держат цвета/формы и
контуры), `--tile-blur` (размытие подсказки tile в исходных пикселях; 0.5 по умолчанию — форма
остаётся, пиксельный шум не возвращается «шариками»), `--cfg`, `--seed`, `--subject "..."` (что
нарисовано, подставляется в общий стилевой промпт), `--prompt "..."` (полностью свой), `--init nearest`
(старый вход — квадратные пиксели; по умолчанию `smooth` — гладкий апскейл, иначе модель честно
перерисовывает квадраты), `--base <чекпойнт>` (другой чекпойнт SDXL; по умолчанию Juggernaut XL v9 —
он рисует реалистично и фактурно, базовый `stabilityai/stable-diffusion-xl-base-1.0` даёт «пластилин»;
новый чекпойнт скачивается в E:\models при первом запуске). Промпт стиля общий для всех наборов, чтобы
арт был единым.

Решётка на полях. Классические тайлы пола несут собственный край (светлее или темнее по ромбу — так
классика показывает сетку), и поле, сложенное из них, показывало художнику решётку, а он честно
рисовал её как тропинки между тайлами (лес, Фотки9). Теперь перед размножением край ромба
заменяется цветом из глубины тайла (`derim_ground`), копии в поле случайно зеркалятся (иначе модель
повторяет узор тайл в тайл), для полей canny выключен, а подсказка tile размыта сильнее.
Перерисовать только землю, не трогая объекты: `gen_all.ps1 -Force -GenArgs "--only ground"`
(объекты берутся из старого `painted_x16.png`; ~треть времени полного прогона).

Силуэты. Край ромба пола и вся нижняя зона кадра вокруг него (там, где пол, стена или подставка
объекта стыкуется с соседями) режутся **точно по пикселям оригинала** — мягкий край там просвечивал
фон, и по каждому полю шла тёмная сетка (Фотки9). Выше зоны силуэт объекта гладкий (`--feather`).
Объекты, стоящие на полу (дерево на траве, камень на песке), в оригинале несут пиксели этого самого
пола; художник рисовал их заново, и под каждым деревом получалась своя «заплатка». Теперь
`build_pack.py` находит пол по совпадению пикселей и кладёт под объект **его же нарисованный тайл**
(`--floor-under 1`, 0 — оставить как нарисовано). Перепаковать все наборы без перерисовки:
`gen_all.ps1 -PackOnly` (секунды на набор).

`build_pack.py --color-match 0.8` (по умолчанию) подтягивает тон каждого кадра к оригиналу: модель
уводит цвета (тёмно-зелёное дерево возвращается оливковым, кадр темнее/светлее), а соседние тайлы и
классические спрайты вокруг должны сходиться по цвету. `--color-match 0` — оставить цвета модели.

## Весь террейн ванильного UFO одной командой

```powershell
powershell -ExecutionPolicy Bypass -File tools\hdart\gen_all.ps1
```

Идёт по всем 26 наборам террейна (ферма первой), каждый: извлечение → рисование → пак в
`user\mods\hd` — единый мод всего HD (террейн, эффекты, дальше юниты; создаётся с
`metadata.yml`, master `*`). Наборы, у которых пак уже есть,
пропускаются — можно прерывать и запускать снова; `-Force` перерисовывает, `-Sets CULTIVAT,BARN` —
только эти, `-GenArgs "--strength 0.85"` — параметры рисования. Лог в `hdart_sheets\gen_all.log`.
На 5090 около 5 с на кусок, ~1300 кадров террейна — часа два.

Подсказки на все кадры ванильного террейна лежат в `hints.py` (написаны по листам, ~1300 штук);
`hints.json` рядом с листами набора их дополняет. Земля после рисования сшивается по краям
(`--seamless 1`, по умолчанию): край ромба смешивается с продолжением поля за противоположным краем,
чтобы соседние тайлы сходились без сетки; заодно убирается половина «наклона» яркости внутри тайла.
Высокие посевы (рожь) рисуются полем, но с промптом объекта, а не «вид сверху».

В игре: включить мод `hd`, масштаб 4, режим HD 1 или 2. Старые папки `hd_ufo`, `hd_globe`, `hd_demo` больше не
нужны — всё лежит в `user\mods\hd`.

`placeholder_sheet.py` делает «болванку» (гладкий апскейл) вместо нарисованного листа — для проверки
пути без видеокарты.

## Разные клетки земли: варианты (`--variants`)

Поле из одной и той же клетки видно как сетку. Поэтому каждый пол рисуется ещё N раз, с другими словами
и чуть другим цветом. Движок раскладывает эти варианты по карте пятнами: крупные (около 6 клеток) и
мелкие на них (около 2,5 клетки). Край пятна рваный и плавно смешан, пятна идут через границы клеток без
шва. Раскладка своя у каждого боя (считается по блокам карты) и не меняется после загрузки сохранения.

Варианты стоят на шкале, базовая картинка — в середине: нечётные (v1, v3) в одну сторону, чётные (v2, v4)
в другую. Поэтому v1 и v2 никогда не соприкасаются, а базовая картинка занимает больше всего места
(при двух вариантах около 44 % поля, варианты — примерно по 28 %).

| Земля | v1 (в одну сторону) | база | v2 (в другую) |
|---|---|---|---|
| трава | короткая, редкая | как нарисована | выше и гуще |
| почва | суше, светлее | | темнее, влажная |
| песок | светлее, мелкая рябь | | темнее, крупный, с галькой |
| снег | свежий, гладкий | | слежавшийся, со льдом |
| камень | светлее, в пыли | | темнее, с гравием |
| грязь | суше, в трещинах | | мокрая, с лужами |
| лесная подстилка | сухие листья | | мох и папоротник |

v3 и v4 — следующий шаг в ту же сторону (`--variants 4`). Вид земли берётся из подсказки кадра:
у «камня на траве» земля — трава, у «песка с черепом» — песок. Сделанная земля (дороги, бетон, полы баз
и НЛО) вариантов не получает.

Добавить варианты к уже нарисованным наборам (перерисовываются только полы, база и объекты остаются):

```powershell
# проба на двух наборах
powershell -ExecutionPolicy Bypass -File tools\hdart\gen_all.ps1 -VariantsOnly -Sets CULTIVAT,DESERT
# все природные наборы: CULTIVAT, FOREST, JUNGLE, DESERT, MOUNT, POLAR, MARS
powershell -ExecutionPolicy Bypass -File tools\hdart\gen_all.ps1 -VariantsOnly
```

По умолчанию 2 варианта (`-Variants 4` — четыре). Набор, у которого варианты уже есть, пропускается
(`-Force` перерисовывает). Новый набор сразу с вариантами — `gen_all.ps1 -Sets FOREST -Variants 2`.

Что посмотреть в `hdart_sheets\<набор>\`:

- `variants_field.png` — поле без вариантов и с ними, разложенное так же, как в игре;
- `crops\variant<n>_crop_*.png` — что нарисовала модель.

Подстроить без перерисовки (секунды):

- `gen_all.ps1 -PackOnly -Sets CULTIVAT -PackArgs "--variant-tone 1.5"` — разница цвета между
  вариантами (1 — как задано, 0 — цвет как у базы, 2 — вдвое сильнее);
- `-PackArgs "--variants off"` — пак без вариантов (старые файлы удаляются).

Свои слова:

- для отдельных полов — файл `hdart_sheets\<набор>\looks.json`, например
  `{"3": "dry ploughed soil|wet ploughed soil@0.9,1.1,0"}`: варианты по порядку через `|`, после `@` —
  яркость, насыщенность, теплота;
- для всех полов набора — `-GenArgs "--variant-looks 'short grass|tall grass'"` (слова в одинарных кавычках);
- только некоторые полы — `-GenArgs "--variant-frames 0,3"`.

В паке варианты лежат рядом с кадром: `hd\TERRAIN\<набор>\<i>.v1.png`, `<i>.v2.png`. Старый движок их не
читает. Опция `oxceHdGroundVariants` (Дополнительно → OXCE, раздел поля боя, по умолчанию вкл.) выключает
варианты; в списке она подписана `STR_HD_GROUND_VARIANTS`, как и остальные HD-опции.

## Картинки модов в 4× без потерь: `upscale_ui.py`

Для сотен и тысяч картинок мода (уфопедия X-Piratez: `Resources\Pedia`, 1734 штуки) — не художник,
а модель сверхразрешения Real-ESRGAN: детерминированный апскейл, который убирает дизеринг и
пикселизацию и дорисовывает мелкие детали, но ничего не выдумывает (текст, лица, композиция —
как были). Один раз: `spandrel` в venv и файл модели (64 МБ):

```powershell
tools\hdart\.venv\Scripts\python.exe -m pip install spandrel
Invoke-WebRequest -Uri https://github.com/xinntao/Real-ESRGAN/releases/download/v0.1.0/RealESRGAN_x4plus.pth -OutFile E:\models\RealESRGAN_x4plus.pth
```

Прогон (все PNG/GIF папки → `user\mods\hd\hd\UI\<имя файла>.png` + `.pal.txt`; на 5090 — доли
секунды на картинку, ~2,5 ГБ на 1734 картинки в 4×):

```powershell
tools\hdart\.venv\Scripts\python.exe tools\hdart\upscale_ui.py --dir Пиратки\Dioxine_XPiratez\user\mods\Piratez\Resources\Pedia --mod user\mods\hd --model E:\models\RealESRGAN_x4plus.pth
```

Движок (опция «HD-картинки», Дополнительно → OXCE → Общие, по умолчанию вкл.) узнаёт картинку по имени
файла (`Resources/Pedia/AAP_002.png` → `hd/UI/AAP_002.png`) или по имени спрайта (`typeSingle`), находит
её по содержимому там, где она рисуется (статья уфопедии, экран), и показывает в разрешении дисплея —
в мировом слое под классическим интерфейсом, который поверх неё масштабируется xBRZ («HD-картинки:
сглаженный интерфейс»; выкл — ступенчато). Остальной интерфейс не меняется. Картинки грузятся по мере
показа (в памяти до 768 МБ последних, не все сразу). Файлы мода в `Resources\...` не трогать —
игра читает только 8-битные оригиналы, HD-версии лежат отдельно в `hd\UI`. `--scale 8` (два прохода,
2560×1600) — для 4K-дисплеев; на 1080p–1440p игра показывает картинку 320×200 в 1280×800, так что
`--scale 4` (по умолчанию) — это и есть «полный размер». `--dedither 0.45` слегка растворяет
палитровый дизеринг до модели (0 — выкл), `--names` — только эти файлы, `--limit N` — проба на N
картинках, `--force` — переделать. Для рисованных картинок можно попробовать модель
`RealESRGAN_x4plus_anime_6B.pth` (там же на GitHub, `--model`) — жёстче линии.

Один и тот же мод `hd` обслуживает несколько игр, а имена картинок совпадают (`BACK08.SCR` в ваниле —
зелёный фон уфопедии, в Пиратках — тёмная рамка `EQP_TONED.gif`), поэтому при первом показе движок
сжимает картинку обратно до классического размера и сравнивает с изображением, которое она заменяет
(в палитре из `.pal.txt`): цвета — среднее расхождение по каналам, форма — корреляция светотени.
Своя картинка расходится по цвету на 0–15 из 255, перерисованная (`photo_ui.py`, фотореализм) — на
30–35, но светотень держит на 0,75–0,95; чужая — 40+ по цвету и 0,25 и ниже по форме. Отбраковка
только когда цвет дальше 30 **и** форма ниже 0,55; в лог идёт
`hd/UI/<файл> is not a picture of <имя> (colours off by N, shape M%) - not used`, экран рисуется
классически. Так что картинки ванильного интерфейса можно держать в том же моде (в Пиратках они
просто не применятся), а фотореалистичные переделки проходят.

## Эффекты (этап 4b): `gen_fx.py`

Огонь, дым, вспышки попаданий, звезда рукопашной и большой взрыв рисуются процедурно — без
видеокарты, за секунды — паком классических наборов: `hd\SMOKE.PCK\<i>.png` (0–3 огонь на тайле,
4–7 горящий юнит, 8–19 дым трёх плотностей × 4 кадра, 26–35 попадание пули, 36–45 лазера, 46–55
плазмы; 20–25 — значки званий, не трогаются), `hd\HIT.PCK\0..3.png` (звезда рукопашной),
`hd\X1.PCK\0..7.png` (большой взрыв 128×64). Размер и привязка кадров — классические, движок
кладёт их туда же; дым получает настоящую прозрачность вместо дизеринга, огонь — языки пламени и
свечение, попадания — вспышку и искры.

```powershell
py -3 tools\hdart\gen_fx.py --mod user\mods\hd
py -3 tools\hdart\gen_fx.py --mod user\mods\hd --preview fx.png     # плюс лист всех кадров
```

`--seed` меняет случайность, `--scale` — масштаб пака (4 по умолчанию).

### Огонь: 8 фаз и 10 стилей

Огонь теперь одно зацикленное пламя из 8 фаз. Кадры 0–3 (огонь на клетке) и 4–7 (горящий юнит) — чётные
фазы, `<i>.v1.png` рядом — нечётные: движок показывает их на нечётном такте анимации, поэтому пламя
течёт вдвое плавнее. Клетки по-прежнему начинают с разных фаз. В HD-режимах огонь стоит на поверхности
клетки (на насыпи, на склоне), а не утоплен в ней.

Сравнить стили:

```powershell
py -3 tools\hdart\gen_fx.py --fire-compare fire_compare
```

В папке `fire_compare`:

- `fire_styles.gif` — огонь на клетке, на тёмной земле и на снегу, со скоростью игры; колонка 0 — нынешний огонь;
- `fire_styles_unit.gif` — горящий юнит;
- `fire_styles.png` — 8 фаз каждого стиля;
- `fire_styles.txt` — список стилей.

| Стиль | Какой |
|---|---|
| 1 | классика: оранжевые языки со свечением |
| 2 | высокий: высокие узкие языки |
| 3 | костёр: низкий и широкий, много углей |
| 4 | буйный: турбулентный, рвётся на клочья |
| 5 | дымный: тёмно-красное пламя под пеленой дыма |
| 6 | жаркий: яркое жёлто-белое ядро |
| 7 | мягкий: полупрозрачный |
| 8 | чёткий: резкие края, мало оттенков |
| 9 | газовый: синий у основания, оранжевый выше |
| 10 | искры: пламя и летящие вверх искры |

Записать выбранный стиль в мод (переписываются только кадры огня):

```powershell
py -3 tools\hdart\gen_fx.py --mod user\mods\hd --fire-style 4 --only-fire
```

Без `--only-fire` переписываются все эффекты, огонь — стилем 1. `--fire-style 0` — прежний огонь
(описан ниже, без промежуточных картинок; старые `.v1.png` удаляются).

Прежний огонь (стиль 0): четыре кадра — это не четыре фазы одного пламени, а четыре разных расклада языков.
Тайл выбирает кадр своим случайным сдвигом (`Tile::_animationOffset`), поэтому горящее поле состоит
из четырёх разных силуэтов, а не из одной размноженной свечки. Языки поднимаются из общего низкого
тела (не каждый сам по себе), их боковой мах растёт с высотой (domain-warp по шуму), верхушки
съедаются и рвутся на клочья; цвет — температура пикселя (белое только в самом низу ядра, тело
оранжевое, верхушки красные), всё полупрозрачное, сильнее к верхушкам, плюс тёплое пятно на земле
под огнём.

## Юниты мода в 32 бита: `upscale_units.py` (X-Piratez: `Resources\Sprites`, 698 наборов)

Юнит на поле боя собирается из кадров набора (`spriteSheet` брони, 32×40: ноги, торс, руки в восьми
направлениях, оружие в руках — из `HANDOB.PCK`). Наборы объявлены в `Piratez_Resources.rul` через
`extraSprites` (лист `subX/subY`, кадры по рядам; имя набора не всегда совпадает с файлом — 65 из 698,
например `SUCCUBUS.PCK` = `VDD_00.png`). Скрипт читает листы **прямо из мода**, имена и номера кадров
берёт из rul, палитру — из самого листа; на выходе `hd\<набор>\pack.hdp` — один файл на набор с
RGBA-PNG каждого непустого кадра в `--scale` раз (4 по умолчанию: 128×160).

**Чем кадр увеличивается.** Кадр 32×40 — не фотография: почти каждый пиксель поставлен художником
руками, и модели сверхразрешения там не из чего восстанавливать — она доедает мелкие акценты
(блики, пряжки) и дорисовывает своё (тёмные обводки вокруг конечностей, сдвиг цвета). Поэтому
основа — **xBRZ** (`sprite_scale.py`, точный порт `src/Engine/Scalers/xbrz.cpp`, сверен с C++
попиксельно): он читает диагонали, которые пиксели обозначают, и выкладывает их ровными гладкими
линиями, одиночные пиксели оставляет одиночными и не выдумывает ни одного цвета, которого в кадре
не было. Это тот же алгоритм, которым движок сглаживает спрайты без пака, так что пак заведомо не
хуже того, что в игре уже есть.

Модель поверх этого — не обязательна и работает как **слой фактуры**: от её картинки берётся только
мелкая деталь (то, что осталось после размытия) и накладывается на картинку xBRZ как изменение
яркости, с ограничением (`--detail 0.6`, `--detail-limit 0.3`), так что силуэт, формы и цвета
остаются от xBRZ. Модели при этом показывают не пиксель-арт, а картинку xBRZ в двойном размере
(`--model-input xbrz2`) — так она ведёт себя куда разумнее.

```powershell
# без модели вообще, только xBRZ (быстро, ничего не выдумывает) — проба на глаз:
tools\hdart\.venv\Scripts\python.exe tools\hdart\upscale_units.py --rul Пиратки\Dioxine_XPiratez\user\mods\Piratez\Ruleset\Piratez_Resources.rul --mod Пиратки\Dioxine_XPiratez\user\mods\hd --preview-only --sets PIR_570.PCK,HYENA_RIDER.PCK
# с моделью (xBRZ + её фактура); в превью обе колонки рядом, видно, что даёт модель:
tools\hdart\.venv\Scripts\python.exe tools\hdart\upscale_units.py --rul ...\Piratez_Resources.rul --mod ...\user\mods\hd --model E:\models\RealESRGAN_x4plus_anime_6B.pth --preview-only --sets PIR_570.PCK
# все 698 наборов (~172 тыс. кадров; xBRZ без модели — ~10 мин, ~0,9 ГБ на диске в 4×)
tools\hdart\.venv\Scripts\python.exe tools\hdart\upscale_units.py --rul ...\Piratez_Resources.rul --mod ...\user\mods\hd
```

Модель скачивается один раз (не нужна для xBRZ):

```powershell
Invoke-WebRequest -Uri https://github.com/xinntao/Real-ESRGAN/releases/download/v0.2.2.4/RealESRGAN_x4plus_anime_6B.pth -OutFile E:\models\RealESRGAN_x4plus_anime_6B.pth
```

`--method xbrz | detail | model` (по умолчанию `xbrz` без модели, `detail` с моделью; `model` — старое
поведение, чистая картинка модели), `--detail 0..1` и `--detail-limit` — сколько фактуры пускать
(0.6 / 0.3 по умолчанию; мягче — 0.4 / 0.2), `--jobs` — рабочих процессов (по умолчанию четверть
ядер, не больше 4): xBRZ и подготовка кадра считаются на одном ядре, и без нескольких процессов
видеокарта простаивает, `--batch` — кадров за проход модели (32),
`--scale 2..6` и 8, `--pngs` — россыпью `hd\<набор>\<n>.png` (для правки руками; перекрывает кадр
пака), `--sets` — только эти наборы, `--preview` / `--preview-only` — листы сравнения в
`hd\preview\<набор>.png`, `--force` — переделать, `--hard-alpha` — ступенчатый край силуэта.

Для наборов, которых нет листами (ванильные PCK, наборы, которые правят несколько модов), есть второй
вход — листы выгружает сама игра: `$env:OXCE_HD_EXPORT = "E:\hdexport"` и запуск игры с модами (пишет
`<набор>.png` + `.png.txt` в палитре боя, кадр в кадр как в бою, и выходит; `OXCE_HD_EXPORT_SETS =
units | all | A.PCK,B.PCK`), затем `upscale_units.py --export E:\hdexport ...`.

**Про номера кадров.** Наборы базовой игры (`HANDOB.PCK`, `FLOOROB.PCK`, `BIGOBS.PCK`, `SMOKE.PCK`,
`HIT.PCK`, `BASEBITS.PCK`, `INTICON.PCK`) мод не нумерует свободно: ванильные кадры движок считает
общими, а всё, что мод добавляет сверх них, переносит в диапазон, выделенный этому моду
(`ExtraSprites::getFrame`: `indexWithOffset += _current->offset`). Номер из rul — это не тот номер,
который в итоге рисует игра, и вычислить его снаружи нельзя: он зависит от списка модов и их
порядка. Поэтому такие наборы делаются **только** через выгрузку из игры (`OXCE_HD_EXPORT`), а из
rul скрипт их не берёт и говорит об этом строкой. Наборы, которые мод создаёт сам (юниты
X-Piratez), нумеруются свободно (`_sharedFrames = INT_MAX`) — их можно делать из rul.

**Про палитру.** Файл спрайта несёт свою палитру, но движок берёт из него только индексы
пикселей (`Surface::loadImage` копирует их как есть) и рисует через палитру боя — значит и HD-кадр
должен делаться в палитре боя, а не в той, что лежит в файле. Моды в этом неаккуратны: в Пиратках
листы юнитов несут палитру боя, а среди файлов `Resources\HANDOB` попадаются свои собственные
(`Megavolt.png` расходится в 236 цветах из 256). Скрипт берёт палитру, на которой сходится
большинство файлов прогона, и красит ею все кадры; `--palette <файл.png>` задаёт её вручную, а
наборы со своей палитрой перечисляются строкой при старте.

Лист режется ровно так, как режет игра (`ExtraSprites::loadSprite`): файл кладётся на лист того
размера, который объявлен в rul (больше — обрезается, меньше — остаток пустой), и делится на
`width/subX` × `height/subY` кадров с нумерацией по рядам от индекса файла. Если размеры файла и rul
разошлись, скрипт говорит об этом строкой и берёт числа из rul — иначе кадры за пределами набора
попали бы в пак под чужими номерами. Число кадров записано в `settings.txt`, так что набор, у
которого оно изменилось, переделывается сам.

**Про видеопамять.** В модели одновременно живут десятки карт признаков на весь батч, так что
занятая память — это `--jobs` × `--batch` × ~33 МБ (кадр 32×40 через `xbrz2` с полем). Восемь
процессов по 128 кадров — это 32 ГБ, то есть вся 5090 и зависший компьютер. Скрипт теперь считает
это сам: при старте каждый процесс смотрит, сколько памяти свободно, берёт свою долю (свободное /
число процессов / 2) и режет батч до неё, а если всё равно не влезло — ловит ошибку памяти, делит
батч пополам и продолжает. Поэтому большой `--batch` безопасен, он просто не будет выполнен целиком.

Рядом с паком пишется `settings.txt` — чем он сделан (масштаб, метод, модель, `detail`…). При
повторном запуске набор пропускается, только если настройки те же; поменял `--detail` или модель —
пак переделается сам, `--force` больше не нужен. Паки, сделанные до появления этого файла,
считаются своими и не трогаются — их переделывает только `--force`.

Движок (режимы «HD-паки» и «сглаживание») при первом рисовании набора читает только таблицу пака,
кадр читается с диска при первом рисовании (доли миллисекунды) и держится в памяти, пока в неё
укладывается (384 МБ; давно не рисовавшиеся кадры выбрасываются и читаются снова при надобности) —
семьсот наборов стоят памяти столько, сколько юнитов на карте. Пак, сделанный в 4×, показывается и
при 2×/3×/6× (пересчёт при чтении). Перекраска скриптами (лица, волосы, звания) работает: движок
прогоняет скрипт по классическому кадру и переносит замену индексов на HD-пиксели.

## Юниты (эксперимент): `gen_all.ps1 -Units`

Наборы юнитов (`UNITS\*.PCK`: XCOM_0..2 — солдаты, SECTOID, FLOATER, ..., TANKS, HANDOB — оружие в
руках, FLOOROB — предметы на полу) рисуются тем же конвейером, покадрово: кадр — это часть фигуры
(ноги, торс, руки, оружие) в одном из восьми направлений, движок собирает фигуру сам, поэтому
художник работает осторожно (strength 0.6, tile 0.75, canny 0.4 — форма и цвета части сохраняются,
добавляется материал) с промптом персонажа (`SUBJECTS` в gen_hd.py). Пак — `hd\<набор>\<кадр>.png`.

```powershell
powershell -ExecutionPolicy Bypass -File tools\hdart\gen_all.ps1 -Units -Sets XCOM_0
powershell -ExecutionPolicy Bypass -File tools\hdart\gen_all.ps1 -Units          # все 20 наборов
```

Перекраска лиц/волос/званий скриптами (spriteFaceGroup и т.п.) на HD-кадрах работает как сдвиг
цвета: движок прогоняет скрипт по классическому кадру и переносит замену индексов на HD-пиксели
(коммит «HD frames for scripted unit sprites»). Что получится с частями тела, нарисованными порознь,
— это и есть эксперимент; альтернатива на потом — собирать фигуру, рисовать целиком и резать обратно.
