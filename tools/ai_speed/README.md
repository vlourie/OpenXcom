# Замер скорости стенда ИИ

Скрипты аудита `docs/research/ai-sim-speed-audit-2026-09-30.md`. Все запускают игру только
невидимо (`ai_probe.Hidden`: свой рабочий стол + SDL dummy, R-124) и пишут итоги в `runs/`
(в гит не идёт). Интерпретатор — `py -3.13` (R-101), в трубу — с `PYTHONIOENCODING=utf-8` (R-001).

| Скрипт | Что делает |
|---|---|
| `run_one.py` | один бой: время процесса и боя, ЦП, память, доля E-ядер, размер лога → `runs/<имя>.json` |
| `cmp_runs.py` | таблица вариантов против базы: ускорение и **побайтное совпадение семи потоков записи** |
| `series_eq.py` | две серии `ai_arena.py` побайтно по каждому бою (таблица, запись, кандидаты, клетки, пути, потери): шлюз пассивности на `fair22` |
| `par_test.py` | N одинаковых боёв одновременно: боёв в минуту на этой машине |
| `hang_count.py` | сколько из N запусков не вышли сами (гонка `~StartState`, R-150) |
| `prof_battle.py` | выборочный профиль главного потока (StackWalk64 по `.pdata`, имена из `nm`) → `runs/<имя>.samples.json` |
| `prof_report.py` | отчёт по выборкам: плоский, включающий, дерево от `Game::run`; `--phase battle` — только бой |
| `attach_all.py` | по стеку каждого потока живого (повисшего) процесса игры → `runs/<имя>.samples.json` |
| `hang_stack.py` | самый частый стек из выборок с ближайшими экспортами системных DLL — чем занят повисший процесс |

## Порядок

```powershell
$env:PYTHONIOENCODING = "utf-8"
py -3.13 tools/ai_speed/run_one.py --build build-ai36 --mission STR_LOC_SPACE_STATION_1 --seed 201 --name st_base
py -3.13 tools/ai_speed/run_one.py --build build-ai36 --mission STR_LOC_SPACE_STATION_1 --seed 201 --name st_tools --opt oxceHdKillCam=false --opt oxceHdUi=0 --penv SDL_AUDIODRIVER=none --display 640x400
py -3.13 tools/ai_speed/cmp_runs.py st_base st_tools
```

`--build` принимает имя каталога от корня (`build-ai36`) или абсолютный путь к опытной сборке
(с патчем `docs/research/ai-sim-speed-exp.patch` флаги `--env OXCE_AI_FASTLOG=1` и остальные `OXCE_AI_*`).

Флаг считается пассивным, только если в строке варианта все семь потоков стоят с `=`
(`=result =decide =rec =cand =state =path =casualty`) — на станции **и** на городе (R-149),
потом на 22 боях `fair22` (R-113): две серии `ai_arena.py` на одной сборке, без флага и с ним,
и `series_eq.py` — таблица без `seconds`, запись, кандидаты, клетки, пути и потери побайтно по
каждому бою. Рядом обязателен контрольный опыт: заведомо непассивный флаг (`OXCE_AI_TICK=100`
в опытном патче) на той же станции даёт `!result`, другое зерно — `!` по всем потокам.

## Быстрый режим стенда — `OXCE_AI_FAST` (с build-ai39)

`AiProbe::fast()`: стенд пропускает всё, на что никто не смотрит, — ни одного кадра
(`Game::run`, `Map::draw`), ни одной анимации тайлов кроме дверей НЛО (у них кадр 7 — это
«дверь открыта», `Tile::openDoor`, а `Tile::getTUCost` при кадре больше 1 отдаёт проход через
дверь за 0 ОВ — механика), нет сцены добивания (`UnitDieBState::finalBlow` ждала до 4 с реального
времени на смерть), нет звука (`Game::initAudio` → `Options::mute`), лог держится одним
открытым файлом с буфером 1 МБ (сброс четыре раза в секунду и на каждой ошибке; раньше файл
открывался на каждую строку — треть короткого боя), процесс выходит сразу за строкой итога
(`CrossPlatform::exitNow`, без выгрузки мода и сохранения настроек). Пока грузится мод, главный
цикл спит по 1 мс (`StartState::think`): без кадров он крутился 3 млн раз в секунду и отбирал
кучу у потока загрузки (картинки интерфейса грузились 28 с вместо 1 с).

`tools/ai_probe.py` включает его по умолчанию (`OXCE_AI_FAST=1`, если не задано); контрольный
опыт — `--env OXCE_AI_FAST=0`. В `cfg` записи (`[AIRECHEAD]`, `[AIREC]`) переменная не входит:
она не меняет, как стенд играет. В сборке для игроков `fast()` — заглушка `false`.

Приёмка на build-ai39 (зерно 201, все семь потоков `=` против той же сборки без флага):

| бой | без флага | FAST | ускорение боя |
|---|---|---|---|
| бомбардировщик сектоидов (28 ходов, тормозит картинка) | 62,0 с | 17,8 с | ×3,5 |
| станция (15 ходов, тормозит ИИ) | 112,9 с | 111,8 с | ×1,0 (на опытной сборке ×1,1–1,3, шум ±15 %) |
| город мёртвых (61 ход, тупик; опытная сборка) | 375 с | 174 с | ×2,2 |
| охота на шамблера (39 ходов) | 50,0 с | 16,8 с | ×3,0 |
| база пришельцев VR (7 ходов, зерно 303, вне fair22) | 23,2 с | 7,6 с | ×3,1 |
| база Туле (12 ходов, зерно 303, вне fair22; 49 884 строки записи) | 252,2 с | 97,7 с | ×2,6 |

Старт процесса (всего минус бой) 6,7 → 3,0 с; контрольный опыт — другое зерно с флагом даёт `!` по
всем потокам.

Серия `fair22` (22 боя): `p39a` без флага = `p39f2` с флагом по `series_eq.py` — IDENTICAL 22 из 22,
сумма боёв 1951 → 767 с (×2,5), средний бой 89 → 35 с, 22 боя на 4 потоках за 209 с (см. журнал в
`docs/research/ai-sim-speed-audit-2026-09-30.md`, «Сделано»). Память процесса 1,0 ГБ → 0,6 ГБ.

Чего в быстром режиме **нет** и почему: короткий цикл ходьбы «вне экрана» (`UnitWalkBState`,
2 фазы вместо 8/16) прошёл все семь потоков на трёх одиночных боях, а на `fair22` разошёлся в
2 боях из 22 (`p39f`): число тиков между шагами юнита решает, в каком кадре его встречает
дверь НЛО, а от кадра зависит цена прохода (`Tile::getTUCost`). Длина цикла ходьбы — механика
(R-155); в стенде она прежняя.

## Свет на шаге — `OXCE_AI_LIGHTSKIP` (с build-ai41)

`AiProbe::lightSkip()`: на шаге юнита и в конце его пути (`UnitWalkBState`) стенд не пересчитывает
свет карты, если юнит сам не светит — ни личного света брони (`personalLight*`; у врага в Пиратках он
0 у 929 броней из 933), ни светящегося предмета в руках, ни огня (`TileEngine::unitLightPower` — та же
формула, из которой берёт свет и `calculateUnitLighting`, правило в одном месте). Ходьба такого юнита
не меняет ни одного источника света, а все остальные события света (выстрел, брошенный или поднятый
светящийся предмет, смерть, падение, телепорт, переключение личного света, попадание, изменение
местности) пересчитывают его сами. Юнит, который светит, пересчитывает как прежде. В сборке для
игроков `lightSkip()` — заглушка `false`.

`tools/ai_probe.py` включает по умолчанию (`OXCE_AI_LIGHTSKIP=1`, если не задано); контрольный
опыт — `--env OXCE_AI_LIGHTSKIP=0`. В `cfg` записи не входит, как `OXCE_AI_FAST`. Строка итога
`[AILIGHT]` в логе: `lighting_recalc_count` (пересчётов на шагах сделано), `lighting_skipped_count`
(пропущено), `units_with_personalLightHostile`, `units_lit_now`, `shade`; без флага `skipped` 0,
с флагом `recalc(0) = recalc(1) + skipped(1)` до единицы.

только эта ветка, FAST включён, каждая карта парой без флага / с флагом (`cmp_runs.py`, семь
потоков); враг закреплён `OXCE_AI_RACE=<раса>` там, где нужны квады-фонари:

## Профиль поиска пути — `OXCE_AI_PATHPROF` (с build-ai42)

Только прибор, игру не меняет: `AiProbe::pathAsk()` получает каждый `Pathfinding::calculate` и
`findReachable` с ключом запроса (вид, юнит, откуда, куда, тип хода, цель ракеты, потолок ОВ, ОВ и
энергия юнита), временем, отпечатком ответа (путь, его ОВ и энергия, strafe, телепорт; у `findReachable` —
клетки и их цена) и адресом места вызова. Внутри решения (`beforeThink`…`logDecision`) тот же ключ
второй раз — повтор; ключ, который был в предыдущем решении, когда карта и юниты с тех пор не сдвинулись
(`pathRevision`: позиции и статусы юнитов, части карты, двери НЛО, огонь, дым), — межрешенческий повтор;
у повтора сверяется отпечаток ответа (`mis`, `xmis` — одинаковый запрос ответил по-разному, кэшировать
нельзя). Запросы вне решений (сам ход, проверки игры) считаются отдельно. Выключен — `pathAsk` не зовётся
вовсе. В сборке для игроков заглушки.

Строки лога: `[AIPF] unit= same= tt=<think, мкс> n= u= r= t= tr= x= tx= mis= xmis= calc= reach= bres=
astar= nopath=` на каждое решение, `[AIPF] total …` в итоге боя, `[AIPF] site=0x… kind= n= r= t= tr=`
на каждое место вызова, первые 40 `[AIPF] mis|xmis … was=алг/длина/ОВ now=… us=мкс/мкс site0= site=`.
Разбор — `py -3.13 tools/ai_speed/path_prof.py <прогон…> --build build-ai42`: доли think, повторы,
самые дорогие решения, места вызова по именам (`nm` по exe сборки от якоря `AiProbe::active`).

```powershell
py -3.13 tools/ai_speed/run_one.py --mission STR_LOC_SPACE_STATION_1 --seed 201 --name pf_st1 --build E:/OpenXCom/build-ai42 --env OXCE_AI_PATHPROF=1
py -3.13 tools/ai_speed/path_prof.py pf_st1 --build build-ai42
```

Грабли прибора: `optional::emplace(Ask{…})` создаёт временный объект, и его деструктор отчитывается сразу,
с ответом предыдущего запроса, а настоящий — на выходе: каждый запрос считался дважды, ровно половина
«повторов» и половина «расхождений» были этим двойником. Оба наблюдателя в `calculate` (`Trace`
для `OXCE_AI_TRACE_PATH` и `Ask`) строятся на месте, копирование запрещено. Цифры и выводы —
`docs/research/ai-path-audit-2026-10-01.md`.

Что намерено (зерно 201, станция / Город мёртвых / бомбардировщик сектоидов-элиты): поиск пути —
82,7 / 19,4 / 36,8 % think (36,8 / 10,2 / 13,5 % боя); запросов на решение 9,5 / 11,7 / 12,9, из них
`findReachable` 3 (запись стенда, `think`, `reachableWithAttack` с другим потолком ОВ); повторов по
ключу внутри решения 28 / 48 / 30 %, ответ у всех 45 427 совпал (`mis` 0); их время — 8,0 / 5,1 / 3,9 %
боя, но три четверти на станции — собственный `findReachable` записи (`AiCandidates::generate`), а
повторы самой игры (`selectPointNearTarget` к клеткам вокруг цели) — 2,1 / 3,0 / 1,1 % боя. Время
станции — не повторы, а одиночные дорогие запросы большой карты: A* врага к узлам засады
(`setupAmbush`, 318 × 31,7 мс, повторов 0) и `findReachable` по 11,6 мс. Межрешенческие повторы при
той же ревизии — 2,9 / 0,1 / 0,1 % боя, и в городе 27 из них ответили по-разному: видимость, список
замеченных, присед и тип движения в ревизию не входят (`Pathfinding::isBlocked`). Вывод: узкий кэш
внутри решения безопасен по измеренному, но даёт 4–8 % боя (из них игра 1–3 %); межрешенческий — нет.
Кэш не написан, решение за Vitali.

## Повтор записи стенда — `OXCE_AI_RECORD_REUSE` (с build-ai43)

Запись решения (`OXCE_AI_RECORD`) до того, как юнит думает, строила список кандидатов
`AiCandidates::generate`, а в нём — свой `findReachable`; `AIModule::think` первым делом делает тот же
запрос (тот же ключ, тот же ответ по отпечатку — профиль выше). Теперь `generate(…, withMoves=false)`
строит всё, кроме ходов, и запись ждёт ответ игры: `Pathfinding::findReachable` в конце спрашивает
`AiProbe::reachWanted` (думающий юнит, без цены действия, ОВ и энергия те же, что в начале think) и
отдаёт клетки с ценой в `reachTaken` → `AiCandidates::addMoves` — тот же порядок, те же хэши.
Запись делается **до** `BattleUnit::think`, а он до `AIModule::think` сам тратит ОВ: перезаряжает
оружие в руке, если в сумке есть обойма (`reloadAmmo`), раз в ход проверяет аптечку
(`medikit_think`, кости внутри), а `AIModule::think` после 200 сорванных ходов обнуляет ОВ. На таком
решении ответ think — другая досягаемость (меньше ОВ), и запись по-прежнему спрашивает сама до think
(`AiProbe::spendsBeforeThink` — оружие в руке без полного боезапаса и обойма к нему в сумке, аптечка в
сумке при ещё не бывшей проверке, счётчик > 200; «да», когда исключить трату нельзя — теряется
только экономия). Решение, где think так и не спросил, получает запрос записи после think
(`reachFallback` в `logDecision`; `handleAI` после этого всё равно считает путь заново, так что
сброс узлов ничего не ломает). Строка итога `[AIREUSE] reuse= taken= own= abort= reload= medikit=
fallback= tudiff= fallback_us=`: `taken` — ходы из ответа think, `own` — запись спросила сама до
think (по причинам: счётчик сорванных ходов, перезарядка, аптечка), `fallback` — после, `tudiff` —
запросы думающего юнита с другими ОВ или энергией, чем в начале. На принятой записи `fallback` и
`tudiff` обязаны быть 0: иначе предикат пропустил трату, и запись разошлась с прежней. Цифры
(зерно 201, reuse=0 → 1): станция `findReachable` 1 326 → 888, think 37,1 → 30,9 с, бой 85,3 → 77,6 с;
город 21 288 → 13 971, поиск пути 9,75 → 8,00 с; бомбардировщик 2 201 → 1 453, 2,14 → 1,73 с; семь
потоков `=` на всех трёх — `docs/research/ai-path-audit-2026-10-01.md`, п. 6. По умолчанию
включено; `OXCE_AI_RECORD_REUSE=0` — прежний путь (контроль). В сборке для игроков заглушки. Игру
не трогает: решение ИИ и его действие те же, меняется только, кто считает досягаемость для записи.

## Профиль засады — `OXCE_AI_AMBUSHPROF` (с build-ai43)

Только прибор: `AIModule::setupAmbush` отчитывается `AiProbe::ambush*` на каждом шаге отбора узла —
сколько узлов карты просмотрено, сколько прошло дешёвые проверки (рядом и в досягаемости с атакой;
враг не видит; свой путь дошёл), каждый поиск пути врага (A* без потолка ОВ): дошёл ли, ОВ и шаги,
раскрытые узлы A* (`Pathfinding::getExpanded`, счётчик снятий с открытого списка), время, счёт до
укрытия против лучшего на тот момент, укрытие, стал ли лучшим; и итог вызова. Строки `[AIAMB] u= e=
etu= upos= epos= nodes= near= hidden= own= ownn= ownok= ownexp= ownus= eok= efail= expok= expfail= tok=
tfail= taken= chosen= best= target= tus= fast= us=` на вызов, `[AIAMBN] … pos= d= de= dze= own= ok=
cost= len= exp= us= s0= best= cover= s= take=` на поиск врага, `[AIAMB] total …` в итоге боя. Разбор —
`py -3.13 tools/ai_speed/ambush_prof.py <прогон…>`: доли, отсев после дорогого A*, сколько узлов
можно было отвергнуть до A* без изменения выбора (`s0 + 25 <= best`), раскрытые узлы и время
успешных и безуспешных поисков, место выбранного узла среди остальных. Выключен — ничего не
считается; алгоритм засады не менялся.


## Отрицательная память засады — `OXCE_AI_AMBUSH_MEMO` (с build-ai43, AMBUSH_NEGATIVE_MEMO_V1)

Профиль выше показал: засада станции — 222 неудачных A* врага по 39 мс, из них 104 — повторные к тому
же врагу в том же вызове `setupAmbush`. Утверждение, которое запоминается: A* в `Pathfinding::calculate`
сбрасывает все узлы и снимает открытый список до пустого, так что после **неудачи** (раскрытых узлов
> 0, пути нет) закрытые узлы — это все клетки, куда враг вообще может дойти с места, где стоит, при
этих же ценах; узел вне них недостижим для того же запроса (тот же враг, та же клетка, `BAM_NORMAL`,
без ракеты, потолок 1000). `Pathfinding::closedTiles` отдаёт эти флаги (только чтение; пусто, если
последний поиск не был такой неудачей — ранний отказ до A* оставляет флаги старого поиска — или
хоть один закрытый узел стоил больше половины потолка: у потолка порядок обхода мог бы закрыть
клетку другой ценой). Память — локальная `std::vector<char>` в `AIModule::setupAmbush`: засевается
первой такой неудачей вызова, узлы вне неё пропускают поиск врага (`continue` — весь код после
неудачного поиска и так под `if (enemyPath)`), узлы внутри ищутся как прежде (положительный ответ
не повторяется никогда), на выходе из вызова уничтожается; в `Pathfinding` ничего не хранится,
между решениями ничего не переживает. Режимы: `0` — выключено (движок без переменной), `1` — пропускать,
`2` — проверка: поиск идёт всё равно, а ответ памяти сверяется с ним (`[AIAMBMEMO] … bad=` обязан
быть 0 — это контрольный опыт утверждения, R-086). С 01.10 `ai_probe.py` включает `1` по умолчанию
(второе мнение после шлюза); **контрольный опыт обязателен** — `--env OXCE_AI_AMBUSH_MEMO=0` рядом с
каждой серией, где память могла бы что-то изменить. Инвариант записан у кода в `AIModule::setupAmbush`:
помнится только `NO_PATH` после полного A* (без раннего отказа и потолка), положительные ответы не
повторяются, жизнь — один вызов; расширение любого из трёх — новая приёмка (семь потоков `=`, режим 2
с 0 расхождений, fair22 IDENTICAL). Строка `[AIAMBMEMO] mode= skip= verify= bad=` в
итоге боя пишется и без профиля; с профилем в `[AIAMB]` поля `memo= mver= mbad=`, пропущенный узел —
`[AIAMBN] … exp=0 us=0 … memo=1`, `ambush_prof.py` считает его отдельно от поисков. В сборке для
игроков `ambushMemo()` — 0, памяти нет. Цифры (станция, зерно 201, та же сборка, пара без EcoQoS
`--unthrottle 1`, memo 0 → 1): засада 8,93 → 4,76 с (28,7 → 17,8 % think), think 31,10 → 26,69 с,
бой 77,7 → 72,9 с, неудачных A* врага 222 → 123, памятью отвечено 99 (из 104 повторов 5 не
отвечены: первая неудача вызова была ранним отказом, exp=0, засевать нечем); режим 2 — 99 проверено,
0 расхождений; бомбардировщик — 6 неудач по одной на вызов, память не срабатывает, время то же;
семь потоков `=` на обеих картах; fair22 с `OXCE_AI_AMBUSH_MEMO=1` (`p43m1b`) IDENTICAL 22/22 против
той же сборки без памяти и против build-ai41 — `docs/research/ai-path-audit-2026-10-01.md`, п. 8.
Флаг стоит в списке skip `AiProbe::cfgText`: без этого `cfg` в `[AIRECHEAD]` отличается, и
`series_eq.py` даёт DIFFERENT по `rec` во всех боях при побайтно тех же записях (так вышло с первым
шлюзом `p43m1`) — новый флаг стенда, который меняет, что считается, а не как играет стенд, добавлять
