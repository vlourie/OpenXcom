# Сайт поддержки OXCE-HD на тестовой станции

Ты на **второй машине** Vitali: Windows 11 + Docker Desktop, где **уже крутятся 2-3 чужих сайта**.
Задача — поднять здесь сайт поддержки (тикеты, отчёты F8 из игры) и довести его до состояния,
в котором его можно тестировать «в реальной обстановке». Основная разработка идёт на другой
машине, в репозитории `E:\OpenXCom` (ветка `hd-render`); этот архив — срез из него.

Отвечай по-русски. Среда — Windows, PowerShell 5.1 и Git Bash.

## Что в архиве

| Путь | Что там |
|---|---|
| `portal/Dockerfile` | образ сайта: сборка на .NET 10 SDK, запуск на aspnet 10, порт 8080, пользователь `app` |
| `portal/src/Xp.Portal` | сам сайт (ASP.NET Core, Razor Pages + API `/api/v1`, EF Core + PostgreSQL) |
| `portal/src/Xp.Manifest`, `Xp.Launcher.Core` | общие библиотеки, нужны для сборки |
| `portal/deploy/compose.yaml` | боевая раскладка: db, clamav, migrate, portal, caddy (80/443, Let's Encrypt), ddns |
| `portal/deploy/compose.station.yaml` | **поверх** боевой для этой машины: caddy на `HTTPS_PORT` со своим сертификатом, ddns выключен, письма в файлы |
| `portal/deploy/Caddyfile.station` | HTTPS через `tls internal` |
| `portal/deploy/station.ps1` | всё управление: `up`, `status`, `logs`, `admin`, `reset-2fa`, `mail`, `root-cert`, `down` |
| `portal/deploy/README.md` | как устроен боевой сервер (тома, секреты, ddns) — читать обязательно |
| `docs/portal/*.md` | архитектура, план, открытые вопросы; `openapi-v1.json` — зафиксированное API |

Проект стека — `xp-portal` (`name:` в compose.yaml), контейнеры `xp-portal-*`, тома `xp-portal_*`.
Всё остальное в Docker на этой машине — **чужое**.

## Запуск

```powershell
cd portal\deploy
powershell -ExecutionPolicy Bypass -File .\station.ps1          # = up
```

`up` при первом запуске сам пишет `.env` и `portal.env`:
- `PORTAL_HOST` — IPv4 интерфейса маршрута по умолчанию (не vEthernet WSL/Docker);
- `HTTPS_PORT` — первый свободный порт от 8443;
- `FRONT_SUBNET` — первая `172.30.N.0/24`, не пересекающаяся ни с одной сетью Docker;
- `POSTGRES_PASSWORD`, `Portal__Secret` — случайные.

Потом `docker compose -f compose.yaml -f compose.station.yaml up -d --build` и ждёт `/ready`.
Уже существующие `.env`/`portal.env` не перезаписывает никогда.

Все прочие команды compose — только с обоими файлами:
```powershell
docker compose -f compose.yaml -f compose.station.yaml ps -a
```

## Правила — нарушать нельзя

1. **Чужие контейнеры, сети, тома и порты не трогать.** Никаких `docker system prune`,
   `docker volume prune`, `docker network prune`, `docker rm` по чужим именам. Перед любой
   командой, которая что-то удаляет, — убедиться, что она ограничена проектом `xp-portal`.
2. **Никогда `docker compose down -v`** — это удаляет базу, вложения и ключи Data Protection.
   Остановить — `station.ps1 down`, тома остаются.
3. **`Portal__Secret` не менять** после того, как им что-то подписано: гаснут все гостевые ссылки
   на тикеты. Секреты (`.env`, `portal.env`) в чат не выводить целиком.
4. **Порты 80/443 не занимать**, пока Vitali явно не скажет, что они свободны или что сайт
   должен встать за существующий прокси (см. ниже).
5. **Код сайта здесь не правим.** Нашёл баг — опиши его в `REPORT.md` (что делал, что ждал, что
   вышло, строки лога) и скажи Vitali: чинится в репозитории, сюда приезжает новым архивом.
   Исключение — настройки развёртывания (`.env`, `portal.env`, override-файлы compose): их
   подгонять под эту машину и есть твоя работа; каждую такую правку тоже записать в `REPORT.md`,
   чтобы её перенесли в репозиторий.
6. **Проверять фактом, а не кодом возврата**: `station.ps1 status` (ответ `/ready` = `Healthy`),
   страница в браузере, строка в логе. «Команда отработала без ошибок» — не результат.

## Первичная проверка (сделать и записать в REPORT.md)

1. `station.ps1 status` — все сервисы `running` (кроме `migrate`: он `exited (0)` — так и надо).
2. Открыть `PORTAL_PUBLIC_URL` из `.env` — главная страница, переключение ru/en.
3. Гостевой тикет без регистрации: создаётся, по секретной ссылке виден, можно дописать.
4. Вложение: через 2-3 минуты после старта clamav меняет статус «проверяется» на чистый.
   Тестовый вирус — строка EICAR в .txt — должен уйти в карантин.
5. Регистрация: письмо подтверждения — `station.ps1 mail` (SMTP не задан, письма пишутся файлами).
6. Администратор: `station.ps1 admin <почта> <имя>` → вход → 2FA → «Управление».
7. `curl.exe -k <url>/openapi/v1.json` — API отвечает.

## Типовые беды

| Симптом | Причина и что делать |
|---|---|
| `Pool overlaps with other one on this address space` | `FRONT_SUBNET` занята: поменять в `.env` на свободную `172.30.N.0/24`, `up` |
| `Bind for 0.0.0.0:8443 failed: port is already allocated` | поменять `HTTPS_PORT` и `PORTAL_PUBLIC_URL` в `.env` (порт в обоих!), `up` |
| `unknown tag !override` или ошибка разбора `compose.station.yaml` | Compose старше 2.24.4 — обновить Docker Desktop |
| `portal` перезапускается, в логе `Portal:Secret` | пустой или короткий секрет в `portal.env` |
| `migrate` `exited (1)` | пароль базы: `POSTGRES_PASSWORD` только буквы и цифры; при смене пароля ПОСЛЕ первого запуска база его не узнает (он записан в томе `db-data`) — вернуть прежний |
| clamav съедает память, WSL тормозит | ему нужно ~1,5 ГБ; проверить лимит памяти WSL (`%UserProfile%\.wslconfig`, `memory=`), не убивать чужое |
| Вход не держится, после логина снова форма | зашли по `http://` или по другому адресу, чем `PORTAL_PUBLIC_URL`: куки только для HTTPS |
| Браузер «соединение не защищено» | нормально: `tls internal`. Убрать — `station.ps1 root-cert` и установить `caddy-root.crt` в доверенные корневые |

## Выход в интернет — только по слову Vitali

Сейчас сайт виден только в локальной сети. Чтобы тестировать «снаружи», есть два пути,
выбирает Vitali:

**A. За уже существующий обратный прокси этой машины** (скорее всего так и надо, раз тут крутятся сайты).
1. Разведка, ничего не меняя: `docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Ports}}"` —
   кто держит 80/443 (traefik, nginx-proxy, caddy, nginx, npm — Nginx Proxy Manager?). Его сеть:
   `docker inspect <контейнер> --format "{{json .NetworkSettings.Networks}}"`. Его конфиг —
   метки traefik, `VIRTUAL_HOST`, Caddyfile или conf.d. Доложить Vitali, что нашёл, и предложить план.
2. Делается отдельным override-файлом (например `compose.proxy.yaml`), боевые файлы не трогать:
   - `caddy` из этого стека не запускать (`profiles: ["off"]`);
   - `portal` подключить к сети прокси (`networks:` + `external: true` внизу файла);
   - `Portal__PublicUrl` — настоящий https-адрес; `Portal__TrustedNetworks__0` — подсеть сети
     прокси (иначе сайт не поверит `X-Forwarded-Proto: https` и зациклит редирект на HTTPS, а
     ограничение частоты будет считать всех одним IP);
   - прокси должен слать `X-Forwarded-For` и `X-Forwarded-Proto`, лимит тела запроса не меньше 600 МБ
     (сайт сам режет вложения по 50 МБ, zip до 100 МБ);
   - маршрут в самом прокси — так, как у него заведено (метки, конфиг) — показать Vitali до применения.
3. Проверка снаружи: `curl https://<домен>/ready` с телефона без Wi-Fi или любого внешнего сервиса.

**B. Боевой режим** (`compose.yaml` без override): только если 80/443 на роутере и на машине
свободны для этого сайта. Тогда работает Let's Encrypt и ddns (`x-piratez.mywire.org`) — см.
`portal/deploy/README.md`.

Лаунчер и игра шлют отчёты на адрес из настроек лаунчера (`PortalUrl`). Самоподписанный сертификат
лаунчер не примет — для проверки из игры нужен либо путь A/B с настоящим сертификатом, либо
`caddy-root.crt` в доверенных на машине, где запущена игра.

## Обновление

Vitali привозит новый архив. Распаковать поверх в ту же папку, **сохранив** `portal\deploy\.env`
и `portal\deploy\portal.env` (в архиве их нет, так что распаковка их не затрёт), затем `station.ps1 up`.
Схема базы обновляется сервисом `migrate` сама. Откатиться — распаковать прежний архив и `up`.

## Что сообщать Vitali

В `REPORT.md` в корне (UTF-8 со спецификацией — его читают в PowerShell): дата, что проверено,
что сломано с точными строками лога, какие настройки развёртывания пришлось поменять и зачем.
Результат — файл, а не сообщение в чате.
