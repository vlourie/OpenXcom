## R-012  Цена названа по коду и описанию, а не по замеру
Статус:   слиты в R-091 (было: активны)
Файлы:    src/Engine/Hd*.cpp, src/Engine/Hd*.h, docs/PERF.md, BrutalAI/**, tools/aibench/*
Симптом:  Разбор «где горлышко» называет виновником переполнение кэша; замер показывает, что тот же кэш занят на 1-2% потолка, а тормоза в другом месте. То же с ИИ: damagePotential названа самой дорогой функцией хода по описанию модуля, под неё написан кэш — а таймер показал 1,1 с из 697 с хода, то есть 0,16%
Причина:  Константы вида tonedCap 256 МБ, budget 384 МБ, 4096 записей — это верхние границы на случай худшего, а не расход. В бою X-Piratez при k=4 реальная занятость кэшей HD около 88 МБ против примерно 2,5 ГБ суммы потолков: ошибка в 30 раз. Сумма потолков вообще недостижима, потому что кэши наполняются разным и в разные моменты
Правило:  Прежде чем оптимизировать функцию, поставить на неё таймер и увидеть её долю в логе — ускорять то, что не измерено, нельзя, даже если оно выглядит дорогим. Числа расхода брать только из работающей игры: строки HD perf в логе, CSV из tools/measure_hd.ps1, drawMs/flipMs из дампа F8. Потолок из кода можно называть потолком, но не расходом и не причиной тормозов. Гипотезу о переполнении проверять счётчиком в логе ДО того, как чинить
Защита:   tools/measure_hd.ps1 + строки HD perf в HdCanvas.cpp: печатают занятость всех кэшей раз в 2 с; для ИИ — строка [AIPHASE] с долями фаз и таймерами (dmgPotMs, reachHit/reachMiss), правка принимается только после того, как её цель названа в этой строке

## R-015  Команда для мода собрана по шапке скрипта, а -Mod и -Sheets остались ванильными

## R-035  Двойная обратная косая в команде схлопывается — замена молча становится пустой
Статус:   слиты в R-090 (было: обезврежены)
Файлы:    tools/*.py, *.md, *.sh
Симптом:  Команда sed или perl отрабатывает с кодом 0, счётчик совпадений говорит «найдено 1», а файл не меняется ни на байт. Вторая и третья попытки с другим инструментом дают тот же результат, и начинаешь думать, что файл заблокирован или запись не долетает
Причина:  Слой запуска команд схлопывает две обратные косые в одну ещё до того, как строку увидит оболочка. В замене вида s/.../print("BSBSn"/ perl получает одиночную косую с n, то есть настоящий перевод строки, и меняет текст на точно такой же — подстановка проходит, размер не меняется, ошибок нет. Та же беда в heredoc: путь с user превращается в escape-последовательность и питон падает на unicodeescape
Правило:  Встроенный скрипт с обратной косой не запускать вовсе: ни heredoc, ни python -c / perl -e, ни sed -i / perl -i. Скрипт пишется файлом инструментом записи в scratchpad и запускается по пути, правка исходника - инструментом правки. Нужна косая в данных - chr(92) в питоне. Если что-то всё же заменялось командой - проверять не по коду возврата, а по размеру файла до и после
Защита:   .claude/hooks/backslash-guard.ps1 (PreToolUse на Bash и PowerShell: heredoc, -c/-e, sed -i, perl -i с обратной косой не запускаются; с 26.09 и подстановка sed с косой в конвейере или с > в файл); проверка python tools/test_backslash_guard.py

## R-037  Ключ вида /E в Git Bash превращается в путь E:/
Статус:   слиты в R-090 (было: активны)
Файлы:    tools/*.ps1, tools/*.py, *.md
Симптом:  robocopy отвечает 'ERROR : Invalid Parameter #3 : "E:/"' и код 16, хотя команда написана верно и в cmd работает. То же будет у любого windows-инструмента с ключами через одну косую: taskkill /IM, reg /v, sc /f
Причина:  Git Bash (MSYS) переводит аргументы, похожие на пути POSIX, в пути Windows ещё до запуска программы: одиночный /E становится E:/. Программа получает уже испорченный аргумент, поэтому в её выводе видно чужое значение, а не то, что написано в команде
Правило:  Ключи windows-инструментов из Bash писать через ДВЕ косые: robocopy src dst //E //NFL, taskkill //IM //F. Либо выставить MSYS2_ARG_CONV_EXCL='*' на команду. Проверять не по коду возврата (у robocopy 1 - это успех, а 16 - ошибка), а по тому, появился ли результат на диске

## R-045  PowerShell 5.1 портит аргументы внешним программам
Статус:   слиты в R-090 (было: активны)
Файлы:    tools/hdart/*.ps1;tools/*.ps1
Симптом:  argparse: expected one argument; JSON приходит без кавычек. Вторая сторона: скрипт запущен через powershell -File с массивом ключей, ошибок нет, программа поднялась - и просто не сделала того, что ключ просил. Снимок лаунчера с -Arguments "--page","review" полчаса показывал главную вместо нужной вкладки, и первый вывод был ошибочный: "Start-Process теряет ключи"
Причина:  Windows PowerShell 5.1 склеивает командную строку сам: пустая строка пропадает, внутренние кавычки съедаются. У powershell -File к этому добавляется своё: МАССИВОВ там нет вовсе, всё после имени скрипта - литеральные строки, и -Arguments "--page","review" приходит в параметр [string[]] ОДНИМ элементом "--page,review". Программа получает один непонятный ключ и молча его не видит. Start-Process тут ни при чём: с -ArgumentList '--headless','check' ключи доходят (проверено кодом возврата 3)
Правило:  Массив в скрипт через powershell -File не передавать - либо powershell -Command "& { ... } -Arguments a,b", либо скрипт сам разбирает полученную строку по запятым и пробелам. Проверять не по "ошибок нет", а по тому, ЧТО программа сделала: страница открылась та или нет. Прежде чем винить запуск, поставить контрольный опыт на том же ключе (тот же exe прямым вызовом против Start-Process)
Защита:   train_lora.ps1 -DryRun показывает собранную строку; tools/shot_window.ps1 сам разбирает -Arguments по запятым и пробелам
