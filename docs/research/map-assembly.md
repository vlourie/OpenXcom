# Как игра складывает карту боя из кадров

Дата: 2026-09-28 | Уверенность: высокая (код и данные Пираток), низкая — только по разделу «как это использовать» (раздел 6, выводы, а не факты)

## Краткий ответ

Клетка карты = 4 независимых слоя (`TilePart`: пол, зап.стена, сев.стена, объект), у каждого
свой кадр 32×40 из своего набора PCK, свой Y-сдвиг (`P_Level`) и своя стоимость хода.
Движок рисует их в фиксированном порядке (пол → зап.стена → сев.стена → объект-фон → юнит →
объект-перед), **не зная**, что несколько кадров образуют один предмет — эта связь нигде в
данных не записана явно и существует только как договорённость картостроителя: одинаковый
кадр кладут в соседние клетки руками. HD-слой сейчас выбирает картинку **только по identity
классического кадра** (указатель на буфер пикселей = (набор, номер кадра)) — координаты клетки
и соседи до `blit()` не доходят вообще, кроме пола, для которого есть отдельный канал
(`setGroundCell`) с мировыми x,y,z. `bigWall` (уголы/диагонали) не влияет на рисование
никак — это только геометрия для LOS и путей; сама картинка стены с уголом — обычный кадр
объекта, нарисованный художником целиком по диагонали.

## Детали

### 1. Формат данных карты

**.MAP** (`BattlescapeGenerator::loadMAP`, `src/Battlescape/BattlescapeGenerator.cpp:2082`):
заголовок 3 байта `size[3]` = `(sizey, sizex, sizez)` (строка 2094-2097, именно в этом
порядке — не x,y,z). Дальше подряд идут блоки по 4 байта на клетку:
`(floor, westwall, northwall, object)` — индекс объекта в СКВОЗНОЙ нумерации по всем наборам
террейна (см. ниже). Порядок обхода в файле — x быстрее всего, потом y, потом z **сверху
вниз** (строки 2168-2179: x++, при переполнении y++, при переполнении y — z--). Байт 0 в
любой из 4 колонок — «клетки нет», ничего не ставится.

Байт клетки → (набор, запись MCD) — `RuleTerrain::getMapData` (`src/Mod/RuleTerrain.cpp:239`):
идём по списку `mapDataSets` террейна по порядку их перечисления в рулсете, вычитаем размер
(`MapDataSet::getSize()`, число записей MCD) набора из индекса, пока не попадём в диапазон
следующего набора. Если индекс вышел за пределы всех наборов — тайл молча заменяется на
BLANKS 0 (комментарий в коде: «oops! someone at microprose made an error in the map!»).

**.MCD** (`MapDataSet::loadData`, `src/Mod/MapDataSet.cpp:107-263`): запись ровно **62 байта**,
`#pragma pack(push,1)`, читается подряд `while (mapFile->read(...))` — число записей в наборе
определяется размером файла, а не отдельным счётчиком. Раскладка полей (offset, 0-based; имя
как в структуре `MCD` в коде):

Важное расхождение имя-байта / назначение (проверено кодом, `MapDataSet.cpp:189`):
```
to->setBlockValue((int)mcd.Light_Block, (int)mcd.Stop_LOS, (int)mcd.HE_Block,
                   (int)mcd.Block_Smoke, (int)mcd.Flammable, (int)mcd.HE_Block);
```
т.е. `setBlockValue(lightBlock, visionBlock, HEBlock, smokeBlock, fireBlock, gasBlock)` берёт
`visionBlock` из байта `Stop_LOS`, `fireBlock` из байта `Flammable`, а `gasBlock` повторно из
`HE_Block`. Это не опечатка исследования — это то, что стоит в коде движка; для механики,
но не для рисования, это важно не перепутать при чтении MCD руками.

`Tile_Type` (offset 53) — не то же самое, что колонка `.MAP`, в которой лежала эта запись:
запись может стоять в колонке "object" файла .MAP, но иметь `Tile_Type=2` (север. стена) —
тогда `Tile::setMapData` кладёт её в `_objects[O_NORTHWALL]`, а не туда, откуда взят байт.
Подтверждено кодом двери (`Tile.cpp:387-388`): `setMapData(..., dat->getObjectType())` —
целевой слой ВСЕГДА берётся из `Tile_Type` новой записи, не из текущего слоя.

### 2. Восемь кадров записи и анимация

`Frame[0..7]` — не «8 разных объектов», а **8 фаз одной анимации одной записи**
(`Tile::animate`, `src/Savegame/Tile.cpp:695-719`): каждый тик боя `currentFrame` сдвигается
на 1 по кругу 0..7, `updateSprite` берёт `getSprite(currentFrame)` = `Frame[currentFrame]`.
Если все 8 байт одинаковы — анимации нет (статичный кадр). Пример статичного объекта:
`BARN` запись 17 (обычная дверь), `Frame[0..7] = [17,17,17,17,17,17,17,17]`.

НЛО-дверь — единственное исключение из равномерного тика: `Tile::animate` пропускает её,
пока она не триггернута (`isUfoDoor && (currentFrame==0 || ==7)` — «статична»); `openDoor`
(`Tile.cpp:392-403`) переводит с 0 на 1 («начала открываться»), дальше `animate()` тикает её
1→2→...→7 вместе со всеми, `closeUfoDoor` сбрасывает на 0. Пример из Пираток:
**`ACHURCH2` запись 27** — `UFO_Door=1`, `Frame[0..7] = [44,45,46,47,48,49,50,51]`, то есть
ровно 8 последовательных кадров PCK набора: 44 = закрыта, 51 = открыта.

### 3. Порядок рисования клетки (`Map::drawTerrain`, `src/Battlescape/Map.cpp:1275`)

Внешний обход: `for itZ (beginZ..endZ) { for itY { for itX { ... } } }` — по Z снизу вверх,
внутри Z по Y, внутри Y по X (строки 1441-1448). `endZ` обрезается до текущего этажа камеры,
если не включён режим «все слои» (`_camera->getShowAllLayers()`, строка 1414-1417) — про
крыши см. ниже.

Внутри клетки, в порядке фактических вызовов `surface->blit(...)`:

1. пол — `tile->getSprite(O_FLOOR)`, `Map.cpp:1488-1500`; сдвиг по Y = `-getYOffset(O_FLOOR)*k`
   (P_Level записи); если у пола есть варианты пака — включается `setGroundCell` (см. §5).
2. курсор «сзади» (красная/жёлтая рамка под юнитом), только если клетка под курсором.
3. юнит(ы) «за» текущей клеткой — только при анимации соседнего движущегося юнита
   (`isUnitMovingNearby`, спецкейс на три клетки сзади).
4. **западная стена** — `getSprite(O_WESTWALL)`, `Map.cpp:1552-1561`.
5. **северная стена** — `getSprite(O_NORTHWALL)`, `Map.cpp:1562-1571`; четвёртый параметр
   `blit` — `half = bool(tile->getSprite(O_WESTWALL))`: если у клетки есть ещё и западная
   стена, северная рисуется **только правой половиной** своего кадра (`Canvas32::blit`,
   `src/Engine/HdCanvas.cpp:471-474`: `srcDomain.beg_x = srcDomain.end_x/2`). Это и есть
   ответ «как рисуется угол»: угловой столбик целиком нарисован художником в спрайте
   ЗАПАДНОЙ стены (он всегда рисуется целиком), спрайт северной стены его дублирует в своей
   левой половине — и эта половина просто не блитится, чтобы не рисовать столбик дважды.
6. объект, если `isBackTileObject(O_OBJECT)` — «объект-фон» (`Map.cpp:1572-1583`); это
   отдельный флаг записи MCD (`MapData::isBackTileObject`, работает как «эта стена ведёт
   себя как южная/восточная», т.е. должна быть ЗА юнитом, а не перед ним).
7. предмет на полу (`BattleItem`) — сдвиг `+ tile->getTerrainLevel()*k` (не `P_Level`
   записи, а `Tile::getTerrainLevel()`, см. §4).
8. снаряд/трассер, если в этой клетке.
9. пар/дым-частицы «за» юнитом.
10. юнит этой клетки (`drawUnit`), плюс юниты «спереди» при анимации соседа.
11. дым/огонь тайла.
12. пар/дым-частицы «перед» юнитом.
13. превью пути (стрелки).
14. объект, если НЕ `isBackTileObject` — «объект-перед» (`Map.cpp:1891-1904`), тот же кадр,
    что в п.6, но с противоположным условием: у клетки ровно один слой `O_OBJECT`, флаг
    `isBackTileObject` лишь решает, в какой из двух точек списка он рисуется.
15. курсор «спереди» (перекрестье прицела, точность).

Экранная позиция клетки — `Camera::convertMapToScreen` (`src/Battlescape/Camera.cpp:487-492`):
```
screenX = mapX*(spriteWidth/2) - mapY*(spriteWidth/2)
screenY = mapX*(spriteWidth/4) + mapY*(spriteWidth/4) - mapZ*((spriteHeight+spriteWidth/4)/2)
```
(`spriteWidth/Height` уже умножены на `k`, `Map.cpp:166-168`, `BASE_SPRITE_WIDTH=32`,
`BASE_SPRITE_HEIGHT=40`, `Map.h:75-76` — совпадает с «база 32×40» из CLAUDE.md). Сдвиг конкретного
слоя внутри клетки — `screenPosition.y - tile->getYOffset(part)*k`, где `getYOffset` = P_Level
ИМЕННО этой записи (у пола, стен и объекта он может быть разным).

### 4. TerrainLevel (высота рельефа) vs YOffset (сдвиг спрайта) — два разных поля

Это два независимых механизма, оба берутся из MCD, но не путать:

* **P_Level** (offset 49) → `MapData::getYOffset()` → сдвигает СПРАЙТ этой конкретной записи
  при блите (используется для пола/стены/объекта индивидуально, `Map.cpp:1495,1558,1568,1579,1899`).
* **T_Level** (offset 48, **signed**) → `MapData::getTerrainLevel()` → используется только
  при вычислении `Tile::_cache.terrainLevel` (`Tile::setMapData`, `src/Savegame/Tile.cpp:229-254`):
  ```
  level = FLOOR ? floor->getTerrainLevel() : 0
  if OBJECT: level = min(object->getTerrainLevel(), level)   // "какая выше, не сумма"
  ```
  Это значение — `Tile::getTerrainLevel()` — сдвигает по Y **юнитов и предметы, стоящие на
  тайле** (`Map.cpp:1590,1605,...` для предметов; юниты сдвигаются в `UnitSprite`, не
  проверено построчно в этом прогоне — см. «чего не выяснил»), а не сам кадр пола/стены/объекта.

Отрицательные значения T_Level — «выше» (комментарий в `Tile.h:219`: «more negative = higher,
e.g. -8 = lower stairs, -16 = higher stairs»). Статистика по 611 наборам террейнов Пираток
(см. §MCD-статистика): T_Level≠0 у 26.94% записей, самые частые значения -12, -4, -8, -24,
-16, -20 — шаг в 4 вокселя, кратный делению этажа (24 вокселя = полный этаж, `Camera.cpp:491`).

**Лестница на практике — НЕ серия клеток с нарастающим T_Level, а один MCD-объект с одним
кадром**, который художник нарисовал как целый визуальный пролёт. Пример: `BARN` запись 16
(`composite_hints.json` описывает её как «one long straight staircase... rising diagonally»),
байты: `bigWall=0, T_Level=-16, Tile_Type=3(объект)`. Стоит в блоке `CULTA19` (террейн `CULTA`)
в клетках `(2,2,0)`, `(7,2,0)`, `(4,7,0)`, `(5,7,0)`, `(1,6,1)` — то есть повторяется как
обычный объект на РАЗНЫХ отдельных клетках карты, без соседства друг с другом; подъём на
следующий Z обеспечивается тем, что T_Level=-16 поднимает юнита почти на 2/3 этажа прямо в
этой клетке, а соседняя клетка на Z+1 уже просто пол следующего этажа. Никакой связи «это
серия одной лестницы» в данных нет — она видна только по повторению кадра/типа объекта и по
описанию, которое дал человек (`composite_hints.json`), не движком.

### 5. Составные объекты — конкретные примеры

Данные НЕ содержат явной связи «эти кадры — один объект». Кандидаты для восстановления связи
(проверено на практике инструментами `tools/hdart/*`, не движком): соседство клеток на
карте (одинаковый набор+кадр в соседних x,y или тот же x,y на z+1), общий `Die_MCD`/`Alt_MCD`,
таблица `census/over_base.tsv` (что́ было нарисовано поверх чего), и готовые скрипты
`obj_series.py`/`long_object.py`/`floor_group.py`, которые как раз решают эту задачу для
арта (не для механики).

**Дерево (крона на Z+1, не 2×2)** — `MOUNTGRASS` запись 64 (ствол) и 65 (крона), террейн
`PLAINS_ARBOREAL`, блок `PLAINS06`, обе как `O_OBJECT`:
```
(1,0,0) объект MOUNTGRASS:64   (ствол, на уровне земли)
(1,0,1) объект MOUNTGRASS:65   (крона, та же x,y, этаж выше)
```
Проверено ещё в двух клетках того же блока: `(0,1,0)/(0,1,1)` и `(8,9,0)/(8,9,1)` — тот же
паттерн. То есть у этого дерева опора на карте 1×1, а не 2×2, как можно было предположить —
крона просто рисуется как отдельный кадр на тайле-двойнике этажом выше (см. про эту же связку
и грабли `docs/RAKES.md` R-119: если рисовать этот кадр в отрыве от нижнего, крона выходит
несвязанной с формой ствола).

**Длинный предмет из повторов одного кадра** — барная стойка, набор `BRICKBAR`, террейн
`WESTOWN_LOKNAR`, блок `WESTOWN_SALOON`, все как `O_OBJECT`, все с общим `Die_MCD=23`:
```
(15,2,0) BRICKBAR:13   (15,3,0) BRICKBAR:13
(15,4,0) BRICKBAR:14   (сев./угловой кадр)
(15,5,0) BRICKBAR:13   (15,6,0) BRICKBAR:13
(15,7,0) BRICKBAR:14
(15,8,0) BRICKBAR:13
(12,9,0) BRICKBAR:16  (13,9,0) BRICKBAR:16  (14,9,0) BRICKBAR:16   (прямой участок вдоль X)
(15,9,0) BRICKBAR:12   (торец/угол)
```
Прямой участок стойки — один и тот же кадр (13, потом 16 на повороте вдоль X), уложенный
подряд в соседние клетки руками картостроителя; торцы и углы — отдельные, специально
нарисованные кадры (12, 14). Единственная связь между ними в данных — общий `Die_MCD=23`
(после разрушения все превращаются в одну и ту же «обломочную» запись) и соседство на карте.

**Крыша = O_FLOOR верхнего этажа**, не отдельный механизм. Набор `C_EXT_ROOF_RED` (интерьер
летающей машины `AIRSPEEDER`, тоже описан в рулсете как обычный террейн): бо́льшая часть его
45 записей — `Tile_Type=0` (пол) с `T_Level` от 0 до -8 и разным `P_Level` (наклон/выступ
кровли), несколько записей `Tile_Type=1/2` (гребень крыши как стеновой кадр). На карте
`AIRSPEEDER` эти записи реально стоят как **пол** тайлов `z=1` (верхняя палуба):
```
(5,4,1) пол C_EXT_ROOF_RED:0     (плоская панель, T_Level=0)
(5,3,1) пол C_EXT_ROOF_RED:39    (5,3,1) сосед по Y — край/скат)
(6,3,1) пол C_EXT_ROOF_RED:2
```
Поскольку камера с нижнего этажа (`_camera->getViewLevel()==0`) рисует только `itZ` от 0 до
`min(endZ, viewLevel)=0` (`Map.cpp:1414-1417`), пол `z=1` **не рисуется вовсе**, пока игрок не
поднимет уровень обзора до 1 (тогда рисуются и 0, и 1: `beginZ` всегда 0, `endZ`=`viewLevel`) —
именно так «крыша» показывается только с высоты или при взгляде на разрез сверху, а изнутри
здания снизу её не видно.

**bigWall и рисование**: `bigWall` НИГДЕ не читается в `Map::drawTerrain` (грепом по файлу —
ни одного вхождения). Он влияет только на `Pathfinding` (`src/Battlescape/Pathfinding.h:100-201`,
`bigWallTypes`: `BLOCK, BIGWALLNESW, BIGWALLNWSE, BIGWALLWEST, BIGWALLNORTH, BIGWALLEAST,
BIGWALLSOUTH, BIGWALLEASTANDSOUTH, BIGWALLWESTANDNORTH`, значения 1-9 с ASCII-схемами прямо в
коде) и на `TileEngine` (LOS/блокировка взрыва по направлению, `TileEngine.cpp:3928-4024` и
далее). Диагональная форма стены — это просто то, что художник нарисовал по диагонали внутри
обычного кадра объекта 32×40; движок её не режет и не собирает. По статистике MCD Пираток
(611 наборов, 24605 записей): `bigWall` ненулевой лишь у 11.4% записей, и диагонали
(`BIGWALLNESW`/`NWSE`) есть **только** среди `Tile_Type=объект` (см. таблицу ниже) — ни разу
не встретились у пола или обычных стен.

### 6. Двери и разрушение

Обычная дверь (`Door!=0`) — **не анимация**, а подмена всей записи целиком на запись
`Alt_MCD` (`Tile::openDoor`, `Tile.cpp:379-390`): `setMapData(dataset->getObject(altMCD), ...,
altMCD, ... altRecord->getObjectType())`. Пример: `BARN` запись 17 (закрыта, кадр 17) →
`Alt_MCD=18` → запись 18 (открыта, кадр 18, тоже статичная). `getObjectType()` новой записи
может отличаться от старой — движок кладёт результат в слой, соответствующий НОВОЙ записи,
не старой позиции.

Разрушение (`Tile::destroy`, `Tile.cpp:535-563`): если у уничтожаемой записи `Die_MCD != 0`,
клетка подменяется на `dataset->getObject(dieMCD)` (та же логика — целая запись, свой
`Tile_Type`, свой кадр/кадры). Если сгорел пол на Z=0 — подстановка спец-тайла «выжженная
земля» (`MapDataSet::getScorchedEarthTile`). У Пираток `Die_MCD≠0` — 11048 записей из 24605
(44.9%), то есть почти половина всех объектов имеет «уничтоженную» версию.

## Чего НЕ выяснил

- Как именно `UnitSprite` сдвигает юнита по `Tile::getTerrainLevel()` — нашёл только сдвиг
  предметов (`BattleItem`) в `Map.cpp`, код `UnitSprite::draw` не читал построчно в этом
  прогоне.
- Не нашёл ни одного явного признака в данных (MCD/MAP/рулсетах), который помечал бы «эти N
  записей — один составной предмет» — судя по коду, такого признака в движке действительно
  нет (пусто, не потому что не искал), но это негативный факт, а не позитивный — оставляю
  открытым на случай, если он всё же где-то есть в других частях рулсета (например,
  `MCDPatch`), которые не смотрел подробно.
- Не проверял скейлинг `srcDomain` (base-pixel координаты half-blit севера) на корректность
  относительно HD-кадра (`k`-масштаб) в `doBlitHd` — код читал (`HdCanvas.cpp:1971-1975`,
  `2112-2117`), но не проверял математику совпадения половины в base-пикселях с шириной HD-кадра.
- Не проверял, как именно диагональные стены (`BIGWALLNESW/NWSE`) выглядят как воксельная
  форма (LOFT) для LOS — смотрел только на счётчики и на факт «не влияет на blit».
- Не нашёл готового способа отличить «непрозрачный AltMCD, реально не используемый» (802 из
  982 записей с Alt_MCD≠0, но Door=0) от «данных, которые читает какой-то ещё не найденный мной
  путь кода» — судил по `grep getAltMCD()`, все вызовы просмотрены, но не исключаю скрипты
  ruleset-патчей (`MCDPatch`), которые не разбирал.
- Роль `Stop_LOS`/`Block_Smoke`/`Flammable` в `setBlockValue` (перепутанные по названию поля
  параметры, см. §2) не перепроверял на предмет опечатки vs осознанного решения апстрима —
  просто зафиксировал, что в коде сейчас именно так.
