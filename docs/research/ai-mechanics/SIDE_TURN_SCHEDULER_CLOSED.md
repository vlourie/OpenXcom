## Что установлено

**Порядок действий стороны в OXCE менять можно, безопасно и дёшево:**
- выбор следующего юнита идёт через `BattlescapeGame::handleAI`;
- без флага сборка побайтно совпадает с D0;
- лимиты движка соблюдаются: активаций сверх предела 0, рост ТЕ 0, повторов в проходе 0;
- запись детерминирована;
- 49 мкс на выбор.

**Сделать врага от этого заметно опаснее не удалось.** 96 боёв, 24 сценария × 2 сида:

| Показатель | Результат |
|---|---|
| Урон отряду игрока | +2,1%, 95% CI −3,8% … +6,4% |
| Исходы | без общего изменения: 23 / 5 / 20 в обоих плечах |
| Исполненных атак врага | −5% (5794 → 5492) |
| Потери врага | −8%, не значимо |
| Перестановок стрелка вперёд | 2165 |
| Сразу атаковал после перестановки | 67% (1445); урон прошёл в 15,6% атак — как у врага в среднем |
| Сбои и лишние активации | не найдены |

- **2165 перестановок устойчивого преимущества не дали.** Исполненных атак стало на 5% меньше: ранние атаки частично
  заменили атаки остальных юнитов, а не добавились к ним. Примерно треть поднятых юнитов атаковать не стала.
- **Эффект L2 нестабилен.** 159 → 1 реакция игрока в первом ходу врага на других 22 сценариях не повторяется:
  −0,5 на бой, CI −2,0 … +0,6. В самом L2 при другом сиде враг вышел слабее.
- **«Урон отряду» и «урон атаками врага» — разные величины.** Определения и разбор — в §2а отчёта пилота.
  - Урон отряду — потеря здоровья бойцами игрока от любых источников за бой, урон сверх смерти не считается.
  - Урон атаками — урон исполненных атак врага в его ход по игроку и гражданским, урон сверх смерти включён.
  - В ходы врага урон отряду почти не изменился: −8,6 HP на бой.
  - Падение «урона атаками» почти целиком приходится на урон сверх смерти и по гражданским: −41 из −49.
  - В ходы игрока урон отряду вырос на 20,5 HP.
  - Ни один из этих сдвигов не значим.

Пилот не доказывает, что смена очерёдности бесполезна при любых условиях. Он показывает другое: конкретный алгоритм
«сначала активировать того, кто может стрелять» достаточного преимущества не дал. Планировщик улучшает очерёдность, но
не суммарный результат действий стороны.

**COVER (этап 3).** 0 реакций из 36 приказов прикрыть. Прикрывающего не пускает порог очков реакции в
`TileEngine::getSpottingUnits`. На M10 этот порог остановил 256 проверок из 294, на L2 — 249 из 402. До списка
стрелков не дошла ни одна. Подробно — в `SIDE_TURN_SCHEDULER_STAGE3_RESULT.md`.

## Вывод для дальнейшей работы (Vitali)

Технически работают многие отдельные механизмы:
- TACTICAL DIRECTOR;
- COORDINATED ENGAGEMENT;
- STAGE_RALLY;
- Scheduler.

Ни один из проверенных вариантов не дал убедительного устойчивого усиления врага.

Поэтому подход меняется. Следующий этап начинается не с очередной механики и не с патча `AIModule`, а с
**конкретной боевой задачи**. Например:

> У врага шесть бойцов, игрок занимает укреплённое здание. Как этим шести бойцам действовать совместно, чтобы
> повысить вероятность победы?

Порядок работы:
1. Сформулировать боевую задачу.
2. Составить тактический план действий.
3. Проверить законность плана по правилам игры: ТЕ, видимость, реакционный огонь, FAIR.
4. Только потом проектировать код, который нужен для этого плана.

Без отдельного GO ничего из этого не начинается.
