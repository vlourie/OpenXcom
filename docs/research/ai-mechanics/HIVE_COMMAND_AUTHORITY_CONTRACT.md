# HIVE COMMAND: полномочия и контракт штаб → боец

2026-11-05. Только исследование: боёв, сборок и правок кода не было. Основное дерево, спавн, Git, игровой каталог и выпуск не тронуты.

**Может ли существующий AIModule поддерживать настоящую иерархию военного командования через ограниченный интерфейс намерений, или нам необходим пересмотр конкретных этапов принятия решений?**

**Иерархию направления — да, через ограниченный интерфейс, без пересмотра этапов. Гарантированное исполнение взаимозависимых планов — нет, и этого не даст никакой пересмотр AIModule.**

- **Что интерфейс может.** Штаб решает, где находится армия, против кого она собирается и когда задача снята. В 48 архивных боях 64 % решений бойцов — патруль, а 41 % бойцо-ходов проходит только в патруле. Там штаб ведёт бойца, не споря с его боевым выбором. Это и есть путь к управлению всеми 30 бойцами, а не парой.
- **Что интерфейс не может.** Он не заставит бойца нанести конкретный удар в конкретный момент. Точно этого можно добиться только подавлением: 16 % уже готовых атак не исполняются из-за штатного выбора режима.
- **Что не может никто.** Между подготовкой и ударом идёт ход игрока, и он не подчиняется штабу. Поэтому **план, которому для пользы нужно пережить ход игрока всеми участниками, надо отсекать на этапе полководца, а не лечить в исполнителе.**
- **Пересмотр этапов** нужен только для порядка действий внутри хода и для веса режимов. Это отдельное решение и не первый шаг (раздел 5).

Ни один вариант пока не доказывает, что армия станет сильнее: пользы для боя не показал ни один этап HIVE.

## 1. Карта полномочий

Строки — основное дерево, в нём HIVE нет. Номер без имени файла здесь и ниже — `src/Battlescape/AIModule.cpp`. `SavedBattleGame.cpp` и `BattleUnit.cpp` лежат в `src/Savegame`, остальные файлы — в `src/Battlescape`. «Сейчас» — кто решает в коде. Штаб, командир и боец — как должно быть по контракту.

## 2. Контракт штаб → боец

### Данные

Намерение — запись только для чтения. Боец читает её сам внутри `think()`, до готового действия.

```cpp
struct SoldierIntent {
    int id, squad, issuedTurn, expiresTurn;   // срок: истёк - записи как нет
    IntentKind kind;                          // MOVE_AREA, HOLD_AREA, ENGAGE_CONTACT
    Position areaCenter; int areaRadius;      // район, не клетка
    int contactId;                            // -1 если нет
    Position contactAt; int contactSeenTurn;  // только законное знание стороны
    KnowledgeClass knowledge;                 // KNOWN, LAST_KNOWN, INFERRED
    int priority;
};
struct IntentReport {                         // пишет движок и боец, читает штаб
    int intentId, unit, turn;
    IntentOutcome outcome; RefusalReason why;
    Position endedAt; bool unitOut;
};
```

| Поле контракта | MOVE_AREA | HOLD_AREA | ENGAGE_CONTACT |
|---|---|---|---|
| Цель и ожидаемый результат | быть в районе | быть в районе к концу срока | контакт атакован своими или выбыл |
| Доступные ресурсы | бойцы подразделения, срок; TU — только сведения для плана | то же | то же; число бойцов с пригодным оружием |
| Срок | N ходов, обычно 2–3 | N ходов, с пересмотром штабом | 1 ход, продление только при новом подтверждении |
| Обязательные ограничения | FAIR, правила движка | то же | то же; контакт только законно известный |
| Допустимые отклонения | любой бой, побег, засада, паника | то же, а также выход из района ради атаки | другая цель, побег, любая уже готовая атака |
| Причина отказа | `NO_PATH`, `MODE_OTHER`, `OUT` | `NO_NODE`, `MODE_OTHER`, `OUT` | `NOT_SEEN`, `NOT_VALID`, `NO_EFFECT`, `NO_LINE`, `NO_TU`, `MODE_OTHER`, `CLOSER_THREAT`, `OUT` |
| Фактический результат | `DONE`, `PARTIAL`, `REFUSED`, `EXPIRED`, `OUT` | то же | то же и `TARGET_OUT` |

Новая тактика — новый способ штаба выбирать районы и контакты, а не новый вид приказа. Новых точек в движке она не требует, пока хватает этих трёх видов.

### Шесть правил

1. **Намерение только упорядочивает или выбирает среди уже законного.** Оно не запрещает кандидата и не отменяет готовое действие.
2. **Кубик режима, ESCAPE, цепочка запасных вариантов, заряд, выстрел, граната не трогаются.** Запреты `PO_HOLD`, `PO_STAND`, `OO_STAY` и откат заряда (`operationDefers`) контрактом исключены.
3. **Нельзя подменять результат после `think()`.** Откат внутри `think()` тоже нельзя: `setupAttack` и `setupPatrol` уже меняют состояние (`setCharging:4938`, поворот `:1919`), откат хрупок.
4. **Отклонение бойца — не ошибка.** Оно пишется с причиной, и штаб на него отвечает новым планом, а не усилением приказа.
5. **Штаб не даёт бойцу знаний сверх законных.** Контакт ставится только из `getVisibleUnits` живых своих или из памяти с пометкой класса. Боец всё равно проходит `validTarget:6333` и `knownPlace:167`.
6. **Штаб не бросает кости и не пишет TU, энергию, позицию.** Сдвиг RNG от пропуска `getPatrolNode` неизбежен, поэтому один сид пользы не докажет (раздел 7).

Цена правил 1–3: заряд раньше срока больше не откладывается. Постановку как в запуске 4 V0 такой контракт не исполнит. Это осознанно: она и не окупилась.

### Точки чтения

| Точка | Что меняется | Что боец проверяет сам |
|---|---|---|
| `AIModule::setupPatrol:1900`, выбор узла | предпочтение узла в районе или ближе к нему | штатный путь и TU; нет такого узла — штатный выбор |
| `AIModule::selectNearestTarget:3006` | контакт вместо ближайшего среди прошедших все проверки | видимость, `validTarget`, линия |
| `findFirePoint:4021`, `setupAmbush:2168` | ограниченная прибавка к оценке клетки в сторону района, без запрета клеток | штатная оценка и достижимость |
| `BattlescapeGame::handleAI`, после решения `:549` | журнал и отчёт о решении | влияния нет |
| `BattlescapeGame::popState:1468`, `checkForCasualties:919` | отчёт о факте | влияния нет |

Не трогаются: `evaluateAIMode`, `setupEscape`, `meleeAction`, `projectileAction`, `UnitWalkBState`, `TileEngine`, `handlePanickingUnit`.

## 3. Как полководец проверяет осуществимость

Замер — 48 архивных боёв D0, без единой строки HIVE (`cm/hive_authority/feasibility.txt`, `feas2.txt`). В скобках разброс по боям: 10-й и 90-й процентили. Разброс большой, средние читать только как порядок величины.

**За игрока здесь играет стендовый бот. Живой игрок может вести себя иначе.**

### Доказанная осуществимость: движок считает это сейчас

| Что | Откуда | Замер |
|---|---|---|

### Оценочный риск: разрешено учитывать, нельзя считать доказанным

**Выбыть за ход игрока** (убит или оглушён): 715 из 10867 бойцов, 6,6 %. Сюда не вошли ходы, которыми бой кончился, поэтому цифра занижена.

| Законный признак: до ближайшего видимого стороной врага | Выбыло |
|---|---|
| до 5 клеток | 215 из 1122, 19,2 % (4–67) |
| 6–10 | 143 из 1385, 10,3 % (0–44) |
| 11–20 | 223 из 2803, 8,0 % (0–29) |
| больше 20 | 95 из 3542, 2,7 % (0–14) |
| никого не видно | 39 из 2015, 1,9 % (0–12) |

Другие оценки:

- **Цель через ход.** Из видимых стороной: сместились на 3+ клетки машины 177 из 339 (52 %), люди 484 из 874 (55 %). Сменили направление 56 % и 64 %. Остались видны 73 % и 69 %. Подход с кормы заранее не планируется.
- **Точность — не эффект.** Выбранные выстрелы с точностью стрелка 80+ нанесли урон или оглушение лишь в 136 из 1002, 13,6 %. Удары 80+ — в 48 из 168, 28,6 %. Поле `p` не учитывает дальность и броню, поэтому это не «шанс» из плана. Те же причины обесценивают расчётные 35 % и 67 % из V0.
- **Эффект по паспортной броне.** Отказ `no_effect` в CI иногда ошибался: в запуске 2 из 34 пар «боец + контакт» с таким отказом боец всё равно атаковал контакт в 15, с уроном в 4. Текущая броня цели — скрытое знание.
- **Выбор бойца.** Готовая атака или заряд исполнились в 6537 из 7793, 83,9 % (75–95). Остальное ушло в патруль, побег и засаду штатно.
- **Исполнение ходьбы.** Дошли до клетки за одно решение: в COMBAT 71 %, в ESCAPE 82 %, в засаду 86 %. Патруль не показателен: узел часто дальше одного решения. Всего 12756 из 31874 решений о ходьбе не потратили TU совсем.

### Неизвестное: нельзя выводить ни из чего

- Планы игрока и его невидимые бойцы.
- **Опасна ли клетка, которую ещё не проверяли.** Наблюдатели своей клетки дают `getSpottingUnits`, а для пустой клетки та же функция почти всегда отвечает «линии нет» (R-635). Надёжного инструмента у штаба нет.
- Паника, текущая броня, запас TU врага на реакцию.

**Почему «по нему ещё не стреляли» не доказывает безопасность:**

- 329 из 715 выбывших за ход игрока, **46 %, в начале этого хода никто не видел** (`seenby 0`).
- На клетке, где кто-то уже пережил ход игрока в этом бою, выбыло 172 из 3567, 4,8 %. На новой клетке 7,4 %. Разница есть, но клетка не становится безопасной. Причину разницы я не выделял: старые клетки чаще в тылу.
- `seenby` резко разделяет риск: 0 — 3,5 %, 1 — 23,8 %, 2+ — 45,1 %. Но для штаба это скрытый факт, он доступен только журналу. Показывать его штабу нельзя.

### Правило отбора плана

До назначения штаб отвечает на три вопроса:

1. **Доказанные условия выполнены?** Нет — плана нет.
2. **Сколько ходов игрока надо пережить до пользы?** Ноль — план допустим по этому вопросу. Один и больше — следующий вопрос.
3. **Даёт ли первый шаг каждого участника пользу, даже если остальные выбудут или цель уйдёт?** Нет — план не назначается.

Слово «безопасно» в плане запрещено. Есть только класс риска по законным признакам и список неизвестного.

Проверка на эпизоде V0: постановка вплотную к дальности выстрела цели (в запуске 4 выстрел с дистанции 5, то есть класс «до 5»), один ход игрока до пользы, в одиночку постановка пользы не даёт. **По этому правилу операцию бы не назначили,** и запуск 4 подтвердил почему. Правило пока не проверено на других эпизодах и может отсекать слишком много.

## 4. Три архитектурных ограничения

### A. Почему штаб не может надёжно влиять на конкретное действие, не подавляя бойца

1. **Цель выбирается не в одном месте.** `_aggroTarget` пишут `selectNearestTarget:3028`, `meleeAction:4936`, пси и снайпер. `meleeAction` сам ищет цель заново в `:4917`.
2. **Кандидатов четыре, режим выбирает кубик.** `think:1104–1123` готовит побег, засаду, атаку и патруль, а `evaluateAIMode:3860` бросает кубик по шансам из состояния бойца. Задачи среди них нет. Бросок идёт не всегда: режим COMBAT с готовой атакой не пересматривается `:1152`, поэтому уже начатое держится, а смена требует нового случая.
3. **Сделанное в `think()` имеет последствия.** Заряд ставится в `setCharging:4938`, он сам закрепляет COMBAT `:3886`. Взвод гранаты тратит TU в `:1285`. Отменить задним числом чисто нельзя.
4. **Замер CI.** На 873 вопроса: уже та же цель 429, отказ 357, взяли контакт 87. Изменено 74 решения из 1772, атаками стали 14 из 322. Большая часть влияния — ходьба. Бойцы и без штаба чаще всего бьют того же, кого он назвал.

**Вывод.** Выбор цели — слабый рычаг, выбор режима — запретный. Сильный рычаг находится раньше: **где боец окажется, когда начнётся его решение.** 64 % решений (25388 из 39508) и 41 % бойцо-ходов (4760 из 11622) проходят только в патруле, атакуют 29 % бойцо-ходов.

**Минимальная точка:** `setupPatrol:1900`, предпочтение узла. Вторая: `selectNearestTarget:3006`. Уже есть в экспериментальных деревьях в похожем виде, но с запретами, которые надо снять.

### B. Почему несколько бойцов не могут гарантированно исполнить взаимозависимый план

1. **Ход игрока.** Цепочка на паре бойцов в 3 клетках друг от друга, при видимом враге в 15 клетках от первого: оба в строю 2661 из 3099, 85,9 %; и оба с полными TU 85,1 %; и цель жива и видна **66,0 % (15–100)**. Это верхняя граница: ещё не учтены путь, линия и выбор режима.
2. **Нет групповых действий.** Бойцы ходят по одному в порядке `_units` (`SavedBattleGame.cpp:1004`), по 2 действия на выбор, с одним повторным проходом `_AISecondMove` (`BattlescapeGame.cpp:406`). Движок не умеет ни «подожди напарника», ни резерв TU на чужое действие.
3. **Ходьба не атомарна.** Она останавливается при новом враге и реакции (`UnitWalkBState.cpp:240`, `:255`). Не останавливается только заряд и побег (`:281`). После остановки новый `think` и новый выбор.
4. **Кубик у каждого свой.** При 84 % исполнения готовой атаки двое исполнят обе примерно в 7 случаях из 10, если считать независимо. Это грубая оценка, а не замер.

**Гарантии нет по правилам игры, и код её не добавит.** Поэтому план строится на устойчивости, а не на гарантии:

- польза каждого шага в одиночку (правило отбора);
- назначать больше участников, чем нужно;
- при выбытии штаб переназначает, а не только отменяет;
- согласовывать внутри одного хода стороны сильнее, чем через ход игрока: между бойцами остаётся только реакция, а не весь ход врага.

**Минимальная точка:** не исполнитель, а отбор в штабе, код движка не меняется. Согласование внутри хода упирается в порядок, это вариант 2.

### C. Как получать факт, чтобы следующий план учитывал прошлый

Сейчас:

- `HiveCommand::decided` (дерево, `BattlescapeGame.cpp:553`) видит решение, но не результат.
- Результат собирает стендовый `flushExec` (`AiProbe.cpp:1550`), он есть только при `OXCE_AI_DEV`. На игровом пути его нет.
- В V0 штаб получил итог, но использовал его только для закрытия операции. В CI он реально повлиял на следующий выбор 4 раза (`SKIP`).

| Какой факт | Где взять в игровом пути | Законно ли для штаба |
|---|---|---|
| Что боец решил, почему отказался | после решения, `handleAI:549` | да, это своё |
| Где действие кончилось, сколько TU осталось | `popState:1468` | да, своё |
| Свой выбыл: где, когда | `checkForCasualties:919` | да |
| Кто ударил своего | `BattleUnit.cpp:2019` даёт стрелка | **только если он виден**; иначе вывод «враг где-то рядом» (INFERRED) |
| Цель упала | `isOut` | **только если сторона видит её**; это уже дыра V0, см. его отчёт |
| Сколько урона нанесено врагу | здоровье врага | **нет,** это скрытое; игрок его тоже не видит. В стенде только для журнала |

Использование в следующем плане, минимально:

- риск района: свои потери по районам и ходам, с забыванием;
- контакт: отказы `NO_EFFECT` и `NOT_SEEN` снижают его приоритет для этого оружия;
- намерение: `EXPIRED` и `REFUSED` подряд — штаб снимает задачу и пишет причину;
- подразделение: выбывшие участники вызывают перераспределение на этом же плане.

Хранение: `HiveCommand::saveText` и `loaded` (дерево, `SavedBattleGame.cpp:700`) нужно расширить. Проверки загрузки посреди боя ещё не было. Без этого нельзя в игру.

## 5. Варианты

Объём — моя оценка по дереву, не замер.

### Вариант 1. Интерфейс намерений без пересмотра этапов

**Суть:** раздел 2 целиком. Правки: `setupPatrol`, `selectNearestTarget`, прибавка к оценке клетки в `findFirePoint` и `setupAmbush`, два отчёта о факте.

| | |
|---|---|
| Объём | `AIModule` — 30–60 строк в 3–4 функциях; `BattlescapeGame` — около 10; `HiveCommand` — замена `PatrolOrder` на намерение, удаление `PO_HOLD`, `PO_STAND`, `OO_*`, `operationDefers`; сохранение боя |
| Что даст | управление всей армией вне боя: сосредоточение, сектора, смена задачи по обстановке, реакция на потери. Отказы с причиной и настоящая обратная связь |
| Не даст | одновременного удара, порядка действий, гарантии атаки. В бою штаб почти ничего не меняет |
| Риски | **пользы может не оказаться:** боец в нужном месте всё равно решает сам. Охрана без `PO_STAND` хуже держит место. Сдвиг RNG меняет бой и усложняет сравнение |
| Автономия | не затрагивается: кандидаты те же, режим тот же |

### Вариант 2. Вариант 1 плюс пересмотр двух этапов

**Этап порядка.** Штаб определяет очередь внутри хода стороны. Правка: `selectPlayerUnit` (`SavedBattleGame.cpp:1004`) или выбор в `handleAI:406`, `:649`, `secondPassWrapped`. Открывает «разведка стреляет первой, остальные решают по её результату» в одном ходу, без хода игрока между ними.

**Этап режима.** В `evaluateAIMode:3860` появляются множители от задачи. Кубик остаётся.

| | |
|---|---|
| Объём | ещё 100–200 строк в `AIModule`, `BattlescapeGame`, `SavedBattleGame` |
| Что даст | согласование внутри одного хода и больший вес боя у выбранных подразделений |
| Риски | **порядок — самая глубокая правка:** функция общая со стороной игрока, менять её надо только для ИИ. Порядок меняет реакции и баланс. Выбор не чисто механика ИИ, близко к правилу 2 CLAUDE.md |
| Автономия | **множитель боя снижает долю побега, хотя ветку не трогает.** Это мягкая форма того, что ты отверг. Нужно твоё явное решение и граница. Без него этап режима не делать |
| Ограничения | гарантий по-прежнему нет; ход игрока остаётся |
