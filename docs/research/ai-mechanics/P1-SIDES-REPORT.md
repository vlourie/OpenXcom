## 1. Как устроено

### 1.1 Две стороны

В `AiProbe.h` появился `enum Side { SIDE_GAME = 0, SIDE_BOT = 1 }`.

- `SIDE_GAME` — всё, за что ИИ ходит у живого игрока: враг, гражданские, паникующие и подконтрольные бойцы игрока.
- `SIDE_BOT` — тестовый бот за игрока, только под стендом.

`sideOfFaction(f)` возвращает `SIDE_BOT` только для `FACTION_PLAYER` при включённом боте (`OXCE_AI_BOT` под стендом).
`sideOf(unit)` определяет сторону по фракции юнита.

В релизной сборке обе функции всегда возвращают `SIDE_GAME`. `param` там сторону не читает, профиль релиза прежний.

### 1.2 Новая переменная: `OXCE_AI_SIDES=1`

Без неё сторона бота читает то же, что и раньше, — поэтому A-dev побайтно равен базе. С ней:

- **враг** читает прежнее: `OXCE_AI_*` из окружения под стендом, профиль AI3 в режиме игры;
- **бот** читает только `OXCE_AIP_<хвост имени>`. Например, `OXCE_AI_CAREFUL` для бота — это
  `OXCE_AIP_CAREFUL`. Ключи врага и профиль AI3 бот не видит вовсе (проверка E2: при SIDES без `OXCE_AIP_*` все
  `env.*` бота пусты).

`OXCE_AI_SIDES` действует только при активном стенде или режиме игры (`active()`). Опций игры она не меняет и сама
профиль врага не трогает (проверка A2).

В шапку записи боя `cfgText` пишет и `OXCE_AIP_*`, так что окружение обоих плеч видно в каждой записи.

### 1.3 Чтение параметра

- `param(name, def, side)`, `envOn(name, side)`, `sideEnv(name, side)` — чтение со стороной.
- Функции режимов (`hypoLos`, `fairKnowledge`, `oxceFixes`, `bestCell` и ещё 19, см. `fn.*` в дампе) теперь принимают
  сторону.
- В `AIModule.cpp` статические кэши параметров стали парами:
  `static const auto xS = AiProbe::sided(...)` и `x = xS[AiProbe::sideOf(_unit)]`.
  Кэш сохранён, лишних чтений окружения в ходе боя нет.
- Чтение без стороны (`envOn(name)`, `ai3Env`, `getenv`, `logParam`) разрешено только для глобальных имён (раздел 3).
  Аудит считает нарушением любое такое чтение имени, влияющего на решения.

## 2. Где сторона не очевидна

Требование Vitali: «если параметр вызывается без контекста стороны, это надо отдельно разобрать, а не автоматически
относить к врагу». Ниже все такие места и принятые решения.

| место | чья сторона | почему |
|---|---|---|
| поиск пути (`Pathfinding::aStarPath`, `isBlocked`) | идущего юнита (`_unit`, `unit`) | путь — часть решения того, кто идёт |
| поле зрения при ходьбе (`walkFovSkip`) | смотрящего | экономия расчёта для того, кто смотрит |
| `getSpottingUnits`, `upstreamSpot` | замечающего юнита `bu` | кто замечает — тот и решает |
| `tryReaction`, риск по своим (FF_RISK) | реагирующего | реакция — решение стреляющего |
| `canTargetUnit`, гипотетическая видимость (HYPO_LOS) | `sideOfFaction(_save->getSide())` | гипотетическую проверку задаёт только ИИ в свой ход; потенциальный юнит — либо сам решающий, либо его цель |
| `BattlescapeState`, `upstreamVis` | выбранного юнита | экран показывает видимость выбранного |
| `getPatrolNode` | патрулирующего юнита | |
| `updateHonestKnownPosition` | `sideOfFaction(side)` — стороны, чью память правим | |
| `AiKnownPlace::trueBody` | решающего | в конструктор добавлен параметр `decider` |
| `zeroEffectMode`, `zeroHonestMode`, `sniperAoeMode`, `BattlescapeGame::reserveAffordableMode` | юнита из нового параметра `const BattleUnit *unit` | раньше функции вызывались без юнита |
| `BattleUnit::save` — память ИИ в сейве | любая сторона | память пишется, если честное знание включено хоть у одной стороны; это запись, а не решение. Иначе при знании только у одной стороны её память не попала бы в сейв |
| `OXCE_AI_REVIVE` | юнита | раньше читался сырым `getenv` мимо профиля; для `SIDE_GAME` значение то же, что было |
| `FIREPOINT_BLOCKED_V1_INTEROP` | юнита | |
| журнальные ключи `TRACE_MELEE`, `CELLPROF`, `TRACE_PATH` | `SIDE_GAME` явно | пишут журнал или профиль времени, на решения не влияют; тумблер один на запуск |
| `LIGHTSKIP` в строке журнала | обе стороны | журнал печатает значение врага и, при SIDES, отдельно бота |

### 2.1 Особые случаи

**Шесть «чистых» исправлений** — `counterFix`, `astarCostFix`, `escapeSignFix`, `staleEscapeFix`, `upstreamSpot`,
`upstreamVis`:

- под стендом включены у обеих сторон безусловно (`active()`), как и в базе;
- П-1 этого не менял: исправление ошибки движка у бота одно и то же в обоих плечах, так что разницы плеч оно не даёт.

**`oxceFixes`** при боте с `OXCE_AI_SIDES` для стороны бота читается из `OXCE_AIP_OXCE_FIXES`. Для врага —
как раньше.

**`postWalkFix`, `panicTurnFix`, второй проход** вызываются только для юнитов бота. Это сторона бота по построению.

**`upstreamSpot` и `upstreamVis` (О6) — механика зрения, а не только решения ИИ.** Они меняют, кто кого видит,
то есть и обзор живого игрока. В разделе «Границы» итогового отчёта мерки это надо оговорить: плечо с О6 меняет не
только ум врага.

## 3. Глобальные имена

Эти имена обслуживают обе стороны одним значением; ни одно решение их не читает. Список один на аудит и на
проверку дампов — `p1_audit_rules.py`.

| группа | имена | почему одно на всех |
|---|---|---|
| режимы стенда | `PROBE`, `BOT`, `SIDES`, `FAST`, `HDPACE`, `REALTIME`, `SEED`, `PROBE_TURNS`, `PROBE_SAVE` | определяют сам запуск, а не поведение стороны |
| сценарий боя (`NewBattleState`) | `CAMPAIGN`, `CRAFT`, `SQUAD`, `MISSION`, `TERRAIN`, `RACE`, `DIFF`, `LOADOUT_FIX` | исходные условия; должны быть одинаковыми для обеих сторон |
| запись и пробы | `RECORD*`, `COVERMAP*`, `TRACE_DECISION`, `MEDIPROBE`, `BLAST_PROBE`, `FAIR_SAVECHECK`, `ATTRIB_PROBE`, `EXPOSURE_PROBE`, `ESCAPE_ALT_PROBE`, `ESCAPE_ALT_CAP` | только пишут, решений не меняют |
| журнал и профиль времени | `TRACE_PATH`, `TRACE_MELEE`, `*PROF`, `PROFILE_DUMP` | только пишут |
| поля записи | `BUILD`, `EXE`, `GAME`, `WORK`, `KEEP_DECIDE` | имена полей шапки записи, а не переключатели |

`OXCE_AI_LOADOUT_FIX` отнесён к сценарию: он подгоняет снаряжение отряда до боя, а не управляет ходом. По
разделу 7.2 этапа 1 он должен быть одинаковым во всех плечах — это и обеспечивает одно значение на запуск.

## 6. Дампы профилей

### 6.1 Как снимается

`OXCE_AI_PROFILE_DUMP=<файл>` — новый хук в `main.cpp` сразу после `Options::init` и до SDL. Он пишет TSV
`ключ / враг / бот` и выходит. Опции берутся из `-user` и `-cfg` во временной папке `dumpuser`, настоящий
конфиг не читается и не пишется.

**Хук есть и в релизе.** Без переменной он ничего не делает. С переменной релиз печатает профиль и выходит, не
открывая окна. При переносе в основное дерево — решить, оставлять ли его в релизе. Он полезен для проверки
выпуска, а риск — только в том, что у игрока такая переменная окружения окажется случайно.

Строки дампа:

- `build`;
- `opt.*` — три опции BetterAI;
- `mode.*` — в DEV `active`, `harness`, `play`, `bot`, `sides`, `autoClose`, `fast`, `hdPace`;
- `side.player`, `side.hostile`, `side.neutral`;
- `fn.*` — 23 функции режимов по сторонам;
- `param.<имя>` — 96 имён; если параметр не задан, пишется `−999`;
- в DEV `env.<имя>` — сырое значение для стороны;
- в релизе `rel.fixes` и `rel.ai3`.

### 6.2 Матрица

4 сборки × 15 наборов окружения × 4 набора опций = 240 запусков, 24 секунды.

**Наборы окружения:**

| набор | что в нём |
|---|---|
| H0–H6 | стенд (`PROBE` + `BOT`): без SIDES / с SIDES; ключи врага `OXCE_AI_*` = 3; ключи бота `OXCE_AIP_*` = 2; профиль AI3 у врага |
| P0–P4 | режим игры через `OXCE_AI3_PLAY`, те же сочетания |
| N0 | без окружения |
| N1 | только `BOT` + `SIDES` + `OXCE_AIP_*` |

**Опции:**

- O1 — исправления;

### 6.4 Выборка строк

Формат значений — `враг / бот`.

| ключ | П-1, стенд H5, O3 | база, H5, O3 | П-1, игра P4, O0 |
|---|---|---|---|
| `param.OXCE_AI_CAREFUL` | 3 / 2 | 3 / **3** | 3 / 2 |
| `param.OXCE_AI_TACTICS` | 3 / 2 | 3 / **3** | не задан / 2 |
| `param.OXCE_AI_HYPO_LOS` | 3 / 2 | 3 / **3** | 1 / 2 |
| `fn.bestCell` | 3 / 2 | 3 / **3** | 0 / 2 |
| `fn.fairKnowledge` | 0 / 0 | 0 / 0 | 1 / 0 |
| `fn.hypoLos` | 0 / 0 | 0 / 0 | 1 / 0 |
| `env.OXCE_AI_REVIVE` | 3 / 2 | 3 / **3** | 3 / 2 |
| `side.player` | 1 (бот) | 0 | 1 (бот) |

На базе бот получает значения врага (3) — это и есть блокер. В П-1 у бота свои значения (2). В режиме игры профиль
AI3 включает врагу честное знание и `HYPO_LOS`, а бот их не получает.

`fn.hypoLos` = 0 под стендом при `HYPO_LOS` = 3 — это не ошибка. Режим включается только значением 1, а дамп
показывает итог функции. Тестовые значения 3 и 2 выбраны, чтобы различать стороны, а не чтобы включать режимы.

## 7. Пробел: плечо P под стендом

В разделе 11 этапа 1 плечо **P** — «BetterAI выкл». Шесть чистых исправлений из раздела 2.1 под стендом включены
всегда, у обеих сторон:

| сборка, режим | исправления |
|---|---|
| релиз, BetterAI выкл | выключены |
| DEV, без окружения, BetterAI выкл | выключены |
| DEV, стенд, BetterAI выкл | **включены** |

Значит, враг плеча P на стенде — не тот враг, которого получает игрок с выключенным BetterAI: у него уже стоят шесть
исправлений. Так было и в базе, П-1 это не вводил и не чинил. Для мерки «FX против P» это значит, что О6 и ещё пять
исправлений в разнице плеч не участвуют.

Решить до когорт:

- (а) принять: P — это «ванилла плюс шесть исправлений», и записать это в шапку;
- (б) дать врагу под стендом выключатель этих шести (сторона `SIDE_GAME`), бот оставить с ними.

Вариант (б) — правка `src`. Без слова Vitali она не делалась.
