## 0. Коротко

1. Журнал — **новый общий модуль `AiTrace`**, собирается в обе сборки без `#ifdef`. Пишет только в свой файл и
   только при переменной окружения. DEV-журналы `[AIDECIDE]`/`[AISTATE]` для этого не годятся: в выпуске это
   заглушки (D06), а `logState` в DEV не пассивен (`updateSightings` пишет память бота, `AiProbe.cpp:3925`).
2. Решение врага записывается **парой «вход → выход»** вокруг одного места: вход — рядом с `AiProbe::beforeThink`
   (`BattlescapeGame.cpp:469`), выход — рядом с `AiProbe::logDecision` (`:549`). Вход — отпечаток состояния из девяти
   частей. Тогда первое расхождение сразу показывает, где оно возникло: в решении, в исполнении или между ходами.
3. **Две отдельные проверки.**
   - **Доказательство A — тот же код решений.** Ставятся три условия. Во-первых, одинаковый манифест переключателей.
     Во-вторых, ни одной DEV-ветки, меняющей решения врага. В-третьих, каждое решение с одинаковым входом даёт
     одинаковый выход. Синхронность всего боя для A не нужна.
   - **Доказательство B — те же результаты боя.** Из одного сейва и на одних часах весь ход врага совпадает
     целиком. Если не совпадает, каждое первое расхождение объяснено, а частота расхождений не выше, чем у одной и
     той же сборки, запущенной дважды.
4. Бот в сравнении **не участвует**. Обе сборки грузят один сейв на ходу игрока и сразу передают ход. Бот нужен только
   на станции, чтобы набрать разнообразные сейвы.
5. Нужны три архитектурных решения Vitali (раздел 9):
   - **(Р1)** переключатели врага — одна реализация на обе сборки;
   - **(Р2)** выпуску нужен минимальный водитель пробы под переменной окружения;
   - **(Р3)** для доказательства B — виртуальные часы в выпуске под той же переменной.

   Без Р1 доказательство A невозможно в принципе (D02: стенд всегда включает О1–О4 и О6).

## 2. Схема журнала

### 2.1 Файл и формат

- Отдельный файл `ai_trace.jsonl` в каталоге `-user`. Одна запись — одна строка JSON. Поле `"v":1` — версия схемы.
- В `openxcom.log`, сейв, `options.cfg` и интерфейс журнал не пишет ничего.
- Включается только переменной окружения `OXCE_AI_TRACE=<уровень>`, опции в игре нет. Значение читается один раз в
  `static const`. Игрок включить журнал не может, а в настройках он не залипнет.
- Уровни:

| Уровень | Что пишет | Зачем |
|---|---|---|
| 0 | ничего (по умолчанию) | игра |
| 1 | H, P, S, D, E, F (ниже); в D — поля юнита, решение, ГСЧ и хэши частей, кроме карты; хэш карты — в S и при смене ревизии карты | доказательство A и B |
| 2 | как 1, но хэш карты в каждом D, плюс X (исполнение) и события (выстрел реакции, гибель) | разбор расхождений |
| 3 | как 2 и отпечаток ГСЧ на каждом внутреннем `think` (RETHINK, повтор после подбора оружия, AI3-RETRY) | поиск места внутри решения |

### 2.3 Отпечаток состояния: девять частей

FNV-1a по целым числам, как `StateHash` стенда (`AiProbe.cpp:972`). Каждая часть пишется отдельно, чтобы первое
расхождение сразу называло свою часть.

| Часть | Что входит | Чем шире текущего DEV `stateHash` |
|---|---|---|
| `u` — юниты | id, позиция, направление, ОВ, энергия, HP, оглушение, мораль, огонь, статус, фракция, присев, полёт, смертельные раны, броня по сторонам, `turnsSinceStunned`, `reselectAllowed`, `hiding`, цель атаки с разбега (`getCharging`), кого видит (`getVisibleUnits`, по порядку) | присев, полёт, раны, броня, оглушение по ходам, разрешение повторного выбора, укрытие, разбег |
| `k` — знание | по каждому юниту и каждой фракции: `getTurnsSinceSpottedByFaction`, `getTurnsLeftSpottedForSnipersByFaction`; кого юнит заметил в этот ход; `isCheating()` стороны | **новая часть**: знание врага в DEV-хэше не учтено, а решения от него зависят (`AIModule.cpp:1170`, `:2027`, `:3545`) |
| `i` — предметы | сумма `itemHash` по всем предметам (у юнитов и на полу), без id | как сейчас |
| `o` — порядок | порядок предметов в каждом инвентаре | как сейчас |
| `m` — карта | части клеток, двери, огонь, дым, флаг `dangerous`, освещение клетки | добавлены `dangerous` (ИИ сам помечает клетки, `BattlescapeGame.cpp:608`) и свет |
| `n` — узлы | у каждого узла: занятость и флаги, которые меняются в бою | **новая часть**: патруль выбирает узлы по занятости |
| `a` — память ИИ | `AIModule::probeHash` (`AIModule.cpp:391`) каждого юнита с модулем | сейчас только у решающего юнита |
| `g` — машина боя | сторона, ход, выбранный юнит, `_AIActionCounter`, `_AISecondMove`, `_endTurnRequested`, очередь состояний (типы), общее затенение, `alienItemLevel` | добавлены ход, выбранный юнит, второй проход, запрос конца хода, затенение |
| `b` — статика BetterAI | release-часть `AiProbe`: `counterUnit/Turn/Side`, память блокированного шага `blockedSteps` (`AiProbe.cpp:105–110`) | **новая часть**: это состояние живёт вне сейва и влияет на решения |

ГСЧ пишется числом `RNG::getSeed()` (`RNG.cpp:114` — только чтение).

Ограничение, которое берём сознательно. При загрузке сейва память AIModule вне сейва (`_reachable`, `_escapeTUs` и
другие, см. `AIModule::save` `:613`) начинается с умолчаний. Для сравнения DEV и выпуска это не помеха: обе сборки
грузят один файл. Но сейв не равен живому бою в ту же секунду, и выводов о живом бое из одного сейва не делаем.

### 2.6 Чего журнал не делает никогда (правило пассивности)

- Не вызывает ГСЧ: только `RNG::getSeed()`.
- Не зовёт `Pathfinding::calculate`, `TileEngine::calculateFOV`, `canTargetUnit` и любые неконстантные методы
  юнитов, клеток, AIModule.

  поэтому там риск мал, но тест П4 его ловит.
- Не трогает сейв, опции, интерфейс, звук.

## 4. Как сравнивать DEV и выпуск

### 4.1 Одинаковый вход без бота

1. **Набор сейвов.** DEV-бои стенда с ботом на станциях. Сейв пишется в начале каждого хода игрока: штатное
   автосохранение `Options::autosaveFrequency` (`NextTurnState.cpp:572`) при `oxceNoBattleSaves = false`, или
   `OXCE_AI_PROBE_SAVE`. Сработает ли автосохранение при `autoClose` (`NextTurnState.cpp:317`), проверить в 0В.
   Бот здесь только поставщик разнообразных начальных состояний, в сравниваемом ходе он не участвует.
2. **Прогон.** Каждая сборка запускается с `-load <сейв>`: штатный ключ, `Options.cpp:820`. Ход игрока сразу
   отдаётся, ИИ играет N ходов, игрок пропускает свои, затем сохранение и выход. Это та же проба, что DEV-`harness`
   без бота (`AiProbe.cpp:944–969`), но в обеих сборках одним кодом (решение Р2).
3. **Проверка входа.** Первая S в обеих сборках обязана совпасть всеми девятью частями. Если не совпала, расходится
   уже загрузка или переход хода. Это отдельная находка, остальное сравнение для этого сейва не ведётся.

### 4.2 Сопоставление записей

Ключ — `(turn, side, k, unit, n)`. Сравнение идёт до первого несовпадения ключа или содержания. Дальше цепочку не
сравниваем: после первого расхождения события законно разные (документ решения, §3).

### 4.3 Разбор первого расхождения

| Что совпало | Что разошлось | Вывод | Куда смотреть |
|---|---|---|---|
| всё до D_k | `in` у D_k, причём D_{k-1} совпал целиком | **исполнение** предыдущего действия или события между решениями | X предыдущего D (ур. 2): шаг, выстрел реакции, взрыв, падение; часть отпечатка называет, что именно |
| `in` у D_k | выход D_k (`act/to/aim/weapon/run/kneel/fire/reserve/mode/rng1/ai1`) | **код решения** — провал доказательства A | ур. 3: `rng` по внутренним `think` показывает, на каком вызове ГСЧ разошёлся; затем манифест и DEV-ветки |
| выход D_k | только `path` | **поиск пути** (часть решения) | `Pathfinding`, D07/D08: `keepPathPrefix`, `lightSkip`, `BLOCKED_STEP` |
| все D стороны | E стороны | обработка конца хода (огонь, дым, оглушение, мораль, подкрепления) | E — по частям |
| — | S первого хода | загрузка или переход хода | шапки: опции, моды, `rngAtLoad` |

Каждое первое расхождение даёт **минимальный повторяемый пример**: сейв, сборка, номер записи и часть отпечатка.

## 6. Тест пассивности журнала

Журнал выключенный и включённый должен давать один и тот же бой. Наблюдатель — не журнал, а итоговый сейв и
итог боя.

## 11. Утверждено Vitali 23.10: решения и обязательные условия

Этап 0Б принят. Р1–Р4 утверждены с условиями ниже. Эти условия имеют приоритет над разделами 1–10, где расходятся.

### 11.1 Порядок доказательств (фиксирован)

1. **Единый профиль ИИ** (Р1): одна реализация решений врага в DEV и выпуске.
2. **Журнал и доказательство его пассивности** (тесты П0–П7).
3. **Сравнение решений DEV и выпуска** — доказательство A.
4. **Полное сравнение ходов врага** — доказательство B.

Следующий пункт начинается только после PASS предыдущего. Этап 1 (новая мерка) не начинается. Результаты старых
серий не служат доказательством улучшения ИИ у игроков.

### 11.2 Р1 — общие переключатели (одобрено)

- **Одна реализация** вычисления всех флагов врага для DEV и выпуска. Различаться могут только явно выбранные
  настройки: опции BetterAI или явные переменные стенда, видимые в манифесте.
- **Журнал фиксирует полный эффективный профиль врага**, а не имя режима («BetterAI», «AI3»). Запись P даёт
  значение каждого переключателя, который действительно влияет на решения или исполнение врага: каждую функцию из 2.5,
  каждое значение `param`, которое код фактически получил (имя, умолчание вызова, итог), и `maxActions` по видам
  юнитов. Профили считаются равными, только если равны все значения.
- **Умолчания игрока не меняются:** BetterAI у игроков выключен по умолчанию.
- **`FAIR_KNOWLEDGE` игрокам не включается:** в сборке игрока до него не дотягивается ни одна опция; он доступен
  только явной переменной стенда в DEV.
- **Существующие правила и механика не меняются:** переезжают определения функций-переключателей, а не их смысл.
  Выключенный BetterAI обязан давать те же решения, что сейчас (отпечаток, а не глаз).
- **Старые результаты не переписываются под новую базу.** Прежний профиль стенда (О1–О4, О6 всегда при `active()`)
  воспроизводится только явной настройкой совместимости, например `OXCE_AI_COMPAT=clean1`, которую ставит
  `ai_probe.py` для старых серий. Контроль: серия как cp1n с этой настройкой — `tsv_eq` IDENTICAL со старой таблицей.
  Старые таблицы остаются как есть, с пометкой «старый профиль стенда».

### 11.3 Р2 — общий водитель испытаний (одобрено)

- Запуск только из **идентичного сейва**: одинаковый файл (хэш у запускателя) и одинаковая первая S (11.6).
- Водитель **только** отдаёт ход игрока, закрывает окна боя, сохраняет и выходит. Он **не подменяет `think()`**, не
  обходит игровую логику, не меняет состояние боя. Ход игрока пропускается штатным концом хода.
- **Бот не вмешивается в проверяемый ход:** в манифесте `bot = 0`, `careful = 0` для всех сторон. Иначе прогон не
  засчитывается.

### 11.4 Р3 — виртуальные часы (условно одобрено)

- **Только для доказательства B.** Отдельная переменная `OXCE_AI_TRACE_CLOCK`, независимая от журнала и водителя.
- **Часы для замера производительности не подменяются.** Виртуальные часы заменяют только игровой такт
  (`slowTick`, `Timer.cpp:33`). Замеры (`SDL_GetTicks`, `steady_clock` в `Game.cpp`, `drawMs`/`flipMs`) остаются на
  реальном времени. Шапка H пишет режим часов. Числа производительности из прогона с виртуальными часами не
  принимаются, замеры раздела 7 идут только на реальных.

### 11.5 Р4 — счётчик ГСЧ (одобрено)

- Счёт ведётся в **общей точке получения случайных чисел** — `RandomState::next()` (`RNG.cpp:82`). Через неё идут
  `generate`, `percent` и вещественные значения. Одно увеличение `uint64` у каждого экземпляра.
- **ГСЧ дополнительно не вызывается.** Журнал читает только счётчик игрового генератора `x` и `getSeed()`; счётчик
  `x_seedless` пишется отдельно и в сравнение не входит (косметика).

### 11.6 Дополнение к доказательству A

Одинаковый вход и выход — необходимое, но не достаточное условие. A дополнительно сравнивает:

| Что | Как | Где пишется |
|---|---|---|
| последовательность вызовов ГСЧ | в каждом D число вызовов (`cnt0 → cnt1`) и зерно до и после; на уровне ≥ 3 — то же на каждом внутреннем `think` и хэш последовательности диапазонов вызовов (`min`, `max`, вид), снятый в обёртках `RNG::generate`/`percent` без лишних вызовов | D, ур. 1 и 3 |
| эффективные флаги | манифест P (11.2) обеих сборок | P |
| выбранное действие и его параметры | тип, клетка, цель, оружие, режим огня, бег, присед, резерв ОВ, затраты ОВ, первый шаг и длина пути, режим ИИ, память ИИ после | D |
| исполняемая ветка | метки веток, которые AIModule уже передаёт в общих для обеих сборок вызовах `AiProbe::propose` (`AIModule.cpp:558` — слот и источник) и `AiProbe::chosen` (`:712`, `:999`, `:1056`, `:1126`, `:1325`). В выпуске это сейчас заглушки, журнал подключается к ним в обеих сборках одинаково. На уровне 1 — хэш последовательности меток, на уровне 3 — сами метки | D |

- **PASS A означает эмпирическую эквивалентность проверенных путей решений**, не полную эквивалентность кода.
- **Непроверенные ветки отмечаются явно.** Отчёт A даёт перечень всех меток веток из кода (статический список
  источников `propose` и слотов `chosen`) и отмечает, какие встретились в сравненных парах; невстреченные
  перечисляются как «не проверено».
- При расхождении отчёт называет первую разошедшуюся метку ветки и первый разошедшийся вызов ГСЧ.

### 11.7 Дополнение к пассивности

- **Основной строгий критерий** — побайтное совпадение итоговых сейвов, если формат сохранения детерминирован.
  Новый тест **П0**: одна сборка сохраняет одно и то же состояние дважды подряд, сейвы обязаны совпасть побайтно
  после нормализации времени записи. Если П0 не проходит, основным критерием становится отпечаток (ниже), а отличия
  сериализации описываются.
- **Независимый отпечаток игрового состояния** — девять частей 2.3 плюс зерно и счётчик ГСЧ. Его пишет **водитель**,
  а не журнал: в каждом E (конец стороны) и в F, **при любом уровне журнала, включая 0**. Тогда прогоны «журнал
  выкл» и «журнал вкл» сравниваются по каждой стороне каждого хода, а не только по итогу. Сейвы разные, а
  отпечатки равны — служебное отличие сериализации. Отпечатки разные — настоящее изменение боя: FAIL пассивности.
- **Включение журнала не меняет ни одного решения:** П1 сравнивает отпечатки водителя на каждом конце стороны,
  П2 — общие поля D между уровнями 1–3.
- **Производительность — отдельно** (раздел 7, 11.4) и в вердикт пассивности не входит.

### 11.8 Конечная цель (без изменений)

Противники действуют группами, пользуются укрытиями, сохраняют ОВ для ответного огня и принимают разумные
тактические решения — без читов и без изменения механики X-Piratez. Этапы 0В–6 — путь к этому с доказательствами
на каждом шаге.
