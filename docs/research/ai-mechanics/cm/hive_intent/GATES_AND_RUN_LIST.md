### Ответы на вопросы раздела

1. **Где подключить.** Три точки выше, все внутри `setupAttack` и `findFirePoint`, то есть до решения. Намерение выдаётся в `planTurn` после `coordinate`, до планов подразделений.
2. **Можно ли передать цель в реальные ветки.** Да. Атаки с контактом роли и другой целью при открытом контакте: 20 из 131, 12 из 110, 44 из 170. Вмешательство существует в данных, а не только на бумаге. Это верхняя оценка по кандидатам журнала, shadow уточнит её (R-617).
3. **Штатные проверки сохраняются.**
   - Снайперская ветка: контакт берётся только из готового списка `spottedTargets`. В него попадает лишь то, что прошло `validTarget`, `knownPlace`, `extendedFireModeChoice`, `zeroEffectReject`, `sniperAoeEfficacyReject`.
   - Ветка выстрела: контакт сначала проходит проверки `selectNearestTarget` (`validTarget`, честное знание, луч, `canTargetUnit`), затем сам `projectileAction`. Если тот вернул `BA_RETHINK`, возвращается штатная ближайшая цель и `projectileAction` вызывается снова; причина отказа `attack_unsuitable`.
   - Точка огня: `validTarget(…, true, false)` и знание места.
   - Кубик режима, `combatOdds`, расход TU и исполнение не трогаются. После `think` ничего не подменяется.
4. **Результат действия.** `HiveCommand::decided` снимает TU бойца и состояние целей. Сверка идёт при следующем `beforeThink` любого бойца или в `sideEnds`, когда стек действий уже отработал: это TU, реально списанные за выстрел, а не план. Путь игровой, стендовый `flushExec` не нужен. Здоровье цели только пишется в журнал, для планирования не используется.
5. **RNG.**
   - Выключенный флаг: один ранний выход, ни одного нового вызова.
   - Точка 1: `RNG::generate` остаётся, меняется только индекс после него.
   - Точка 2: выбор без RNG; штатный шум `extendedFireModeChoice` идёт и при другой цели. Откат на ближайшую цель может вызвать его второй раз, только после `attack_unsuitable`, с записью в журнал.
   - Точка 3: выбор без RNG.
   - В `HiveCommand` по-прежнему ни одного вызова RNG.
   - Первое различие активного боя обязано быть на решении с изменившимся `aim` при тех же предшествующих хэшах `hr` (проверка T6).
6. **Эпизод.** M6 s1, ход 1, контакт 470 (см. ниже). Первый ход выбран потому, что до него бой не успевает разойтись с `ra1`.

## Проект

**Данные.** В `Squad` одна запись `HiveCombatIntent { squadId, type, contactId, objective, priority, issuedTurn, expiryTurn, status }`. Типы ровно три: `ENGAGE_CONTACT`, `SUPPORT_CONTACT`, `MAINTAIN_OBJECTIVE`. Намерения живут один ход и выдаются заново на следующем плане. В сейв не пишутся, формат HIVE1 не меняется. После загрузки посреди хода боец до следующего плана действует как в RA (оговорка в отчёт).

**Штаб.** После `coordinate`: приоритетный контакт — законно видимый сейчас (`KNOWN`, `seenTurn == turn`), с наибольшим числом видящих бойцов стороны. При равенстве — прежний приоритетный, затем меньший id. Контакт пропускается, если за прошлый ход отказов `no_effect` и `weak_effect` было не меньше двух и больше, чем фактических атак по нему: это единственное применение обратной связи в V0.

**Командиры.**
- `ENGAGE`: если подразделение видит приоритетный контакт — он; иначе свой `roleContact`. Приоритет 2.
- `REINFORCE`: `SUPPORT_CONTACT` на `roleContact`. Приоритет 2.
- Прочие: `MAINTAIN_OBJECTIVE`, объект — `anchor` или цель задачи; контакт — приоритетный, только если подразделение его видит. Приоритет 1. Охрана за контактом не идёт, остаётся на посту.
- В активном режиме смена контакта `ENGAGE` проходит через существующий `setRole`, чтобы не видящие цель шли к ней через существующий `planContactUnit`. В shadow только запись в журнал.
- Контакт выбыл посреди хода: намерение закрывается со статусом `contact_down`, штаб перевыбирает из видимых (в `beforeThink`).

**Боец: единая проверка `intentRefusal`.** Только чтение, без кубика. Причины отказа:

| Причина | Условие |
|---|---|
| `contact_gone` | контакт вышел из боя |
| `not_valid_target` | не проходит `validTarget` |
| `not_visible` | нет луча или сторона не знает его текущее место |
| `no_line` | `canTargetUnit` |
| `no_weapon` | нет оружия или патронов |
| `out_of_range` | вне дальности оружия |
| `no_tu` | нет TU ни на один режим |
| `no_effect` | ожидаемый урон по правилам не больше нуля |
| `weak_effect` | ожидаемый урон меньше половины от штатной цели |
| `closer_threat` | штатная цель в 3 клетках или ближе, а контакт дальше |
| `too_far_for_priority` | приоритет 1 и контакт дальше штатной цели больше чем на 4 |
| `not_spotted` | снайперская ветка: контакт не отмечен для снайперов стороны |
| `mode_choice_rejected` | снайперская ветка: штатный выбор режима отверг контакт |
| `attack_unsuitable` | `projectileAction` не дал атаки по контакту |
| `maintain_keeps_post` | точка огня при `MAINTAIN_OBJECTIVE` |
| `own_melee`, `own_grenade`, `own_psi`, `own_other`, `leeroy` | атака не через три точки |

Отказ означает законный штатный выбор, без простоя и без отмены действия.

**Возврат к задаче.** В `patrol` на ответ `FREE` из `arrived`, `completed`, `pause` при живом `ENGAGE` или `SUPPORT` — один раз за ход на бойца повторяется существующий `planContactUnit`. Новых планировщиков нет, это повторный вызов прежнего. Лечит находку RA (патруль уходит от цели). Если выбранного узла нет — по-прежнему `FREE`.

**Обратная связь `[HIVEINTENT]`:**

| Событие | Что значит | Требование GO |
|---|---|---|
| `ISSUE` | выдано подразделению | штаб → командир |
| `CHOICE site own chosen changed no` | принято или отклонено с причиной; в shadow `would` | принято; выбран законный вариант; отклонён с причиной |
| `DECIDED` | сразу за `[AIDECIDE]`: действие, цель, снимок | |
| `RESULT kind tu_spent hit down` | факт после исполнения. `ATTACKED_CONTACT`, `OTHER_ATTACK`, `WALK_TOWARD`, `WALK_OTHER`, `NOT_EXECUTED`, `NO_ACTION` | действие выполнено; контакт атакован; другое полезное действие |
| `CLOSE status` | итог подразделения за ход: `done`, `expired`, `contact_down`, `cancelled` | задача устарела или отменена |

Не делается: новые типы, штаб, патруль, удержание, фильтр подкреплений, планировщик, спавн, оптимизатор атак, замена действия после `think`, кубик режима, `combatOdds`.

## Проверка оценки по факту запуска 2 (до запуска 4)

- `effect_check.py`: из 34 пар «боец + контакт» с отказом `no_effect` тот же боец реально атаковал этот контакт в 15, с уроном в 4.
- Прямой случай: 1000024 на ходу 4 при tu 111 отказался от 448 (`no_effect`), при tu 78 с той же клетки выбрал 448 сам и убил выстрелом на 34, сторона right.
- Гипотеза: оценка считает паспортную броню, а `BattleUnit::damage` вычитает изношенную (`getArmor(side)`, у патрона `ToArmorPre: 0.05`). Текущая броня игрока оценке не дана намеренно: это скрытое знание.
- Запись `event=EFFECTNOTE` только в журнал показывает паспорт и текущую броню при каждом отказе. На решения не влияет, бросков нет. Сборка пересобрана до запуска 3, запуски 1 и 2 шли на прежних файлах.
- Если гипотеза подтвердится, `no_effect` в отчёте значит «по паспорту брони»; решение оценки не меняется. Отказ остаётся в безопасную сторону: боец делает свой штатный выбор.

## Поправка после запуска 4 (первый активный), до запуска 5
