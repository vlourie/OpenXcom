# Решение и план проверки OXCE-HD / X-Piratez AI

**Дата:** 23.10.2026  
**Статус:** проект решения по итогам независимого аудита и замечаний команды; **не разрешение на изменение кода, сборку, запуск боёв либо выпуск**.  
**Источник:** `ai_review_2026-10-23.zip`, сопроводительный `AI-REVIEW-2026-10-23.md`, замечания к независимому аудиту.

## 1. Принятое направление

1. **Инвариант — тот же код принятия решений врага в стенде и в выпуске** для эквивалентного набора переключателей. Побайтовое равенство программ и боёв не требуется: в стенде есть бот игрока, журналы и ускорители. Нельзя подменять проверку идентичности кода сравнением числа побед.
2. **Проверка эквивалентности решений требует одинакового входа.** Для сравнения реального хода врага в обеих сборках нужны эквивалентные состояния в момент до `AIModule::think`: карта, юниты, ОВ, память, опции, версия данных мода и состояние RNG. Совпадение миссии и начального сида само по себе **недостаточно**, если ранее за игрока ходил бот или произошли разные события.
3. **Сначала без боёв:** исследовать условную компиляцию `OXCE_AI_DEV`, ветви `AiProbe`, таблицы AI3, конфигурационные опции и вызывающие функции. Зафиксировать обнаруженные расхождения и их влияние.
4. **Мерка должна охватывать разные миссии**, не заменять разнообразие сотнями новых сидов для 22 миссий. Нужны сильные фракции (МЕРКи, элита Гильдии, тяжёлое и взрывное вооружение) и различные этапы кампании. Ранние стадии с корректными развёртываниями — отдельная подготовительная работа.
5. **O1–O14 проверять малыми смысловыми группами**, например механика/память/патруль и атакующие/специальные случаи, с проверкой комбинаций и регрессий. Делать 14 больших изолированных серий без необходимости не следует.
6. **Целевой дизайн не изменён:** враги взаимодействуют в группах, умеют осмысленно резервировать ОВ для ответного огня и стремятся занимать укрытия. Это желаемое поведение, но не безусловное правило «всегда за стеной»: укрытие не должно лишать врага возможности атаковать, проходить сценарий или использовать специальную роль.
7. **Не менять игровую механику** (правила стрельбы, видимости, урона, поведения сохранений); только логику выбора разрешённых действий. Детерминированно, объяснимо, без ML. «Честное знание» пока оставлено в бэклоге, но источник знаний должен быть отделён от тактического планировщика.
8. **Истинное игровое окружение** — сборка OXCE-HD на Пиратках. Испытания — только на согласованных удалённых станциях. Изменения не отправлять в Git без отдельного разрешения.

## 3. Предрегистрация эксперимента (заполнить до боёв)

- **Единица рандомизации:** развёртывание миссии + начальное состояние + исходный сид. Для оценки эффекта алгоритма — парное сравнение на одних сценариях. При разных действиях случайность «расходится», это не отменяет парный дизайн, но запрещает сопоставлять отдельные события после первой дивергенции как будто они одинаковы.
- **Основные исходы:** суммарный урон бойцам игрока и гибель/выведение из строя бойцов. **Дополнительно:** исходы, длительность боя, результат по фракциям, число застреваний, время на ход, пиковая задержка и аварии.
- **Страты:** фракция/тип врага, стадия кампании, размер и вертикальность карты, сложность вооружения, тип миссии, наличие летунов/2×2/турелей. Не агрегировать всё в одну среднюю величину без раскрытия страт.
- **Статистика:** парные разности, интервалы неопределённости, кластеризация по миссии/развёртыванию. При 22 независимых миссиях бутстрап по миссии нестабилен; нужно расширить число независимых миссий, а не только сидов. Перестановочный анализ и иерархические модели — как проверки устойчивости, не как способ «добрать значимость».
- **Порог приёмки:** до начала серии записать минимальный полезный прирост, максимально допустимую регрессию тяжёлой фракции/карты и задержки. Значения порогов предстоит утвердить отдельно, чисел сейчас не придумывать.
- **Переносимость:** бот не равен человеку. Нужен небольшой отдельный набор воспроизводимых человеческих тактик (агрессивный штурм, осторожное продвижение, защита, гранаты) или записанных игровых состояний.
- **Роли испытаний:** быстрые механические проверки → короткий пилот для грубых ошибок → полноценная заранее зарегистрированная когорта только для перспективных кандидатов.

## 4. Проект канонического журнала (НЕ реализован)

Для **каждого решения вражеского юнита**: версия/хеш сборки; хеш данных мода; режимы BetterAI, AI3 и все значимые параметры; уникальный идентификатор снимка; ход/сторона/ID юнита; состояние карты/памяти стороны/юнита; ОВ и энергия; `RNG::getSeed()` перед и после решения; итоговый тип действия, оружие, цель, позиция, режим и предусмотренные затраты. Для исполнения — отдельно фактический путь/сдвиг ОВ/изменение видимости. **Хеши двух существующих разных реализаций (`AiCandidates` и `AiProbe`) не считаются идентичными.** Логи DEV нельзя побайтно сравнить с релизом, потому что релизные `beforeThink`, `logDecision` и `logState` сейчас — заглушки.

Важное ограничение: пассивная инструментальная функция не должна двигать юнита, выполнять поиск пути со сбросом состояния, тратить ОВ/энергию или получать случайные числа. Сначала доказать, что включение записи не меняет бой, и лишь затем сравнивать режимы.

## 5. Разрешения и стоп-условия

**Сейчас разрешены только чтение предоставленного кода и подготовка документации.** Нельзя изменять `src/`, параметры игры/настроек, `CMakeLists`, выполнять Git commit/push, запускать бои, менять сборки игроков или включать экспериментальные опции. После статического аудита представить владельцу список расхождений и *только затем* запрашивать разрешение на следующие действия.

**Стоп:** нет доказательства эквивалентности реального кода вражеских решений — не использовать результаты стенда как доказательство улучшения для игроков. **Стоп:** новая логика ломает данные мода, RNG при выключенном флаге, механику или сохранение — не продвигать.
