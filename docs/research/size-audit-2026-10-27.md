## 6. Сжатие

### PNG мода hd (выборка 780 файлов и 240 кадров из 40 паков; a6_png.py)

Все HD-картинки движок читает одной функцией `HdSprites::decodePng` → `lodepng::decode(…, LCT_RGBA, 8)`:
любой тип PNG (RGB, RGBA, палитра, серый) раскрывается в одинаковый RGBA8. Поэтому пережатие без потерь
и смена типа цвета дают **те же пиксели**, а значит тот же кадр при любом `k` — проверка всё равно обязательна
(декодировать до и после и сравнить побайтно, затем Ctrl+F8 и `hdtest_compare.py` при `k=1` и `k=4`).

| Группа | МиБ | Тип в выборке | PIL optimize | + убрать пустую альфу | WebP lossless |
|---|---:|---|---:|---:|---:|
| hd/UI | 1 857 | RGBA 103, RGB 25, палитра 32; **97 из 160 — RGBA с полностью непрозрачной альфой** | −4,5 % | **−13,6 %** | −34,4 % |
| hd/TERRAIN | 766 | RGBA | −2,1 % | −2,1 % | **−61,7 %** |
| pack.hdp | 328 | палитра (кадры 128×160) | −0,2 % | −0,2 % | −23,2 % |
| hd_18+/UI | 132 | палитра | 0 | 0 | −11,3 % |
| BIGOBS / FX / BASEBITS | 45 / 20 / 24 | RGBA | −2,5 / 0 / −1,4 % | −2,8 / 0 / −2,9 % | −41 / −41 / −31 % |

Оценка на всю установку: пережатие PNG без потерь (optimize + RGB у непрозрачных) — **≈270 МиБ** (почти всё —
интерфейс); WebP lossless — **≈1 240 МиБ** (−40 % арта). libwebp уже входит в статическую сборку
(`src/CMakeLists.txt`: `… webp … sharpyuv`), так что ветка «RIFF/WEBP → WebPDecodeRGBA» в `decodePng`
не тянет новых зависимостей. Цена: замер скорости декодирования под `HdWorkers` (не делали) и проверка IDENTICAL.

**Важно:** пережатие уже выпущенного арта меняет хэши всех файлов — каждый нынешний игрок один раз скачает
весь арт заново (до 3 ГиБ). Поэтому — только для нового и перерисованного арта, либо одной волной вместе
с плановым большим обновлением.

## 9. План

Риск для `k=1` и механики указан у каждого пункта. «Сразу» — правка скриптов сборки, без движка и лаунчера;
всё равно через `editq` и с проверкой.

### Сразу (скрипты)

1. **Голоса — детерминированно и без перезаписи того же звука.** В `build_test_mods.to_ogg` добавить
   `-fflags +bitexact -flags:a +bitexact`; в `build_voicepack_mods.build` не стирать мод целиком, а писать во
   временную папку и **оставлять прежний файл, если новый совпадает с ним без учёта серийника и CRC**
   (сравнение как в `a3_ogg.py`). Без второй части первая сборка с bitexact ещё раз сменит все 36 303 файла.
   Экономия: до 557 МиБ на каждую пересборку голосов (5 раз за 5 дней). Риск: никакого для кадра и механики —
   звук побайтно тот же после декодирования. Проверка: пересобрать дважды подряд — `git status`/хэши модов
   не меняются; затем `xp-release build` показывает ~0 новых блобов голосов.
2. **exe — не перепаковывать Enigma при том же коде.** В `build.ps1` хранить хэш неупакованного
   `openxcom.exe` + хэши DLL + `.evb`; совпали с прошлым выпуском — брать прошлый упакованный exe как есть.
   Экономия: 37–61 МиБ в ~30 % выпусков (1 544 МиБ за историю). Риск: нет (тот же файл).
   Альтернатива — отказаться от Enigma: 5 DLL (0,8 МиБ, не меняются) класть рядом с exe и линковать с
   `-Wl,--no-insert-timestamp`; это правка сборки и требует решения.
3. **Сторож «пустых перемен» в выпуске.** Перед `xp-release build` (или в нём отчётом) сравнить с прошлым
   выпуском: OGG с той же разметкой без серийника, PNG с теми же пикселями, exe с отличием только в `.enigma*` —
   печатать МиБ и останавливать выпуск выше порога (например 20 МиБ) до явного «да». Ловит повтор пп. 1–2.
4. **`intro_voice/hd.zip` из выпуска.** В `build_config.json` — `ModExcludeFiles` + `"hd.zip"` (другого zip в
   выпуске нет). У игроков лаунчер его удалит как файл своего корня. −25,2 МиБ установки. Риск: нет —
   движок этот zip не читает. Это правка конфигурации сборки, не данных игры.
5. **Чистка `dist` автоматикой** (по правилу «убирать ненужное на всех машинах» — в `ai_sweep.py` или
   `build.ps1`): архивы `xp-releases_*`, разложенные на станции (столбец 3 в `.sent.txt` + отметка станции),
   `dist\_voice`, `dist\_patch`, старые `_work\manifest_*.txt`, старые .pdb лаунчера кроме последнего —
   ≈1,9 ГиБ сейчас. `dist\UI` (581 МиБ) — сначала выяснить, чей это вывод.
6. **Новый арт сразу экономно.** В конвейере сохранения: непрозрачные картинки интерфейса — RGB, PNG с
   optimize/oxipng без смены пикселей. На уже выпущенный арт не применять (волна перекачки).

### Правка ReleaseBuilder, лаунчера и Caddy (без движка)

7. **manifest и notes со сжатием.** Caddy: `encode gzip` для `/releases/releases/*` и `/releases/channels/*`
   (не для `/blobs/`); лаунчер: `AutomaticDecompression = GZip | Brotli` для маленьких файлов
   (`GetSmallAsync`), хэш и подпись — по распакованным байтам, как сейчас. 19 → 5 МиБ на запуск и выпуск.
   Старые лаунчеры не шлют `Accept-Encoding` и получают как раньше. Риск: низкий, ничего в игре не меняется.
8. **Сжатые блобы для сжимаемых типов.** ReleaseBuilder рядом с `blobs/sha256/<h>` кладёт `blobs/zstd/<h>`
   для exe/dll/yml/rul/map/pck/txt/wav (не PNG/OGG), в manifest — поле размера сжатого; лаунчер новой версии
   качает сжатый вариант (Range по сжатому файлу работает: он статичный), распаковывает, проверяет sha256
   распакованного. Старые лаунчеры берут несжатый. Экономия: exe 61 → ~10–12 МиБ в каждом выпуске с кодом,
   выпуск лаунчера 36,8 → ~16, полная установка −130 МиБ. Обычное обновление (пп. 1, 2, 7, 8 вместе):
   **~76 МиБ → ~17 МиБ**. Цена: место на станции (+~20 % к блобам этих типов), правка `Updater`/`RepoClient`.
9. **Сборка мусора хранилища.** Команда `xp-release gc --keep N` (блобы и manifest, на которые не ссылается
   ни один из N последних выпусков каждого канала и ни один опубликованный указатель) и такой же шаг на станции.
   При N=5: −8,4 ГиБ дома и столько же на станции. Риск: откат дальше N выпусков станет невозможен —
   N выбрать с Vitali; на станции — только после того, как в `stable` давно нет ссылок на старое.

### Правка движка — только по слову Vitali

10. **`CollapsePilotData` из `.rdata`.** 24,35 МиБ таблиц, жмутся до 0,7–1,8 МиБ. Хранить их сжатыми в exe и
    распаковывать при первом обращении, либо вынести в файл данных с проверкой хэша. −23 МиБ сырого exe.
    Если сделан п. 8 — выигрыш на передаче всего ~1 МиБ за выпуск, и пункт теряет смысл. **Риск для
    механики средний:** это модель обрушения; нужен стенд «модель = движок», как у партий 15–21, и IDENTICAL
    при `k=1`/`k=4`.
11. **WebP lossless для HD-арта.** Ветка в `HdSprites::decodePng` по сигнатуре RIFF/WEBP (libwebp уже в сборке).
    −1,24 ГиБ установки (TERRAIN −62 %, UI −34 %). Пиксели те же — кадр при любом `k` тот же, механика не
    задета. Нужны: замер времени декодирования под `HdWorkers` против нынешнего PNG (не мерили — скорость неизвестна),
    побайтная сверка RGBA до/после на всех файлах, Ctrl+F8 IDENTICAL. Волна перекачки — см. п. 6:
    вводить по наборам вместе с перерисовкой или одной большой волной.
12. **Голоса в Opus 24–32 кбит/с** (−55…65 %, −300…365 МиБ) — нужен декодер Opus в звуке движка и решение
    Vitali по качеству (сжатие с потерями). Без правки движка: Vorbis q3 (−22 %, −125 МиБ) — тоже его решение
    по слуху. Обе меры — одна волна перекачки голосов (559 МиБ) у нынешних игроков.
13. **Стричь COFF-символы exe** (`strip --strip-debug` или `-s` при линковке): −5 МиБ сырого exe (~1 МиБ
    сжатого). `.edata` оставить — по ней строятся имена в трассе падения. Проверить, что лог падения
    по-прежнему с именами.

## 10. Что не стоит делать

- Сжимать архив для станции: PNG/OGG не жмутся, время упаковки вырастет в разы.
- Дробить `pack.hdp` или вводить блоки внутри файлов: паки за месяц не менялись ни разу.
- Пережимать музыку и звуки Пираток и чужих модов: это их данные; к тому же у 26-мегабайтной `GMGEO12.ogg`
  та же цена для всех установок Пираток.
- Пережимать весь выпущенный арт ради −9 %: игроки один раз скачают 3 ГиБ, чтобы потом экономить 270 МиБ
  только на новых установках.
