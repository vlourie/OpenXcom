# Обновление игры одним архивом — план (29.10.2026)

Задача Vitali 29.10: игрок, отставший на любое число выпусков, получает обновление одним архивом,
а не десятками тысяч файлов. Архив собирает станция по запросу и держит в кэше.
Этот файл — только план, код пока не менялся.

## Что есть сейчас (проверено по коду и `D:\xp-repo`)

- Проверка файлов у игрока уже идёт по списку. В `launcher/state.json` лежат путь, хэш, размер и время
  записи каждого файла; при обычной проверке перечитываются только изменённые. Замер на этой машине
  (журнал лаунчера, 26.10): 74 809 файлов за 1,6 с, перечитано 3 354. Сканирование — не узкое место.
- Архивы `releases/<выпуск>/packs/<от>.tar.br` (tar + brotli, внутри блобы по имени-хэшу) сборщик
  выпуска строит только от 3 последних выпусков канала (`PackFrom = 3`, `portal/src/Xp.ReleaseBuilder/ReleaseRepo.cs:37`).
- Сколько нужно до 2026.10.28-2 при отставании (посчитано по манифестам):

### Найденная ошибка: архивами не пользуется почти никто

`Setup.Chosen` (`portal/src/Xp.Launcher.Core/Setup.cs:199`) собирает урезанный манифест под выбранные
компоненты и **не переносит поле `Packs`**. `Updater.Scan` (`Updater.cs:108`) кладёт в план именно его,
поэтому `PackFor` (`Updater.cs:264`) у игрока с выбранными компонентами всегда видит пустой список
и качает файлы по одному — даже при отставании на один выпуск. Компоненты выбраны у всех, кто прошёл
мастер установки (на этой машине их 9). Подтверждение: в журналах лаунчера этой машины за всё время
нет ни одной строки `pack from`. В тестах (`UpdatePackTests.cs`) компоненты не выбираются, поэтому
ошибка не видна.

Исправление — одна строка (`Packs = m.Packs` в `Chosen`) и тест. Это шаг 1: он один закрывает отставание
на 1–3 выпуска (при выпусках раз в день это три дня).

## Устройство архива по запросу

### Запрос

`POST /api/v1/packs` (портал), тело:

```json
{ "channel": "stable", "to": "2026.10.29", "from": "2026.10.22-11", "art": ["art.hd"] }
```

- `from` — выпуск игрока; пустая строка означает первую установку.
- `art` — выбранные художественные компоненты (`ComponentKind.Art`). Всё остальное (движок, моды,
  дополнения — единицы мегабайт) входит в архив всегда. Так у одной пары «от — до» не больше трёх
  вариантов (`[]`, `[art.hd]`, `[art.hd, art.hd18]`), и кэш не размножается от наборов модов.

Ответы:

- `200 {"url": "packs/<to>/<ключ>.tar.br", "size": …, "sha256": …, "blobs": …, "raw": …}` — архив готов;
- `202 {"retryAfter": 5}` — собирается, спросить ещё раз;
- `404` — нет такого выпуска, `from` не опубликован в канале или `to` не текущий/предыдущий;
- `400` — неверные имена; `429` — превышен лимит запросов.

Ключ архива — SHA-256 от строки `to|from|art(отсортировано)`. Повторный запрос с тем же ключом
отдаёт готовый файл.

### Доверие

Подписи у архива нет, и она не нужна: `PackReader.Unpack` проверяет каждый блоб внутри по SHA-256 и
размеру из **подписанного** манифеста, а чужие и лишние блобы пропускает. `size`/`sha256` из ответа
нужны только для докачки и проверки целостности передачи. Защита от раздутого ответа: лаунчер сам
считает предел по подписанному манифесту (сумма размеров нужных блобов + 1 КиБ на блоб на заголовки tar
+ 1 МиБ) и не качает архив больше предела. На диск проверяется место, как сейчас.

### Сборка на станции

- Портал читает манифесты и блобы с диска: в `compose.yaml` порталу добавляется
  `${RELEASES_DIR}:/srv/releases:ro` (сейчас он ходит к хранилищу по HTTP через `caddy:8081`).
- Разница считается по двум манифестам: блобы `to` нужных компонентов, которых нет в `from`.
- Формат тот же, что у сборщика выпуска: код записи переносится из `ReleaseRepo.WritePacks` в общий
  `Xp.Manifest/PackWriter.cs`; сборщик выпуска вызывает его же. `PackReader` у лаунчера не меняется.
- Сжатие: PNG brotli не ужимает, поэтому для архивов по запросу уровень ниже, чем у выпуска (q9).
  Уровень выбирается замером на станции (шаг 6): время сборки архива на 600 МБ при q1/q4/q9.
- Одновременно собирается один архив (очередь в фоновой службе), одинаковые запросы ждут одну сборку.
  Запись во временный файл, затем переименование.
- Кэш — каталог `/srv/packcache` (новый том, у портала на запись, у Caddy на чтение). Caddy отдаёт его
  как `/releases/packs/*` с докачкой по Range, как блобы.
- Очистка: архивы, у которых `to` уже не текущий и не предыдущий выпуск канала, удаляются; общий
  потолок `PackCacheMaxGb` (по умолчанию 30, уточнить по диску станции), сверх него — давно не
  запрашивавшиеся первыми.
- Прогрев (шаг 7): после нового выпуска портал заранее собирает архивы для самых частых выпусков
  игроков. Эти выпуски берутся из `LauncherInstall.GameRelease` — статистика уже есть, она без
  личных данных. Плюс архив первой установки. Тогда первый игрок не ждёт.

### Лаунчер

В `Updater.DownloadAsync`: если подписанного архива нет (`PackFor` вернул null), а по одному качать
не меньше `LazyPackMinFiles` файлов (порог по замеру, ориентир 300), лаунчер спрашивает портал.

- На `202` ждёт с подписью «Сервер собирает архив обновления…», не дольше 3 минут.
- На `200` качает архив тем же `FetchPackAsync` (с докачкой) и распаковывает.
- Чего в архиве не хватило — докачивает по одному, как сейчас.
- Любой сбой (404, нет обработчика на старом сервере, таймаут, ошибка проверки) — по одному, как сейчас.
- Первая установка (`plan.From == null`) идёт тем же путём с `from: ""`.
- Старые лаунчеры ничего не замечают: подписанный манифест не меняется.
