## Краткий ответ
- У предмета три картинки: `bigSprite` (BIGOBS, 32x48 — инвентарь), `floorSprite` (FLOOROB, 32x40 — на полу), `handSprite` (HANDOB, 32x40 — в руках бойца в бою). Отдельных кадров «левая рука», «двуручное», «прицеливание» в рулсете нет: есть только номер `handSprite` и восемь кадров подряд `handSprite + направление`.
- Прицеливание двуручным оружием — не поворот картинки, а сдвиг номера кадра: `(направление+2)%8` плюс таблица сдвигов `offX/offY` по направлению. Сам кадр — готовый рисунок, нарисованный художником под этот угол.
- Точка вылета снаряда (механика, `TileEngine::getOriginVoxel`) и нарисованный ствол (`UnitSprite::blitItem`) никак не связаны. HD-вспышка ставится по нарисованным пиксёлям кадра (`HdFx::noteTip`), а не по механике.
- Между `bigSprite` и `handSprite` движок связи не имеет: это два независимых рисунка, номера задаёт рулсет.
- HD-путь для предметов в руке и на полу есть (общий `HdSprites`, `hd/HANDOB.PCK/`, `hd/FLOOROB.PCK/`), но паков на диске нет; `HdItems` обслуживает только BIGOBS.

Полей `bigSpriteAlt`, `floorSpriteAlt`, `handSpriteAlt` в `src/` нет (grep пуст). Отдельных кадров под левую руку, двуручный хват, прицеливание, вариант по заряженному боеприпасу — нет.

Номер кадра становится кадром так. Поля грузятся через `loadSpriteOffset` → `loadOffsetNode` (Mod.cpp:2056-2133). Индекс меньше `maxSharedFrames` набора — замена ванильного кадра, без сдвига. Иначе к индексу добавляется `curr->offset`, то есть 1000 на каждый зарезервированный блок предыдущих модов (Mod.cpp:2578-2594, `getOffset` :2254-2261: `id > max → id + _modCurrent->offset`). Поэтому у Пираток AK (`handSprite: 352`) живёт в кадрах 1352..1359, `bigSprite: 168` → 1168, `floorSprite: 312` → 1312 (таблица — inventory-items-hd.md §6.5). Форма `{index, mod}` тоже поддерживается. Ванильные размеры по TAB: BIGOBS 57, FLOOROB 73, HANDOB 128 кадров. Piratez HANDOB.PCK в extraSprites: ширина 256, высота 40, subX 32, subY 40 (Piratez_Resources.rul:9400), то есть лист из 8 кадров в одну строку (проверено на `Resources/HANDOB/AK.png`: 256x40).

Выбор кадра в руке — `UnitSprite::selectItem` (UnitSprite.cpp:97-115): `index = item->getRules()->getHandSprite()`, кадр `getFrame(index + dir)`; нет такого кадра — исключение; затем скрипт `selectItemSprite`, которому передаются `sprite_index`, `sprite_offset` (= dir), предмет, сейв, `blit_part` (`BODYPART_ITEM_RIGHTHAND/LEFTHAND`), анимационный кадр, тень. Скрипт по умолчанию «add sprite_index sprite_offset; return sprite_index;». Для HANDOB нулевой кадр из скрипта = предмет не рисуется; для BIGOBS и FLOOROB есть откат на исходный кадр.

### 2. Какой кадр по направлению

Направления — `Pathfinding::dir_x = {0,+1,+1,+1,0,-1,-1,-1}`, `dir_y = {-1,-1,0,+1,+1,+1,0,-1}` (Pathfinding.h:45-46, R-084). На экране `sx = dx - dy`, `sy = (dx + dy)/2`: 0 вверх-вправо, 1 вправо, 2 вниз-вправо, 3 вниз, 4 вниз-влево, 5 влево, 6 вверх-влево, 7 вверх.

- Обычное положение: `selectItem(item, _itemR, unitDir)`, кадр `handSprite + unitDir`.
- Прицеливание (`STATUS_AIMING`) и правый предмет двуручный (`isTwoHanded()`): `dir = (unitDir+2)%8`, кадр `handSprite + dir`, смещение `offX[unitDir]/offY[unitDir]` (UnitSprite.cpp:477-483, routine 0). Левый двуручный при прицеливании — то же `dir+2`, но таблицы `offX6/offY6` (:539-587).
- Левая и правая рука — один и тот же набор кадров; левый предмет рисуется кадром `handSprite + unitDir`, отличается только таблицей смещений (`offX2/offY2` для одноручного) и порядком слоёв.
- Двуручный в обеих руках: `sortRifles` (:1525-1546) оставляет активную руку (`getActiveHand`, BattleUnit.cpp:3863), вторую обнуляет. Правый двуручный без прицеливания: левый предмет скрыт; левый двуручный без прицеливания: правый скрыт.
- Поворота картинки нет. Проверка на листе `Resources/HANDOB/AK.png` (кадры 0..7 слева направо): ствол кадра 2 смотрит вверх-вправо (направление 0), кадра 3 — вправо (1), 4 — вниз-вправо (2), 5 — вертикаль (3), 6 — вниз-влево (4), 7 — влево (5), 0 — вверх-влево (6), 1 — вертикаль (7). То есть кадр `f` нарисован стволом вдоль направления `(f-2)%8`, а в покое (кадр = направление) оружие «носится» повёрнутым на два шага относительно взгляда. Это вывод по картинке одного листа, на пикселях не мерился; согласуется с `dir+2` при прицеливании.

### 4. Поворот при прицеливании
Только сдвиг номера кадра `dir+2` и таблицы смещений. Картинка не вращается. Для одноручного оружия прицеливание кадр не меняет (меняется рука, `rarmShoot` только у двуручных).

### 6. Точка выстрела и вспышка
Механика: `TileEngine::getOriginVoxel` (TileEngine.cpp:5987-6063). Воксель клетки = клетка*(16,16,24). `z += -terrainLevel + getHeight() + getFloatHeight()`, затем `-3` для броска или `-4` для остальных. Направление считается как `getDirectionTo(origin, action.target)` (:5925) — угол на цель, а НЕ `unit->getDirection()`. Для центра клетки: `dirXshift = {8,14,15,15,8,1,1,1}`, `dirYshift = {1,1,8,15,15,15,8,1}` × размер брони, то есть точка на краю клетки в сторону цели; для LEFT/RIGHT — взвешенное среднее 2:1 с соседним направлением. Цель-вейпоинт (не солдат): +8,+8,+16.

`Projectile::calculateTrajectory` (Projectile.cpp:109-206) берёт этот воксель и добавляет разброс (`applyAccuracy`). `getPosition(offset)` (:548) — воксель на траектории; `getOrigin()` (:591-596) — `_trajectory.front().toTile()`, то есть КЛЕТКА для звука, а не воксель (R-085).

`ProjectileFlyBState`: `createNewProjectile` (:450) вызывает `unit->aim(true)` (:543 дуговой, :586 прямой; в ветке броска `aim(true)` нет), затем `hdMuzzle(projectile->getPosition(0))` (:553, :596). `aim(false)` — :884. `hdMuzzle` (:433-448): `HdFx::flashClip(правила оружия, боеприпаса, _unit->getDirection())`, затем `HdFx::spawn(HdFx::colour(...), origin, weapon->getId())`. Ближний бой — `MeleeAttackBState.cpp:225` aim(true); `ExplosionBState.cpp:455, :492` aim(false).

Рисунок: `HdFx::noteTip` (HdFx.cpp:523-563) в момент `blitItem` берёт кадр оружия и считает точку вспышки — самый дальний непрозрачный пиксель кадра (это НЕ обязательно дуло, см. §6а) по проекции `px*sx + py*sy` (`sx = dX-dY`, `sy = (dX+dY)*0.5`, dX/dY из Pathfinding), усредняя по полосе 0.75*ширина/32; `tipX/tipY = x + lround(mx/n + 0.5)`. `Map.cpp:1553` очищает отметки в начале `drawTerrain`; вспышка рисуется в `Map.cpp:2793-2808`: `convertVoxelToScreen(f.first->voxel, ...)`, а если `f.first->tip` — берётся `tipX/tipY`, кадр центрируется `x - width/2, y - height/2`. Нужна живая вспышка с этим id (`wantsTip`, :511); `FLASH_MS` — HdFx.cpp:54.

Связи между точкой механики и нарисованным стволом нет (R-214): точка механики — край клетки на высоте `getHeight() ... - 4`, нарисованный срез ствола уходит от неё на 8-12 базовых пикселей. Единственная «связь» — HD-вспышка, которая ищет крайнюю точку по рисунку классического кадра. Следствие для HD-рисунка: у HD-кадра HANDOB срез ствола и хват должны совпасть с классическим по месту (иначе вспышка и руки разойдутся), а там, где крайняя точка классики — не дуло (§6а), вспышка встанет мимо дула при любом HD-рисунке.

### 6а. Поправка 05.10: точка `noteTip` — крайняя точка рисунка, а не дуло

Код (src/Engine/HdFx.cpp:523-563, дословно):

```cpp
void noteTip(int item, const Surface *frame, int direction, int x, int y)
{
	if (!frame || direction < 0 || direction > 7)
	{
		return;
	}
	// the facing on screen, as Pathfinding::dir_x / dir_y through the isometric view
	static const int dirX[8] = { 0, 1, 1, 1, 0, -1, -1, -1 };
	static const int dirY[8] = { -1, -1, 0, 1, 1, 1, 0, -1 };
	const double sx = dirX[direction] - dirY[direction], sy = (dirX[direction] + dirY[direction]) * 0.5;
	// the muzzle: the drawn pixels furthest along the facing (the end of the barrel), averaged
	double best = -1e9;
	for (int py = 0; py < frame->getHeight(); ++py)
		for (int px = 0; px < frame->getWidth(); ++px)
			if (frame->getPixel(px, py))
				best = std::max(best, px * sx + py * sy);
	if (best < -1e8)
	{
		return;
	}
	const double band = 0.75 * frame->getWidth() / 32.0;   // a classic pixel, in the pixels of this frame
	double mx = 0, my = 0;
	int n = 0;
	for (int py = 0; py < frame->getHeight(); ++py)
		for (int px = 0; px < frame->getWidth(); ++px)
			if (frame->getPixel(px, py) && px * sx + py * sy >= best - band)
			{
				mx += px;
				my += py;
				++n;
			}
	for (Live &l : live)
	{
		if (l.item == item)
		{
			l.tip = true;
			l.tipX = x + (int)std::lround(mx / n + 0.5);
			l.tipY = y + (int)std::lround(my / n + 0.5);
		}
	}
}
```

Вызов (src/Battlescape/UnitSprite.cpp:165-170, в `blitItem` сразу после `blitScripted`):

```cpp
const BattleItem *weapon = item.bodyPart == BODYPART_ITEM_RIGHTHAND ? _itemR : _itemL;
if (weapon && HdFx::wantsTip(weapon->getId()))
{
	HdFx::noteTip(weapon->getId(), item.src, _unit->getDirection(), _x + item.offX * _scale, _y + item.offY * _scale);
}
```

Использование (src/Battlescape/Map.cpp:2800-2807): если `tip`, центр клипа вспышки ставится в `tipX, tipY` (`blitFrame(..., x - width/2, y - height/2)`), иначе в точку механики `convertVoxelToScreen(voxel)`.

Что из кода следует:
1. Направление — направление ЮНИТА (`_unit->getDirection()`), а кадр при прицеливании двуручным — `(d+2)%8`. Мера — проекция на направление взгляда на экране, по ВСЕМ непрозрачным пикселям кадра. Отличить ствол от мушки, штыка, магазина, приклада или плеча лука код не может: выигрывает то, что дальше выступает вдоль взгляда.
2. Полоса 0.75 пикселя: на прямых направлениях (d 1, 3, 5, 7) в неё попадает весь торец, на диагоналях (0, 2, 4, 6) — пиксели одной ступеньки. Если в полосу попали РАЗНЕСЁННЫЕ пиксели, их среднее может лечь мимо рисунка.
3. `item.src` — кадр набора `getHdSurfaceSet("HANDOB.PCK")`, то есть классический кадр, увеличенный nearest в k раз (`SurfaceSet::hdScaledCopy`, 32k x 40k); `getPixel` читает его индексы, а не пиксели HD-пака. Точка вспышки берётся из классики при любом HD-паке.
4. Единицы (поправка 05.10, прежний вывод «сдвиг +0.5 пикселя базы» неверен). Все величины — в пикселях холста карты, уже умноженных на k: кадр 32k x 40k, `x, y` вызова — `_x + offX * _scale` при `_scale = _k` (`Map.cpp` `unitSprite.setScale(_k)`), `Canvas32::blitFrame(hd, x, y)` пишет команду с `y0 = y`, `y1 = y + hd.height` — тоже пиксели холста. `mx/n` — средний НОМЕР пикселя полосы; центр пикселя `p` лежит в `p + 0.5`, поэтому `mx/n + 0.5` — центр полосы в непрерывных координатах, а `lround` приводит его к целой координате угла. Это округление, не сдвиг: ошибка не больше 0.5 пикселя холста, то есть 1/(2k) пикселя базы (при k=4 — 1/8). Ровно на половине — при целом среднем: среднее 10, центр 10.5, `lround` даёт 11, на 0.5 пикселя холста правее-ниже центра. Клип рисуется от `tip - width/2`, его центр попадает в ту же целую координату. Для вспышки это ниже заметного; главное расхождение — §6а п.1-2 (крайняя точка вместо дула).

### 7. Связь с картинкой инвентаря
- Инвентарь рисует `bigSprite` (BIGOBS) в сетке (`Inventory.cpp` drawItems :340-: `slot.x + slotX*SLOT_W`; в руке — `slot.x + getHandSpriteOffX()`). Кнопки рук боя — тоже BIGOBS (`BattlescapeState::drawItem` :2054-2072: `HdItems::attachHand(...)`, иначе `rule->drawHandSprite(BIGOBS.PCK ...)`; вызовы :2197-2198). Смещение: `RuleItem::getHandSpriteOffX/Y` :1833-1845 = `(HAND_W - invW)*SLOT_W/2`, `(HAND_H - invH)*SLOT_H/2`.
- `handSprite` в инвентаре и на кнопках не участвует. Два номера независимы: `bigSprite` и `handSprite` ни из чего друг из друга не выводятся (у AK 168 и 352).
- Скрипты: `selectItemSprite` вызывается для `blit_item_righthand/lefthand/floor/big` (`BattleItem::getFloorSprite` :673 с `BODYPART_ITEM_FLOOR`; `getBigSprite` :707 с `BODYPART_ITEM_INVENTORY`; `UnitSprite::selectItem`). Один и тот же скрипт может различить части по `blit_part`. `recolorItemSprite` (BattleItem.cpp:1593-1605, ScriptFill :1778-1793): есть свой скрипт у предмета — берётся он; иначе заполнение идёт как у юнита (`BattleUnit::ScriptFill(item->getUnit())`).
- Выбора картинки по заряженному боеприпасу в движке нет (inventory-items-hd.md §6.2); `compatibleAmmo` читается RuleItem.cpp:540-557 и в рисовании не участвует. Ссылка на картинку боеприпаса в UI: `InventoryState.cpp:2393-2395` (превью по `bigSprite` боеприпаса).
- Piratez: глобальный `YSCRIPT_ENERGY_SHIELDS_RECOLOR_ITEM` меняет пиксели у семи щитов; остальные предметы он не меняет (R-198).

### 8. Текущий HD-путь для предметов
- HANDOB: `UnitSprite` берёт `_itemSurface = getHdSurfaceSet("HANDOB.PCK")` (UnitSprite.cpp:44-60); FLOOROB: `ItemSprite` — `getHdSurfaceSet("FLOOROB.PCK")`, draw :55-70 (blitScripted + `unlit`), `drawShadow` :77 (тень 16). `Mod::getHdSurfaceSet` (Mod.cpp:1026-1071, :1141-1156) строит копию набора в k раз крупнее (`hdScaledCopy`) и один раз вызывает `HdSprites::loadPack`.
- `HdSprites::loadPack` (HdSprites.cpp:1065-1147): читает `hd/<набор>/pack.hdp`, `<индекс>.png` и варианты `<индекс>.vN.png`. Размер кадра должен равняться размеру классического или быть кратным (:1123-1131), иначе предупреждение «ignored». Необязательный `hd/<набор>/color.txt` (`colorAuthority: pack`, `frames: ...`, `readColour` :959) помечает кадры, сохраняющие свои цвета. HD-кадр ищется по указателю буфера классического кадра. Бюджет паков 384 МБ (:158, `OXCE_HD_PACK_BUDGET`).
- `k` берётся из набора как `k = размер HD / размер классики` (максимум 4), для HANDOB/FLOOROB то же, что для остальных наборов; в режимах `_hdMode >= HD_MODE_PACKS`.
- `Canvas32::blitScripted` (HdCanvas.cpp:603-864): скрипт всегда считается на базовом 8-битном кадре. Нет скрипта — обычный блит (:609-613). Есть пак и скрипт ничего не поменял — HD-кадр рисуется как есть (:714-721). Скрипт поменял пиксели — каждый HD-пиксель берёт `cb * (яркость HD + 2) / (яркость базы + 2)` (R-030); если скрипт сам задаёт уровень рампы, фактура сжимается множителем 0.3 (R-128); HD-пиксель над пустым базовым берёт перекраску ближайшего непустого в окне 3x3. Для кадров с `ownColour` при тени используется второй воркер `unlit`, заполненный с тенью 0 (R-224). Кэш — `_smoothScripted` по хэшу. Режим 2 без пака — xBRZ, иначе nearest.
- `HdItems` (HdItems.h/.cpp) обслуживает ТОЛЬКО BIGOBS: папка `hd/BIGOBS.PCK` (:49), бюджет 64 МБ (:75), файлы `<кадр>.<ТИП>.png`, `.hand.png`, `.wide.png`, `<кадр>.png`; `pick` (:280-) требует `k >= 2`, `enabled()` и что предмет не перекрашен сейчас (`recoloured` :215-242, сравнение пикселей после прогона скриптов, R-198).
- На диске: `user/mods/hd/hd/BIGOBS.PCK` содержит один файл `1168.STR_RIFLE_AK.wide.png` (так же в установке Пираток). Паков HANDOB и FLOOROB нет ни в репозитории, ни в установке. Путь движка готов, данных нет.

Ограничения: HD-кадр должен быть той же геометрии, что классический (место хвата, срез ствола, кратные размеры); у кадра нет отдельных HD-смещений — `offX/offY` общие и берутся в базовых пикселях; порядок слоёв HD не меняет; для предметов со скриптом перекраски HD-кадр перекрашивается яркостным множителем (теряет оттенок пака).

## Что из этого следует для рисования HD-оружия
- Картинка из инвентаря (BIGOBS) — главный образец ВНЕШНЕГО ВИДА: материал, цвет, детали. Её ракурс (вид сбоку/сверху, горизонталь) в бой автоматически не переносится: HANDOB — отдельные рисунки.
- Кадры HANDOB — образец УГЛА, ПОЛОЖЕНИЯ РУК И МУЗЛА: на каждом из 8 кадров художник уже задал, куда смотрит ствол (кадр `f` — вдоль направления `(f-2)%8`), где ствол кончается и какая часть закрыта телом. HD-кадр должен повторять это место за местом. Точку вспышки HD-рисунок не обслуживает: сейчас она берётся крайней точкой классического кадра (у части стволов это выступ над дулом, §6а), для HD HANDOB нужна явная отметка дула на каждом кадре.
- Угол из инвентаря в бой не переносить: прицеливание — это другой КАДР, а не поворот. Из одного вида оружия 8 HD-кадров получаются только перерисовкой по HANDOB.
- Двуручный и одноручный хват, левая/правая рука и прицеливание — это не разные кадры, а таблицы смещений и порядок слоёв; HD-оружию отдельные кадры «под левую руку» не нужны.
- Рядом с оружием смотреть `compatibleAmmo` и кадр/педию боеприпаса: магазин рисуется в самом кадре оружия (движок картинку по заряду не меняет).
- Скрипт перекраски у предмета (щиты Пираток) отключает HD-кадр BIGOBS и перекрашивает HD HANDOB/FLOOROB яркостным множителем; обычное оружие — нет.
