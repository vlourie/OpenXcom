## 1. Решения специалиста, на которых стоит контракт

1. Пилот на SCC.
2. Полоса `b = 4` пикселя базы с растушёвкой 1 пиксель, полоса — край основного HD-кадра.
3. `n ≥ 4`; для URBAN:69/70 `n = 6`. При `n < 4` адресации нет, `n = 3` не поддерживается.
4. Выбор варианта последовательно во время блитов запрещён: только заранее рассчитанное поле
   индексов на полную сетку карты.
5. V1 — только north и west, разрешение по паре «кадр:слот».
6. Разрешение адресации стены не отключает варианты пола того же кадра.
7. Тон должен совпадать около соединения; освещение и фактура внутри стены не запрещаются.
8. 23 % изменяемой площади — свойство URBAN:69/70, не общее правило.
9. Отсутствие швов доказано только на синтетике; настоящий арт проверяется заново.
10. Если различия на 23 % почти незаметны, польза адресации оценивается до масштабирования.

**Уточнения при приёмке контракта (разбор 06.10)** — внесены в разделы ниже:

| уточнение | где |
|---|---|
| нумерация: 0 — основной кадр, при n = 6 файлы 1–5; отсутствующий или несовместимый вариант — основной кадр без перенумерации остальных | 2, 5.2, 6.3 |
| версия: `address.txt` явно объявляет версию SCC, слот и n; неизвестная версия или плохая запись выключает соответствующую адресацию с диагностикой | 6.3 |
| жизненный цикл: поле готовится и при загрузке боя; перезагрузка паков и смена n обновляют таблицы до отрисовки; потоки только читают | 4.2, 4.3 |
| анимация и разрушение: связанные кадры — одно n и согласованные номера; в первом пилоте только `URBAN:69:north` и `URBAN:70:west`, остальные состояния — основная графика | 5.4 |
| 100×120×30 — стресс-сценарий по максимумам осей, а не доказанная карта | 4.4, 9 |
| запрет — на потерю точных RGBA-пикселей, включая квантование и дизеринг; индексное хранение само по себе не запрещено | 6.4 |
| прототип: опция выключена по умолчанию, обе ориентации стен и все фактические пути рисования, IDENTICAL и при одинаковых вариантах, и при выключенной опции | 8 |

Разбор принимает контракт как основу изолированного прототипа. Разрешение на правку движка и
генерацию **не выдано**: оно даётся отдельно словом Vitali.

## 2. Формула (без изменений, ADDRESSING_V1)

```
fmix32(v):  v ^= v >> 16;  v *= 0x85EBCA6B;  v ^= v >> 13;  v *= 0xC2B2AE35;  v ^= v >> 16
cell_hash(x, y, z, part) = fmix32( x*73856093 ^ y*19349663 ^ z*83492791 ^ part*2654435761 )
```

Всё — `uint32`, без плавающей точки.

| часть | `part` | линия `b` | место на линии `a` |
|---|---|---|---|
| west (`O_WESTWALL`) | 1 | `x` | `y` |
| north (`O_NORTHWALL`) | 2 | `y` | `x` |

```
ban     = { f(a-1, z)  если a > 0,
            f(a, z-1)  если z > 0 }
allowed = 0..n-1 без ban, по возрастанию
f(a, z) = allowed[ cell_hash(x, y, z, part) % len(allowed) ]
```

`(x, y) = (b, a)` для west, `(a, b)` для north.

**Допустимые n.** n — объявленное число вариантов пары (раздел 6.3), вариант 0 — основной кадр.
- `n ∈ [4, 16]` — адресация;
- иначе пара выключена, рисуется основной кадр, одна строка в лог.

Верхняя граница 16 — это `MAX_VARIANTS = 15` плюс основной кадр (`HdSprites.cpp:145`) [код].

**Нумерация.** Значение поля `v ∈ [0, n−1]`:
- `v = 0` — основной кадр (`<кадр>.png` или кадр в `pack.hdp`);
- `v = 1..n−1` — файлы `<кадр>.<слот>1.png … <кадр>.<слот><n−1>.png`. При n = 6 это файлы 1–5.

Поле строится **по объявленному n** из `address.txt`, а не по числу найденных файлов. Если вариант с
номером `v` отсутствует или не годен (размер, битый PNG), клетки с этим `v` рисуются основным кадром.
Остальные номера не сдвигаются, поле не пересчитывается: клетка с `v = 4` рисует файл 4, даже если
файла 2 нет.

**Сверка реализаций.** Реализация на C++ (`scc_field.cpp`, тот же код, что пойдёт в движок) и
эталон на Python дают побайтно одно поле: 70×70×10, n = 6, по 49 000 байт на часть, **0 различий**
[замер, `scc_cmp.json`]. Значит, формула переносится между языками без двусмысленностей (`uint32`,
`%` без знака, порядок `allowed`).

C++ выбирает k-е разрешённое значение без списка:
- сдвигает k за каждый запрет, который не больше k, в порядке возрастания;
- при двух равных запретах учитывает один.

Это и проверено сверкой.

## 3. Начало расчёта и порядок обхода

### 3.1 Начало

- **Граница каждой линии:** клетка `a = 0` не имеет запрета слева, этаж `z = 0` — запрета снизу.
  Других начальных данных нет: ни зерна, ни содержимого карты.
- `a = 0` — это `y = 0` для west и `x = 0` для north, то есть край карты с наименьшей координатой.
- `z = 0` — нижний этаж (`Tile::getPosition`).

### 3.2 Порядок

Значение `f(a, z)` зависит только от `f(a−1, z)` и `f(a, z−1)`. Значит, поле — **единственное**
решение рекуррентности с заданной границей. Любой порядок, в котором клетка считается после этих
двух, даёт одно и то же [вывод, индукция по `a + z`].

| порядок | различий с «z снаружи, a внутри» | клеток |
|---|---|---|
| a снаружи, z внутри | 0 | 8 640 на часть |
| случайный порядок клеток, ленивый расчёт с запоминанием | 0 | 8 640 на часть |

[замер, `scc_stab.json`, 40×36×6, обе части]

**Контрактный порядок движка** — для однозначности кода, не ради результата:
- линии `b` по возрастанию;
- внутри линии `z = 0, 1, …`;
- внутри этажа `a = 0, 1, …`.

### 3.3 Что поле не видит

Поле — чистая функция `(x, y, z, part, n)`. Из этого:

| | почему не влияет |
|---|---|
| размер карты | значение клетки зависит только от клеток своей линии с меньшими `a` и `z`; клетки правее и выше в расчёт не входят. [замер] Карты 70×70×10, 50×50×4, 100×40×12, 13×99×3, посчитанные отдельно, равны срезу поля 100×120×12: **0 различий** |
| содержимое карты, блоки MAP, их границы | не входят в формулу; поле строится по всей сетке, есть там стена или нет |
| разрушение, двери | меняется кадр клетки (запись `die` / `alt` MCD), но не поле. Уцелевшая стена рядом рисуется тем же вариантом. [замер] Ряд из 50 стен, одна разрушена: SCC — 0 изменений у 49 уцелевших. Отвергнутая альтернатива «цепочка только по существующим стенам» — 2 изменения |
| камера, видимая часть, прокрутка | поле строится целиком до отрисовки; блит только читает готовое значение |
| порядок отрисовки, потоки | поле только для чтения; рабочие потоки `HdWorkers` его не касаются |
| `k`, режим HD, свет, ночное зрение | не входят в формулу |
| сохранение и загрузка | в сохранение не пишется ничего: после загрузки те же координаты дают те же значения |

### 3.4 Участок карты

Участок **никогда не считается со своим началом.** Если начать участок с `a0 > 0` или `z0 > 0`,
граница переносится, и поле получается другим [замер, 70×70×10, n = 6]:

| участок (x × y × z) | часть | своё начало: различий | от начала карты: различий | клеток |
|---|---|---|---|---|
| [20..50) × [30..60) × [2..8) | west | 2 130 | 0 | 5 400 |
| [20..50) × [30..60) × [2..8) | north | 2 182 | 0 | 5 400 |
| [0..70) × [35..70) × [0..10) | west (сдвиг по `a`) | 1 650 | 0 | 24 500 |
| [35..70) × [0..70) × [0..10) | north (сдвиг по `a`) | 1 768 | 0 | 24 500 |
| [0..70) × [0..70) × [5..10) | west / north (сдвиг по `z`) | 10 310 / 10 486 | 0 / 0 | 24 500 |
| [35..70) × … west, [0..70) × [35..70) north (сдвиг только по линиям `b`) | — | 0 | 0 | 24 500 |

Последняя строка — контроль: линии друг от друга не зависят, поэтому сдвиг по `b` ничего не меняет.

**Правило:** значение для любого участка — срез поля, посчитанного от `(0, 0, 0)` хотя бы до правого
верхнего угла участка. В движке участков нет вовсе: поле строится на всю карту (раздел 4).

### 3.5 Зерна боя нет

У узора пола зерно есть: `Map::groundSeed` — хэш размера и имён блоков MAP [код, `Map.cpp:412`].
В V1 SCC зерна нет, потому что специалист потребовал независимости от блоков MAP.

**Следствие:** одна и та же клетка `(x, y, z)` в двух разных боях получает один и тот же вариант.
Стены в разных боях стоят в разных местах, поэтому повтор между боями глазом не связывается [вывод].

Добавлять зерно — отдельным решением и только со сменой `version` в `address.txt` (раздел 6.3).

## 4. Поле индексов

### 4.1 Хранение

- **Таблица:** `uint8 F[z][y][x]` на каждую пару (часть, n), где n встречается среди включённых пар
  «кадр:слот» этой части.
  - В пилоте одна пара на часть: (west, 6) и (north, 6), то есть две таблицы.
- **Владелец — `Map`**, основной поток.
  - `Canvas32` получает константный указатель на поле.
  - Рабочие потоки `HdWorkers` поле не читают: вариант выбирается при записи команды, до постановки
    (`HdCanvas.cpp` 477–498) [код].

### 4.2 Когда строится

1. **При создании `Map`, до первой отрисовки, — и в новом бою, и при загрузке боя.** Таблица
   строится целиком, по всей сетке `getMapSizeX × Y × Z`, для каждой нужной пары (часть, n).
   - Место — `Map::init`, рядом с `createCanvas` (`Map.cpp:376`), где уже ставится зерно узора пола
     [код].
   - Оба пути попадают туда одинаково [код]: начало боя — `BriefingState.cpp:288`, загрузка
     сохранения — `LoadGameState.cpp:195` и `ListLoadOriginalState.cpp:206`, возврат из опций —
     `OptionsBaseState.cpp:172`. Каждый делает `new BattlescapeState`, а его конструктор вызывает
     `_map->init()` (`BattlescapeState.cpp:470`).
   - Строка в лог: `HD address: field <X>x<Y>x<Z> <part>:<n> built in T ms`.
2. **Перед записью первого блита кадра — проверка, и при расхождении перестройка целиком.**
   В начале `Map::drawTerrain`, в основном потоке, до записи команд:
   - размер карты не равен размеру поля;
   - поколение паков `HdSprites::generation()` не равно поколению, при котором читались объявления
     `address.txt`. Тогда объявления читаются заново: новые пары (часть, n) получают таблицу, пары
     с изменившимся n — новую таблицу, ненужные таблицы освобождаются.

   Так как поле — чистая функция, перестройка не меняет значений клеток при том же n. При смене n
   значения меняются, и это ожидаемо: другая серия файлов.
3. **Потоки рисования только читают.**
   - Таблицы меняются только в основном потоке и только между кадрами (пункты 1 и 2), когда команды
     прошлого кадра уже выполнены.
   - `HdWorkers` поле не видят вовсе: в команду идёт уже выбранный кадр (раздел 4.1).
4. **Запрещено:**
   - выбирать вариант по ходу блитов;
   - строить по видимой части;
   - продолжать поле с места, где остановилась камера.

### 4.3 Когда сбрасывается

| событие | что делать |
|---|---|
| новый бой, следующая стадия миссии, оборона базы | `Map` создаётся заново (`BattlescapeState.cpp:160`) [код] — поле строится заново (4.2.1) |
| загрузка сохранения боя | то же: новый `BattlescapeState`, новый `Map`, поле строится заново (4.2.1); из сохранения ничего не читается |
| размер карты изменился при живом `Map` | перестроить целиком (4.2.2) |
| перезагрузка паков (новое поколение `HdSprites`) | перечитать `address.txt` до записи блитов; построить таблицы для новых n, освободить ненужные (4.2.2) |
| смена объявленного n у пары | её клетки переходят на таблицу нового n до первого блита кадра (4.2.2) |
| разрушение, двери | ничего |

### 4.4 Стоимость

Программа `scc_field.cpp`: тот же расчёт, что пойдёт в движок, `g++ -O2`. Сборка релиза — `-O3`
(`CMakeCache.txt`), так что замер с запасом. Цифры — лучшее и среднее из 60 построений обеих таблиц
(west + north) [замер, `scc_field_cpp.txt`].

| карта | откуда размер | n = 4 | n = 6 | n = 8 | n = 16 | память (обе таблицы) |
|---|---|---|---|---|---|---|
| 50×50×4 | типичная | 0,11 мс | 0,10–0,11 мс | 0,10 мс | 0,09 мс | 20 КБ |
| 70×70×10 | наибольшая в переписи 378 боёв (`census/maps/battles.tsv`, URBANWAR) | 0,71 мс | 0,63 мс | 0,59 мс | 0,55 мс | 98 КБ |
| 100×120×30 | **стресс-сценарий**: максимумы `width` / `length` / `height` рулсетов Пираток по каждой оси отдельно (`alienDeployments`), сложенные в одну карту. Что такая карта целиком допустима, не доказано | 5,7 мс | 5,0 мс | 4,7 мс | 4,3 мс | 720 КБ |

**Оценка.**
- Один раз на бой и на пару (часть, n), меньше миллисекунды на реальных картах.
- Память — доли процента бюджета пака (384 МБ).

**Оговорки (R-091, R-196):**
- Это замер отдельной программы на машине разработки. Во время замера чужих копий игры не было, но
  загрузку машины не следил.
- Окончательная цифра — строка в логе прототипа на тяжёлой карте Пираток (раздел 8, П-10).

Стоимость самой отрисовки — одно чтение байта и одна проверка на адресованный блит. Изменения
`drawMs` не ожидается [вывод], мерится в П-10.

## 5. Адресация по слотам

### 5.1 Какие слоты

| слот Map | `part` | V1 | механизм |
|---|---|---|---|

### 5.2 Выбор варианта в `Canvas32`

Для каждого блита при записи команды, по убыванию старшинства:

1. `_frameVariant > 0` (огонь, дым, кровь, руки юнита) — прежний путь, без изменений.
2. **Метка клетки стены** (`setCellAddress`): её ставит `Map` только вокруг блитов west и north.
   Если пара (ключ кадра, часть) включена:
   - `v = F[part, n][z][y][x]`;
   - при `v > 0` — файл `<кадр>.<слот><v>`;
   - если этого файла нет, он не того размера или не загрузился — основной кадр **только для этой
     клетки**. Номер `v` у соседей, n и поле не меняются (раздел 2, «Нумерация»).
3. **Метка клетки пола** (`setGroundCell`, только вокруг блита пола) — `groundFrameFor`, **без
   изменений**. Он смотрит только `.v<N>` и `address.txt` не читает.
4. Иначе — основной кадр.

Метки 2 и 3 никогда не стоят одновременно: Map ставит их вокруг разных блитов [код, `Map.cpp`
1822–1829 и 1902–1919].

**Фактические пути рисования стен в `Map`** [код, `Map.cpp` 1899–1920]. Других мест, где рисуется
спрайт `O_WESTWALL` / `O_NORTHWALL`, в `Map.cpp` нет (`getSprite(` встречается ещё только для пола
1818 и объекта 1922, 2261):

| № | ориентация | условие | блит |
|---|---|---|---|
| W1 | west | обычная стена | `blit(..., wallShade, false, _nvColor)` |
| W2 | west | препятствие (`getObstacle`) | `blit(..., obstacleShade, false, _nvColor)` |
| N1 | north | обычная, западной стены в клетке нет | `blit(..., wallShade, false, _nvColor)` — целый кадр |
| N2 | north | обычная, западная стена есть | `blit(..., wallShade, true, _nvColor)` — половинный кадр |
| N3 | north | препятствие, западной стены нет | `blit(..., obstacleShade, false, _nvColor)` |
| N4 | north | препятствие, западная стена есть | `blit(..., obstacleShade, true, _nvColor)` |

Каждый путь — ещё и при ночном зрении (`_nvColor`) и в режимах HD 1 и 2. Метка клетки стены ставится
вокруг всех шести; все шесть берут вариант из поля одинаково.

**Ветки `Canvas32`, которые обязаны выполнить пункт 2:**

- `blitScripted` (640–660).

Через последние две стены сейчас не идут [вывод]. Прототип это проверяет логом (П-3), и тогда лишние

### 5.3 Поправка к отчёту синтетики

**Правило 3 раздела 6 отменено.** Оно говорило: «адресованный кадр выключен из узора пола». По

### 5.4 Ограничения пары

- **Один кадр в двух слотах стены** (BARN:5, PORTROADS:47, BARN_JUNK:5 — отчёт синтетики, раздел
  3.2):
  - у каждого слота свои файлы и своя строка разрешения;
  - перебор стыков делается для каждого слота на его пикселях;
  - разрешить один слот, не разрешив второй, можно.
- **Связанные кадры** — кадры одной петли анимации (`Frame[0..7]` записи), разрушенный вид (`die`),
  второе состояние двери (`alt`, `door`, `ufo_door`). Клетка переходит между ними, не меняя
  координат, а поле у неё одно.
  - Если связанные кадры адресованы, у них **одно n и одна нумерация**: вариант `v` каждого из них
    рисуется как то же самое `v`-е состояние одной и той же стены. Тогда клетка при смене кадра
    остаётся на своём `v`.
    - Одно n обеспечивает это само: таблица общая на (часть, n), значит у клетки то же `v`.
    - Согласованность самих картинок — ворота конвейера.
  - При разных n таблицы разные, и при смене кадра у клетки сменился бы вариант — фактура прыгнула
    бы. Такое разрешение конвейер отказывает (П-12).
  - Связанный кадр без разрешения рисуется основным кадром. Это допустимо: клетка переходит из
    варианта `v` в основное состояние другого кадра, а не прыгает между вариантами одного.
  - Петля анимации разрешается целиком или никак. Иначе петля мигала бы между вариантом и основным
    кадром (R-071).
  - Это ворота конвейера: движок MCD в `HdSprites` не видит.
- **Первый пилот** — только две пары: `URBAN:69:north` и `URBAN:70:west`, n = 6.
  Их связи [замер, MCD URBAN Пираток и ванили совпадают; `census/maps/state_graph.tsv`]:

  | кадр | запись | слот | анимация | дверь / `alt` | `die` → запись → кадр | в пилоте |
  |---|---|---|---|---|---|---|
  | 69 | 65 | north | нет (8 × кадр 69) | нет / 0 | 65 → 70 → **74** | варианты 1–5 |
  | 70 | 66 | west | нет (8 × кадр 70) | нет / 0 | 66 → 71 → **75** | варианты 1–5 |
  | 74 | 70 | north | нет | нет / 0 | нет | основной кадр |
  | 75 | 71 | west | нет | нет / 0 | нет | основной кадр |

  Кадры 74 и 75 — разрушенный вид и для записей 67 и 68 (кадры 71 и 72). Все остальные кадры и
  состояния в пилоте — основная графика.

### 6.1 Как сейчас

[код]
- `HdSprites::loadPack` разбирает имена `<индекс>.png` и `<индекс>.v<N>.png`, `N = 1..15`

- `pack.hdp` хранит только основные кадры (`registerPackFile`, 892–948). Варианты — всегда отдельные
  файлы.
- У кадров террейна единственный потребитель `.vN` — `groundFrameFor`, только в слоте пола.
  - `_frameVariant` ставят огонь и дым (`SMOKE.PCK`), попадания (`HIT.PCK`) и юниты

  варианта попиксельно (1811 и далее).

### 6.2 Почему общие `.vN` несовместимы

| | вариант пола (`groundFrameFor`) | вариант стены (SCC) |
|---|---|---|
| номер | место на шкале (короче ↔ выше трава) | ничего не значит, номера равноправны |
| край кадра | свой; пол сшивается узором пятен и попиксельной смесью | полоса 4 базы — байт в байт основной кадр |
| соседство | варианты смешиваются внутри клетки | варианты встречаются только полосами |
| сколько | от 2 (`count ≥ 2`) | от 4 |

**Проверка существующих файлов** [замер, `scc_floorvar.json`]: все 84 файла `.vN` в моде hd
установки (20 кадров), ворота полосы стены (отчёт синтетики, раздел 5.7).
- Альфа равна основному кадру у всех 84 — это ворота проходят.
- Полоса b = 4 отличается от основного кадра **у всех 84**: от 55 % до 100 % пикселей полосы,
  медиана 98 %.

**Где это ударило бы.** Два кадра с вариантами пола стоят и в других слотах [замер,
`scc_names.json`, `census/maps/frame_usage.tsv`]:
- **ROADS:0** — пол 170 857 клеток, **north 160**;
- **MOUNTGRASS:2** — пол 621, объект 1.

При общих именах разрешение `ROADS:0:north` нарисовало бы на 160 стенах картинки пола с другим краем:
шов на каждом стыке.

**Обратная сторона** [вывод]. Варианты стены, попавшие в узор пола, смешивались бы попиксельно по
неровной границе пятна внутри клетки. Разная внутренность двух вариантов стены дала бы шов посреди
пола, и шкалы между ними нет.

**Вывод: имена раздельные.**

### 6.3 Новые имена и `address.txt`

**Файлы в папке набора** `hd/TERRAIN/<НАБОР>.PCK/`:

```
<кадр>.png              основной кадр (или кадр в pack.hdp) - вариант 0
<кадр>.v<N>.png         варианты пола, как раньше; только слот пола
<кадр>.north<N>.png     варианты северной стены, N = 1..n-1, без пропусков
<кадр>.west<N>.png      варианты западной стены, N = 1..n-1, без пропусков
address.txt             разрешение пар и формула
```

**`address.txt`** пишет конвейер, руками не правится:

```
# ADDRESSING_V1 - пишет конвейер по census/maps, руками не править
version: 1
frames: 69:north:6 70:west:6
```

Файл **явно объявляет** всё, от чего зависит выбор: версию формулы SCC (`version`), слот и n каждой
пары. Ничего не выводится из имён файлов или их числа.

**Разбор:**
- `version` — только `1`: формула раздела 2 без зерна. Нет строки `version` или версия неизвестна —
  **выключена вся адресация набора**, строка в лог `HD address: <набор> version <v> unknown, off`.
- Элемент `frames` — `кадр:слот:n`:
  - кадр — целое, есть в наборе;
  - слот — `north` или `west`;
  - `n` — целое от 4 до 16.
- **Плохой элемент выключает только свою пару**, остальные элементы файла работают. Плохой — не по
  форме, кадра нет, слот не тот, n вне [4, 16], повтор той же пары. Повтор выключает пару в обоих
  местах: какое n верное, неизвестно. Строка в лог с причиной: `syntax`, `frame`, `slot`, `n<4`,
  `n>16`, `duplicate`.
- **Пара включается**, если элемент годен и основной кадр есть в паке. Каждый номер `1..n−1`
  проверяется отдельно:
  - файл `<кадр>.<слот><N>.png` есть;
  - его размер подходит под кадр по тому же правилу `fits`, что у `.vN` (1123–1131), и равен размеру
    основного кадра.

  Негодный номер рисуется основным кадром, остальные номера не сдвигаются (раздел 2, «Нумерация»).
  Строка в лог: `HD address: <набор> <кадр>:<слот> variant <N> missing|size|decode`. Битый PNG
  выясняется только при ленивой загрузке, тогда строка пишется в момент отказа, один раз на файл.
- **Файлы `<кадр>.<слот><N>.png` без строки в `address.txt`, или с N ≥ n, не используются**, строка
  в лог. Разрешение — только явное.
- Строка при загрузке: `HD address: <набор> N pair(s) on, M off`.
- Опция адресации выключена — `address.txt` не читается вовсе, файлы стен не регистрируются.

**Реестр** — отдельная карта по ключу (ключ кадра, часть). Ленивая загрузка та же, что у `.vN`,
расход входит в тот же бюджет кадров паков (384 МБ). Реестр `.vN` не меняется.

**Совместимость:**
- **Старая сборка** с новым паком: хвост `.north1.png` не начинается с `.v`, и `loadPack` его
  пропускает (1093) [код]. Значит, рисуется основной кадр, байт в байт как без файлов. Проверка —
  П-8.
- **Инструменты**, которые ищут `.vN` точным именем (`carpet_check.py:76`, `map_mockup.py:114`), новые
  файлы не видят [код].
- **Тот же кадр полом:** его `.v<N>` работают в слоте пола как раньше, а `.north<N>` / `.west<N>` в
  пол не попадают. Проверка — П-7.

### 6.4 Сжатие файлов

`tools/hdart/optimize_hd.py` в режиме по умолчанию (`palette`) переводит картинку в 256 цветов с
дизерингом, **каждую отдельно** [код, шапка файла]. Полоса варианта и полоса основного кадра,
квантованные порознь, перестают совпадать байт в байт, и ворота 1 раздела 7 ломаются.

**Запрет — на потерю точных RGBA-пикселей**, в том числе через квантование и дизеринг. Индексное
хранение само по себе не запрещено. PNG с палитрой допустим, если картинка в нём умещается в палитру
без изменений: декодированный RGBA каждого пикселя, включая альфу, байт в байт равен исходному.

**Правило:**
- адресованные кадры и все их файлы стен — только сжатие без потерь (`--mode lossless`), вне сжатия
  вовсе или индексный PNG, прошедший побайтную сверку декодированного RGBA с исходником;
- ворота раздела 7 проверяются на файлах той копии мода hd, которую читает игра (R-087), **после**
  любого сжатия.

## 7. Контракт полосы и тона для настоящего арта

**Ворота 1–4** — для каждого файла `<кадр>.<слот><N>.png`, при k = 4.

1. **Полоса.**
   - Внутренность — пиксели с альфой 255 дальше `4·K = 16` пикселей (квадратная мера) от любого не
     полностью непрозрачного пикселя.
   - Всё остальное — полоса. Она **байт в байт равна основному HD-кадру пака**, а не классическому
     кадру ×4.
2. **Альфа** равна альфе основного кадра везде.
3. **Растушёвка** 1 пиксель базы (4 пикселя HD) внутрь от границы полосы.
4. **Тон около соединения.** Кольцо не больше 1,3. Кольцо — перепад яркости через контур «полоса —
   внутренность», делённый на то же у основного кадра.
   - Это единственное требование к тону.
   - Глубже зоны растушёвки внутренность свободна: свет, тень, фактура, пятна (решение специалиста).
   - Нельзя только одно: скачок тона на самом контуре.
   - Синтетика показала, что видимое кольцо даёт именно скачок тона у контура, а не изменение внутри
     (отчёт синтетики, 5.3).

**Ворота 5** — для пары целиком.

5. **Швы.** После `resample` под k = 1, 2, 3 шов на прямом стыке, угле в клетке и этажах равен 0.
   Скрипт — `syn_band.py` с подменой синтетики на файлы.

**Дальше:**

6. **Доля изменяемой площади** считается для каждого кадра своя. 23 % — это URBAN:69/70, не норма.
7. **Повторная проверка настоящего арта:**
   - ворота 1–5 по всем файлам;
   - лист стены 24 клетки × 3 этажа в полный размер, 1:1, рядом с основным кадром;
   - лист стыков из раздела 4 отчёта синтетики на настоящих файлах.

   Синтетика доказала только то, что контракт полосы *может* давать стык без шва.
8. **Польза до масштабирования.**
   - По первой паре (URBAN:69/70) считается, насколько отличаются внутренности: доля пикселей
     внутренности, где вариант отличается от основного кадра и от других вариантов заметнее порога
     яркости.
   - Число идёт в отчёт без автоматического вердикта.
   - Решает Vitali по листу стены. Если различия почти не видны, производство не масштабируется.

## 9. Что остаётся недоказанным

- **Шов на настоящем арте.** Доказано только на синтетике, нужна проверка раздела 7.
- **Видимая польза 23 % внутренности.** Решается листом настоящих вариантов.
- **Стоимость в движке.** Замер выше — отдельная программа; цифра движка будет в П-10.
- **Наибольшая допустимая карта.** 100×120×30 — стресс-сценарий из максимумов по осям, а не карта,
  которая может выпасть в игре. Что такая карта целиком допустима, не доказано; наибольшая
  встреченная в переписи — 70×70×10.
- **Поведение ленивой загрузки на битом PNG** (`setVariantLazy` / `frameOf`) не проверялось — П-9.
- **Через какие ветки `Canvas32` идут стены.** Что через вторые две ветки они не идут, — вывод, а не
  замер; проверяется в П-11.
- **Повтор вариантов между боями** на одних координатах (раздел 3.5) глазом не проверялся.
