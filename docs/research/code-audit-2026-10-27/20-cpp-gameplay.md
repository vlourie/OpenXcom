## 1. Таблица обрушения: формат и как хранить

### Что это
`CollapsePilotData.h` сгенерирован `tools/collapse_pilot_export.py` (`cpp_header(datas)`, ~800–856; запись в `main` ~1016). Структура файла: для каждого блока карты `sets%d[]` (имена наборов), `parts%d[]` (массив `CollapsePart`), `targets%d[]`, `treeCols%d[]`/`crowns%d[]` (у 505 блоков), затем таблица `blocks[]` (со стр. 375101) и `blockCount = 956` (стр. 376059).

Цифры:
- 956 блоков, **368 311 строк частей**. `CollapsePart` — 17 int = 68 байт, образ в `.rdata` **25,05 МБ**; плюс ~73 870 int (targets/деревья/кроны) ≈ 0,3 МБ.
- Файл на диске 22,9 МБ, в exe ~24–25 МБ — **около 40 % exe** (рост exe: 38,2 МиБ на 20.10 → 44,5 на 21.10 → 57,6 на 23.10).
- Опция `oxceCollapse` **выключена по умолчанию** (`Options.cpp:532`, OPTION_OXCE, `STR_HD_COLLAPSE`): у большинства игроков таблица не читается вообще, но лежит в exe и скачивается.

### Как читает движок
- `bind()` (`CollapsePilot.cpp:~845`) связывает блоки с наборами карты сейва; `scan()` (940+) перебирает блоки с `setsOnMap(bi)`; `adopt()` (1052–1112) принимает блок; `settle()` (1649+) считает обрушение; `collapseEvaluate` (`CollapseCore.cpp`) работает по `CollapsePart`.
- `modelSig(bi)` (`CollapsePilot.cpp:~158–182`): FNV по имени, `sx..y1`, `nSets`, `nParts`, именам наборов, всем 17 int каждой части и `targets`. Подпись пишется в сейв. При любом формате, дающем те же int, подпись совпадёт побайтно. Деревья и кроны в подпись не входят.

### Что в данных избыточно (измерено, `proto.py`/`integrity.py` в scratchpad)
- 125 493 различных строки из 368 311.
- Постоянные колонки: `e1x = e1y = 0` у всех частей; `nEdge ≤ 1`; `mark ≤ 1`; `limL ∈ {12, 16}`; `contact` — 22 значения; `flags` — 38. «Хвост» полей `flags..tCount` — всего **205 различных** значений (словарь).
- 733 различных массива `parts` из 956 блоков: **223 блока повторяют чужие `parts`**, это 65 893 лишних строки; полностью одинаковых блоков нет.
- 120 блоков помечены `experimental` (73 888 строк, 20 %): в рантайме их исключает `inThisBuild(bi)` (868–876), но данные в exe всё равно лежат (проверено: `madurban27`, `chemtown94` есть в `dist/_stage/openxcom_hd.exe`).
- Целостность: нет частей вне блока, нет дублей слота (z, kind, y, x), индексы наборов/targets/деревьев в пределах; имена и метки блоков уникальны.

### Прототип бинарного формата
Раскладка по колонкам: `kind`, дельты `dx/dy/dz` по строке, `set`, `mcd`, `tail-id` (uint16 в словарь из 205 хвостов), затем varint для `targets/tree/crowns`. Round-trip проверен на всех 956 блоках, все int совпали.

| Вариант | Размер |
|---|---|
| Сырой бинарный | 3 049 087 Б (+ таблица заголовков 70 936 + tail-таблица 2 463) |
| zlib9 целиком | 279 212 Б (234 079 с дедупликацией блоков) |
| zlib9 по блокам | 354 964 Б (287 512 с дедупликацией) |
| zlib9 группами по ~64 КБ (45 шт.) | 288 034 Б |
| brotli11 / lzma | ≈ 146 тыс. Б |
| только не-экспериментальные (836 блоков), zlib9 целиком | 229 215 Б |
| Заголовки + tail, zlib | ≈ 11,9 КБ |

Для сравнения: сегодняшний образ 25,05 МБ в exe сжимается в пакете выпуска (brotli q9) до ≈ 0,49 МБ + ints ≈ 0,55 МБ, т.е. сеть платит примерно столько же, сколько заплатит новый blob; выигрыш — в размере exe на диске, в сборке и в репозитории, а не в трафике пакета (см. ниже).

### Рекомендация
Бинарный blob ≈ 0,28–0,35 МБ, миниз (`libs/miniz/miniz.c`, уже в сборке; LZMA в движке нет, поэтому не берём). Заголовки блоков (имена, размеры, наборы) — резидентно; тело блока — ленивое декодирование при `scan()/adopt()` только для блоков, наборы которых есть на карте. Где хранить:
- вариант А (проще и надёжнее): файл данных в репозитории, подключается в exe через `.incbin`/CMake-ресурс (размер exe падает на 25 МБ, отдельный файл игроку не нужен);
- вариант Б: файл рядом с игрой в `common` — тогда он идёт по правилам «святого правила про данные» и нужна лишняя проверка наличия; вариант А лучше.

Оценка (не замеряно в C++): inflate целиком 3,9–5,4 мс (измерено на C zlib), сборка структур ≈ 2 мс. На типовой городской карте нужны 254–262 блока ≈ 127–130 тыс. строк (≈ 35 %), ленивая загрузка по наборам ≈ 1,5–4 мс. Опция по умолчанию выключена — при выключенной таблица не декодируется вообще.

Итоги до/после:
- exe: 62 → ~36,7 МБ (−25,3 МБ, −41 %);
- исходник: −376 062 строки (−26 % всех текстовых строк репозитория, −83 % добавленного в `src`);
- git: регенерация 0,3 МБ вместо 22,9 МБ сырых / 1,3 МБ сжатых; история 16 версий ≈ 105 МБ сырых;
- сборка: `CollapsePilot.cpp.obj` сейчас 26,1 МБ, компиляция 8,55 с в релизе и 14–16 с в `build-ai-collapse`; линковка exe медиана 8,4 с (макс 17 с).

Как доказать «побайтно ту же логику»: офлайн-сверка всех 956 блоков (старый заголовок против декодера, поле за полем, порядок строк сохраняется); равенство `modelSig` по всем блокам; существующие векторы `tools/collapse_pilot_run.py`; плюс `hdtest_compare.py` на k=1 не требуется (рендер не затронут), но карта с включённой опцией — сверка стендом обрушения.

### Сколько раз менялась и сколько скачивали
- 16 коммитов, суммарно +508 144 / −132 082 строк. Коммит `1a5248355` переписал 131 737 строк. Размеры версий: 66 КБ → 0,18 → 0,83 → 2,0 → 2,9 → 8,1 → 8,3 → 8,9 → 15,5 → 19,8 → 22,9 МБ.
- Скачивания: сама таблица **не причина** пересылки exe — exe шлётся целиком в каждом выпуске (89 выпусков с 08.10, 41 с 21.10; `size_audit a18`: «exe re-sent with only 53 bytes different»; 41 выпуск с <4 КиБ различий, 1544 МиБ). Доля таблицы в пакете ≈ 0,5–0,6 МБ из ~9 МБ на обновление (≈ 6 %); хранилище сервера ≈ 41 exe-блоб × ~25 МБ ≈ 1 ГБ приходится на таблицу (оценка). Реальных данных о числе скачиваний игроками нет, замеров времени `scan()` в логах не найдено.
- Вывод: основная польза — не трафик, а репозиторий/сборка/exe на диске. Для трафика важнее чинить пересылку exe целиком (это зона аудита сборки/выпуска, `ReleaseRepo.cs`: блобы хранятся сырыми, PackFrom 3).

### Промежуточные шаги (если blob откладывается)
- п.3: `experimental` под `#ifdef OXCE_AI_DEV` — −20 %.
- п.4: дедуп одинаковых `parts` в экспортёре — −65 893 строки; в движке меняется только индекс.
- Оба вместе: 368 311 → 236 718 строк, 25,05 → 16,1 МБ.
- Узкая структура 16 Б вместо 68 дала бы ~3,8 МБ, но потребует правок кода (например, `for (int v : {...})` по полям) и повторной сверки; рядом с blob не нужна.

## 2. Стенд ИИ и стенд обрушения в выпускном exe

### Стенд ИИ (AiProbe)
- Включается CMake-опцией `OXCE_AI_DEV` (по умолчанию OFF), код в `#ifdef OXCE_AI_DEV`. В релизе `AiProbe.cpp` строки 77–424 — заглушки (`#ifndef OXCE_AI_DEV`), строки ~424–6371 — только стенд. Всего «стенд ИИ» 8 128 строк, ~7 100 в релизный exe не попадают.
- Проверка: `tools/build/build.ps1` (`Set-PlayerBuild`, `Assert-ExeNoBench`, `$BenchMarks=@('[AIPROBE] start')`, стр. ~368–411), `Выпуск/release.ps1` (`Get-BenchMark`, стр. 159–163, 290–292), `tools/test_player_build.py`, грабли R-336.
- Результат (измерено подсчётом): в `build-release/bin/openxcom.exe` и `dist/_stage/openxcom_hd.exe` маркеры `[AIPROBE]`, `[AIDECIDE]`, `[AISTATE]`, `[AIRESULT]` = **0**; в `build-ai/bin/openxcom.exe` они есть. Стенд ИИ в выпуск **не попадает**.
- Слабости проверки:
  1. Единственный маркер `[AIPROBE] start` (Log-строка `AiProbe.cpp:593`, внутри dev-части). Переименуют строку — проверка молча станет вечно зелёной. Нет теста на присутствие маркера в исходнике; `test_player_build.py` использует синтетические exe.
  2. Нет позитивного маркера «это игрок» (например, строки версии сборки `player`).
  3. Проверка не покрывает стенд обрушения (см. ниже) и `OXCE_HD_*` автоматику.
  Лечение: добавить 3–4 маркера из разных частей dev-кода (`[AIDECIDE]`, `[AISTATE]`, `[AIRESULT]` уже есть в build-ai — взять их), тест «каждый маркер найден в `build-ai` exe и в исходнике», проверка префикса `OXCE_COLLAPSE_` и `OXCE_AI_` в getenv. Усилие 2 часа.

### Стенд обрушения (дыра)
`standEnv()` (`CollapsePilot.cpp:817–822`) читает `getenv` для `OXCE_COLLAPSE_REMOVE/HIT/FIRE/BLAST/MODEL/UNIT/STUN/BIG/FLY/DROP`. `settle()` вызывает `debugStand(battle, save)` безусловно (стр. ~1668). Вокруг — `debugStand`, `debugParts`, `debugTiles`, `reportCarry`, `terrainHash`, ≈ 250–350 строк; под `#ifdef` только `standOnly`, `logClimb` и часть отчётов. Подтверждено подсчётом в `dist/_stage/openxcom_hd.exe`: «[COLLAPSE] debug» ×11, `OXCE_COLLAPSE_REMOVE` ×1. При включённой опции эти переменные реально меняют карту (снос частей, расстановка юнитов). Игрок с такой переменной окружения получит нестандартную карту; на практике риск низкий, но «в выпуске нет кода стенда» неверно. Лечение: обернуть в `#ifdef OXCE_AI_DEV` (или отдельный `OXCE_COLLAPSE_DEV`), маркер `[COLLAPSE] debug` добавить в проверку выпуска.

### Заглушки AiProbe в горячем коде (п.9)
- 247 вызовов `AiProbe::` в `AIModule.cpp` — пустые не инлайнящиеся заглушки (вызов через границу единицы трансляции).

Лечение: заглушки сделать `inline` в заголовке, строки собирать лямбдой под `#ifdef`. Выигрыш — оценка, замеров нет.

## 3. Ошибки, мёртвый код, дублирование, упрощения

### Мёртвый код (подтверждён по данным)
- `CollapseBlock::keep/nKeep` — во всех 956 блоках `nullptr/0`; цикл `foreignParts` по `b.nParts + b.nKeep` (`CollapsePilot.cpp:750`) эквивалентен циклу по `nParts`.
- `e1x/e1y` — константа 0 во всех частях; `CollapseCore.cpp:210` `if (P[i].nEdge > 1) props.add(x + e1x, y + e1y)` — недостижима (`nEdge ≤ 1`). Убрав поля, образ ужимается с 68 до 60 байт на часть (−2,9 МБ) даже без п.1. Осторожно: поля входят в `modelSig` (все 17 int) — при удалении подпись изменится, и сейвы с подписью разойдутся; нужно сохранить вклад констант в хеш (подмешивать 0 в FNV).
- Мёртвых именованных функций (не лямбд) не найдено; `#if 0` — только upstream/stb; TODO — 3, все не наши; сырых `new` без владельца не найдено.

### Надёжность
- `modelSig` не включает `treeCols/crowns`: правка деревьев/крон в таблице не меняет подпись, старый сейв не заметит расхождения. Низкая, но реальная дыра; менять подпись = ломать сейвы, решать с Vitali.
- «crown_trunc 176» в проверке целостности — ложное срабатывание: пустые `crowns` записываются как `-1`.

### Производительность
- `bind()` (`CollapsePilot.cpp:~845`): `upper(sets[s]->getName())` в цикле по 956 блокам × наборам сейва × k: оценка 57–172 тыс. вызовов с аллокацией на загрузку боя при включённой опции (≈ 5–20 мс). Кэш `upper` по набору — один проход.
- `scan()` на каждый ход перебирает блоки с `setsOnMap(bi)`; индекс «набор → блоки» строится один раз при загрузке (в `setuse.py` посчитано: топ-наборы покрывают сотни блоков) — упрощает п.1 и экономит повторные проходы. Замеров времени нет.
- Идея с риском для механики (не простая экономия): ранний выход в `settle()` при `nRemoved == 0` — нужен офлайн-пруф, что `evaluate(целое)` держит все INBOX-части. Не делать без пруфа.

### Дублирование
- `src/Savegame/Production.cpp`: 7 копий сравнения координат баз `fabs(lon) < 1e-7 && fabs(lat) < 1e-7` (стр. 465, 480, 634, 656, 703 + хелпер `findBaseAt` 411–421, использованный на 730 и 813). Свести к хелперу: −20…25 строк.
- В новых файлах дублей мало: 83 строки из 18 025 в окнах ≥ 8; в `AIModule.cpp` 164 из 7 224.
- Новые опции: из 92 новых строк `OPT` в `Options.inc.h` неиспользуемых нет (проверено, каждая встречается в коде за пределами `Options.cpp`).

### Окружение выпуска
