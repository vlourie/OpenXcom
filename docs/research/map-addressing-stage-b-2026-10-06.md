## 0. Короткий итог

1. **Источник правды** — состояние клеток из сейва (`map_truth.Battle`: `SET`/`ID` по частям). Сборка из
   MAP нужна только для двух вещей: найти клетки, изменённые в бою, и проверить устойчивость индекса
   [подсчёт]. Состояний, которых нет в 379 сейвах, не вводилось.
2. **Хватает двух механизмов**, оба выведены из данных:
   - **A_LINE** — 38 семейств стен: индекс по оси ряда;
   - **B_CELL** — 18 семейств предметов: индекс по клетке.

   Адресация относительно блока карты не нужна. Ряд через границу блока есть только у U_WALL_G (9–10%
   его клеток), а имена блоков в 127 сейвах устарели. Отдельный механизм «состояние в бою» тоже не
   нужен: ключ — текущий кадр клетки, а индекс зависит только от координаты.
3. **Индекс ADDRESSING_V1** — чистая функция `(x, y, z, часть, n)`, где `n` — число кадров вместе с
   основным. Без RNG, без номера кадра, без имён блоков, без соседей. Класс задаёт чётность по оси ряда
   с этажом (у предметов при `n ≥ 8` — раскраска 2×2), член класса задаёт хэш клетки.

   Что это даёт [подсчёт, расчёт]:
   - соседи по ряду и по вертикали никогда не получают один вариант: 0 из 21 598 пар по ряду и 0 из
     10 291 по вертикали на URBAN:69/70;
   - если вырушили соседнюю клетку, картинка не меняется: 0 изменений против 2 627 у индекса по месту
     в ряду;
   - у тех же сейвов боя один и тот же выбор: 2 020 из 2 020 клеток.
4. **Соседний контекст в индекс не входит.** Его заменяет контракт кромки: каждый вариант совпадает с
   основным HD-кадром попиксельно в полосе стыка. Без этого контракта адресация ломает углы: в углах
   URBAN:70 × URBAN:69 встречаются все 16 пар вариантов [подсчёт].
5. **Встраивание** — самое узкое место. Метка клетки ставится вокруг четырёх блитов в
   `Map::drawTerrain` (западная стена, северная стена, задний и передний объект). Выбор кадра идёт в
   уже существующей ветке вариантов `Canvas32::blit` (`HdCanvas.cpp:481`), с её откатом на основной
   кадр. У `Canvas8` метод пустой, поэтому классический кадр не может измениться по построению [код].
6. **Формат — F2**: `hd/<набор>/address.txt`, по образцу `color.txt`, со списком кадров, включённых в
   адресацию. Пишет его конвейер по переписи: 28 файлов, по строке в каждом. Неявное включение по
   наличию `.vN` отвергнуто: оно сразу изменило бы ROADS:0 на северных стенах и MOUNTGRASS:2 как
   предмет.
7. **Цена движка** — около 120 строк в трёх файлах плюс приёмка (IDENTICAL с контролем, замер
   `drawMs`/`flipMs`). Арт не заказывался. При `n = 4` на все 114 кадров с REPEAT это 342 картинки,
   при `n = 6` — 570.

**STOP.** Генерации HD-ассетов, правок `src/` и данных нет. Следующий шаг только по отдельному GO.

## 2. Контекст по семействам (пункт 1 ТЗ)

Расшифровка столбцов:
- **сам / семья / пусто** — каким оказывается сосед по оси ряда:
  - «сам» — тот же кадр;
  - «семья» — другой кадр того же семейства (окно, дверь, другой кусок стены);
  - «пусто» — соседа нет;
  - доля «тот же набор, другой слот» и «чужой набор» — в `family.tsv`, она не больше 20%.
- **ряд** — длина рядов одного кадра: медиана, 90-й процентиль, максимум.
- **концы** (у стен) — узлы на концах рядов: продолжение, угол, тройник, свободный конец.
- **форма** (у предметов) — сколько клеток стоят одни, в линию и в площади 2D.
- **над собой** — доля клеток, над которыми этажом выше стоит тот же кадр.
- **в бою иначе** — сумма трёх счётчиков:
  - клеток семейства, которые стоят не по MAP;
  - клеток MAP, ушедших в бою (вырушено или сменился кадр);
  - клеток, где по MAP другой кадр.

  Разбивка — в `family.tsv`.
- **особое** — кадры семейства, стоящие ещё и в другом слоте; ряды через границу блока; анимация.

Позиция внутри блока карты и координата клетки в таблицу не вынесены: позиция внутри блока на выбор
не влияет (см. 3.3), а координата — сам вход формулы. Для URBAN:69/70 они есть построчно в

## 3. Классы механизмов (пункт 2 ТЗ)

| класс | что покрывает | семейств | вход индекса | соседи без повтора |
|---|---|---|---|---|
| **A_LINE** | западные и северные стены | 38 | ось ряда: `y` у западной, `x` у северной; этаж `z` | по ряду и по вертикали |
| **B_CELL** | предметы: одиночные, линии, площади | 18 | `x`, `y`, `z` | по `x`, по `y`, по вертикали; при `n ≥ 8` ещё и обе диагонали |

Что было проверено и не нужно:
- **C — относительно блока карты.** Не нужно ни одному семейству. Вдобавок такой индекс зависел бы от
  `flattenedMapBlockNames`, а они устарели в 127 сейвах (дефект этапа A, 10.2).
- **D — по состоянию в бою.** Отдельный механизм не нужен. Ключ HD-кадра — указатель на текущий кадр
  клетки, поэтому вырушенная стена, открытая дверь или прорубка рисуются кадром нового состояния. Индекс
  от координаты при этом не меняется.

Ограничения (E) — это не механизмы, а правила контракта (раздел 11):
- **E1 — кадр и предмет, и пол.** JUNGLE:1 стоит предметом на 5 274 клетках и полом на 5 048,
  URBITS:19 — полом на 92. Если такой кадр рисуется полом, его `.vN` раскладывает узор пола
  (`groundFrameFor`, `HdCanvas.cpp:491`). Значит, вариант обязан годиться и для пола.
- **E2 — фазы анимации.** Сейчас таких кадров среди REPEAT нет, правило на будущее: у фаз одной
  анимации одинаковое `n`.
- **E3 — родня по семейству рядом** (окна, составные предметы). Закрывается полосой стыка.
- **E4 — этаж над этажом.** Тоже полоса стыка: верх и низ кадра.

### 3.1 Почему не индекс по месту в ряду

Индекс по месту в ряду (от начала, середина, конец) кажется естественным для длинной стены, но он
неустойчив. Ряд в сейве отличается от ряда в MAP, потому что в бою стены вырушают. Из 534 115
неизменённых клеток стен 2 627 (0.49%) сменили бы картинку посреди боя только потому, что вырушили
соседа; на URBAN:69/70 — 51 из 39 701 [подсчёт]. Индекс от координаты таких смен не даёт по построению.

### 3.2 Почему не соседний контекст в индексе

Выбирать вариант по соседям («на углу — угловой вариант») — это задача этапа D (`HD_TERRAIN_PLAN.md`).
Здесь она не нужна, и у неё та же беда неустойчивости. Стыки с соседями закрывает требование к
картинке (полоса стыка), а не выбор кадра.

### 3.3 Позиция внутри блока карты

На выбор не влияет: ряды через границу блока редки (U_WALL_G), а координата клетки уже различает
повторы одного блока в разных местах карты.

### 4.1 Предметы: почему у B_CELL раскраска 2×2

По 76 971 клетке предметов на кадрах с REPEAT, 378 боёв [подсчёт]. Индекс — по клетке `x + y + z` (V1)
или по раскраске 2×2 (класс `(x+z)&1 | ((y+z)&1)<<1`):

| соседство (тот же кадр) | пар | V1 n=4 | V1 n=6 | V1 n=8 | 2×2 n=4 | 2×2 n=6 | 2×2 n=8 |
|---|---|---|---|---|---|---|---|
| по оси x | 30 317 | 0 | 0 | 0 | 0 | 0 | 0 |
| по оси y | 35 113 | 0 | 0 | 0 | 0 | 0 | 0 |
| диагональ (1,1) — на экране прямо под | 16 553 | 51% | 34% | 25% | 0 | 0 | 0 |
| диагональ (1,−1) — на экране справа в том же ряду | 16 354 | 51% | 34% | 25% | 0 | 0 | 0 |
| вертикаль | 9 039 | 0 | 0 | 0 | 0 | 0 | 0 |

Обе диагонали изо-сетки на экране — ближайшие соседи, поэтому у площадей предметов (U_BASE, CULTIVAT)
повтор по диагонали заметен. Но у раскраски 2×2 при `n = 4` в каждом классе один член, и узор строго
периодичен с периодом 2 по обеим осям. Отсюда правило B_CELL:
- при `n ≥ 8` — раскраска 2×2 (два члена в классе, хэш выбирает);
- при `n < 8` — чётность V1, и повтор по диагонали тогда известен и принят.

Периодичность B_CELL при `n = 8` на линиях предметов не замерялась [не проверено].

## 7. Откат (пункт 6 ТЗ)

Отказ сломаться в каждом случае по отдельности [код, расчёт]:
- **Нет `address.txt` или кадр не в списке** — путь прежний, основной кадр.
- **`n = 1`** (нет ни одного `.vN`) — индекс 0, основной кадр.
- **Индекс указывает на пропуск в нумерации** (`.v1`, `.v3` без `.v2`). Слот пустой, `findVariant`
  вернёт `nullptr`, рисуется основной кадр. `variantCount` при этом считает и пустой слот, так что
  пропуск даёт дыру в разнообразии, но не сбой. Конвейер обязан писать варианты без пропусков, а его
  проверка — это ловить.
- **Вариант другого размера** — существующая проверка размера, основной кадр.
- **Файл варианта не читается** — ленивая загрузка вернёт пусто, основной кадр. Как именно ведёт себя
  `setVariantLazy` при битом PNG [не проверено].
- **Сгенерированный кадр** (`hd->generated`, xBRZ-откат) — адресация не применяется.

Ни в одном случае рендер не останавливается и не рисует пустоту.

- В `Map::drawTerrain` добавляются только вызовы `setCellAddress` вокруг блитов западной стены,
  северной стены, заднего и переднего объекта.
- Состояние клетки из сейва и из боя — единственная правда, в том числе для прорубки баз (контракт
  этапа A).

### 11.2 HD-рендер

Индекс считается так:

```
n  = variantCount(ключ) + 1          // основной + v1..vN; при n <= 1 -> 0
h  = fmix32(x*73856093 ^ y*19349663 ^ z*83492791 ^ часть*2654435761)   // uint32, murmur3 fmix
A_LINE (часть 1 - запад: a = y; часть 2 - север: a = x):
    cls = (a + z) & 1;  k = (n - cls + 1) / 2;  v = cls + 2 * (h % k)
B_CELL (часть 3):
    если n >= 8: cls = ((x+z)&1) | (((y+z)&1)<<1);  k = (n - cls + 3) / 4;  v = cls + 4 * (h % k)
    иначе:       cls = (x + y + z) & 1;  k = (n - cls + 1) / 2;  v = cls + 2 * (h % k)
```

Правила рендера:
- Индекс применяется только если одновременно:
  - кадр перечислен в `address.txt` своего набора;
  - `_frameVariant == 0` (огонь, кровь и руки ставят свой);
  - кадр не сгенерирован (`!hd->generated`);
  - включён режим паков (`_hdMode != HD_MODE_NEAREST`).
- Выбранный `v` идёт в существующий `findVariant` с проверкой размера; при неудаче — основной кадр
  (раздел 7).
- Индекс не зависит от номера кадра. Фазы анимации и состояния двери с одинаковым `n` берут одинаковый
  `v`.
- `Canvas8` метку игнорирует.

### 11.3 Генератор и конвейер

- **Набор кадров** — кадры с REPEAT из `census/maps/conflicts.tsv` в семействах ADDRESSING: 114 штук.
  Пилот — только URBAN:69/70.
- **Нумерация** — варианты `v1..v(n−1)` без пропусков, размер равен размеру основного HD-кадра.
- **`n`:**
  - для A_LINE на длинных стенах — не меньше 4, рекомендуется 6;
  - для B_CELL — 4–6, а для площадей (U_BASE, CULTIVAT, UFOAA_INT) рекомендуется 8: тогда работает
    раскраска 2×2 и нет повтора по диагонали.
- **Полоса стыка.** Каждый вариант попиксельно равен основному HD-кадру в полосе шириной `b` по краям,
  где спрайт перекрывается с соседями или примыкает к ним:
  - торцы стены по оси ряда — продолжение, угол, тройник, родня по семейству;
  - верх и низ — этаж над этажом;
  - у предметов — стороны, где есть соседи из семейства;
  - какие стороны касаются кого, берётся из `census/maps/adjacency.tsv` (связи E, S, U и тот же слот
    C).

  Ширина: `b = 2` пикселя базы, то есть `2k` пикселей HD; достаточно ли этого для глаза —
  [не проверено]. Внутри полосы меняется только содержимое: грязь, сколы, детали панелей. Силуэт и
  альфа равны основному кадру (R-005, R-089).
- **E1 — кадр и пол, и предмет** (JUNGLE:1, URBITS:19). Варианты попадут и в узор пола. В пилот не
  брать; если брать позже, вариант обязан пройти и проверку пола, и проверку предмета.
- **E2 — анимированный кадр** (на будущее). Все фазы получают одинаковое `n`, вариант `vi` всех фаз —
  одна вещь.
- **Двери и состояния (alt).** Если оба кадра состояния адресуются, `n` у них одинаковое, иначе
  открытая дверь сменит деталь. Кадр разрушения (die) — свободен.
- **Проверка до выпуска** (конвейер):
  - нумерация и размеры;
  - полоса стыка — 0 отличающихся пикселей;
  - `address.txt` перечисляет только кадры, у которых есть хотя бы `.v1`;
  - лист поля 9×9 по рядам из реальной карты (R-039).

### 11.4 Метаданные ассета

- **`hd/<набор>/address.txt`** — `version: 1` и `frames: <список с диапазонами>`. Пишет конвейер,
  руками не правят. Остальное выводится и не хранится: класс механизма (из части), число вариантов
  (из файлов), индекс (из координаты).
- **Обе копии мода hd** (репозиторий и установка Пираток) обязаны совпадать (R-087).
- **В отчёте конвейера на каждый кадр:** `n`, ширина полосы, результат проверки стыка.
