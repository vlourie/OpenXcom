# Анатомия родного ИИ боя OXCE (AIModule)
Дата: 2026-09-27 | Уверенность: высокая по коду AIModule.cpp/.h, средняя по инфраструктуре TileEngine/BattleUnit (часть путей не прослежена до конца)

## Краткий ответ

1. Один юнит думает **максимум 2 раза за ход** (`_AIActionCounter >= 2` в `BattlescapeGame::handleAI`, `src/Battlescape/BattlescapeGame.cpp:312`) — обычно "решить и пойти" + "решить и стрельнуть/добить".
2. Решение — четыре режима `AI_PATROL/AMBUSH/COMBAT/ESCAPE` (`AIModule::evaluateAIMode`, `AIModule.cpp:1800`), выбираются взвешенным `RNG::generate` из "odds", на которые влияют aggression, intelligence, здоровье, число видимых/известных/наблюдающих врагов, текущий режим (инерция), _AIMode может быть принудительно исправлен на COMBAT читерским режимом карты (`isCheating()`).
3. Главный источник "нечестного" знания — стат **intelligence** = число ходов, которое ИИ помнит **текущую (!) позицию** обнаруженного юнита (`BattleUnit::getIntelligence`, `src/Savegame/BattleUnit.cpp:4633`, коммент "number of turns an AI unit remembers a soldier's position"). Это официальная механика оригинала, не баг, но она даёт ИИ живую позицию юнита, а не запомненную точку.
4. Более грубые утечки — сознательные читы OXCE/OpenXcom, не связанные со stat'ами юнита: `sneakyAI` удваивает цену пути по клеткам, которые **видит любой юнит на карте** (`Pathfinding.cpp:277,1502`, комментарий в коде "make trouble for the AI (if sneaky)" в `BattleUnit::addToVisibleTiles`), а подбор оружия с земли (`BattlescapeGame::surveyItems`) сканирует **все** предметы, брошенные в этот ход, без проверки видимости.
5. Глобальный чит сложности — `isCheating()` (после 20-го хода или когда живых пришельцев ≤2): каждому пришельцу разом обнуляется таймер памяти по игроку (`SavedBattleGame.cpp:1539-1558`), и `evaluateAIMode` принудительно ставит COMBAT.
6. Инфраструктура памяти — два счётчика на юнита, **по каждой из трёх фракций отдельно**: `_turnsSinceSpotted[faction]` (обычная память) и `_turnsLeftSpottedForSnipers[faction]` (память "снайперов" через "споттеров", механика OXCE). Оба сохраняются в сейв, стареют на 1 при возврате хода к игроку (`updateTurnsSince`, `BattleUnit.cpp:4939`).
7. Слуха как источника информации для ИИ **нет** — ни звук выстрела, ни звук взрыва нигде не читается AIModule. Игрок узнаёт о невидимом стрелке только через направленный звук выстрела (`getSoundAngle`) и через центрирование камеры на снаряде при пропуске анимации; полноценно это не прослежено (см. "Чего не выяснил").
8. Роли различаются через ruleset юнита: `aggression`, `intelligence`, `isLeeroyJenkins` (безмозглый чарджер, отдельная ветка `dont_think`), `sniper`/`spotter` (OXCE, стрельба вне LOS по чужим наблюдениям), `waitIfOutsideWeaponRange` ("засадный" юнит не идёт вперёд без причины), `pickUpWeaponsMoreActively`.
9. Чего ИИ не делает вовсе: не использует осветительные ракеты (BT_FLARE нигде не упомянут в AIModule), не отступает раненых союзников (кроме себя — self-heal через `medikit_think`), не лечит других, не ломает стены специально, не координируется отрядом кроме как через `wayPointAction`/psi (по знанию всей команды) и через sniper/spotter обмен.
10. Резерв ОВ для реакции: `_reserve` выставляется только в режиме PATROL, зависит от `aggression` (0=aimed,1=auto,2=snap), используется в `BattlescapeGame::checkReservedTU` как процент от максимума ОВ (33/40/50%), а не абсолютное число (`BattlescapeGame.cpp:1383-1409`).

## Детали

### 1. Поток решения

**Вход.** `BattlescapeGame::handleAI(BattleUnit *unit)` (`src/Battlescape/BattlescapeGame.cpp:304`):
- если `_AIActionCounter >= 2` ИЛИ `!unit->reselectAllowed()` ИЛИ юнит только что очнулся от стана (`getTurnsSinceStunned() == 0`) — юнит больше не думает в этот проход, выбирается следующий юнит очереди (`_save->selectNextPlayerUnit`), при пустой очереди — конец хода фракции (строка 312-338).
- иначе прячет юнита (`setVisible(false)`), пересчитывает FOV вокруг себя (радиус 1, без полного пересчёта, строка 342), достаёт/создаёт `AIModule`, инкрементирует счётчик и зовёт `unit->think(&action)` (строка 365) — это `BattleUnit::think`, не напрямую `AIModule::think`.
- `BattleUnit::think` (`src/Savegame/BattleUnit.cpp:3387`): сначала `reloadAmmo()`, затем один раз за ход (`_aiMedikitUsed`) пытается вылечить/вколоть себе стимулятор через `medikit_think(BMT_HEAL)`/`medikit_think(BMT_STIMULANT)` в цикле "пока получается" (может использовать несколько аптечек подряд), и только потом `_currentAIState->think(action)` — собственно `AIModule::think`.
- Если `action.type == BA_RETHINK`, `handleAI` зовёт `unit->think(&action)` ещё раз (строка 367-371) — то есть за один вызов `handleAI` `AIModule::think` может отработать дважды подряд без расхода счётчика `_AIActionCounter`.
- После `think`, если оружия/патронов нет и юнит не игрок, `BattlescapeGame::findItem` (строка 384) ищет предмет на земле (см. утечку в разделе 2); если подобрали и `pickUpWeaponsMoreActively` — ещё один `unit->think` ("Re-Rethink", строка 388-394).
- Дальше `handleAI` превращает `action.type` в состояния: `BA_WALK` → `UnitWalkBState`; выстрел/бросок/удар/пси → `UnitTurnBState` + (`MeleeAttackBState` или `ProjectileFlyBState`) либо `PsiAttackBState`.

**`AIModule::think(action)`** (`AIModule.cpp:425`):
- Защита от зависания: если `_walkAbortCounter > 200`, обнуляет ОВ юнита (строка 428-431) — юнит просто перестаёт действовать.
- Собирает срез текущей ситуации на каждый вызов: `_knownEnemies = countKnownTargets()`, `_visibleEnemies = selectNearestTarget()`, `_spottingEnemies = getSpottingUnits(pos)`, `_reachable`/`_reachableWithAttack` через `Pathfinding::findReachable` (полный обсчёт достижимых клеток на каждый think!).
- Leeroy-юниты уходят в отдельную ветку `dont_think` (строка 486-490) — заряд на ближайшего видимого врага, без остальной логики (setup*, evaluate).
- Собирает `_attackAction`/`_ambushAction`/`_escapeAction`/`_patrolAction` через `setupEscape` (если есть наблюдатели), `setupAmbush` (если есть известные враги и нет ближнего боя), `setupAttack`, `setupPatrol` (строка 525-536) — **все четыре собираются на каждый think**, независимо от того, какой режим потом выберется.
- Пси-атака проверяется отдельно и с приоритетом: если `_psiAction.type != BA_NONE` и делай-разрешено по `getAIUseDelay` — выполняется немедленно, минуя `evaluateAIMode` (строка 538-547).
- `evaluate` (нужно ли пересчитать `_AIMode`) включается по условию, специфичному для текущего режима (строка 555-569): PATROL пересчитывает при виде/знании врага или 10% шанс, AMBUSH — если нет винтовки/нет ambush-точки/видит врага, COMBAT — если атака "не решена" (`BA_RETHINK`), ESCAPE — если больше никто не наблюдает или знаемых врагов не осталось. Плюс форс-пересчёт при подборе оружия, при >2 наблюдателях или здоровье <2/3, и всегда при `isCheating()` вне COMBAT.
- `evaluateAIMode()` считает "odds" (см. ниже) и рандомно выбирает режим, с подстраховками (`_AIMode == AI_COMBAT` без реальной атаки скатывается в PATROL/AMBUSH/ESCAPE по цепочке, строка 2005-2049).
- Финальный `switch(_AIMode)` заполняет `action` на выход. ESCAPE — `finalAction=true`, `desperate=true` (игнорирует новых замеченных врагов при ходьбе), поворот на месте в конце (`setHiding(true)`). AMBUSH — тоже `finalAction=true`, укладка кнеляется по `allowsKneeling`. PATROL — выставляет `_reserve` от aggression. COMBAT — если это ещё "иду в точку стрельбы" (`BA_WALK`), не тратит счётчик действия (`action->number -= 1`, строка 670), то есть переход + выстрел могут уложиться в один "тик" счётчика.
- В конце: если `action.type == BA_WALK` и цель совпадает с текущей позицией — превращает действие в `BA_NONE` (юнит "закончил" без хотьбы).

**setupPatrol()** (`AIModule.cpp:741`): движение по узлам патруля (`Node`, `.RMP`). Если дошли до цели — освобождает узел (`freePatrolTarget`), выглядывает в окно (`faceWindow`). Выбор следующего узла — `scout` (после хода >20/при cheat/если ранг узла 0/если стоит в огне: рыщет по ВСЕЙ карте) или "охранник" (только по связям текущего узла, `SavedBattleGame::getPatrolNode`, `SavedBattleGame.cpp:2312`): фильтрует по `TYPE_SMALL/TYPE_FLYING/TYPE_DANGEROUS`, занятости, огню, опасным клеткам, затем скаут берёт случайный подходящий узел, охранник — с максимальным `_flags` (приоритет патрулирования из редактора карт), с бонусом совпадения ранга юнита и ранга узла (`Node::nodeRank`). Отдельная ветка для base-defense: мелкие пришельцы целятся в объекты базы (`isBaseModule()`) через прямой обход клеток комнаты 9×9 либо идут к незанятому "целевому" узлу (`isTarget()`).

**setupAmbush()** (`AIModule.cpp:915`): нужен `selectClosestKnownEnemy()` (см. утечку). Перебирает узлы карты в радиусе 10 от юнита, отсеивает опасные/недостижимые-с-оружием клетки, берёт только те, где юнит НЕ виден цели (`canTargetUnit` от цели к клетке) и не замечен другими (`getSpottingUnits`). Считает "score" = 100 − стоимость_пути_ОВ (+25 бонус за окно как укрытие), и обязательно проверяет, что цель тоже может дойти до этой клетки (`_save->getPathfinding()->calculate(_aggroTarget, pos, ...)`) — то есть ambush ставится только там, где предсказуемо появление цели. После выбора клетки "виртуально" прогоняет цель по её собственному кратчайшему пути назад к текущей позиции и ищет первую точку, откуда юнит смог бы её обстрелять — это и становится `finalFacing`.

**setupAttack()** (`AIModule.cpp:1032`): если есть `_knownEnemies` — сперва пробует `psiAction()` (приоритетно, отдаёт return сразу при успехе), потом `wayPointAction()` (если есть бластер) либо, с шансом `getSniperPercentage()`, `sniperAction()` (снайперская стрельба по чужим "споткам"). Если снайпер не сработал и `selectNearestTarget()` вернул видимого врага — выбор melee/ranged (`selectMeleeOrRanged`), граната (`grenadeAction`), ближний бой (`meleeAction`), стрельба (`projectileAction`) — именно в этом порядке, и как только один из них проставил `_attackAction.type != BA_RETHINK`, остальные всё равно вызываются (нет early return), но выигрывает то, что записало `_attackAction` последним (реально порядок вызовов и есть приоритет: если после melee/ranged есть и граната, и рукопашка, и стрельба — итог тот, который выполнился последним и попал в условие, а не "лучший" по каким-то очкам). Если атаки нет вообще и (наблюдают враги или "по настроению" `aggression < random(0,3)`) — пробует найти огневую точку `findFirePoint()`.

**setupEscape()** (`AIModule.cpp:1123`): перебор до 150 случайных клеток вокруг (`_save->getTileSearch()`, 11×11, сначала систематически 121 вариант, потом 30 "отчаянных" со сдвигом по Z), score считается из: удаления от цели (может быть отрицательным, если новая клетка ближе), штрафа за число новых наблюдателей относительно текущего (`EXPOSURE_PENALTY=10`), штрафа за огонь (`FIRE_PENALTY=40`) и за "опасную" клетку (`getDangerous`, т.е. под грозящим взрывом гранаты, `-100`). Быстрый выход при `score > 100`.

**Огневые режимы.** `scoreFiringMode` считает `accuracy*shots*maxTU/tuCost`, честно учитывает дальность/дропофф и `checkLOF`. `extendedFireModeChoice` (только если в моде включён `getAIExtendedFireModeChoice()`) перебирает Aimed/Auto/Snap/Throw, добавляет рандом от intelligence (`AIFireChoiceIntelCoeff * max(10-intelligence,0)`, интеллект 10 = без рандома, интеллект 0 = ±50%) и бонус к автострельбе от aggression (`AIFireChoiceAggroCoeff`). Без extended-режима `projectileAction()` использует "ванильную" эвристику по дистанции (<4 клеток — автомат, >12 — прицельный, иначе — очередь/прицельный по наличию ОВ).

**Граната** (`grenadeAction`, `AIModule.cpp:2653`): берёт первую подходящую по `getAIUseDelay` гранату/proxy с пояса (`getGrenadeFromBelt`, не проверяет тип урона, т.е. не различает "убойную" и, потенциально, дымовую, если та имеет `BT_GRENADE`/`BT_PROXIMITYGRENADE` — не проверено, различает ли ruleset дым отдельным battleType). Целится либо в текущую позицию цели (`explosiveEfficacy`), либо (если невыгодно) в лучший узел по `getNodeOfBestEfficacy` (учитывает `turnsSinceSpotted <= intelligence` для окрестных юнитов). Для proxy сдвигает точку на соседнюю клетку, чтобы игрок не мог тут же откинуть её назад.

**Рукопашная** (`meleeAction`/`meleeAttack`): либо немедленный удар, если `_aggroTarget` уже в радиусе (`validMeleeRange`), либо "заряд" на ближайшего юнита, включая известных-но-невидимых (см. утечку), с оценкой "штрафа за уклонение" через `selectPointNearTarget` (учитывает `getMeleeDodgeBackPenalty`, атака сзади дешевле).

**Резерв ОВ и конец хода.** `_reserve` заполняется только в PATROL по aggression, читается `BattlescapeGame::checkReservedTU` (`BattlescapeGame.cpp:1383`) как ПРОЦЕНТ максимума ОВ (33/40/50% для snap/auto/aimed) — то есть пришелец резервирует не "на конкретный будущий выстрел", а фиксированную долю бюджета ОВ. Ход юнита кончается, когда `action.type` не приводит ни к чему исполняемому (`BA_NONE`) или AI_ESCAPE/AI_AMBUSH проставили `finalAction=true`.

**sneakyAI** (опция, по умолчанию выключена): не часть `AIModule`, а `Pathfinding` (`Pathfinding.cpp:181,277,1502`). Если включена и юнит `FACTION_HOSTILE`, стоимость шага в клетку удваивается, если `_save->getTile(nextPos)->getVisible()` истинно — это буквально "клетку сейчас видит **хоть кто-то** на карле" (см. раздел 2, это утечка, а не честное избегание).

### 2. Утечки знания

Формат: место → что читается → сила эффекта → чем заменить.

1. **`AIModule::countKnownTargets`** (`AIModule.cpp:1325-1340`) и **`AIModule::validTarget`** (`AIModule.cpp:2995-3016`) → идут по `_save->getUnits()` (ВСЕ юниты боя) и проверяют `getTargetAttackWeight(target) > 0` (или порог), где `getTargetAttackWeight` (`AIModule.cpp:2943-2986`) на строке **2952-2959** прямо гейтит по `_intelligence < target->getTurnsSinceSpottedByFaction(faction)`. Если условие ложно (юнит "известен"), функция возвращает вес БЕЗ проверки текущей видимости — а дальше везде, где используется этот "известный" юнит, читается его **текущая, реальная** позиция (`bu->getPosition()`), не позиция на момент обнаружения. Сила: высокая — это основа режимов AMBUSH/ESCAPE и части COMBAT (waypoint/psi/charge). Честная замена: хранить последнюю замеченную позицию отдельно от текущей и использовать её вместо `getPosition()`, пока юнит не будет увиден снова.
2. **`AIModule::selectClosestKnownEnemy`** (`AIModule.cpp:1481-1498`) → та же дыра, используется в `setupAmbush`, `findFirePoint`, `evaluateAIMode` (для решения "нужен ли escape"). Ambush дополнительно честно проверяет, что финальная точка не видна цели и не видна другим (`getSpottingUnits`) — но САМА цель для расчёта берётся по актуальной позиции.
3. **`AIModule::selectRandomTarget`** (`AIModule.cpp:1504-1522`) → используется в фоллбэке COMBAT (`evaluateAIMode`, строка 2020) — тот же принцип "известный = текущая позиция".
4. **`AIModule::meleeAction`** (`AIModule.cpp:2260-2307`), цикл "заряда" на ближайшего юнита (строка 2279-2297) → `validTarget(bu, true, true)` без проверки видимости, дистанция до 20 клеток, юнит реально "чует" и бежит к невидимому противнику, если тот "известен".
5. **`AIModule::wayPointAction`** (`AIModule.cpp:2361-2442`) → для бластера/waypoint-оружия перебирает всех `validTarget` юнитов без проверки прямой видимости самим стрелком (это отчасти по духу вида оружия — бластер традиционно бьёт "за угол" по команде наводчика, но здесь наводка идёт по позиции цели, известной just because "интеллект" не истёк, а не потому что кто-то из союзников её реально сейчас видит).
6. **`AIModule::psiAction`** (`AIModule.cpp:2723-2921`) → сознательно документировано в комментарии (строка 2718-2720: "Exposed means... regardless of whether we can see them or not, because we're psychic") — это НЕ баг, а объявленный дизайн: пси не требует LOS, если `!item->getRules()->isLOSRequired()`. Тем не менее и здесь используется актуальная позиция цели, а не последняя видимая.
7. **`AIModule::getNodeOfBestEfficacy`** (`AIModule.cpp:3117`) — при выборе узла под гранату проверяет `bu->getTurnsSinceSpottedByFaction(faction) <= _intelligence` для каждого юнита у узла — тот же принцип "временное окно + текущая позиция", но хотя бы честно проверяет условие на месте (не полагается на предвычисленный `validTarget`).
8. **`AIModule::selectSpottedUnitForSniper`** (`AIModule.cpp:1627-1694`) и снайперский стат — см. отдельный подраздел ниже. Опирается на `getTurnsLeftSpottedForSnipersByFaction`, отдельный от `_intelligence` канал.
9. **`Pathfinding::sneakyAI`-удвоение цены** (`Pathfinding.cpp:181, 277, 1502`) → цена шага в клетку удваивается, если `Tile::getVisible()` истинно, а этот флаг — счётчик "сколько юнитов ЛЮБОЙ фракции сейчас видят эту клетку" (`BattleUnit::addToVisibleTiles`, `src/Savegame/BattleUnit.cpp:2491-2500`, комментарий в коде прямо называет это "trouble for AI (if sneaky)"). Это чтение общего игрового состояния видимости, не собственного зрения юнита — при включённой опции чистый чит: пришелец знает геометрию текущего поля зрения ЛЮБОГО юнита на карте, не только тех, кого он сам видит. Сила: средняя (опция по умолчанию `false`, `Options.cpp:256`). Честная замена: убрать общий счётчик, использовать только зрение самого юнита +, возможно, зрение союзников-которых-он-видит.
10. **`BattlescapeGame::surveyItems`** (`BattlescapeGame.cpp:2665-2716`) → перебирает `*_save->getItems()` (ВСЕ предметы боя), фильтр — `getTurnFlag()` (брошен в текущий ход, любым) или включённый `pickUpWeaponsMoreActively`, БЕЗ проверки, видел ли ИИ-юнит момент падения предмета или видит ли клетку сейчас. Пришелец в одном конце карты может пойти поднимать оружие, упавшее с убитого товарища на другом конце, если оно "привлекательное" (`getAttraction()`) и ближе по формуле `attraction/(2*dist+1)`, чем всё остальное. Сила: низкая-средняя (обычно предметы падают рядом с боем, но при дальнобойных смертях эффект заметен). Честная замена: фильтровать по видимости клетки предмета юнитом на момент выбора цели.
11. **`SavedBattleGame::endTurn` — читерский режим** (`SavedBattleGame.cpp:1539-1558`): при ходе >`_cheatTurn` (20 по умолчанию, поле `_cheatTurn(20)`, конструктор `SavedBattleGame.cpp:75`) или живых пришельцев ≤2 и ход > `_cheatTurn/2`, выставляется `_cheating=true`; для КАЖДОГО живого юнита фракции игрока разом `bu->setTurnsSinceSpotted(0)` — то есть счётчик "по хостайл-фракции" обнуляется для ВСЕХ игровых юнитов одновременно, независимо от того, видел ли их хоть один пришелец. Это классический вэнильный "чит для добивания затянувшегося боя", задокументированное поведение OpenXcom, не скрытый баг. `evaluateAIMode` (`AIModule.cpp:1998-2001`) при `isCheating()` жёстко форсирует `AI_COMBAT`, а `think()` (строка 583-587) форсирует пересчёт режима при `isCheating() && _AIMode != AI_COMBAT`.
12. **`getTurnsLeftSpottedForSnipersByFaction`/спотер-снайпер** — см. отдельный подраздел; это не столько "утечка", сколько намеренная OXCE-механика "радио-наводки", но она тоже даёт стрелку знание текущей позиции цели без личного наблюдения, только по чужому "спотту".

**Механика sniper/spotter OXCE** (честна ли): в `TileEngine::calculateUnitsInFOV` (`TileEngine.cpp:1508-1515`), когда юнит `unit` (любой фракции) реально видит `bu`, помимо обнуления обычного таймера памяти этой фракции, ставится `bu->setTurnsLeftSpottedForSnipersByFaction(unit->getFaction(), max(unit->getSpotterDuration(), текущее))`. `getSpotterDuration()` (`src/Mod/Unit.cpp:369-373`) берётся из ruleset юнита (`spotter`, по умолчанию = `intelligence`, если `spotter == -1`). Дальше в `getTargetAttackWeight` (`AIModule.cpp:2952-2959`) юнит с непустым "снайперским" таймером считается ВИДИМЫМ для веса цели, даже если обычная память (`intelligence`) истекла, при условии `_unit->isSniper()` (ruleset-параметр `sniper`, `getSniperPercentage()>0`). Отдельно `AIModule::sniperAction`/`selectSpottedUnitForSniper` (`AIModule.cpp:1627-1694`) целиком строится на этом канале: собирает всех `bu` с `getTurnsLeftSpottedForSnipersByFaction(_unit->getFaction()) != 0`, оценивает лучший тип атаки (`extendedFireModeChoice` с `checkLOF=true` — то есть ЛИНИЯ ОГНЯ реально проверяется геометрически, стрельба не идёт "сквозь скалу") и стреляет С ШАНСОМ `RNG::percent(_unit->getUnitRules()->getSniperPercentage())` (`setupAttack`, строка 1054). Итог: это честная по духу "командная информация" (кто-то из команды реально видел цель в последние `spotterDuration` ходов), но стрелок опять же целится по ТЕКУЩЕЙ позиции цели, не по позиции на момент "спотта" — если цель после этого убежала за угол, стрелок всё равно наведётся на её новое место (утечка комбинируется с п.1).

### 3. Инфраструктура знания

- **`BattleUnit`** (`src/Savegame/BattleUnit.h:105,134`): `_turnsSinceSpotted[FACTION_MAX]` (Uint8, по умолчанию 255 = "никогда") и параллельный `_turnsLeftSpottedForSnipers[FACTION_MAX]`. Плюс `_visibleUnits`, `_unitsSpottedThisTurn` (не по фракциям — это "кого лично Я сейчас вижу/увидел в этот ход", используется в `calculateUnitsInFOV` для решения "нужно ли прервать ход юнита реакцией на нового врага"). Никакого поля "последняя увиденная позиция" в классе НЕТ (проверено грепом по `BattleUnit.h`) — то есть при "известности" всегда читается текущая `_pos`.
- **Сохранение/загрузка**: `_turnsSinceSpotted[FACTION_HOSTILE/PLAYER/NEUTRAL]` пишутся тремя отдельными ключами `turnsSinceSpotted`, `turnsSinceSpottedByXcom`, `turnsSinceSpottedByCivilian` (`BattleUnit.cpp:703-825`) — сохраняются в сейв честно, при загрузке восстанавливаются. `_turnsLeftSpottedForSnipers` — не проверено, сохраняется ли отдельными ключами (не найдено явного `reader/writer` для него в просмотренном диапазоне; см. "Чего не выяснил").
- **Обновление по ходу**: `BattleUnit::updateTurnsSince()` (`BattleUnit.cpp:4939-4949`) увеличивает оба массива на 1 (со стенкой 0..255) — вызывается из `SavedBattleGame::endTurn` (`SavedBattleGame.cpp:1554`) ТОЛЬКО когда сторона возвращается к `FACTION_PLAYER` (то есть раз за полный игровой ход, после того как отыграли и пришельцы, и нейтралы), для каждого юнита боя. Обнуление до 0 — точечное, при реальном обнаружении, в `TileEngine::calculateUnitsInFOV` (`TileEngine.cpp:1510`) и при попадании атакой (`BattleUnit.cpp:1961-1976`, если по юниту стреляли — он "спалился" перед атакующей фракцией даже без обычной проверки видимости, и OXCE-настройка `Mod::EXTENDED_SPOT_ON_HIT_FOR_SNIPING` может продлить это на снайперский канал тоже).
- **Смерть наблюдателя**: память хранится НА ЦЕЛИ (`_turnsSinceSpotted` — поле цели, не наблюдателя), поэтому смерть конкретного споттера её не сбрасывает — это общий "фракционный" факт, а не привязка к живому свидетелю. Не проверено явно, есть ли где-то код, который специально чистит эту память при гибели ВСЕХ юнитов фракции-наблюдателя (вероятно, нет смысла — играет роль только пока жив хоть кто-то этой фракции).
- **`Tile`**: `_visible` (`int`, инкремент/декремент, `Tile.cpp:997-1009`) — счётчик "сколько юнитов ЛЮБОЙ фракции видят эту клетку прямо сейчас", используется `sneakyAI`. `isDiscovered(TilePart)`/`setDiscovered` — это "туман войны" для отрисовки/игрока, отдельный от `_visible`; в `AIModule.cpp` не используется НИ РАЗУ (грепом не найдено) — ИИ полностью игнорирует туман войны при собственных геометрических расчётах (полный доступ к геометрии карты, что логично: карта у движка всегда полностью загружена в память).
- **Слух**: грепом по `Battlescape/*.cpp` не найдено ни одного механизма, который передавал бы AIModule информацию о звуке выстрела/взрыва как таковую (нет полей вроде `heardShotAt`, `noiseRadius` и т.п.). Единственное близкое: `TileEngine::setDangerZone` (`TileEngine.cpp:5933-5975`) помечает клетки вокруг взрыва/приземлившейся гранаты как `Tile::setDangerous(true)`, что читают `validTarget`/`setupEscape`/`selectPointNearTarget`/`grenadeAction` — вызывается из `ProjectileFlyBState.cpp:729` для ЛЮБОГО взрыва независимо от того, кто его устроил (игрок или пришелец) и видел ли его атакуемый юнит. Это не "слух" в строгом смысле, а мгновенное общее знание геометрии опасной зоны — тоже небольшая утечка, но привязанная к физическому явлению (взрыв), а не к скрытому состоянию юнитов.
- **Как игрок узнаёт о невидимом стрелке**: выстрел проигрывает направленный звук (`getMod()->getSoundByDepth(...)->play(-1, getMap()->getSoundAngle(_unit->getPosition()))`, `ProjectileFlyBState.cpp:544-548`) от позиции СТРЕЛКА (значит игрок слышит "откуда" стреляют, даже не видя source). При пропуске полёта снаряда (`cancel()`, `ProjectileFlyBState.cpp:895-913`) камера центрируется на текущей позиции снаряда, если она не на экране. Полный путь "видит ли игрок трассер, если не видит стрелка" не прослежен до конца (см. "Чего не выяснил").

### 4. Роли

Родной ИИ не имеет явного enum "роль снайпер/штурмовик/рукопашник/гранатомётчик/лидер" — поведение складывается из комбинации ruleset-полей юнита (`Unit`/`Armor`) и оружия на поясе:
- **aggression** (`Unit::getAggression`, `Unit.cpp:360`) — влияет на odds `evaluateAIMode` (combat vs escape), на резерв ОВ в PATROL (0=aimed/1=auto/2=snap, для >2 — линейная формула `Clamp`), на шанс автострельбы (`AIFireChoiceAggroCoeff`), на `meleeOdds` в `selectMeleeOrRanged` (агрессия 0 −20, агрессия >1 +10*aggr), на выбор мели/дистанции при выборе следующей клетки patrol (не проверено на 100%).
- **intelligence** (`Unit::getIntelligence`) — окно памяти о позиции цели (см. раздел 2), плюс демпфер рандома при выборе firing mode (`extendedFireModeChoice`).
- **`isLeeroyJenkins`** (`Unit.h:477`, `Unit::isLeeroyJenkins`) — юнит целиком уходит в `AIModule::dont_think` (`AIModule.cpp:147-203`): игнорирует setup*/evaluateAIMode, всегда бежит в ближний бой на ближайшего видимого врага (`selectNearestTargetLeeroy`/`selectPointNearTargetLeeroy`/`meleeActionLeeroy`), эти три функции сознательно "менее умные" версии обычных (не учитывают опасные клетки, remaining TU для чарджа, штраф уклонения) — комментарии в коде подтверждают (`AIModule.cpp:1575-1583`).
- **`sniper`/`spotter`** (OXCE, `Unit.cpp:369-382`) — см. раздел 2. `sniper` (0..100) — процентный шанс сработать снайперской веткой при известных врагах (`setupAttack`, строка 1054). `spotter` (−1 по умолчанию = равен intelligence) — на сколько ходов юнит, увидевший врага, "передаёт" его позицию снайперам своей фракции.
- **`waitIfOutsideWeaponRange`** (`Unit.h:478`, `Unit::waitIfOutsideWeaponRange`) — если true, `findFirePoint`/`projectileAction` НЕ пытаются подстроить дистанцию под оружие (используется для "засадных" юнитов вроде камуфлированных ниндзя, комментарий "e.g. ninja camouflaged in ambush", `AIModule.cpp:2504`).
- **`pickUpWeaponsMoreActively`** (`BattleUnit.h:907`) — снимает ограничение "подбираем оружие только если совсем нет видимых врагов" в `BattlescapeGame::findItem`/`worthTaking`.
- **`getAITargetWeightAsHostile/AsFriendly/AsNeutral/AsHostileCivilians`** (`Armor.h:275-281`, оверрайд на `BattleUnit.cpp:3436-3467`) — вес юнита как цели атаки/AoE меняется по броне, это ближайший аналог "этот юнит важная цель" (например, командиры/лидеры со специальной бронёй получают более высокий вес и потому активнее выбираются целью для гранат/AoE).
- Явного "лидер отдаёт приказы" нет — координация только через `wayPointAction`/`psiAction` (используют общее для фракции знание "известных" целей) и spotter/sniper канал.

### 5. Чего ИИ не умеет

- **Осветительные ракеты / свет**: `BT_FLARE` не встречается в AIModule.cpp вообще (грепом подтверждено) — ИИ никогда не бросает и не использует осветительные средства.
- **Дым**: `grenadeAction` не различает типы урона гранаты — берёт первую по `getAIUseDelay` из `isGrenadeOrProxy()`, оценка через `explosiveEfficacy` считает "сколько врагов заденет", что для дымовой гранаты (если она в рулсете имеет `battleType: BT_GRENADE`) может дать бессмысленный или случайный результат — не проверено, отфильтровывает ли `explosiveEfficacy`/ruleset дымовые гранаты отдельно.
- **Пролом стен**: нет кода, который выбирал бы взрыв ради пробития стены как тактику (только явные цели — юниты, база — `_foundBaseModuleToDestroy` для объектов базы в base-defense).
- **Отход раненых союзников**: `medikit_think` лечит/колет ТОЛЬКО себя (`BattleUnit::think`, `self = _unit`), нет кода передачи аптечки другому юниту или конвоирования раненого назад.
- **Лечение других**: не найдено.
- **Подбор оружия**: ЕСТЬ (`findItem`/`surveyItems`/`worthTaking`), но, как показано в разделе 2, использует глобальное знание о всех брошенных предметах без проверки видимости.
- **Взаимодействие в отряде**: ограничено обменом "известных" целей через общие по фракции таймеры (`_turnsSinceSpotted`/`_turnsLeftSpottedForSnipers`) и `wayPointAction`/`psiAction`; нет явной координации (например, "прикрой меня", синхронной атаки нескольких юнитов на одну цель, распределения целей между юнитами одной фракции в один ход).

## Чего НЕ выяснил

- Сохраняется ли `_turnsLeftSpottedForSnipers[...]` в сейв отдельными ключами (не найдено явного `reader/writer` для него рядом с `_turnsSinceSpotted` в просмотренном диапазоне `BattleUnit.cpp:700-825`) — не проверил весь `load`/`save` файла целиком.
- Полный путь "видит ли игрок трассер снаряда, если не видит стрелка и не видит клетки вылета" — не прослежен целиком по `Projectile`/`Map::drawTerrain`; есть только звук (`getSoundAngle`) и центрирование камеры при пропуске хода. Не проверено, рисуется ли сам снаряд, если ни одна клетка его траектории не в текущем FOV игрока.
