# Инфраструктура для честного ИИ: что уже есть в движке

Дата: 2026-09-27 | Уверенность: высокая для мест кода (даны файл:строка); средняя-низкая для оценки, чего не хватает — это чтение существующего кода, не проверка в игре

## Краткий ответ

1. Плена именных бойцов игрока в OXCE/Пиратках НЕТ: боец, оставшийся без сознания при провале миссии, просто помечается MIA и удаляется из состава (`SavedGame::killSoldier`, cause=null) — правило (в) хозяина проекта опереться не на что, событие «пленили бойца в такой-то броне» придётся создавать с нуля.
2. Знание «фракция видит цель» уже фракционное и мгновенное по конструкции: `BattleUnit::_turnsSinceSpotted[FACTION_MAX]` пишется НА ЦЕЛЬ любым увидевшим её юнитом чужой фракции и не хранит, кто именно её засёк — поэтому оно не может быть отозвано при гибели наблюдателя (структурный пробел под правило (б)).
3. Позиция цели для ИИ всегда живая (`target->getPosition()`), «последней известной позиции» и её возраста в коде не существует — без неё нельзя честно оценить ни местоположение, ни скорость врага (правила б, г).
4. Звук в движке — чисто аудио-эффект: не имеет игровой дальности, не глушится по расстоянию (`distance` всегда 0), угол считается как проекция на экран относительно камеры, а не как честный пеленг по игровым координатам. Понятия «слышимость» как игровой механики в коде нет вовсе.
5. Что игрок видит про невидимого стрелка, кроме звука, тоже определено кодом: трасса и происхождение выстрела рисуются только если исходная клетка выстрела видна игроку (`Map::_projectileInFOV`); иначе — молчаливый «скрытый ход» плюс стерео-щелчок без указания дальности.
6. Оружие в руках видимого юнита читается тем же геттером, что рисует спрайт игроку: `BattleUnit::getRightHandWeapon()/getLeftHandWeapon()` — с этим для «честного» ИИ проблем нет, если юнит-цель в списке `_visibleUnits` наблюдателя.
7. Место в кампании для персистентного знания фракции есть готовое: `SavedGame::_scriptValues` уже сохраняется/загружается и открыта для скриптов; для сложных структур (множество ID брони и т.п.) годного шаблона не нашёл — нужен обычный C++-член с `tryRead/tryWriteAs` по образцу `BattleUnit::save/load`.
8. Добавление необязательного поля в сейв безопасно в обе стороны: `YamlNodeReader::tryRead` ищет узел по имени ключа и не проверяет лишние/отсутствующие ключи — старая сборка новый ключ просто не спросит, новая сборка на старом сейве получит `false` от `tryRead` и обязана сама подставить default.

## Детали

### 1. Плен бойцов игрока

- При провале миссии (`aborted`) боец игрока без сознания или не дошедший до точки выхода получает `STR_XCOM_OPERATIVES_MISSING_IN_ACTION`, ему выставляется `bunit->getStatistics()->MIA = true`, и вызывается `save->killSoldier(true, soldier)` — `DebriefingState.cpp:1710-1732`.
- `SavedGame::killSoldier(resetArmor, soldier, cause=nullptr)` — `SavedGame.cpp:2999-3028` — переносит `Soldier*` из состава базы в `_deadSoldiers` через `soldier->die(new SoldierDeath(*_time, cause))`; `cause == nullptr` в комментарии над функцией явно помечен как «NULL if missing in action» (`SavedGame.cpp:2997`). Это окончательное удаление из активного состава, а не «плен» с сохранением статов у противника.
- Если ВСЕ бойцы игрока без сознания (не при отступлении), происходит `bu->instaKill()` для каждого — `DebriefingState.cpp:1391-1413`, комментарий в коде: «if all our men are unconscious, the aliens get to have their way with them» — то есть тоже смерть, не плен.
- `capturable` (`BattleUnit.h:194`, `BattleUnit.cpp:500,5856`; `Unit.h:475`, `Unit.cpp:113,196,208,468`) — это направление «игрок берёт ПРИШЕЛЬЦА живым для research» (`_capturable && corpseBattlescape.isRecoverable() && spawnUnit==nullptr`, `Unit.cpp:196`), не обратное.
- В `.index/mod/Piratez/rul/values.tsv` слово «captur» встречается только в: медали `STR_MEDAL_CARREER_CAPTURES` (за оглушение пришельцев игроком), предмете/research `STR_POLTERGEIST_CAPTURE` (не про бойцов) и поле `units[].capturable` (тоже про пришельцев, у `STR_14MM_LIGHT_TURRET` и подобных стоит `false`). «prisoner/hostage/abduct» встречаются только в лорных `alienDeployments` (миссия `STR_ALIEN_ABDUCTION` — абдукция мирных НПС для сюжета, не игровых бойцов), в событиях с фоном `PRISONERS1_BACKGROUND.SCR`/`HOSTAGELOVE_BACKGROUND.SCR` и в броне `STR_NEKO_PRISONER_ROBE_UC` — это геоскейп-событийная система набора НОВЫХ рекрутов, а не превращение существующего именного бойца в пленника с сохранением его брони/статов для памяти ИИ.
- Вывод: под правило (в) нужно проектировать новую механику — например, перехват момента ещё ДО `killSoldier` в `DebriefingState.cpp:1730`, пока `soldier`/`bunit` ещё живы как объекты и `soldier->getArmor()` доступен.

### Место в сейве кампании для знания фракции

- `SavedGame` уже содержит `ScriptValues<SavedGame> _scriptValues` (`SavedGame.h:179`), которая сохраняется и загружается через `reader/writer` с `mod->getScriptGlobal()` (`SavedGame.cpp:693` и `896`) и зарегистрирована для скриптования: `sgg.addScriptValue<&SavedGame::_scriptValues>()` (`SavedGame.cpp:3688`). Это готовый, уже сериализуемый контейнер именованных тегов, доступный из ruleset-скриптов, без правки формата сейва — но не проверял, какие типы данных `ScriptTag` поддерживает и можно ли туда положить что-то сложнее одиночного скаляра (флаг на каждый тип брони, вероятно, заведётся отдельным тегом на тип, но список типов брони Пираток нужно объявлять заранее в scripts-рулсете — деталей не смотрел).
- Для структур сложнее набора именованных скаляров (например, произвольное множество ID) естественный путь — обычный C++-член на `SavedGame` с ручным `save()/load()` по образцу `BattleUnit::save/load` (см. ниже про `tryWriteAs`), а не через ScriptValues.

### Совместимость сейва при добавлении необязательного поля (проверено по коду)

- Чтение в проекте идёт через обёртку `YamlNodeReader` (`src/Engine/Yaml.h`, поверх rapidyaml/ryml, судя по типам `ryml::csubstr`/`ryml::NodeRef` — не через yaml-cpp напрямую; замечание в `docs/RAKES.md` R-046 про «yaml-cpp» относится, по всей видимости, к загрузке РУЛСЕТОВ, а не сейвов — эти две системы я не сверял окончательно, см. «Чего не выяснил»).
- `YamlNodeReader::tryRead(key, out)` (`Yaml.h:448-462`) ищет ребёнка ПО ИМЕНИ КЛЮЧА через `getChildNode(key)` и возвращает `false`, если узла нет; это не итерация по всем ключам мапы и не строгая схема — лишние/отсутствующие ключи не вызывают ошибок сами по себе.
- `YamlNodeReader::readNode(key, out)` без default (`Yaml.h:391-398`) — бросает исключение `throwNodeError("missing node ...")`, если `tryRead` вернул `false`. Этот вариант НЕЛЬЗЯ использовать для нового необязательного поля — старые сейвы упадут при загрузке.
- `YamlNodeReader::readNode(key, out, defaultValue)` (`Yaml.h:400-405`) — при отсутствии узла молча подставляет default. Это правильный шаблон для нового поля.
- На запись уже используется идиома «не пишем поле, если оно равно значению по умолчанию»: `writer.tryWriteAs<int>("turnsSinceSpottedByXcom", _turnsSinceSpotted[FACTION_PLAYER], 255)` (`BattleUnit.cpp:823`) — таким же способом стоит добавлять новые поля памяти ИИ.
- Итог: старая сборка на новом сейве — лишний ключ просто никогда не запрашивается, ошибки нет. Новая сборка на старом сейве — обязательно нужен `default` в `tryRead`/`readNode`, иначе либо исключение (при строгом `readNode`), либо непредсказуемое поведение (не проверял, что тип возвращает `tryRead` при отсутствии узла без default — по коду это `false` и `outputValue` не трогается, то есть остаётся тем, что было до вызова — обычно значением по умолчанию из конструктора класса).

### 2. Формат сейва боя

- Видимость на `BattleUnit` (`BattleUnit.h:105-107,134-136`):
  - `_visibleUnits`, `_unitsSpottedThisTurn`, `_visibleTiles`/`_visibleTilesLookup` — рабочие списки, пересчитываются каждый `calculateFOV`; не нашёл их сериализации в `save()`/`load()` (грепал только по `turnsSinceSpotted`/сохранению — за полный список сохраняемых узлов `BattleUnit::save` не проверял, см. «Чего не выяснил»), то есть считать их runtime-only, не персистентными между сохранениями партии.
  - `Uint8 _turnsSinceSpotted[FACTION_MAX] = {255,255,255}` и `Uint8 _turnsLeftSpottedForSnipers[FACTION_MAX]` — ЭТИ персистентны: пишутся под четырьмя ключами `"turnsSinceSpotted"` (индекс `FACTION_HOSTILE`), `"turnsLeftSpottedForSnipers"` (тот же индекс), `"turnsSinceSpottedByXcom"`/`"turnsLeftSpottedForSnipersByXcom"` (индекс `FACTION_PLAYER`, с default 255/0), `"turnsSinceSpottedByCivilian"`/`"turnsLeftSpottedForSnipersByCivilian"` (индекс `FACTION_NEUTRAL`) — `BattleUnit.cpp:821-826`.
- Куда естественно ляжет память ИИ: по аналогии с `_turnsSinceSpotted[FACTION_MAX]` (массив по числу фракций, сериализуемый строка-на-фракцию с default) — новая память «последняя известная позиция/ход наблюдения» ложится тем же паттерном на `BattleUnit` (например `Position` + `Uint8`/`int` номер хода на фракцию). Это моя аналогия по образцу существующего кода, не проверенное решение — не проверял, как это соотносится с юнитами размером 2x2 (у которых `getArmor()->getSize()>1`, `TileEngine.cpp:1479-1484`), и не проверял вместимость `Uint8` для номера хода на длинных миссиях.
- Структурный вывод (подтверждён кодом, важен для правил б/г): `_turnsSinceSpotted` хранится НА ЦЕЛИ и индексируется ТОЛЬКО фракцией наблюдателя — `TileEngine.cpp:1510`: `bu->setTurnsSinceSpottedByFaction(unit->getFaction(), 0)`, без id самого `unit`. Значит:
  - это уже фракционное, не персональное знание — один увидевший враг «рассекречивает» цель для всей своей фракции сразу, это и есть текущий (уже «нечестный» по меркам задачи) механизм принятия решений ИИ: `AIModule.cpp:2953`, `Pathfinding.cpp:645`;
  - при гибели наблюдателя (`UnitDieBState.cpp:90`: `_unit->clearVisibleUnits()`) отметка `turnsSinceSpotted`, которую он поставил на цели ДО смерти, не отменяется и структурно не может быть отменена — не хранится, кто её поставил.

### 3. Слух

- `Sound::play(channel, angle, distance)` (`src/Engine/Sound.cpp:76-93`) вызывает `Mix_SetPosition(chan, angle, distance)` только если включён `Options::StereoSound`; `distance` по умолчанию `0` (`Sound.h:63`) и НИ В ОДНОМ месте вызова в `src/Battlescape/*.cpp` (`BattlescapeGame.cpp:400,1828,3297`; `ProjectileFlyBState.cpp:516,544,548,587,591,710`; `UnitDieBState.cpp:356`; `UnitTeleportingState.cpp:155`; `UnitWalkBState.cpp:347,351,589`; `UnitTurnBState.cpp:80`; `BattlescapeState.cpp:1957`) третий аргумент не передаётся — звук всегда играет на полную громкость независимо от расстояния до слушателя.
- Угол считается не по игровым координатам «слушатель-источник», а по экрану: `Map::getSoundAngle(pos)` (`Map.cpp:3272-3287`) — `_camera->convertMapToScreen(pos, &relativePosition)`, клампится к половине ширины экрана и переводится в диапазон 360°±80° для `Mix_SetPosition`. Это стереопанорама «слева/справа от текущего положения камеры», а не честный пеленг игровыми клетками.
- Понятий «слышимость», «радиус слуха», «шум» как игровой (не аудио) механики в `src/` не нашёл — поиск `hearing|hearSound|noiseLevel|alienNoise` по всему `src` не дал результатов. Это значит: сейчас никакой код ИИ или сейва этот сигнал не читает, вводить его придётся с нуля, включая формулу дальности.
- Что игрок видит про невидимого стрелка, кроме звука: `Map::draw` (`Map.cpp:483-538`) вычисляет `_projectileInFOV`: если сторона хода — игрок, всегда `true`; если ход противника — `true` только если тайл `_projectile->getPosition(0).toTile()` (место вылета) `t->getVisible()` (`Map.cpp:486-490`). При `_projectileInFOV == false` трасса не рисуется, камера не едет к стрелку (`_followProjectile`, `Map.cpp:1332-1338`); есть отдельная, более сложная логика для случая, когда снаряд ПОПАДАЕТ по видимому бойцу игрока (`ignoreAllButAlliesHits`/`hitExplosion`/опции `Options::QOL::dontTraceProjectiles`, `Map.cpp:495-534`) — не разбирал её до конца. Итог для честной оценки: без QOL-упрощений и без прямой видимости позиции стрелка игрок обычно не получает ничего, кроме направленного на экран стерео-щелчка без указания дальности.
- Что можно честно дать ИИ: раз готовой формулы «радиус слышимости оружия» в движке нет, для симметрии с тем, что получает игрок разумно давать ИИ направление события без точной позиции и без гарантии дальности — но конкретную величину (радиус, погрешность) я не нашёл нигде в коде и не подтверждаю числом.

### 4. Передача знания

- ФОВ считается индивидуально на юнит: `TileEngine::calculateFOV(BattleUnit*, ...)` (`TileEngine.cpp:1676`) вызывается для каждого юнита в `TileEngine::recalculateFOV()` (`TileEngine.cpp:5770-5776`, цикл по `_save->getUnits()`), у каждого юнита свои `_visibleUnits`/`_visibleTiles`.
- Но становится фракционным знанием мгновенно через побочный эффект того же расчёта: как только `unit` (любой юнит фракции) видит `bu`, движок сразу пишет `bu->setTurnsSinceSpottedByFaction(unit->getFaction(), 0)` (`TileEngine.cpp:1500-1515`). Другие юниты той же фракции читают это прямо с цели при принятии решений — `AIModule.cpp:2953` (`getTargetAttackWeight`), `Pathfinding.cpp:645` (обход/готовность реагировать на клетке).
- Если наблюдатель гибнет в том же действии, где заметил врага: `turnsSinceSpottedByFaction=0`, записанный на цели ДО его смерти, не откатывается — фракция «знает» о цели ровно так, как будто наблюдатель жив, пока `getIntelligence()` думающего юнита не станет меньше значения счётчика, который растёт на 1 в начале каждого хода (`BattleUnit::updateTurnsSince`, `BattleUnit.cpp:4939-4949`).
- Реакционный огонь (`TileEngine::checkReactionFire`, `TileEngine.cpp:2497-2546`) сам пересчитывает `getSpottingUnits(unit)` заново в момент срабатывания (живую видимость на этот момент) — для самого триггера кэш не используется, но результат («кто стрелял») тоже не создаёт отдельной записи поверх общего `turnsSinceSpottedByFaction`.

### 5. Скорость хода врага

- Явного хранения «сколько клеток враг прошёл за ход» не нашёл ни в `AIModule.h/.cpp`, ни в `BattleUnit.h` — искал по смыслу полей, не проверял исчерпывающе весь `AIModule.cpp` построчно (см. «Чего не выяснил»).
- Позиции, которыми оперирует ИИ при выборе цели (`AIModule::selectNearestTarget`, `AIModule::getTargetAttackWeight`, `AIModule::getSpottingUnits` — все в `AIModule.cpp`), берут ЖИВУЮ `bu->getPosition()`/`target->getPosition()`, а не запомненную на момент последнего наблюдения. Отдельного «last seen position» нет — см. пункт 4: `_turnsSinceSpotted` это только счётчик «прошло N ходов», не координата.
- Вывод: величин, из которых можно было бы честно посчитать скорость (клетка + номер хода последнего наблюдения), в движке сейчас НЕ сохраняется нигде — это придётся вводить с нуля, по аналогии с `_turnsSinceSpotted[FACTION_MAX]` (пункт 2).
- Юнит хранит свои `_tu` (текущие) и максимум через `RuleArmor`/`Unit` статы — это не то, что визуально видит игрок в бою (только через Ufopaedia/Stats for Nerds после исследования юнита) — не проверял, есть ли отдельная «явно исследованная» отметка про конкретный тип юнита, которая разрешила бы ИИ читать это значение по аналогии с тем, что доступно игроку.

### 6. Оружие врага

- Видно, и это ровно то, что видит игрок: `UnitSprite::draw` (`UnitSprite.cpp:183-202`) вызывается `Map` только для юнитов, которые уже отрисовываются (видимых на экране), и использует `_unit->getRightHandWeapon()` / `_unit->getLeftHandWeapon()` через `getIfVisible(...)` (`UnitSprite.cpp:201-202`) для выбора спрайта оружия.
- Значит `BattleUnit::getRightHandWeapon()`/`getLeftHandWeapon()` → `BattleItem::getRules()->getType()` — прямой честный источник «что за оружие в руках», если юнит-цель есть в `_visibleUnits` наблюдателя (то есть действительно виден).
- Не проверял, отличается ли то, что визуально узнаёт игрок по спрайту (например заряженный тип боеприпаса, подствольник) от того, что вернёт `getRules()` — возможно, движок «знает» больше деталей оружия, чем можно различить на глаз по спрайту.
