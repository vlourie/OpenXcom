не изменено ничего, формат сейва не тронут. Все диагностические вставки и прототипы стоят в копии исходников вне
репозитория (`E:\OXCE_AuditDiag\savebench`, снимок коммита `2c1dff5ae`), игра запускалась только на невидимом стенде.

Соседний документ `AUDIT05_ROOT_CAUSES.md` (другая сессия, тот же день) ведёт классы дефектов К1–К7 и пакеты
исправлений. Здесь он не повторяется: этот документ — «пакет 3. Сохранения» из его таблицы плюс разбор цепочки
возникновения для каждой находки.

## 1. Главное

1. **Узкое место записи — не клетки и не диск, а дерево YAML.** Весь сейв сначала строится в памяти как дерево
   (144 байта на узел), и дерево растёт удвоением с копированием. На развитой кампании (36,5 МБ, 2,1 млн узлов)
   запись занимает 597 мс, из них 396 мс — построение дерева и 166 мс — выдача текста; пик памяти 895 МиБ, выделено
   1,28 ГиБ.
2. **Два прототипа без смены формата** (место под дерево заранее + выдача текста за один проход) дают на том же
   сейве 597 → 256 мс и пик 895 → 362 МиБ. Обычные сейвы всех восьми наборов **побайтно совпали** с базой.
3. **Буфер клеток (`calloc` на всю карту) и Base64 — не проблема**: 0,3–0,5 мс и до 1 МБ на самой большой карте.
   Прототип «буфер только под непустые клетки» выигрыша не дал (лишний проход по клеткам), предлагать его не буду.
4. **Размер файла определяет дневник бойцов**: 52–64 % в обычной кампании, 83 % в развитой (30,4 МБ из 36,5).
   В обороне базы — предметы склада, записанные по одному: 73 % (7,6 МБ, 43 428 предметов).
5. **Опция `oxceCompactSave` уже решает почти всё**, но выключена по умолчанию: файл в 7–15 раз меньше,
   запись развитой кампании 597 → 228 мс, загрузка 288 → 153 мс, пик памяти при записи 895 → 131 МиБ.
   На маленьких сейвах выигрыша по времени нет или небольшой минус (оборона базы 159 → 182 мс).
6. **Загрузка**: 55–65 % времени — разбор YAML. Отдельная находка: каждая строка ошибки в журнале стоит около
   4,4 мс (файл журнала открывается и закрывается на каждую строку); сейв с сотней битых ссылок грузится на 70–170 мс
   дольше только из-за этого.
7. Со сменой формата (нужно согласование) самый большой выигрыш — записи об убийствах в дневнике и предметы
   обороны базы; варианты и оценка совместимости — в разделе 7.

## 5. Ответы на отдельные вопросы задания

- **`calloc` полного массива клеток в `SavedBattleGame::save`.** 23 байта на клетку; на карте 80×60×9 — 0,99 МБ,
  время заполнения 0,5 мс при записи в 17,7 мс. Причина полного размера — число непустых клеток заранее неизвестно.
  Прототип «сначала посчитать непустые, выделить ровно под них» медленнее (0,28 → 0,56 мс на `start`): второй проход
  по клеткам дороже обнуления. **Вывод: не трогать.**
- **Запись непустых клеток.** Работает как задумано: пишутся только клетки, для которых `isVoid()` ложно.
  Замечание описи: `Tile::isVoid()` (`Tile.cpp:292`) не смотрит на огонь — клетка с огнём, но без объектов, дыма
  и предметов не записалась бы. Бывает ли такая клетка в игре, **не проверено** (при поджоге дым ставится вместе
  с огнём).
- **Base64.** 0,06–1,2 мс; раздувает клетки на треть (30,7 байта текста на 23 байта данных). При сжатом сейве эта
  треть возвращается сжатием. Отдельной оптимизации не заслуживает.
- **Проходы и промежуточные буферы.** Лишние: первый «мерный» проход выдачи текста (звено 7), копия тела при
  склейке с заголовком (звено 9), копии дерева при росте (звено 4). При загрузке: копия текста в арену (звено 13)
  и два прохода Base64 (звено 14, доли миллисекунды). Первые три убираются без смены формата — раздел 6.

## 6. Прототипы «до / после» (формат не меняется)

Один и тот же файл игры, поведение переключается переменной окружения (`tools/savebench_opt_patch.py`):
**1** — место под узлы и арену заранее (по размеру прошлой записи); **2** — выдача текста за один проход сразу
в итоговую строку; **1+2+8** — оба плюс буфер клеток под непустые.

- Прототип 1: формирование 396 → 138 мс (late), 98 → 45 мс (basedef); выделено 1 282 → 397 МиБ.
- Прототип 2: выдача текста плюс склейка 175 → 92 мс (late), 54 → 28 мс (basedef).

- Прототип 8 отдельной пользы не показал (раздел 5).

**Сверка.** Обычные сейвы: 8 из 8 наборов во всех трёх вариантах побайтно совпали с базой (тело от строки `---`
до конца файла; `evidence/SAVE/compare.tsv`). Сжатые сейвы: 3 набора совпали во всех вариантах; в остальных пяти
распакованное тело отличается в одном или двух вариантах, и только строкой `animFrame` (±1 кадр анимации), а у `geo`
— координатами летящих объектов: между записью обычного и сжатого сейва на стенде шло время игры. К прототипам это
отношения не имеет (тот же разброс есть в варианте 1, который выдачу текста не трогает), но **побайтным
доказательством для сжатых сейвов этих пяти наборов считать нельзя** — нужен повтор на остановленном времени.

Оговорки: в прототипе размер берётся из прошлой записи в том же процессе; для первой записи после запуска нужен
другой источник оценки (число узлов дерева при загрузке — оно почти равно числу узлов при записи: 2 118 448 против
2 118 529). В выпускной код это не переносилось и не оформлялось.
