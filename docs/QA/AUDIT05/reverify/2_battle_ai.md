## 1. Коммит 9bb60528b — A2, бросок при нулевой силе (AUD05-014)

- **Файл:строка (HEAD):** `src/Battlescape/ProjectileFlyBState.cpp:985-1013` (`getMaxThrowDistance`, ранний выход на 987-991);
  единственный вызов — `validThrowRange`, строка 968; деление, ради которого правка, — строка 1010.
  Upstream: `f0134ef80:src/Battlescape/ProjectileFlyBState.cpp:923-950`, деление на строке 943. Форум пишет «strength below 1 as 1».
- **Причина:** `dz -= (double)(50 * weight / strength)/100;` — целочисленное деление, при `strength == 0` аппаратное исключение (падение игры).
  Сила 0 в Пиратках у девяти юнитов (`tools/units_zero_strength.py`, `AUDIT05_FINDINGS_C.md`).
- **Что сделано:** в начало функции добавлено `if (strength <= 0) return 0;`. Больше ничего.
- **Что именно возвращается и что из этого следует для `validThrowRange`** (предел в клетках = `(getMaxThrowDistance + 8) / 16.0`,
  под водой дополнительно умножается на `EXTENDED_UNDERWATER_THROW_FACTOR / 100`; бросок разрешён при `realDistance <= предел`,
  где `realDistance` — расстояние по горизонтали в клетках):
  - **strength = 0:** функция возвращает 0, предел = 8 / 16 = **0,5 клетки** при любом весе и любой разности высот. Разрешён только бросок
    в собственную клетку (расстояние 0); в соседнюю клетку (расстояние 1) — «вне дальности». Это не «сила 1»: при силе 1 предел совсем другой.
  - **strength = 1:** формула прежняя (код после раннего выхода не менялся). Таблица `evidence/C/runs/throwtable_20261119_085611_52456/throw_table.txt`:
    вес 0 → 250,5 клетки (шаг `50*0/1 = 0`, цикл идёт до предела 4000); вес 3, zd 0 → 1,50; вес 20 → 1,00 (при zd 0 и ниже).
  - **обычная сила (>= 1):** путь байт-в-байт прежний; контроль вес 3, сила 40, zd 0 → дальность 541, предел 34,31 клетки (таблица).
  - **strength < 0:** возвращает 0 (предел 0,5). В upstream при отрицательной силе падения нет: `50*weight/strength` отрицательно
    или 0, `dz` растёт, цикл идёт до 4000, предел ~250 клеток. Здесь поведение изменено. Достижимость на практике нет:
    `BattleUnit.cpp:586` делает `obeyFixedMinimum(_stats)` («don't allow to go into minus»), так что у боевого юнита сила не ниже нуля.
- **Сравнение с upstream и прежним:** upstream при силе 0 (и при weight 0, strength 0 — тоже 0/0) падает (SIGFPE). При силе >= 1 — тождественно.
  Единственное расхождение с upstream без падения — отрицательная сила (недостижима, см. выше).
- **Вызывающий код и отказ:** `validThrowRange` вызывается из `ProjectileFlyBState::init` (строка 155; при false бросок не начинается,
  выдаётся «вне дальности»), `TileEngine::validateThrow` (6261; им пользуется и ИИ при выборе броска гранаты) и `MapAim.cpp:264` (подсветка цели).
  Возврат 0 по всем трём путям даёт «цель недостижима» — безопасный отказ, исключения нет.
- **Проверено как:** исполнено — `evidence/C/throw_strength_zero_test.py` (функция вырезается из исходника и собирается под UBSan:
  контроль 541; до правки на силе 0 — «division by zero», после — 0, отчётов нет) и `evidence/C/throw_range_table_test.py`
  (таблица предела, крайние входы; ИТОГ «контроль сошёлся»). В самой игре бросок юнитом с нулевой силой не запускался (`AUDIT05_FINDINGS_C.md`).
  Прямого сравнения «старая функция против новой» при силе >= 1 нет — тождественность следует из диффа (добавлен только ранний выход).
- **Классификация:** код — **ИВ** (с силой 0 безопасно, при силе >= 1 механика неизменна). Описание на форуме — **ОФ**.
- **Статус тег/HEAD:** в теге да, в HEAD да, дальше не менялось.
- **Риски:** механика при штатных данных не меняется, RNG не затронут (функция чистая, без RNG), производительность та же.
  Побочный эффект «сила 0 может бросить только в свою клетку» новый по сравнению с «падением», но не по сравнению с чем-либо, что работало.
- **Нужен ли тест:** исполненный в игре — по желанию (не блокирует): быстрый бой, юнит с `strength: 0` (например `STR_BOSSBRAIN` под контролем)
  с гранатой в руках; ожидание: цель на соседней клетке — «вне дальности», игра не падает.

### Исправленная формулировка для форума (A2)

Текущая формулировка («Fix: treat strength below 1 as 1») неверна. Код не подменяет силу на 1: при `strength <= 0`
функция возвращает 0, то есть предел броска сводится к 0,5 клетки (брошенное можно положить только в свою клетку).
Предлагаемый текст (заменяет пункт A2, абзац после кода):

> Integer division; strength can reach 0 through stat modifiers or in the rules (X-Piratez has nine such units). Fix: `getMaxThrowDistance`
> returns 0 when `strength <= 0`, before the division. `validThrowRange` then computes a limit of (0 + 8) / 16 = 0.5 tiles, so a unit with no strength
> can only throw onto its own tile; for strength >= 1 the result is unchanged. Commit [font=courier new]9bb60528b[/font].

Замечание по сути: в A2 стоит и строка `src/Battlescape/ProjectileFlyBState.cpp` с номером; у upstream она `:943` — проверить, что форум её цитирует
именно так (в посте цитируется только код, строка не названа).

- **Классификация:** **ИВ**, происхождение — **УО** (пункт форума корректен, «Confidence: medium»).
- **Статус тег/HEAD:** в теге да, в HEAD да.
- **Нужен ли тест:** да, исполненный (по желанию, не блокирует): бой с юнитом-пусковой, у которого путь к цели не даёт ни одной точки, под ASan/UBSan.

## 5. Коммит 47fb687a5 — A7, A8, B2 (часть боя)

### 5.1 A7 — берсерк без оружия (AUD05-019)
- **HEAD:** `UnitPanicBState.cpp:86`: `... == 1 && ba.weapon && ba.weapon->getCurrentWaypoints() != 0`. Upstream `:86`.
- **Причина:** `ba.weapon = _unit->getMainHandWeapon()` может быть null; `canUseWeapon` null принимает (`if (!weapon || !unit) return false;`),
  а следующая строка берёт `ba.weapon->...` без проверки. В Пиратках `extendedBerserkWithAimed` = 2 — путь закрыт.
- **Сделано:** добавлено `ba.weapon &&`. При null идёт ветка `else` (BA_AIMEDSHOT, `updateTU()` с `weapon == nullptr` безопасно: `BattlescapeGame.cpp:76-88`,
  очищает TU; `canUseWeapon(null)` — false).
- **Штатный путь:** при непустом оружии то же.
- **Проверено как:** исполнено — `evidence/C/berserk_unarmed_test.py` (мод-заглушка a05Berserk, сейв с пустыми руками и моралью 0):
  `runs/berserk_old_20261119_131740.txt` — Segmentation fault; `berserk_new_20261119_131959.txt` — 140 шагов берсерка с пустыми руками, отчётов нет, сбоя нет.
  Замечание: прогон под ASan (`berserk_asan_20261119_132142.txt`) не подтвердил путь (шагов с пустыми руками 0) — санитайзерной проверки именно этой ветки нет.
- **Классификация:** **ИВ**. Формулировка форума: «`ba.weapon` is dereferenced before the null check that follows» — неточна: нулевая проверка
  внутри `canUseWeapon` идёт ДО разыменования, а сама строка 86 её не имеет. Предлагаемая формулировка: «`ba.weapon` can be null (e.g. no weapon in hand);
  `canUseWeapon` accepts null, but the condition on this line then calls `ba.weapon->getCurrentWaypoints()` without a check. Only reachable with
  `extendedBerserkWithAimed: 1`.»
- **Тест:** не нужен (исполнено).

### 5.2 A8 — ранг подкрепления как индекс `Node::nodeRank[8][7]` (AUD05-022)
- **HEAD:** `Node.cpp:76-79` (`Node::getNodeRank` — `nodeRank[Clamp(unitRank,0,7)][Clamp(preference,0,6)]`), читатели `SavedBattleGame.cpp:2631` и `2642`
  (было `2347` в upstream), `BattlescapeGenerator.cpp:2146`. Это остальные места чтения таблицы (`grep nodeRank\[` — только `Node.cpp` и объявление).
  Форум верно называет `NextTurnState.cpp:980, 1078, 1093` и `SavedBattleGame.cpp:2347`; правка сделана на стороне читателя, а не на стороне
  `setRankInt(alienRank)` (ранг юнита хранит исходное число — это сознательно, `AUDIT05_ROOT_CAUSES.md`: вопрос о хранении настоящего номера отдан решению Vitali).
- **Штатный путь:** ранги 0..7 дают строку без изменения. Ранги >= 8 раньше давали чтение за таблицей (ASan `global-buffer-overflow`, `FINDINGS_C.md`);
  теперь последняя строка (террорист), как делает генератор боя (`BattlescapeGenerator.cpp:2130`: `if (alienRank > 7) alienRank = 7`). В ветке без
  «Улучшенного ИИ» прочитанное значение на выбор узла не влияло (поглощается условием `|| preferred->getFlags() < n->getFlags()`); в ветке с
  ним выбор зависел от чужих байт, теперь детерминирован. RNG не затронут.
- **Проверено как:** чтение кода + исполнено под ASan (бой стенда ИИ на `build-asan-cov` с подкреплениями ранга >= 8 — `FINDINGS_C.md`, п.8 «Воспроизведение»);
  после правки отчётов нет (`FINAL_H.md`: 17 сценариев боя под ASan+UBSan).
- **Классификация:** **ИВ**; пункт форума A8 верен (происхождение OXCE).
- **Риск:** отрицательный `unitRank` теперь клампится в 0; `unit->getRankInt() >= 0` в вызывающем коде остаётся. Побочных эффектов нет.
- **Нужен ли тест:** нет.

### 5.3 B2 — патруль на карте без узлов и связь за списком
- **HEAD:** `SavedBattleGame.cpp:2593-2596` (`std::none_of(... !isDummy())` → `return 0`) и `2610` (связь `< 1` или `>= _nodes.size()` → `continue`).

  там и нельзя было завершить: бесконечный цикл или `generate(0, -1)`). Связи `1..size-1` без изменения.
- **Вызывающий код:** `AIModule.cpp:2114/2117` — `_toNode = getPatrolNode(...)`, null обрабатывается (`if (_toNode != 0)` на 2121 и далее). Рекурсия `2657` (`getPatrolNode(true, ...)`) без изменений.
- **Проверено как:** исполнено — `evidence/C/patrol_graph_test.py`, `runs/graph_20261119_110912_36480/graph.txt`: контроль, `nodes_none`, `nodes_dummy`,

  незакоммиченные правки; сверка в журнале прогона «сборка НОВЕЕ исходников») — применимость к `47fb687a5` по содержимому подтверждена, по хэшу нет.
- **Классификация:** **ИВ**; форум B2 верен (описание «Maps and terrain»: «Patrol node choice on a map with no usable nodes, and a node link index past the node list» — совпадает с диффом;
  в форуме «SavedBattleGame.cpp:2315-2332» — подтверждается upstream).
- **Риск:** «связь за списком — выбросить, остальные узлы выбираются» — для повреждённого сейва; на корректной карте не срабатывает.
