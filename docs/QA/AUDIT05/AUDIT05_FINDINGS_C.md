## AUD05-014 — бросок юнитом с нулевой силой: деление на ноль

1. **Где:** `src/Battlescape/ProjectileFlyBState.cpp`, `getMaxThrowDistance`, строка 1005; вызов — `validThrowRange`, строка 968.
2. **SHA:** `02a05ca68`.
3. **Фрагмент:**
   ```cpp
   double maxDistance = (getMaxThrowDistance(weight, action->actor->getBaseStats()->strength, zd) + 8) / 16.0;
   …
   dz -= (double)(50 * weight / strength)/100;
   ```
4. **Первопричина:** `50 * weight / strength` считается в целых до приведения к `double`; сила юнита берётся из правил как есть.
5. **Условия:** действие «бросок» (`BA_THROW`) юнитом, у которого базовая сила 0. Пути к `validThrowRange`:
   `ProjectileFlyBState::init` (сам бросок), `TileEngine::validateThrow` (проверка броска, в том числе ИИ),
   `MapAim.cpp:264` (подсветка цели броска). В Пиратках юнитов с `strength: 0` девять
   (`tools/units_zero_strength.py`): `STR_BOSSBRAIN`, `STR_SGR_DUMMY_UNIT_0…3`, `STR_TREE_OF_LIFF`, `STR_VERDUN_SHADE`,
   `STR_SPECTRAL_EYE`, `STR_BLACK_PYRAMID_TURRET`. Чтобы дело дошло до деления, такой юнит должен бросать предмет:
   под контролем игрока (взятый под контроль) либо ИИ с гранатой в руках. Есть ли у этих девяти предметы для броска —
   **не проверялось**.
6. **Последствия:** на x86 целочисленное деление на ноль — аппаратное исключение, игра падает.
7. **Происхождение:** OpenXcom.
8. **Воспроизведение:** `py -3.13 docs/QA/AUDIT05/evidence/C/throw_strength_zero_test.py` — текст функции вырезается из
   исходника без изменений и собирается отдельно с `-fsanitize=undefined`; игра не запускается.
9. **Факт:** контроль (вес 3, сила 40) → 541, отчётов нет; вес 3, сила 0 → `runtime error: division by zero`;
   вес 0, сила 0 → то же.
10. **Ожидание:** юнит без силы бросить не может (дальность 0) либо бросает как при силе 1 — игра не падает.
11. **Исправление:** в `getMaxThrowDistance` при `strength <= 0` вернуть 0 (бросок «вне дальности»). Для юнитов с
    силой ≥ 1 расчёт не меняется ни в одном бите.
12. **Риск для механики:** нет для юнитов с положительной силой; для юнитов с силой 0 сегодня механики нет — падение.
13. **Регресс-тест:** п. 8 после правки: сила 0 → число, отчёта нет; контроль 541 прежний.
14. **Приоритет:** P3. **Доказанность:** функция — подтверждено санитайзером; достижимость в игре — доказано кодом, не запуском.
15. **Upstream:** да.
16. **Сырые результаты:** `evidence/C/runs/20261118_234845_9080/`.

   ```cpp
   // BattlescapeGenerator::addAlien - здесь защита есть
   if (alienRank > 7)
       alienRank = 7;
   // NextTurnState::addReinforcement - здесь её нет
   unit->setRankInt(alienRank);
   ```
4. **Первопричина:** `alienRank` в описании высадки — номер члена расы, в модах он бывает больше 7. При генерации боя
   он обрезается до 7 («safety to avoid index out of bounds errors»), при подкреплениях — нет. Юнит подкрепления
   несёт ранг 8 и больше, и патруль читает строку таблицы, которой нет.
5. **Условия:** мод с подкреплениями, где `alienRank` больше 7, и такой юнит идёт в патруль. В Пиратках
   `alienRank` от 8 и выше встречается в `Piratez_Factions.rul` 340 раз; у миссии `STR_LOC_THULEBASE` волны
   подкреплений несут ранги 9, 11, 12, 13.
6. **Последствия:** чтение 4 байт за концом статической таблицы (ASan: `global-buffer-overflow`, 28 байт после
   `nodeRank`, рядом строки `Node.cpp`). В выпуске это соседние статические данные — игра не падает. В ветке
   без «Улучшенного ИИ» прочитанное значение на выбор узла не влияет: условие с ним поглощается следующим
   (`|| preferred->getFlags() < n->getFlags()`). В ветке «Улучшенного ИИ» (`oxceFixes`, строка 2571) оно участвует в
   сравнении «узел своего ранга» — выбор узла охранником зависит от чужих байт, то есть от сборки.
7. **Происхождение:** OXCE (подкрепления, 2020) поверх таблицы OpenXcom; условие ветки 2571 — наш код «Улучшенного ИИ».
8. **Воспроизведение:** бой стенда ИИ на `build-asan-cov`, невидимо:
   `OXCE_AI_RACE=STR_ETHEREAL`, `A05_DIFF=4`, `py -3.13 docs/QA/AUDIT05/evidence/C/scenario_cov_test.py 14 407`
   (зерно 407 собирает `STR_LOC_THULEBASE`).
9. **Факт:** `SavedBattleGame.cpp:2582:30: runtime error: index 9 out of bounds for type 'const int[8][7]'` и
   `AddressSanitizer: global-buffer-overflow … READ of size 4`; стек `getPatrolNode` ← `AIModule::setupPatrol:2114` ←
   `AIModule::think:1122` ← `BattlescapeGame::handleAI:486`. Бой остановлен санитайзером на третьем ходу.
10. **Ожидание:** ранг юнита подкрепления в пределах таблицы, как у юнитов начальной высадки.
11. **Исправление (после согласования):** в `addReinforcement` то же обрезание `alienRank` до 7 перед
    `setRankInt`, что в `addAlien`. Запасной вариант — обрезание в месте чтения.
12. **Риск для механики:** без «Улучшенного ИИ» — нет (значение на исход не влияет). С ним выбор узла у таких
    юнитов станет определённым вместо случайного от сборки; бросков генератора это не добавляет.
13. **Регресс-тест:** п. 8 после правки — бой идёт без отчётов санитайзеров.
14. **Приоритет:** P3. **Доказанность:** подтверждено запуском.
15. **Upstream:** да (OXCE).
16. **Сырые результаты:** `evidence/C/runs/scen_20261119_093047_30936/` (`sanrep_…41404.txt`, имена кадров —
    `….names.txt`, `log_seed407.txt`).

## Наблюдения чтения ядра (не находки)

- **Н-C2** `MeleeAttackBState::think`: повторный удар не проверяет, жив ли атакующий (как в OXCE).
- **Н-C3** `ExplosionBState::think`: после `explode()` нет `return` — цикл идёт по списку взрывов дальше (как в OpenXcom).
- **Н-C4** циклы с условием `!=` по числу из мода: дробины (`ProjectileFlyBState`, `i != pellets`), пар
  (`Projectile::addVaporCloud`, `i != vaporDensity`), `TileEngine::setDangerZone` (`x != radius`) — при отрицательном
  значении в моде цикл не кончается. Есть ли такие значения в Пиратках — **перебором не проверялось**.
- Дополнение к AUD05-018 (броня размера ≥ 3): те же массивы на 4 части читаются в `UnitFallBState::think:183–207`
  (`bodyOffsets[4]`) и `TileEngine::voxelCheck:5007–5008` (`parts[]`).
- `TileEngine::explode:3545–3547` — клетка центра взрыва разыменовывается без проверки (в нашей `explosionArea` проверка
  есть); вызовы передают точку внутри карты. `voxelCheck` — `tempTile->getTerrainLevel()` без проверки нуля, в
  `voxelCheckKnown` проверка есть.

  базовое здоровье юнита: ноль только при негодном значении мода.
