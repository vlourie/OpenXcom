## 2. Пакет 1 (19.11.2026) — коммит `47fb687a5`, не отправлен

### 2.1. Ранги (К1, AUD05-022)

**Что такое ранг.** `alienRank` в описании высадки — номер члена расы (`race->getMember(alienRank)`), а не звание.
В Пиратках у рас больше восьми членов: значений `alienRank` ≥ 8 в `Piratez_Factions.rul` — 340. Жизненный цикл:

| Место | Что делает |
|---|---|
| правила: `AlienDeployment` (`alienRank`, по умолчанию 0) | диапазон не проверяется; отрицательное допустимо при `customUnitType` |
| начальная высадка: `BattlescapeGenerator::addAlien` | обрезает до 7 и **хранит в юните обрезанное** |
| подкрепления: `NextTurnState::addReinforcement` | хранит **как есть** (9, 11, 12, 13 у `STR_LOC_THULEBASE`) |
| сейв: `BattleUnit` (`rankInt`) | читается без проверки |
| бойцы игрока | 0…5 по званию |
| потребители | патруль (`getPatrolNode` → таблица), бонусы характеристик (`RuleStatBonus`), скрипты и Lua (`getRank`), охота на последних (`bughuntRank`), мораль (только игрок) |

**Контракт.** Ранг юнита и строка таблицы узлов — разные понятия. Ранг — любое целое; строку таблицы выдаёт одна
функция `Node::getNodeRank(ранг, предпочтение)`: члены расы за пределом таблицы — «тоже террористы» (строка 7), как
их всегда расставлял генератор; отрицательный — строка 0. Все три чтения таблицы идут через неё.

**Что намеренно не тронуто.** Хранимый ранг подкрепления остаётся настоящим (9, 11…): его читают бонусы
характеристик, скрипты модов и Lua — обрезание изменило бы числа. Расхождение «юнит начальной высадки хранит 7, а
такой же юнит подкрепления — 9» — поведение OXCE; выравнивать его — изменение совместимости модов, **нужно отдельное
решение** (вариант: генератор тоже хранит настоящий номер).

### 2.2. Размер юнита (К1, AUD05-018)

Движок знает только 1×1 и 2×2: массивы частей на четыре (`Pathfinding::getTUCost`, `UnitFallBState::think`,
`TileEngine::voxelCheck`), «большой» = `size > 1`. В установке X-Piratez и `bin/` (292 файла `.rul`,
`tools/armor_sizes.py` → `inventory/armor_sizes.tsv`) явный `size` у брони встречается 110 раз, везде 2; наследование
значение только копирует. **Контракт:** `Armor::afterLoad` (окончательное формирование правил) отклоняет размер не 1 и
не 2 — «Armor size must be 1 or 2». Проверок во внутренних функциях не добавлено.

### 2.3. Граф узлов (К2, AUD05-017)

| Вопрос | Ответ |
|---|---|
| кто создаёт | генератор боя из файлов `.RMP` (`BattlescapeGenerator`), связи пересчитываются при сборке карты; сейв хранит узлы и связи как есть |
| кто проверял | никто |
| пустой граф допустим? | да: карта без узлов — «патрулировать некуда» |
| пустые (dummy) узлы | остаются в списке, чтобы не сдвигать номера; выбирать их нельзя |
| связи | номер узла ≥ 1; меньше 1 — выходы с карты и «нет связи» |
| отсутствие маршрута | `getPatrolNode` возвращает 0; `AIModule::setupPatrol` это принимает (`2c1dff5ae`) |

Правка: `getPatrolNode` при отсутствии не-пустых узлов возвращает 0 до броска генератора (раньше — деление на ноль
либо бесконечный цикл); связь с номером за списком пропускается, как связь «меньше 1» (раньше — исключение
`vector::at`). На карте с узлами броски генератора те же. Пусковая с точками пути — отдельный механизм (результат
поиска пути, а не граф патруля), её пустой список исправлен ранее (AUD05-016).

### 2.4. Граница загрузки сейва боя (К3, AUD05-020, 021)

Источник негодных данных — только файл: игра пишет размеры полей 1, 2, 4, каждую клетку один раз, карту модулей
размером (ширина / 10) × (длина / 10) (`calculateModuleMap` — единственный производитель). Поэтому проверка стоит на
границе, в `SavedBattleGame::load`, рядом с уже имеющимися: каждый размер поля ∈ {1, 2, 4}; повтор номера клетки —
отказ; карта модулей не по размеру карты — отказ «Invalid module map in the saved battle». `unserializeInt` не
менялся: вызов один, и ключ теперь проверен до него.

### 2.5. Кэши интерфейса (К4, вариант А)

Готовые кадры HD-картинок вынесены из `_smooth` в свою карту `_prepared` (ключ тот же, записи другого вида).
`_smooth` хранит только ответы о поверхностях и их сглаженные кадры. Лимит памяти общий (192 МБ), вытесняется самая
давно использованная запись из обеих карт (общий счётчик обращений) — как было при одном списке. Запись одного вида
больше не может заменить запись другого.

## 9. Реакция юнита без единиц времени (19.11.2026) — коммит `6fc9c75e6`, не отправлен

**Первопричина.** `BattleUnit::getReactionScore()` считал `reactions * tu / maxTu`; при `maxTu = 0` это 0 / 0 = NaN.
Дальше NaN уходил в `(int)` в `TileEngine::getSpottingUnits()` и в скрипте `getReactionScore` (UB; на x86 —
−2147483648). Та же формула второй раз была выписана в `determineReactionType` (вычет за реакцию, деление на
`tu` — `TileEngine.cpp:2838`). Запретить `tu: 0` в правилах нельзя: в Пиратках таких юнитов семь.

**Юниты Пираток с `tu: 0`** (проверено по рулсетам): `STR_BOSSBRAIN` (реакция 10, без оружия, `ignoredByAI`),
манекены `STR_SGR_DUMMY_UNIT_*` (реакция 0; оружие с ценой выстрела в TU — действовать не могут), наш звуковой юнит
`STR_HD_TREE_FALL`. Особой механики «реагирует без TU» или бесплатных действий ни у кого нет.

**Правка.** Одна формула `BattleUnit::reactionScore(reactions, timeUnits, maxTimeUnits)`: при `maxTimeUnits <= 0`
возвращает 0, иначе прежнее выражение в прежнем порядке. Ею считаются и рейтинг, и вычет за реакцию.
`BattleUnit::hasReactionFire()` (`maxTu > 0`): юнит без TU не входит в список реагирующих и на него не реагируют.
Нулевой делитель единицей не подменяется.

**Что сохранено.** До правки на x86 сравнения с NaN были ложны: такой юнит не реагировал, и на его действия не
реагировали (цикл наблюдателей при этом шёл — видимость считалась). Это поведение сохранено явно. Единственное
отличие: порог для наблюдателей действующего юнита без TU был `(int)NaN` = INT_MIN, стал 0 — на исход не влияет,
потому что `getReactor` такого юнита целью реакции не берёт. Для `maxTu > 0`: формула, порядок вычислений, RNG те же.

**Вопрос к Vitali (не решалось самим).** Должны ли другие юниты реагировать на действия юнита без TU? Сейчас — нет
(как и было). Изменить — значит изменить механику; в Пиратках такие юниты действий не совершают.

**Проверки.** `evidence/C/reaction_tu_zero_test.py formula` — тело функции вырезано из исходника и собрано с
`-fsanitize=undefined,float-divide-by-zero,float-cast-overflow`: прежняя формула при max TU 0 даёт NaN, int
−2147483648 и два отчёта UBSan; новая — 0 без отчётов; нулевые текущие TU, нулевая реакция, обычные значения —
совпадают; сетка 805 320 пар «рейтинг / вычет» при положительных max TU — отличий 0 бит в бит.
`… battle build-asan 3` — `BattleUnit.cpp` и `TileEngine.cpp` пересобраны с теми же двумя проверками вещественных
операций; бой, где двум бойцам и трём врагам записаны нулевые TU, 3 хода — отчётов санитайзеров нет.
`determinism_test.py` — 6 из 6; итоговый сейв условия base построчно равен сейву прогона до правки (отличия только в
четырёх ключах часов отрисовки). k = 1 — IDENTICAL (режим 0: 4 из 4, режим 2: 6 из 6).

**Чем покрытие ограничено.** Турели, встроенное оружие, действия с нулевой ценой TU проверены на уровне формулы

### Генерация боя как транзакция

Было: исключение генератора уходило из `btnYesClick` наверх, игра закрывалась («OXCE-HD has crashed»). При

Что генератор успевает изменить в кампании до отказа (прочитан `run()` и `deployXCOM` целиком):

| Что | Где | Последствие, если просто поймать исключение |
|---|---|---|
| склад базы: запрещённые условиями старта техника и предметы **добавляются** на склад, корабль их при этом не теряет | `deployXCOM`, корабль | бесплатное удвоение имущества |
| склад базы: при обороне базы предметы **снимаются** со склада в бой | `deployXCOM`, база | потеря имущества (на стенде 41 072 → 24 314 предметов к моменту отказа) |
| броня бойцов: замена и превращение по условиям старта и среде | `deployXCOM` | бойцы остаются в чужой броне |
| голос бойца: назначается при первом бою | `BattleUnit` | найден сверкой сейвов, не чтением |
| глобальный RNG | весь `run()` | другой расклад следующей попытки = обход отказа перезаходом |
| отметки «в бою» у корабля, цели, базы | сеттеры генератора | корабль и цель зависают |

Решение одно на все точки входа: `BattlescapeGenerator::runOrRollback` запоминает перечисленное до `run()` и при

`STR_BATTLE_GENERATION_FAILED` (`refusalMessage`). Автоповтора, нового зерна, замены местности или корабля нет.

Не откатывается: раскладка снаряжения бойца при включённой опции «без снаряжения бойцов» (она и так очищается
в начале каждого боя), перезапуск переменных Lua и масштаб HD (на кампанию не влияют).

### Оборона базы: отказ генерации — не результат нападения (`bf0983915`)

Первопричина: в движке нет состояния «нападение ожидает». `GeoscapeState::handleBaseDefense` первым делом ставит НЛО
`DESTROYED`, а миссию мгновенного возмездия — `interrupted`; после отказа генератора (раздел 18) это оставалось как есть,
то есть нападавшие «уходили» без боя — бесплатная победа.

Решение без изменения формата сейва: перед `AlienMission::ufoReachedWaypoint` экран снимает состояние НЛО
(`AssaultArrival`: участок траектории, высота, обнаружение, скорость, счётчик волны), при отказе
`holdBaseAssault` возвращает его и заносит НЛО в `_heldAssaults` (память экрана). Итог:

- база, склад, бойцы, техника, деньги — как до нападения (сверено стендом);
- НЛО остаётся над базой в воздухе: его можно сбить обычным порядком; нападение не «съедено»;
- повтора каждые 5 секунд нет (5 следующих тиков — ни одного нового сообщения);
- после загрузки игры — ровно одна новая попытка (на стенде: бой `STR_BASE_DEFENSE` построен, 161 юнит).

Ограничения, названные прямо: (1) если причина отказа постоянная (ошибка данных мода), нападение не состоится никогда,
пока игрок не собьёт НЛО или автор не исправит мод — это не тупик кампании, но и не «честный» бой; (2) если у базы есть
оборонительные сооружения, они стреляют по НЛО при каждой попытке (результат выстрелов сохраняется); (3) счётчик
следующей волны возвращается только когда он кратен 30 (иначе оставлен новый — безопасная сторона).

Варианты, если такое поведение не подходит (любой из них — изменение механики, нужен выбор Vitali):
A — как сейчас (нападение отложено); B — нападавшие уходят (как было до правки, бесплатная победа);
C — хранить отложенное нападение в сейве (новое поле формата сейва, повтор по таймеру, а не после загрузки).

переход. Второй отказ подряд без решения игрока (конец хода или «прервать» сбрасывают счётчик) — выход в главное меню

### Контракт склада (`7ca8be6db`)

Первопричина та же, что в разделе 18 (счёт предмета в `int`), но предел сверялся только со складом. Теперь единая
функция `Base::getStoreRoom(предмет)` = INT_MAX − склад − все перевозки этого предмета на базу; ею пользуются покупка
и перевозка (в обмене — обе базы). Оплаченная покупка и согласованная перевозка всегда помещаются в счёт, включая
то, что уже в пути. Запись в журнал в `ItemContainer` осталась только как страховка для путей, которые идут мимо этих
экранов (производство, трофеи, скрипты): там количество задаёт игра, а не игрок.

Отрицательное количество — найдено стендом: `Base::storesOverfull` приводил занятый объём ×100 к `int`; выше 21,4 млн
единиц объёма приведение давало отрицательное число, склад «освобождался», а `PurchaseState::increaseByValue` получал
отрицательный `maxByStores` → `picked=-2147483508`, сумма отрицательная (деньги прибавились бы). Исправлено в корне
(сравнение в double с тем же округлением) и на границе (число к покупке/перевозке не меньше 0). В обычной игре
недостижимо, обычные значения считаются так же.

Цена перевозки: обычная ветка `sum * mult / div` не тронута; ветка, где произведение не помещается в 64 бита,
считает `(q·div + r)·mult/div = q·mult + r·mult/div` — тождественно, округление то же. Сверено со счётом в 128 битах
на 202 117 суммах: 0 расхождений (в Пиратках mult = div = 1).

Не закрыто: автопокупка недостающего снаряжения корабля (`PurchaseState`, ~677) пределом счёта не ограничена — количества
там задаёт экипировка корабля, до INT_MAX не доходят.

### 20.1. Оборона базы: фазы нападения (`c073b6ed4`)

**Что было.** После `bf0983915` отказ генерации возвращал НЛО в состояние до прибытия целиком. Повтор после
загрузки шёл с прибытия: `BaseDefenseState` открывался снова, сооружения стреляли по тому же НЛО при каждой
попытке. Кроме того, `holdBaseAssault` без снимка прибытия отказывал — оставалась ветка «нападавшие ушли».

**Фазы.** 1) прибытие НЛО (`time5Seconds`, снимок `AssaultArrival`); 2) сооружения (`BaseDefenseState`);
3) подготовка боя (`handleBaseDefense` → генератор); 4) бой. Незавершённой может остаться только фаза 3.

**Существующих полей не хватает.** Проверены поля НЛО и миссии: `status`, `secondsRemaining`, `trajectoryPoint`,
`damage`, `shield`, `hitFrame`, `fireCountdown`, поля миссии `nextWave`, `spawnCountdown`, `missionSiteZone`. Ни одно
не означает «сооружения отработали»: `damage` не отличает обстрел базой от боя с перехватчиком, а у миссии с
`ignoreBaseDefenses` обстрела нет вовсе. Занимать поле с другим смыслом запрещено условием.

**Решение.** Одно необязательное поле сейва НЛО `baseDefenseDone` (bool). Пишется только когда установлено; сейв без
поля читается как `false` и ведёт себя как раньше; старая сборка новое поле не читает и идёт прежним путём.
`BaseDefenseState::btnOkClick` ставит флаг перед `handleBaseDefense`; `time5Seconds` не открывает экран сооружений,
если флаг стоит, и идёт сразу к бою. `holdBaseAssault` стал безусловным: без снимка НЛО возвращается по тому, что
прибытие заведомо меняет; НЛО «на земле» поднимается над базой.

| Условие | Как выполнено |
|---|---|
| база не уничтожается | отказ не доходит до ветки поражения; стенд: база и склад те же |
| уход не засчитывается, победа не начисляется | ветки «ушли» больше нет; очки и миссия не меняются |
| НЛО нельзя обстреливать многократно | флаг на НЛО, в сейве; стенд: после загрузки обстрела нет |
| нет бесконечного автоповтора | повтор один — после загрузки игры; 5 тиков стенда без новых окон |
| RNG не меняется | генератор и его вызовы не тронуты |
| постоянный дефект данных | сообщение `STR_BASE_DEFENSE_GENERATION_FAILED`: база цела, сооружения повторно не стреляют, кампанию можно сохранить |

**Не проверено:** сейв новой сборки в старой сборке запуском не открывался (вывод по коду: неизвестные ключи YAML
пропускаются); НЛО, сбитый сооружениями до боя, идёт прежним путём и флаг ему не нужен.

### 20.4. Проверка правил после загрузки (`61864658c`)

остановки остаётся (откатить нельзя — скрипт пишет прямо в объекты игры), выходные значения — какие успел выставить.
Затем скрипт пишется в журнал и до перезапуска игры не исполняется: вызывающий получает то же, что от пустого
скрипта. Иначе скрипт, вызываемый на каждого юнита или пиксель, держал бы поток 0,19 с при каждом вызове.
Ограничения: остановленных скриптов запоминается до 32 (33-й будет останавливаться на каждом вызове заново);
бюджет — константа, из правил не настраивается; ходы боя на стенде не пошли, нагрузка в ходах оценена по
отсутствию `loop` в правилах, а не замером.
