# AUDIT-05, этап D — ИИ и поиск пути

Проверяемый SHA: `fad953ad4`. Производственный код на этапе D **не менялся**.
Сборка ASan+UBSan: `build-asan\bin\openxcom.exe`, SHA-256 `38e3903c…1ffe9486` — собрана из `02a05ca68` и не
пересобиралась; после неё в ветку вошли `9bb60528b` (бросок с нулевой силой) и `fad953ad4` (время сейва, статистика
пула) — файлы ИИ и поиска пути они не трогают.

Метод этапа — **сверка с OXCE 8.7.1 по дифу** (`git diff v8.7.1 HEAD`), а не построчное чтение всего кода:
главный вопрос этапа A был «что из стенда ИИ исполняется у игрока» и «выключено — как в OXCE». `Pathfinding.cpp`
прочитан целиком; в `AIModule.cpp` просмотрены все 67 мест, где строка OXCE заменена или удалена, и все 54 чистые
вставки (по началу и концу, длинные тела новых функций стенда не читались); `AiProbe.cpp` — только часть выпуска
(заглушки, строки 60–450).

## Ответы на вопросы этапа A

**1. Что из кода стенда ИИ исполняется у игрока.** Почти ничего. `AiProbe.cpp` делится `#ifndef OXCE_AI_DEV`: в выпуске
вместо стенда — заглушки (строки 84–430), возвращающие «нет» / 0. `AiCoverMap::mode()` в выпуске всегда 0 — карта
укрытий не строится, потоков не запускает; `AiCoverMap::touch` из `Tile.cpp` выходит на первой проверке.
`AiCandidates` зовётся только из стендовой половины `AiProbe.cpp`. В выпуске работают только ветки опции
«Улучшенный ИИ» (`oxceBetterAi`, по умолчанию **выключена**): исправления O1–O14 (`oxceBetterAiFixes`) и AI3
(`oxceBetterAiAi3`, девять флагов таблицы `AI3_PLAYER`).

**2. «Выключено — как в OXCE».** По дифу — **да** для `Pathfinding.cpp`, `AIModule.cpp` и разбора хода ИИ в
`BattlescapeGame::handleAI`: каждая заменённая строка OXCE стоит под условием, которое при выключенной опции даёт
исходное выражение (таблица — в разделе «Что проверено»). Формат сохранения ИИ (`AIModule::save/load`) не менялся;
`PathfindingNode`, `PathfindingOpenSet` — без единой нашей правки. Запуском (сравнение боя с эталонной OXCE 8.7.1 на
одном сиде) это **не проверялось** — вывод сделан чтением.

**Обрушение зданий** (`CollapsePilot`, `CollapseCore`, 3 тыс. строк) к ИИ не относится: это физика под опцией
`oxceCollapse` (по умолчанию выключена). На этапе D проверены только входы: все восемь функций, вызываемых из боя,
при выключенной опции выходят сразу (`trunkArmor` возвращает броню как есть), отладочный стенд (`OXCE_COLLAPSE_*`)
в выпуске вырезан. Само тело не читалось — переносится в этап E.

## AUD05-015 — оборона базы: нулевой узел в `setupPatrol`

1. **Где:** `src/Battlescape/AIModule.cpp`, `AIModule::setupPatrol`, строки 2051–2053 (в OXCE 8.7.1 — строка 821).
2. **SHA:** `fad953ad4`.
3. **Фрагмент:**
   ```cpp
   if ((!oxceFixes || _fromNode) && _fromNode->isTarget() &&
       _save->canUseWeapon(_attackAction.weapon, _unit, false, BA_SNAPSHOT) &&
       _save->getModuleMap()[_fromNode->getPosition().x / 10][_fromNode->getPosition().y / 10].second > 0)
   ```
4. **Первопричина:** `_fromNode` ищется выше (строки 1928–1948) только среди узлов **того же уровня**, что и юнит; если
   на уровне юнита нет ни одного не-пустого узла, он остаётся нулевым. Ветка миссий, кроме обороны базы, это
   проверяет (`!_fromNode`), ветка обороны базы — нет.
5. **Условия:** миссия `STR_BASE_DEFENSE`; враг размера 1, изначально враждебный, с оружием прямой наводки, которое
   повреждает клетки (`ToTile > 0.01`), в начале патруля стоит на уровне карты, где нет узлов маршрута. Есть ли в
   базах Пираток уровни без узлов — **не проверялось**.
6. **Последствия:** чтение по нулевому адресу, игра падает в ход врага.
7. **Происхождение:** OpenXcom (в OXCE 8.7.1 то же).
8. **Воспроизведение:** запуском не воспроизводилось. Доказательство — текст функции: между поиском `_fromNode` и
   строкой 2051 присваиваний ему нет.
9. **Факт:** при включённом «Улучшенном ИИ» условие `(!oxceFixes || _fromNode)` защищает; при выключенном
   (умолчание) — нет.
10. **Ожидание:** без узла юнит идёт во вторую ветку (ищет ближайшую цель) либо в общий выбор узла.
11. **Исправление:** проверку `_fromNode` на ноль сделать безусловной (убрать `!oxceFixes ||`). Остальное в O12
    (обход комнаты 10×10 вместо 9×9, проверка клетки) — изменение поведения, оставить под опцией.
12. **Риск для механики:** нет: там, где OXCE сегодня работает, `_fromNode` не нулевой и условие не меняется;
    меняется только случай, в котором игра падает.
13. **Регресс-тест:** нужен сейв обороны базы с врагом на уровне без узлов — такого сейва нет; без него правка
    проверяется только чтением (R-907: путь отказа не прогнан — так и писать в отчёте).
14. **Приоритет:** P3. **Доказанность:** доказано кодом, не запуском.
15. **Upstream:** да.
16. **Сырые результаты:** нет.

## AUD05-016 — пусковая с точками пути: `front()` на пустом списке

1. **Где:** `src/Battlescape/AIModule.cpp`, `AIModule::wayPointAction`, строка 5159 (в OXCE 8.7.1 — 2436).
2. **SHA:** `fad953ad4`.
3. **Фрагмент:**
   ```cpp
   if ((bot || AiProbe::oxceFixes()) && _attackAction.waypoints.empty()) { … _attackAction.type = BA_RETHINK; return; }
   _attackAction.target = _attackAction.waypoints.front();
   if (LastWayPoint != _aggroTarget->getPosition())
   {
       _attackAction.type = BA_RETHINK;
   }
   ```
4. **Первопричина:** точка кладётся в список только когда луч от очередной клетки пути упёрся в местность или в цель;
   по открытой прямой к цели, в которую луч на высоте 16 не попадает (например, юнит ниже 16 вокселей — боец на
   колене имеет высоту 14), список остаётся пустым. То же при `waypoints: 0` у оружия.
5. **Условия:** враг с оружием `BA_LAUNCH` выбрал цель (путь снаряда найден), ни одна точка не добавлена.
6. **Последствия:** `front()` пустого `std::list` — неопределённое поведение. В нашей сборке (g++ 16, `-O3`, без
   `_GLIBCXX_ASSERTIONS`) читается служебный узел списка, в `target` попадает мусор, но следующая строка всегда
   ставит `BA_RETHINK` (`LastWayPoint` остался позицией стрелка), и мусорная цель не используется. Падения нет.
   При сборке с проверками контейнеров (`_GLIBCXX_ASSERTIONS`, отладочная MSVC) игра остановится.
7. **Происхождение:** OpenXcom.
8. **Воспроизведение:** запуском не воспроизводилось; была ли у врага пусковая в боях под санитайзерами — не измерялось.
9. **Факт:** защита O10 есть, работает только при «Улучшенном ИИ» (и у бота стенда).
10. **Ожидание:** пустой список → `BA_RETHINK` без чтения списка.
11. **Исправление:** сделать проверку `waypoints.empty()` безусловной.
12. **Риск для механики:** нет: и сегодня в этом случае выходит `BA_RETHINK`; `target` перед следующим `think`
    перезаписывается. Генератор случайных чисел не трогается.
13. **Регресс-тест:** бой с вражеской пусковой по бойцу на колене на открытой прямой — сценария нет.
14. **Приоритет:** P4. **Доказанность:** доказано кодом.
15. **Upstream:** да.
16. **Сырые результаты:** нет.

## AUD05-017 — карта без узлов маршрута: `getPatrolNode`

1. **Где:** `src/Savegame/SavedBattleGame.cpp`, `SavedBattleGame::getPatrolNode`, строки 2535–2543; `src/Engine/RNG.cpp:92`.
2. **SHA:** `fad953ad4`.
3. **Фрагмент:**
   ```cpp
   fromNode = getNodes()->at(RNG::generate(0, getNodes()->size() - 1));
   while (fromNode->isDummy())
   {
       fromNode = getNodes()->at(RNG::generate(0, getNodes()->size() - 1));

   ```
4. **Первопричина:** случай «у юнита нет исходного узла» рассчитан на карту, где узлы есть; пустой список и список из
   одних пустых (dummy) узлов не предусмотрены.
5. **Условия:** патруль ИИ (`setupPatrol`), `_fromNode` нулевой, на карте нет узлов вообще либо все пустые.
6. **Последствия:** узлов нет — `generate(0, -1)` делит на ноль (аппаратное исключение, падение); все узлы пустые —
   цикл не кончается, игра висит.
7. **Происхождение:** OpenXcom.
8. **Воспроизведение:** не воспроизводилось; карты без узлов в Пиратках **не искались**.
9. **Факт:** проверок на пустой список узлов в `src` нет (`grep getNodes()->empty` — пусто).
10. **Ожидание:** без узлов патруль не выбирается (`return 0`), юнит остаётся на месте.
11. **Исправление:** в начале ветки `fromNode == 0`: если не-пустых узлов нет — вернуть 0. Для карт с узлами бросок
    генератора остаётся тем же.
12. **Риск для механики:** нет для карт с хотя бы одним не-пустым узлом.
13. **Регресс-тест:** отдельная сборка функции с пустым списком узлов под UBSan (как тест AUD05-014).
14. **Приоритет:** P4 — ошибка данных мода, а не игры игрока. **Доказанность:** доказано кодом.
15. **Upstream:** да.

## AUD05-018 — броня размера 3 и больше

1. **Где:** `src/Battlescape/Pathfinding.cpp`, `Pathfinding::getTUCost`, строки 447–477; `src/Mod/Armor.cpp:208`.
2. **SHA:** `fad953ad4`.
3. **Фрагмент:**
   ```cpp
   const int numberOfParts = armor->getTotalSize();   // size * size
   Position offsets[4] = …
   const Tile* startTile[4] = { };
   const Tile* destinationTile[4] = { };
   …

   ```
4. **Первопричина:** `size` брони читается из правил без проверки диапазона; код движения рассчитан на 1 и 2.
5. **Условия:** мод с `size: 3` (или больше, или 0 и меньше) у брони, юнит в бою.
6. **Последствия:** при 3 — девять частей в массивах на четыре: запись за концом массива на стеке. Это же место
   clang-tidy отметил как возможный нулевой `destinationTile[3]` (`Pathfinding.cpp:590`).
7. **Происхождение:** OpenXcom / OXCE.
8. **Воспроизведение:** не воспроизводилось; есть ли в Пиратках броня с размером не 1 и не 2 — **не проверялось**
   (игра 3×3 не поддерживает нигде, так что вряд ли).
9. **Факт:** в `Armor.cpp` размер сравнивается только с 1 (строки 210, 223).
10. **Ожидание:** мод с таким размером не загружается, с понятной ошибкой.
11. **Исправление:** проверка `size` 1 или 2 при загрузке брони (ошибка мода). Это правило модов — **решать Vitali**,

12. **Риск для механики:** нет для существующих модов с размером 1–2.

14. **Приоритет:** P4. **Доказанность:** доказано кодом.
