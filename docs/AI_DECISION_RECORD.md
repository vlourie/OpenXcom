# DecisionRecord v1 — запись решений ИИ

Формат, в котором стенд ИИ пишет каждое решение юнита: что он видел, из чего выбирал, что выбрал и почему,
что из этого вышло и что с ним сделал ход врага. Все следующие шаги плана V2 (`docs/research/ai-arena-v2-plan.md`:
L0, L1, Arena, запись ходов Vitali) читают только эту запись. **Формат заморожен:** новое поле — версия `v:2`
и строка здесь, старые поля не меняют смысла. Проект v2 (состояние после обязательных трат до think) — в конце.

Только сборка стенда (`-DOXCE_AI_DEV=ON`, build-aiN). В выпуске игрокам функции `AiProbe` пустые.

## Включение

| Переменная | Что делает |
|---|---|
| `OXCE_AI_RECORD=1` | писать запись |
| `OXCE_AI_TRACE_DECISION=12,40` | для записей с этими `rec` ещё и `[AITRACE]` — оценки всех клеток, которые перебрали правила |
| `OXCE_AI_KEEP_DECIDE=1` | ai_arena сохраняет и прежние строки `[AIDECIDE]/[AIMELEE]/[AIPATH]` в `<метка>.decide.gz` |
| `OXCE_AI_RECORD_PATH=1` | вместе с `OXCE_AI_RECORD`: у хода патруля к узлу ещё и `[AIPATROL]` — путь и что держит первый шаг (план V2, L0-B); в хэш `cfg` не входит |
| `OXCE_AI_RECORD_PATH=2` | forensic (с build-ai44): к тому же ещё `before`, `best`, `best_ok` — ближайшая к узлу досягаемая клетка, до 17 полных A* стенда на каждый остановленный патруль (на станции четверть боя, аудит п. 11); по умолчанию 0 — без `[AIPATROL]` |

```
PYTHONIOENCODING=utf-8 OXCE_AI_BUILD=build-ai30 py -3.13 tools/ai_arena.py --missions @fair22.txt --seeds 202 --careful --squad 8 --jobs 4 --label det37a --env OXCE_AI_RECORD=1
```

Движок пишет строки в `openxcom.log`, ai_arena раскладывает их по файлам серии (каталог
`%TEMP%/oxce_ai_probe/arena`, на второй машине `C:/OXCE_AIWorker/work/oxce_ai_probe/arena`). Каждая строка файла
начинается с `seed=<зерно> want=<миссия> ` — это ключ боя.

| Файл | Строки |
|---|---|
| `<метка>.rec.gz` | `[AIRECHEAD]`, `[AIREC]`, `[AIEXEC]`, `[AIAFTER]`, `[AITRACE]` |
| `<метка>.cand.gz` | `[AICAND]` — тяжёлые списки кандидатов, один раз на хэш |
| `<метка>.decide.gz` | только с `OXCE_AI_KEEP_DECIDE=1` |
| `<метка>.path.gz` | `[AIPATROL]`, только с `OXCE_AI_RECORD_PATH=1` или `2` |

Серии до v1 (build-ai29 и первый build-ai30) писали всё в `.decide.gz` без `exp`, `[AIEXEC]` и `[AIAFTER]`;
`rec_diff.py` читает и их.

## Связи

- `rec` — номер записи в бою, с 0. `[AIEXEC]`, `[AITRACE]` ссылаются на него полем `rec`.
- `[AIAFTER]` покрывает записи `first..last` одного юнита одной стороны за один ход.
- `cand.moves` и `cand.acts` в `[AIREC]` — хэши; сами списки в `[AICAND] moves=<хэш>` и `[AICAND] acts=<хэш>` того же боя.
- `gen` и `cfg` — поколение движка и набор настроек. **Данные разных `gen` или `cfg` не смешивать:**
  BASE_V1 (careful8g9) и BASE_V2 (build-ai28 + единый порядок предметов) — разные поколения.

## `[AIRECHEAD]` — раз на бой

```json
{"v":1,"gen":"base_v2","cfg":"<хэш>","seed":202,"env":{"OXCE_AI_CAREFUL":"1", ...}}
```

`env` — все переменные `OXCE_AI_*` прогона по алфавиту, кроме своих для боя (`SEED`, `MISSION`, `CAMPAIGN`),
записи (`RECORD`, `TRACE_DECISION`, `PROBE_SAVE`, `KEEP_DECIDE`) и машины (`BUILD`, `EXE`, `GAME`, `WORK`).
`cfg` — хэш этого текста: один на серию и одинаковый на обеих машинах.

## `[AIREC]` — решение

```json
{"v":1,"gen","cfg","seed","rec","turn","side","unit","order","n",
 "state":{"pos","dir","tu","hp","stun","morale","kneel","h":{"u","i","o","m","r0","r","a0"},"state_id"},
 "cand":{"n","set","order","moves","nmoves","acts","nacts","rng"},
 "base":{"id","k","in","exp","tk","t","to","w","run","mode","slot","src","src_rec","score",
         "reason":{"trail":[],"odds":[],"props":[]}},
 "rule":null}
```

| Поле | Смысл |
|---|---|
| `turn`, `side` | ход и сторона (0 игрок, 1 враг, 2 нейтралы) |
| `order` | какой по счёту юнит стороны в этом ходу впервые решал |
| `n` | номер действия юнита в ходу (`BattleAction::number`) |
| `state.pos … kneel` | юнит **до** того, как подумал (`AiProbe::beforeThink`) |
| `state.h` | отпечатки **после** думанья: `u` юниты, `i` предметы, `o` порядок, `m` карта, `r0` ГСЧ до, `r` ГСЧ после, `a0` память AIModule до |
| `state.state_id` | `u xor m`. В `u` входят счётчик действий ИИ движка (`getAIActionCounter`) и очередь состояний боя, поэтому `state_id` другой на **каждом** решении: это отпечаток для сверки прогонов, а не ключ «то же состояние». «То же состояние» между двумя решениями юнита — записи подряд (никто другой не решал), те же `pos dir tu hp stun kneel morale`, `h.i` и `h.m` (`rec_diff.same_state`) |
| `cand.n` | всего кандидатов; `set` — хэш набора, `order` — хэш порядка |
| `cand.moves`, `nmoves` | хэш и длина списка достижимых клеток |
| `cand.acts`, `nacts` | хэш текста и длина списка прочих действий |
| `cand.rng` | 1 — генератор кандидатов тронул ГСЧ (ошибка: запись обязана не менять бой) |
| `base` | выбор базового ИИ (ниже) |
| `rule` | правило L0/L1, которое переписало выбор; в v1 всегда `null` |

### `base` — что выбрал базовый ИИ

| Поле | Смысл |
|---|---|
| `id`, `k` | id кандидата и вид: `m` ход, `M` ход к точке ИИ вне досягаемости, `a` атака, `k` присесть, `t` поворот, `e` конец хода, `r` передумать (RETHINK), `x` прочее |
| `in` | 1 — выбор есть среди кандидатов |
| `exp` | почему вид действия известен (ниже) |
| `tk` | у атаки — во что она целит (ниже), иначе `null` |
| `t`, `to`, `w`, `run` | `BattleActionType`, клетка, оружие, бегом |
| `mode` | режим AIModule: 0 patrol, 1 ambush, 2 combat, 3 escape |
| `slot` | откуда взято действие: `p` patrol, `a` ambush, `x` combat (атака), `e` escape, `l` leeroy, `s` psi, `b` revive/flee |
| `src` | правило, заполнившее слот (`firepoint`, `eval`, `shot`, `melee`, `grenade`, `grenade.node`, `sniper`, `waypoint`, `psi`, `ambush`, `escape`, `escape.known`, `firepoint.fallback`, `firepoint.random`, `patrol.node`, `patrol.module`, `leeroy`, `revive`, `flee`) |
| `src_rec` | в каком решении правило заполнило слот: слот живёт между решениями. Правило прошлого решения засчитывается, если его действие того же типа (атака за атаку), либо это ход на свою клетку, ставший `BA_NONE` (`walk.self` в trail: побег или патруль решил остаться). У RETHINK правила нет — `src` = `"rethink"`, `src_rec` = `null` |
| `score` | счёт правила: лучший счёт клетки у ambush/escape/firepoint, `eval` — счёт×1000, у psi — вес атаки; `null` — счёта у правила нет |
| `reason.trail` | метки пути по AIModule (`walk.self` — ход на свою клетку стал `BA_NONE`, и т. п.) |
| `reason.odds` | жребий режима: `{"p","a","c","e","roll","mode"}` — шансы четырёх режимов, выпавшее число и режим |
| `reason.props` | все предложения правил в этом решении: `{"s" слот,"src","sc" счёт,"t","to","w"}` |

### `exp`

| Значение | Когда |
|---|---|
| `cand` | выбор есть среди кандидатов |
| `ai_point` | ход вне списка: к клетке, которую ИИ выбрал за пределами досягаемости этого хода (вид `M`) |
| `occupied` | шаг на соседнюю клетку, где стоит другой юнит; исполнился ли — `walk` в `[AIEXEC]` |
| `target` | атака вне списка; во что целит — `tk` |
| `none` | не объяснено — ошибка записи, цель v1 — ноль |

### `tk`

`enemy` — враг, которого юнит видит или сторона видела не раньше `intelligence` ходов назад; `enemy_unknown` —
враг, о котором юнит не знает; `friend`, `self`, `down` (лежит без сознания); `last_seen` — клетка, где сторона
последний раз видела врага; `door`, `terrain` (стена или объект), `tile` (пустая клетка); `none` — вне карты.
У `BA_LAUNCH` целью считается последняя точка маршрута.

## `[AICAND]` — списки кандидатов

```
[AICAND] moves=<хэш> unit=<id> list=x.y.z:tu;x.y.z:tu;...
[AICAND] acts=<хэш> unit=<id> list=[{"id","k","t","to","tu"[,"u","w","p","lof","d"]},...]
```

Ходы: клетка и цена в ОВ, `-1` — вне досягаемости (узлы карты, места врагов). Действия: id, вид, тип, клетка, ОВ;
у атаки ещё `u` цель, `w` оружие, `p` шанс, `lof` линия огня, `d` расстояние. Строка пишется один раз на хэш
в бою, хэш действий считается по тексту списка.

## `[AIEXEC]` — исполнение

Пишется, когда действие решения закончилось: перед следующим `beforeThink`, в конце хода стороны
(`BattlescapeGame::endTurn`) или в конце боя. После конца боя (в том числе по лимиту `OXCE_AI_PROBE_TURNS`) запись
не ведётся: решение, принятое ИИ в том же кадре, уже нечем исполнить. `[AIDECIDE]` его по-прежнему пишет — так
число решений сравнимо с сериями до v1.

| Поле | Смысл |
|---|---|
| `walk` | для хода: 1 — путь найден и шаг пошёл, 0 — пути нет, `null` — не ход |
| `pos`, `dir`, `tu`, `kneel`, `hp`, `stun`, `down` | юнит после действия |
| `spent` | ОВ до думанья минус ОВ сейчас |
| `hp_lost` | сколько здоровья юнит потерял за действие (реакция врага) |
| `seen`, `spotted` | сколько живых врагов видит он и сколько видят его |
| `dmg`, `stunned`, `downed` | урон, оглушение и сбитые враги |
| `fdmg`, `fdowned` | то же по своим |
| `born` | юниты, появившиеся за действие (зомби и т. п.) |
| `trail` | метки, пришедшие во время исполнения |

## `[AIAFTER]` — после хода врага

Пишется, когда сторона начинает следующий ход (или бой кончился, `end` 1): по каждому юниту, решавшему в прошлом
ходу стороны.

| Поле | Смысл |
|---|---|
| `side`, `turn`, `now` | сторона, ход решений и текущий ход |
| `first`, `last`, `n` | записи юнита за тот ход |
| `dead`, `down`, `hp`, `stun`, `wounds`, `pos`, `spotted` | юнит сейчас |
| `hp_lost`, `stun_gain` | что с ним сделал ход врага (от состояния после его последнего действия) |

## `[AITRACE]`

```json
{"v":1,"rec":12,"unit":1000005,"tiles":{"firepoint":[[x,y,z,счёт],...],"ambush":[...],"escape":[...],"eval":[...]}}
```

Только для записей из `OXCE_AI_TRACE_DECISION`: все клетки, которые правило оценило, со счётом.

## `[AIPATROL]`

```json
{"v":3,"rec":40,"unit":1000005,"pos":[x,y,z],"to":[x,y,z],"bam":0,"pushed":1,"len":14,"cost":62,
 "first":{"dir":3,"tu":4,"en":2,"to":[x,y,z]},"sn_en":2,"sn_n":7,"tu":30,"energy":70,"kneel":0,"reserve":0,"free":2,"reserved":28,"rmode":9,
 "after":26,"snap":18,"known":0,"seen":0,"lof":0,"lof_tu":0,"stop":"reserve","nreach":9,
 "before":62,"best":{"to":[x,y,z],"reach":24,"after":38,"reserve":0},"best_ok":{"to":[x,y,z],"reach":8,"after":54,"reserve":1}}
```

Только с `OXCE_AI_RECORD_PATH=1` или `2`, только у решения, где база выбрала патруль к узлу (`slot` p, `src` `patrol.node`,
ход), сразу после того, как игра посчитала путь (`BattlescapeGame::handleAI`). Движок это не меняет: цены берутся
отдельным `Pathfinding` стенда, проверка резерва — `checkReservedTU` с `justChecking`. Поля `before`, `best`, `best_ok`
(forensic: до 17 полных A* на остановленный патруль) — только в режиме `2`; в режиме `1` строка кончается на `nreach`.

| Поле | Что |
|---|---|
| `rec` | запись `[AIREC]` этого решения |
| `to`, `bam` | узел патруля и вид хода (`BattleActionMove`) |
| `pushed`, `len`, `cost` | нашёлся ли путь, число шагов и цена всего пути в ОВ (сумма `getTUCost` по пути игры); `cost` −1 без пути |
| `first` | первый шаг: направление, ОВ, силы, клетка |
| `sn_en`, `sn_n` | v3 (ENERGY_PATROL_END_V2): наименьшая цена в силах шага в соседнюю клетку и число возможных шагов — `getTUCost` из клетки юнита в 10 направлениях тем же `bam`, без учёта других юнитов (прибор на время подсчёта снимает их с клеток вокруг и сразу возвращает) и без резерва ОВ; `sn_en` −1, если шага нет |
| `tu`, `energy`, `kneel` | юнит в момент решения |
| `reserve` | пропустит ли первый шаг проверка резерва ОВ (−1 — шага нет) |
| `free`, `reserved` | v2: сколько ОВ резерв оставляет на ход (наибольший шаг, который он пропускает; −1 — ни одного) и сколько держит (`tu − free`) |
| `rmode` | v2: режим резерва — у врага `AIModule::getReserveMode`, у игрока резерв стороны (`BattleActionType`: 0 нет, 7 авто, 8 навскидку, 9 прицельно) |
| `after`, `snap` | v2: ОВ после первого шага (с учётом «встать»; −1 — шага нет) и цена выстрела реакции — навскидку оружием, которое берёт `TileEngine::determineReactionType` (−1 — нет) |
| `known`, `seen`, `lof`, `lof_tu` | v2: врагов известно (правило `AiCandidates`), видит сам, врагов под выстрелом с линией огня — всего и по цене ≤ ОВ |
| `stop` | что остановит первый шаг, в порядке `UnitWalkBState`: `nopath`, `kneel` (не встать), `invalid`, `tu`, `energy`, `reserve`, `occupied`; `none` — шаг будет |
| `nreach` | клеток из списка ходов `[AICAND] moves` с ценой ≤ ОВ, кроме своей |
| `before` | цена пути до узла со своей клетки по поиску стенда (только если `stop` не `none`) |
| `best` | из 16 досягаемых клеток, ближайших к узлу, та, откуда путь до узла дешевле всего: клетка, цена дойти (`reach`), цена остатка (`after`), пустит ли резерв ход на `reach` ОВ |
| `best_ok` | то же среди клеток, которые резерв пускает |

Сравнение «в тени»: база стоит (`stop` не `none`), а L0-B пошёл бы на `best_ok`, если `after` < `before`.
Строки v1 (build-ai31) — без полей v2. Разбор по причинам — `E:\OXCE_AIWorker\source\l0b_path.py`.

## DecisionRecord v2 — проект (01.10): состояние после обязательных трат до think

Только проект, кода нет; не в одной правке с опытами стенда (память засады, повтор записи). Решение —
`docs/DECISIONS.md` 2026-10-01 (второе мнение): v1 заморожен, v2 — новая версия формата, не правка старой.

**Что не так в v1.** Запись снимается в `BattlescapeGame::handleAI` до `BattleUnit::think`
(`AiProbe::beforeThink`), а `BattleUnit::think` до `AIModule::think` сам тратит ОВ: перезаряжает оружие в
руке обоймой из сумки (`reloadAmmo`), раз в ход лечится и колется (`medikit_think`, кости внутри), и
`AIModule::think` после 200 сорванных ходов обнуляет ОВ. На таком решении `state.tu`, `state.energy` и
`cand.moves` v1 — состояние, которого ИИ не видел: он выбирал из досягаемости с меньшими ОВ, а `base.in`
сверяется с набором, построенным до трат. Таких решений мало (станция 2 из 440, город 0, бомбардировщик
53 из 801 — `[AIREUSE] own=`), но правила L0/L1, которые учатся «на том же состоянии», получают на них
чужое состояние. Нынешний `spendsBeforeThink` (запись сама считает досягаемость до think, когда трату
исключить нельзя) держит v1 побайтно — это мост совместимости, не семантика.

**Семантика v2.** Решение записывается в состоянии, в котором его принимает `AIModule::think`: после
обязательных трат, перед первым `findReachable` (`AIModule.cpp:522`) — точка `AiProbe::beforeDecide`
сразу после обхода зависания (`AIModule.cpp:500`). Оттуда: `state.tu`, `state.energy`, `state.hp/stun`
(аптечка их меняет), `cand` — из ответа игры на этот самый `findReachable` (как сейчас `reachTaken`), и
`base.in`/`exp` сверяются с этим набором. Своего `findReachable` у записи нет вовсе — `own`, `fallback`,
`tudiff` исчезают по построению, `spendsBeforeThink` не нужен. Что сделали траты — отдельный блок:

```json
"pre":{"tu0":84,"en0":70,"reload":1,"heal":0,"stim":1,"abort":0}
```

`tu0`/`en0` — до трат (то, что писал v1), `reload` — перезарядок, `heal`/`stim` — применений аптечки,
`abort` — ОВ обнулены обходом зависания; пустые траты — `"pre":null`. Повторное думанье (`BA_RETHINK`,
`handleAI` зовёт `think` второй раз) — отдельная запись, как в v1 (`k: r`), `pre` у неё `null`.
Остальные поля и их смысл — как в v1; `v: 2`. `[AIEXEC].spent` считается от `state.tu` v2 (после трат),
траты до think в него не входят — они в `pre`.

**Границы.** (1) v1 — исторический, читается как есть; скрытого пересчёта v1 → v2 нет: по v1 нельзя
восстановить ни ответ think, ни порядок трат. (2) Серии v1 и v2 не смешивать: `rec_diff.py`, `series_eq.py`,
`l0b_path.py` сверяют `v` и отказываются сравнивать разные; опыты L0/L1, начатые на v1, доигрываются на v1.
(3) `gen` остаётся `base_v2` — поколение движка то же, изменился формат записи. (4) Запись по-прежнему не
трогает ГСЧ и бой (`cand.rng` 0, семь потоков `=`).

**Приёмка** — таблица «Приёмка формата» выше (fair22, зерно 202, два прогона с записью против серии без
записи) плюс: `[AIREUSE] own=0 fallback=0 tudiff=0` на всех картах по построению; `pre` непустой ровно у
решений, где v1 давал `own` (станция 2, бомбардировщик 53); на решениях без трат запись v2 совпадает с v1
во всех полях, кроме `v` и `pre`.
