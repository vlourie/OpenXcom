## Второе ревью: три замечания

| Замечание | Исправление | Целевая проверка | Контроль на прежнем коде |
|---|---|---|---|
| 1. `Load()` под игрой переносил испорченный `builds.json` в `.bad` и писал новый | чтение отделено от починки | тест `A_damaged_list_under_a_running_game…`: под игрой ни один файл не изменился | починка при чтении — тест падает |
| 2. «Вышла сама» проверялось только по дампу | `wait_game()` возвращает (код, принудительно); у каждой игры четыре проверки | живая приёмка 44 из 44; контроль на зависшем процессе | прежняя проверка зачла бы зависший процесс |
| 3. `Delete()`: папка перенесена, список не записан — сборка без конфига | сначала список, потом папка; папка не ушла — сборка возвращается в список | тесты `A_delete_whose_list_cannot_be_written…`, `A_delete_whose_folder_cannot_be_moved…` | оба теста падают |

**1. Чтение без записи.** `Load()` — только чтение: при испорченном файле возвращает список,
собранный в памяти по папкам `user/builds/*`, и пишет в журнал лаунчера одну строку: «unreadable…
the list is rebuilt in memory, the file is repaired when the game is closed». Окно (`FillBuilds`),
`CurrentOptionsFile` и запуск этим списком пользуются как есть. Починка (`.bad` и новый файл) — в
`Repaired()`. Его зовут только действия после `Guard` и `Ensure`, и тот под игрой не чинит: целый
по папкам список отдаёт как есть, а пустой доходит до `Guard` и получает отказ.

Тест `A_damaged_list_under_a_running_game_is_read_and_nothing_is_written`. Испорченный
`builds.json` при работающей игре. `Load`, `CurrentOptionsFile`, `Ensure` и `MarkPlayed` работают;
создание, копия, переименование, выбор и удаление получают `UpdateBlockedException`. Снимок хэшей
всех файлов установки до и после совпал, `.bad` нет. После закрытия игры первое `Ensure` чинит файл.
Прежний тест прерванной миграции дополнен: `Load()` файл не трогает, `.bad` появляется только после
`Ensure()`. **Контроль:** с починкой при чтении падают оба теста.

**Найдено попутно.** `MarkPlayed` (отметка «сыграно» и `last`) стоял в `Play` после
`GameProcess.Start` и писал `builds.json` уже под игрой. Теперь он вызывается до старта, а под
работающей игрой пропускается без отказа: это отметка, а не действие игрока. Грабли — R-179
(`docs/rakes/portal.md`). Остальные записи `Builds.cs` проверены по списку: каждая идёт после
`Guard` или из `Repaired()`.

**2. Штатный выход игры.** `wait_game()` возвращает код выхода и признак «снята по таймауту
taskkill». У каждой игры, A и B, четыре отдельные проверки — одна не заменяет другую:

| Проверка | A | B |
|---|---|---|
| вышла сама: без таймаута и taskkill | OK | OK |
| код выхода 0 | OK | OK |
| кадр-дамп есть | OK | OK |
| сейв загружен, в логе кадры `GeoscapeState` | OK | OK |

**Контроль** — `wait_game` и `exited_cleanly` вынуты из скрипта и прогнаны на трёх процессах:

| Процесс | Итог |
|---|---|
| завис, снят по таймауту | `forced`, код 1 — FAIL по «вышла сама» и по коду, хотя кадр и геоскейп на месте (прежняя проверка дала бы PASS) |
| вышел сам с кодом 0 | PASS |
| вышел сам с кодом 3 | FAIL только по коду |

Оба живых запуска повторены (02.10, 18:12–18:16). Итог — 44 из 44 вместо 39 из 39: прежние три
проверки выхода стали восемью. Все прочие проверки и аудит §3.2 совпали с прошлым прогоном.

**3. Удаление сборки.** Порядок обратный: сначала записывается список без сборки, потом папка
переносится в резерв. Если запись списка не удалась, ничего не изменилось. Если не удалось
перенести папку, сборка возвращается в список на прежнее место, вместе с прежним `last`, и ошибка
уходит наверх. Если процесс прервётся между шагами, в `user/builds` останется папка без сборки. Сборки
без своего `options.cfg` в списке не бывает.

| Тест | Как вызван сбой | Проверено |
|---|---|---|
| `A_delete_whose_list_cannot_be_written_keeps_the_build_with_its_settings` | `builds.json` открыт другим (замена файла отказывает) | отказ; сборка в списке, `last` прежний, хэш её `options.cfg` прежний, в резерве пусто; после освобождения удаление проходит |
| `A_delete_whose_folder_cannot_be_moved_puts_the_build_back` | открыт `options.cfg` сборки (папку не перенести) | отказ; список восстановлен, `last` прежний, хэш конфига прежний, резерв пуст |

**Контроль:** прежний порядок (папка, потом список) — падает `A_delete_whose_list…`. Новый порядок без возврата
сборки в список — падает `A_delete_whose_folder…`. После контролей код восстановлен, в нём нет меток контроля,
тесты сборок — 15 из 15.

**Чего приёмка не проверяет.** Настройка игры менялась ключом командной строки, а игра выходила
сама через дамп. Это подтверждает, что игра пишет в конфиг своей сборки, но меню опций игры
не открывалось и сохранение из него не проверено.

## Что сделано

**Сборка — своя папка конфига.** `user/builds/<id>/options.cfg`; игра получает её ключом `-cfg`.
Список сборок — `launcher/builds.json` (схема 1: `last`, `builds[]` с `id`, `title`, `template`,
`targetGame`, `engineMaster`, `cfg`, `created`, `lastPlayed`).

**Запуск («Играть»)**: профиль применяется к конфигу выбранной сборки, затем

```
openxcom_hd.exe -user <установка>/user/ -cfg <установка>/user/builds/<id>/ -master <мастер>
```

Пути абсолютные, через `/`, с `/` на конце; рабочий каталог — папка установки.

**Миграция** — при первом старте лаунчера с этой версией: `user/options.cfg` копируется
побайтно в `user/builds/<активный мастер>/`; сам файл остаётся на месте и больше не трогается.
Память профиля (`launcher/profiles.json`, `profile-mods.json`) хранится по ключу мастера; id первой
сборки равен мастеру, поэтому она наследует эту память — профиль не перезаписывает уже
выставленное. Прерванная миграция и испорченный `builds.json` восстанавливаются по папкам
`user/builds/*`; испорченный файл откладывается как `.bad` при первом действии без игры, а под игрой
список собирается только в памяти.

**Управление**: новая сборка из профиля (§3.5), копия (побайтно конфиг и память профиля),
переименование, удаление (папка переносится в `launcher/backup/builds/<id>-<время>`, не стирается;
последнюю сборку удалить нельзя), выбор. В окне — выбор сборки на главной над кнопкой «Играть»,
кнопки в «Настройки → Игра → Сборки». Для скриптов — `--headless builds list|new|copy|rename|delete|select|args`.

**Запрет записи под игрой**: перед любой записью — проверка, что игра из этой установки не
запущена (`GameProcess.IsRunningIn`). Идёт — отказ `UpdateBlockedException`, в headless код 2.
Покрыто: создание, копия, переименование, удаление, выбор сборки, миграция, запись профиля
(окно, «сброс профиля», мастер установки, headless `profile`), обновление и откат (были и раньше).

**Мелкие следствия**: мастер установки (`SetupPage`) пишет профиль в конфиг сборки и читает свои
моды из него же; headless `profile` пишет в конфиг текущей сборки, а не в `user/options.cfg`, и под
игрой отказывает (раньше не отказывал).

`standard`, `UFO`, `TFTD` и `user/mods` — соединения на установку Пираток (только чтение);
`openxcom_hd.exe`, `xp-profiles.json`, состояние лаунчера, `options.cfg` и сейв `NoCodexCatZ.sav` —
копии. Установка Пираток не менялась. Лаунчер — текущая сборка `XPiratezLauncher.exe` в режиме

`-battleScrollSpeed 13`: движок при выходе сохраняет его в конфиг тем же путём `Options::save`.

### Аудит §3.2 — что игра пишет на живом запуске

Охват — два запуска одного сценария: загрузить сейв, постоять на геоскейпе, выйти по дампу. Экраны,
которые пишут сами (сохранение, меню опций, моды, бой), не открывались; аудит говорит только об
этих двух запусках и не заменяет обход всех записывающих экранов.

| Запуск | Добавлено | Изменено |
|---|---|---|
| игра на сборке A | `stderr.txt` (папка установки), `user/openxcom.log` | `user/builds/piratez/options.cfg` |
| игра на сборке B | — | `stderr.txt`, `user/openxcom.log`, `user/builds/build/options.cfg` |

В этих двух запусках `user/options.cfg`, сейвы, состояние лаунчера и чужие сборки не изменились.
В моды (через соединение — в установку Пираток) игра не записала ни одного файла. Лог игры и
`stderr.txt` — общие на установку, как и записано в §3.2: для игрока это безопасно, пока идёт одна игра.

## Чего этап не делает и что осталось
