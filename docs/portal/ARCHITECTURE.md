## 2. Главные выводы аудита

1. **Портал пишется с нуля.** Расширять нечего, поэтому берётся базовая архитектура из ТЗ, но
   с одной поправкой: **.NET 10 LTS, а не .NET 8.** Поддержка .NET 8 кончается 2026-11-10, через
   семь недель; .NET 10 LTS поддерживается до ноября 2028 и уже установлена.
2. **Лаунчер обновляет только наше.** Управляемые файлы — это exe движка и его DLL, `common`,
   `standard`, `user/mods/hd`, `user/mods/intro_voice`. Всё остальное в каталоге игры (`UFO`,
   `TFTD`, сам мод `Piratez`, русификатор, сейвы, `options.cfg`) лаунчеру **не принадлежит** и не
   трогается ни при обновлении, ни при восстановлении. Причины две: права на распространение
   (OPEN_QUESTIONS, вопрос 1) и то, что в `user/mods` игрока лежат чужие моды.
3. **Движок в сеть не ходит.** В OXCE нет HTTP-клиента, и заводить его в C++ ради формы — это и
   массовая правка, и новый класс уязвимостей. Вся сеть — в лаунчере.
4. **Форма F8 — окно лаунчера, а не виджеты движка.** Классические виджеты — это 320×200 без
   многострочного ввода, без буфера обмена и без выбора файла. Движок делает то, что умеет только
   он: снимает кадр, собирает контекст, ставит паузу — и запускает лаунчер в режиме отчёта.
5. **Этап 1 не ждёт домена и БД.** Updater работает с любым статическим хостингом: manifest и
   файлы — это просто объекты. API нужен начиная с этапа 2.

### 3.1 Launcher (C#, .NET 10, Windows 10/11)

- **Оболочка.** Avalonia 11.3 + NativeAOT, интерфейс кодом без XAML-привязок, отрисовка
  WGL/программная (ANGLE выбрасывается после публикации). Замер на прототипе: 33 МБ в пяти
  файлах против 51,6 МБ у WinForms self-contained. Сборка NativeAOT требует MSVC и vswhere в
  PATH — см. `RELEASING.md`.
r- **Каталог игры.** Указывается один раз; признаки — `OpenXComEx.exe` или `openxcom_hd.exe`
  рядом с `common` и `user`. Своё состояние лаунчер держит в `<игра>/launcher/`: `state.json`
  (канал, установленный релиз, кэш «путь → размер, время, SHA-256»), `staging/`, `backup/`,
  `queue/`, `logs/`.
- **Проверка.** Быстрая — по кэшу (размер + время совпали → хэш не пересчитывается), полная —
  кнопка «Проверить/восстановить файлы» пересчитывает SHA-256 всех управляемых файлов.
  1,9 ГБ — это несколько секунд на одном ядре.
- **Загрузка.** Только недостающее и изменённое; `.part` + HTTP Range для докачки; хэш каждого
  файла до установки; параллельно 4 потока; прогресс, скорость, текущий файл.
- **Установка.** staging → проверка всех хэшей → резервная копия заменяемых → переименование на
  месте (`File.Replace`/`MoveFileEx`). Журнал транзакции на диске: если лаунчер упал посреди,
  при следующем старте он докатывает или откатывает её. Хранится ровно одна резервная копия —
  «откатить последнее обновление».
- **Игра запущена** — определяется по процессу с путём exe внутри каталога игры; обновление
  заблокировано.
- **Файл, изменённый игроком.** Управляемый файл с чужим хэшем, которого нет ни в одном
  известном релизе, не заменяется молча: список показывается, игрок выбирает «заменить» или
  «оставить» (тогда файл помечается как локально изменённый до следующего релиза).

### 3.2 Bootstrapper

`xp-bootstrap.exe`, тот же NativeAOT. Лаунчер обновляется из своего канала `launcher-<канал>`:
скачивает и проверяет (подпись + SHA-256) новые файлы в
`%LOCALAPPDATA%\XPiratezLauncher\update\<релиз>\`, копирует bootstrapper во временную папку,
запускает его с `--pid --source --target --exe --file…` и выходит. Bootstrapper ждёт выхода,
кладёт прежние файлы в `.old-<время>`, ставит новые, запускает лаунчер с `--updated` и 30 с
ждёт метку `.update-ok`. Нет метки или лаунчер упал — возвращает прежние файлы и запускает
старую версию. Журнал — `%LOCALAPPDATA%\XPiratezLauncher\bootstrap.log`.

### 3.3 GameIntegration (C++, минимальная правка движка)

Три места, все в новом файле `src/Engine/Feedback.*` плюс по нескольку строк в точках вызова:

1. **F8 — отчёт** (сделано на этапе 3).
   `Game::run` ловит `Options::keyFeedback` (F8, без Ctrl и Alt) раньше верхнего состояния, так
   что мир клавишу не видит. `Feedback::open`:
   - `Screen::screenshot` в `<user>/reports/<uuid>/shot.png` — кадр до появления чего-либо нового;
   - `context.json`: формат, id отчёта, id сессии (один на запуск игры), время UTC, версия движка,
     мастер-мод, активные моды с версиями, ОС (`RtlGetVersion`), язык, имя верхнего состояния
     (без `OpenXcom::`), признак боя, размер и режим экрана, `oxceHdMode`/`oxceHdScale`, и пути
     лога, папки сейвов и игры — **ссылками**, без копирования. Пути нужны лаунчеру, на сервер
     они не уходят: в тикет идёт текстовая выжимка без путей (`Report.ContextText`, поле
     `Ticket.Context`);
   - `snapshot.sav` — сохранение текущей игры, как она есть в момент F8 (`SavedGame::save`, путь
     `../reports/<uuid>/snapshot.sav` от папки мастер-мода; `save()` константный и только читает).
     Не пишется в ironman (это был бы обход ironman), в превью боя и без загруженной игры; имя
     файла — поле `save` в `context.json`, пусто — снимка нет. Время записи — строка в логе;
   - запуск формы `<лаунчер> --report "<папка>"` через `CreateProcessW`. Лаунчер ищется так:
     переменная `XP_LAUNCHER` (её ставит лаунчер, запуская игру), затем
     `<игра>/launcher/launcher-path.txt` (пишет лаунчер, открыв каталог игры), затем
     `<игра>/XPiratezLauncher.exe`;
   - поверх стека кладётся `FeedbackState` (`_screen = false`, пустые `init`/`handle`): его
     `think()` раз в кадр спрашивает `WaitForSingleObject`, вышел процесс — состояние снимается.
   - **Пауза.** `Game` вызывает `think()` только у верхнего состояния, поэтому, пока
     `FeedbackState` наверху, стоят геоскейп-время, анимации боя, ИИ и таймеры, а ввод до мира
     не доходит. Флаг паузы геоскейпа (`GeoscapeState::_pause`) не трогается вовсе — после
     закрытия игра оказывается ровно в том состоянии паузы, в каком была.
   - Надписи поверх игры нет: кадр просто стоит, форма — отдельное окно поверх (`Topmost`).
   - Полноэкранный режим: SDL 1.2 при потере фокуса сворачивается; после закрытия формы окно
     игры разворачивается. **Не проверено** на живом полноэкранном режиме — пункт матрицы тестов.
   - Во время ролика (FLC-вступление) у плеера свой цикл событий, F8 там не работает.
   - Лаунчер не найден — пишется только папка отчёта и строка в лог, игра не встаёт на паузу;
     отчёт подхватит список «Отчёты» лаунчера. Не-Windows сборки — только папка.
   - Лаунчер в режиме `--report` не берёт общий мьютекс (форма открывается рядом с уже
     открытым лаунчером), а берёт свой на id отчёта: второй F8 на тот же отчёт выходит сразу.
     Папка, откуда пришёл отчёт, запоминается в `settings.json` (`reportRoots`), чтобы список
     отчётов нашёл её и при игре с папкой пользователя вне каталога игры.
   - **Отправка** (`Xp.Launcher.Core/Reports.cs`): `report.json` рядом с `context.json` хранит
     черновик и состояние (`draft`/`queued`/`sent`). Тикет создаётся один раз с
     `Idempotency-Key` = id отчёта; файлы шлются по одному, уже лежащие на сервере (имя + размер)
     не шлются повторно. Лог — только с галочкой, хвост до 4 МБ, вычищенный `Redactor`
     (пути игры и профиля, `C:\Users\<имя>`, имя пользователя, почта, токены). Сейв — только с
     галочкой, больше лимита — сжимается в zip, и всё равно больше — пропускается с причиной.
     В списке сейвов первым стоит снимок «Эта игра, как она есть сейчас», дальше последние сейвы
     мастер-мода; файл, который не начинается как сейв, в список не попадает. Перед отправкой сейв
     проверяется целиком тем же правилом, что и на сайте (`TextFiles.CheckSave`), — причина отказа
     показывается игроку на его языке. Язык тикета — язык игры (`context.json` → `language`); на
     нём же говорит форма, если в лаунчере язык ещё не выбран.
     Нет связи или 5xx/408/429 — отчёт в очереди; очередь отправляется **только кнопкой** в
     окне «Отчёты», в фоне ничего не уходит. Отправленных хранится 20 последних.
2. **Маркер сессии.** В начале `main` — `user/session.json` (pid, время, версии); штатный выход
   его удаляет; `crashDump` дописывает туда путь дампа и текст ошибки.
3. **Где лежат вещи.** Движок ничего не отправляет. Лаунчер, запустивший игру, дополнительно видит
   её код выхода.

Правка не касается пути рисования: IDENTICAL при `k = 1` проверяется как обычно, чтобы доказать,
что кадр не изменился.

### 3.4 API, Portal, Admin (один сервис ASP.NET Core, .NET 10) — `portal/src/Xp.Portal`

- **Один процесс, три части.** `/api/v1` — JSON для лаунчера и скриптов; сайт и админка —
  Razor Pages с серверной отрисовкой, без JS вовсе (CSP `script-src 'self'`, стили только файлом).
  Строки — `Strings/ru.json` и `en.json` в сборке, одинаковый набор ключей проверяет тест; ru по
  умолчанию, переключатель `/lang/{ru|en}` ставит cookie.
- **Данные.** PostgreSQL + EF Core, миграции кодом; `Xp.Portal migrate` применяет их и создаёт
  роли, в Docker это отдельный одноразовый сервис перед сайтом.
- **Файлы.** Каталог на томе (`Attachments:StorageRoot`, вне `wwwroot` — проверяется при старте),
  имена — случайные 32 hex, имя от пользователя только для показа. S3 отложен: хранилище закрыто
  классом `ObjectStore`, замена — одна реализация. Вложения идут потоком: размер считается на
  лету, первые 8 КБ сверяются с сигнатурой типа, файл за лимитом обрывается. Лог и сейв
  проверяются **целиком**, на лету: UTF-8 без NUL от первого байта до последнего, у сейва ещё
  заголовок `name:` … `version:` (`ContentCheck`). ZIP читается по записям без распаковки на диск
  (`ZipCheck`): не больше `MaxZipEntries` записей и `MaxZipUnpackedBytes` в распакованном виде,
  внутри только разрешённые типы, без вложенных архивов, и каждая запись проходит ту же проверку
  содержимого. Скачивание — по ссылке
  с HMAC-подписью на 5 минут, и права проверяются заново при каждом открытии; картинки — в
  браузере под `CSP: sandbox`, остальное — только скачиванием; «проверяется» и «в карантине» не
  отдаются никому.
- **Антивирус.** `ScanWorker` отправляет каждое новое вложение в clamd (INSTREAM): чисто →
  доступно, найдено → карантин навсегда, clamd недоступен → ждёт следующего прохода. Без
  настроенного clamd (разработка) файл помечается «без проверки антивирусом» и доступен команде.
- **Авторизация.** ASP.NET Core Identity: Argon2id (PHC-строка, слабые параметры → перехэш при
  входе), TOTP со своей страницей и резервными кодами, подтверждение почты, сброс пароля,
  блокировка после 5 неудач, rate limit на вход. Страницы команды требуют роль **и** вход с
  вторым фактором (`amr=mfa`); отметка переживает ежеминутную сверку security stamp. Смена ролей
  тут же сбрасывает старые сессии человека. Первый SuperAdmin — только `Xp.Portal admin create`.
- **Права.** Роли `User`/`Admin`/`SuperAdmin` + permissions (`tickets.code`, `tickets.graphics`,
  `tickets.balance`, `tickets.translation`, `tickets.general`, `docs.edit`, `roadmap.edit`,
  `releases.publish`). Класс `Viewer` — единственное место, где решается доступ: фильтр выборки
  очереди и проверка каждой страницы тикета. Тикет чужого раздела для Admin — такой же 404, как
  несуществующий, и в дубликат его отметить нельзя.
- **Фоновые задания.** Уведомление пишется в таблицу `NotificationJob` в той же транзакции, что
  и тикет. `TelegramWorker` берёт задания `FOR UPDATE SKIP LOCKED`, повтор через 30 с × 2ⁿ (до
  часа), уважает `retry_after` Telegram, после N попыток — `Dead`; повтор мёртвых — кнопкой.
  Маршрут: свой чат/тема на раздел, иначе маршрут `*`.
- **Язык тикета.** `Ticket.Language` — тег как у игры (`ru`, `en-US`), нормализуется
  (`TicketLanguage`). F8 — язык игры, форма сайта — язык интерфейса сайта. Очередь фильтруется по
  основной части тега (`en` собирает `en-US` и `en-GB`) и отдельно «без языка»; команда может
  исправить язык на странице тикета, это пишется в историю.
- **Тикеты гостей.** Номер для людей (`XP-000123`) + токен 128 бит, выведенный HMAC из секрета
  сервера и id тикета; в БД только SHA-256 токена. Повтор с тем же `Idempotency-Key` возвращает
  тот же тикет и ту же ссылку, с другим содержимым — 409. Страница по ссылке — `no-store`,
  `Referrer-Policy: no-referrer` на всём сайте.
- **Журналы.** Действия над тикетом — история тикета (кто, что, было → стало). Действия над
  людьми и настройками (роли, 2FA, маршруты Telegram) — общий журнал для SuperAdmin.

### 3.5 ReleaseBuilder (консольный .NET-инструмент)

Вход — готовый каталог версии, то есть `dist/_stage` из существующего `build.ps1`.
1. Обходит каталог, считает размер и SHA-256.
2. **Файлы хранятся по содержимому**: ключ объекта — `blobs/sha256/<ab>/<хэш>`. Одинаковая
   картинка в 43 паках (грабли R-049) хранится и качается один раз, а новый релиз заливает
   только новые блобы.
3. Собирает manifest, подписывает Ed25519 закрытым ключом (ключ — только на машине релиза или
   в секрете CI).
4. Заливает блобы и manifest, регистрирует релиз в API как `draft`.
5. Публикация в канал, отзыв и возврат канала на прежний релиз — в админке (permission
   `releases.publish`), с записью в аудит.

### 3.6 Графические утилиты

Статические страницы портала: Canvas + Web Worker (+ `OffscreenCanvas`), ничего не
отправляется на сервер. Ограничение — 8192×8192 и 64 Мп на картинку, понятная ошибка сверх того.

## 4. Хранилище релизов (схема 1)

Статическое дерево, отдаётся любым HTTP-сервером с поддержкой Range (в разработке —
`xp-release serve`, в продакшене — CDN или nginx):

```
blobs/sha256/<ab>/<sha256>           файлы по содержимому, общие для всех релизов
releases/<id>/manifest.json          состав релиза (компактный JSON)
releases/<id>/manifest.json.sig      подпись Ed25519
releases/<id>/release.json           статус draft/published/revoked — служебный, НЕ подписан
channels/<канал>.json + .sig         подписанный указатель канала
channels/<канал>.history.json        история канала — служебная, НЕ подписана
```

Лаунчеру канала `stable` соответствует канал `launcher-stable`, `test` — `launcher-test`.

**Указатель канала** — то, что лаунчер читает первым:

```json
{"schema":1,"channel":"test","sequence":2,"releaseId":"2026.09.22-dev2",
 "manifestSha256":"9e42…","manifestSize":6492703,"updated":"2026-09-22T18:52:06Z"}
```

`sequence` монотонно растёт при каждой смене канала (публикация, отзыв). Лаунчер запоминает
наибольший виденный номер и отказывается от указателя с меньшим — сервер не может подсунуть
старый уязвимый релиз (replay). Размер и хэш manifest берутся из подписанного указателя,
поэтому manifest отдельно не доверяется, а сверяется.

**Manifest:**

```json
{
  "schema": 1,
  "release": { "id": "2026.10.1-hd", "version": "2026.10.1", "channel": "stable",
               "published": "2026-10-01T12:00:00Z", "mandatory": false,
               "minLauncher": "1.0.0", "launch": "openxcom_hd.exe",
               "changelog": { "ru": "...", "en": "..." } },
  "components": { "engine": "OXCE 8.7.0+hd 3846d4c5f" },
  "roots": ["common/", "openxcom_hd.exe", "standard/", "user/mods/hd/", "user/mods/intro_voice/"],
  "files": [
    { "path": "user/mods/hd/hd/TERRAIN/DESERT.PCK/0.png", "size": 48213,
      "sha256": "…", "component": "hd" }
  ],
  "deletes": ["user/mods/hd/hd/UI_old/Foo.png"]
}
```

Адрес файла не хранится: он выводится из `sha256`. `roots` строятся автоматически — каждый
мод в `user/mods/` отдельным корнем, файлы верхнего уровня поимённо; сам `user/` корнем быть
не может, сборка релиза с таким файлом останавливается.

**Подпись** — отдельный JSON рядом с файлом: `{"algorithm":"ed25519","keyId":"739d80ec62db6e46",
"signature":"<base64>"}`, подписаны точные байты файла. `keyId` — первые 8 байт SHA-256 открытого
ключа. Открытые ключи зашиты в лаунчер из `portal/keys/release-keys.txt` строками
`dev|prod <base64>`; релизная сборка лаунчера доверяет только `prod` и без него не собирается.
Для смены ключа в список кладётся следующий ключ заранее, за релиз до перехода.

**Правила пути (проверяются до любой записи на диск):** только `/`, относительный, без `..`,
`.` и пустых сегментов, без `:`, `\`, `<>"|?*`, управляющих символов и имён устройств Windows
(`CON`, `NUL`, `COM1`…), без точки или пробела в конце сегмента, длина до 240 символов, путь
обязан попадать под один из `roots`. После нормализации проверяется, что полный путь лежит
внутри каталога игры. Удаления — только из `deletes` и только внутри `roots`.

**Защита поверх подписи.** Даже подписанный manifest не может писать в `user/` (кроме
`user/mods/<мод>/`) и в `launcher/` — это зашито в лаунчер (`InstallPolicy`): сохранения,
`options.cfg` и чужие моды игрока не трогаются никогда. Исполняемых шагов в manifest нет:
миграции, если понадобятся, — это код лаунчера конкретной версии, а не команды с сервера.

r## 5. Модель данных (основные сущности)

`User`, `Role`, `Permission`, `UserPermission` (специализации Admin) ·
`Ticket` (номер, категория, статус, приоритет, заголовок, описание, шаги, ожидаемое/фактическое,
версии, источник `web`/`f8`/`crash`, автор или гость + хэш токена, ответственный, `DuplicateOfId`,
`IdempotencyKey` уникальный) · `TicketMessage` (публичное/внутреннее) · `TicketAttachment`
(ключ объекта, имя от пользователя только для показа, размер, MIME по magic bytes, статус
проверки `pending`/`clean`/`quarantined`) · `TicketHistory` ·
`GameSession`, `CrashReport` (связан с тикетом) ·
`Release`, `ReleaseChannel`, `ReleaseFile`, `ReleaseManifest` ·
`DocumentationArticle` (версия игры, дата изменения) · `RoadmapItem`, `RoadmapHistory` ·
`DonationTarget` (получатель, URL, домен из allowlist) · `TelegramRoute`, `NotificationJob` ·
`AuditLog`.

Состояния тикета: `new → triaged → in_progress → needs_info → resolved → closed`, плюс
`duplicate`, `rejected`; переходы проверяются на сервере.

## 6. API — контракт в `docs/portal/openapi-v1.json`

Живое описание — `/openapi/v1.json`; зафиксированную копию сверяет тест
`OpenApiContractTests`, намеренная правка — `XP_UPDATE_OPENAPI=1 dotnet test`.

| Метод | Путь | Кто | Ответы |
|---|---|---|---|
| POST | `/api/v1/tickets` (заголовки `Idempotency-Key`, `X-Correlation-Id`) | гость, лаунчер | 201 · 200 повтор · 400 · 409 ключ с другим телом · 429 |
| GET | `/api/v1/tickets/{number}` (заголовок `X-Ticket-Token`) | держатель токена | 200 · 404 |
| POST | `/api/v1/tickets/{number}/messages` | держатель токена | 204 · 400 · 404 |
| POST | `/api/v1/tickets/{number}/attachments` (multipart, поток) | держатель токена | 201 · 400 · 403 нет согласия · 404 · 413 |
| GET | `/health`, `/ready` | мониторинг | `Healthy` без деталей |

API не читает cookie сайта: доступ — только токеном в заголовке, поэтому межсайтовый запрос из
браузера с открытой сессией ничего не может. Неверный токен и несуществующий номер — один и тот
же 404. Ошибки — `application/problem+json` с машинным `code` и `traceId`, без stack trace.
`/api/v1/crash-reports` и манифест через API — этапы 4 и позже; админка — страницы, не API.

## 7. Модель угроз (кратко)

| Угроза | Защита |
|---|---|
| Подмена manifest или файла (взлом CDN, MITM) | подпись Ed25519 + SHA-256 каждого файла; HTTPS — только второй слой |
| Запись вне каталога через manifest | правила пути, проверка `GetFullPath`, только `roots` |
| Утечка ключа подписи | ключ только на машине релиза/в секрете CI; два ключа в лаунчере для ротации |
| Вредоносное вложение | allowlist расширений + magic bytes + лимиты; хранилище вне web-root, `Content-Disposition: attachment`, `nosniff`; ClamAV в карантин; ZIP не распаковывается |
| Чтение чужого тикета перебором | секретный токен гостя, проверка владельца, фильтр категорий у Admin |
| Спам и брутфорс | rate limit по IP и токену, honeypot + задержка, опционально капча |
| Утечка приватного в Telegram | сообщение собирается только из номера, категории, обрезанного и экранированного заголовка, версии, времени и ссылки |
| Личные данные в логах | вычистка в лаунчере до отправки: имя Windows-пользователя, домашние пути, email, токены; игрок видит файлы до отправки |
| Самообновление подменили | bootstrapper проверяет подпись; при сбое — откат |

## 8. Что не делаем

- Движок не получает сети, форм, TTF-полей ввода и чего-либо, что влияет на механику.
- Лаунчер не распространяет `UFO`, `TFTD` и чужие моды, пока не решён вопрос прав.
- Собственного приёма платежей нет: донаты — внешние ссылки.
- Телеметрии нет. Sentry не подключается без отдельного решения.
