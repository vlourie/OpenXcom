## 0. Коротко

1. **Одна папка игры, много «сборок».** Сборка — это целевая игра, набор модов в нужном
   порядке и настройки игрока. Все моды физически лежат в одной `user/mods`, у каждой
   сборки свой `options.cfg`. Переключение — запуск игры с другим `-cfg`, файлы не
   копируются. Движок это умеет уже сейчас.
2. **Мастер движка и целевая игра — разные вещи.** RoSigma и X-Com Files могут стоять на
   одном мастере движка. Поэтому совместимость пишется на **целевую игру** (`targetGame`),
   а `master` из `metadata.yml` — только факт о движке (`engineMaster`).
3. **Совместимость в четыре слоя:** движок → целевая игра → мод с модом → арт с ресурсом.
   Четвёртый слой у нас пока не решён вовсе, его надо закрыть до первой чужой игры (§5.4).
4. **Опции движка показываются по возможностям.** Мод объявляет, что даёт; движок
   подтверждает, что ресурс есть и подходит. Никаких проверок по имени мода в коде.
5. **«Загрузилось» — ещё не «совместимо».** У проверки три отдельных результата с понятным
   объёмом, и каждый привязан к точному составу сборки (хэши, порядок, настройки). Сменился
   состав — в том числе через меню модов в самой игре — результат недействителен. Провал —
   красный, «не запускалось» — жёлтый, сбой стенда — не результат вовсе (§5.1).
6. Этап 1 обходится **без правки движка**. Последующие правки движка касаются интерфейса,
   путей и проверки ресурсов, а не механики.

## 2. Термины

| Термин | Что это | Пример |
|---|---|---|
| **Установка** | одна папка игры с одной линией движка (EDITIONS §2) | `X-COM HD\` с `openxcom_hd.exe` |
| **Мастер движка** (`engineMaster`) | то, что движок считает мастером: `isMaster: true`, ключ `-master`, папка сейвов | `xcom1`, `xcom2`, `piratez`, возможно `40k` |
| **Целевая игра** (`targetGame`) | то, во что игрок играет; на неё пишется совместимость | Piratez, RoSigma, X-Com Files |
| **Мод** | любая папка в `user/mods` с `metadata.yml` | RU-патч, `hd_core`, пример общего дополнения |
| **Сборка** | целевая игра + упорядоченный список модов (вкл/выкл) + свой `options.cfg` | «Пиратки HD», «RoSigma + общее дополнение» |
| **Шаблон сборки** | пресет из каталога, из которого сборка создаётся | `piratez-hd` |
| **Возможность** (capability) | функция движка, которой нужен контент мода | `baseAnim`, `craftOutlines` |
| **Отпечаток сборки** | хэш, который определяет сборку для проверок (§5.1) | — |

Зачем два поля вместо одного. Если RoSigma и X-Com Files обе стоят на мастере движка
`xcom1`, то одним `master: xcom1` нельзя сказать «это общее дополнение подходит для
RoSigma, но не для X-Com Files». И будущий `hd_rosigma` нельзя защитить от X-Com Files: движок включит его
в обеих. `engineMaster` — факт из `metadata.yml`, он задаёт, что движок вообще позволит.
`targetGame` — наше понятие из каталога, и на нём держится вся совместимость.

> **Этап 0, проверить до проектирования.** По словам специалиста, авторский репозиторий
> описывает RoSigma как подмод 40k OXCE. Значит, у неё может быть **обязательная
> зависимость** от 40k, а мастер движка может оказаться `40k`, а не `xcom1`. Смотреть
> `metadata.yml` текущего релизного архива RoSigma и X-Com Files, а не репозиторий и
> не память. Пока файла нет, пример в §4 условный.

## 3. Сборки: одна папка, мгновенное переключение

### 3.1 Как это работает в движке уже сейчас

Проверено по коду `src/Engine/Options.cpp`:

- `-cfg <папка>` (`loadArgs`, `_configFolder`) — откуда читать и куда писать `options.cfg`.
  В нём живут список модов с порядком и вкл/выкл, все опции и флаг
  `oxceRecommendedOptionsWereSet`. Другие `*.cfg` в папку конфига движок не пишет:
  `Options::save` везде зовётся с именем по умолчанию.
- Моды на ПК ищутся только в `standard/` и `<user>/mods` (`FileMap::scanModDir`),
  независимо от `-cfg`. `<data>/mods` сканируется только в мобильной сборке.
- `-master <id>` — какой мастер движка поднять.
- Сейвы лежат в `<user>/<мастер движка>/` (`getMasterUserFolder`).

Значит, сборка — это своя папка конфига:

```
X-COM HD\
  user\mods\Piratez, ROSIGMA, hd_core, hd_piratez, ...         все моды, одна копия каждого
  user\builds\piratez-hd\options.cfg                           список модов и настройки сборки
  user\builds\rosigma\options.cfg
  user\piratez\*.sav    user\xcom1\*.sav                       сейвы по мастеру движка
```

**Запуск — только с абсолютными путями и фиксированным рабочим каталогом:**
`<установка>\openxcom_hd.exe -user <установка>\user\ -cfg <установка>\user\builds\rosigma\
-master <engineMaster>`, рабочий каталог — папка установки. Относительный путь в аргументе
движок разрешит от текущего каталога процесса, а он у лаунчера и у игры, запущенной
ярлыком, разный (та же природа, что у грабель R-097).

Флаг `oxceRecommendedOptionsWereSet` хранится в `options.cfg`
(`Mod.cpp`, применение рекомендаций). Поэтому с отдельным конфигом на сборку рекомендации
мода приходят **в каждую сборку свои**. Как это работает при копировании — §3.5.

### 3.2 Что игра пишет мимо `options.cfg` — аудит по коду

| Файл | Где (код) | Папка | Общий для сборок? | Что делаем |
|---|---|---|---|---|
| `openxcom.log` | `Options.cpp:903` | `user/` | **да** | игрок: только одна игра за раз (§3.6). Проверки: свой `-user` на прогон (§5.3) |
| отчёты F8 | `Feedback.cpp:238` | `user/reports/` | да | в `context.json` отчёта записывать id сборки |
| `oxce-update.txt` | `MainMenuState.cpp:190` | `user/` | да | не трогаем, это проверка обновлений OXCE |
| сейвы, автосейвы, quicksave | `SaveGameState`, `ListSaveState` | `user/<мастер>/` | да, внутри мастера | §3.3 |
| `battle.cfg` (новый бой, экран корабля) | `NewBattleState.cpp:396`, `CraftInfoState.cpp:629` | `user/<мастер>/` | да | терпимо на этапе 1; уходит вместе с сейвами в путь сборки на этапе 6 |
| снимки экрана, дампы Ctrl+F8, AIExposure | `Screen.cpp:185`, `HdTest.cpp:40`, `BattlescapeState` | `user/<мастер>/` | да | без вреда; уходят вместе с сейвами |
| `options.cfg` | `Options::save`, на выходе из игры (`Game.cpp:668`) и в меню опций | папка `-cfg` | **нет** | правда сборки |
| `options.cfg.bak` | `ProfileWriter` (лаунчер) | папка `-cfg` | нет | — |

Вывод: настройки разделяются полностью, а всё прочее делится по мастеру движка или по всей
установке. Для игрока это безопасно, пока в установке одновременно идёт одна игра (§3.6).
Для параллельных проверок — нет, поэтому у каждого прогона свой `-user` (§5.3).

### 3.3 Что хранится и где

| Что | Где | Кто пишет |
|---|---|---|
| описание сборок: id, имя, шаблон, целевая игра, мастер движка, линия | `launcher/builds.json` | лаунчер |
| моды, порядок, настройки игры | `user/builds/<id>/options.cfg` | игра (меню модов и опций) и лаунчер по правилам `ProfileWriter` |
| последняя сборка | `launcher/builds.json` | лаунчер |
| файлы модов | `user/mods/<мод>`, одна копия на установку | лаунчер по manifest или игрок руками |

Правило записи в `options.cfg` из EDITIONS §12.5 остаётся: лаунчер меняет только список
модов и ключи профиля. `InstallPolicy` расширяется с `user/options.cfg` на
`user/builds/*/options.cfg`.

**Перед каждым запуском лаунчер перечитывает `options.cfg` сборки** и заново проверяет
состав — игрок мог поменять моды в меню самой игры:

1. Слои 1–2 (§5) по фактическому списку активных модов. Мод чужой целевой игры, включённый
   из игрового меню, — запуск блокируется с причиной и кнопкой «вернуть состав сборки».
2. Обязательные компоненты игры (`games.requires`, §4.1) все включены? Нет — `targetGame`
   сборки в этот момент **недостоверен**: карточка пишет «состав не соответствует игре
   RoSigma: выключен 40k», запуск — только явным подтверждением.
3. Отпечаток (§5.1) пересчитывается. Не совпал с проверенным — прежние результаты к нему
   не относятся, и статус берётся по таблице §5.1 как для нового отпечатка без результатов
   («не проверялось»); сама сборка запускается.

**Миграция:** при первом запуске нового лаунчера нынешний `user/options.cfg` копируется в
папку сборки по текущему мастеру. Сам `user/options.cfg` остаётся для запуска exe без
лаунчера.

### 3.4 Сейвы

Сейвы делятся по **мастеру движка**. Сборки одного мастера делят папку: RoSigma и X-Com
Files на одном мастере увидят сейвы друг друга.

**Чей это сейв — без отдельной метки сказать нельзя.** В заголовке `.sav` есть список модов,
но у двух сборок он может быть одинаковым при разных настройках («RoSigma» и её копия с
другими опциями). Поэтому:

- **этап 1:** общий каталог и честное предупреждение. Лаунчер по списку модов показывает
  **подходящие** сборки («подходит к: RoSigma, RoSigma-копия»), но не утверждает, чей сейв;
- **этап 6:** свой путь сейвов у сборки — новый ключ `-saves <подпапка>`, тогда
  `getMasterUserFolder()` = `user/<мастер>/<подпапка>/`. Без ключа — как прежде, старые
  сейвы на месте. Вместе с сейвами туда уходят `battle.cfg`, снимки и дампы (§3.2). Механика
  не меняется, только путь. Делать после аудита §3.2 на живой игре: пройти все экраны,
  которые пишут файлы, и сверить, что ничего не легло мимо.

### 3.5 Новая сборка и копия сборки

| Действие | `options.cfg` | `oxceRecommendedOptionsWereSet` | Что получает игрок |
|---|---|---|---|
| новая сборка из шаблона | из профиля шаблона, без пользовательских ключей | `false` | рекомендации своего состава модов при первом запуске |
| копия сборки | побайтная копия исходной | как у исходной (`true`) | свои прежние настройки; рекомендации заново не накатываются |
| «сбросить настройки к профилю» | заново из профиля | `false` | как новая сборка |

### 3.6 Безопасная запись и обновление

- **Пока игра работает, лаунчер не меняет её конфиг и используемые компоненты.** Игра пишет
  `options.cfg` на выходе (`Game.cpp:668`) и затрёт любую запись лаунчера, сделанную в
  промежутке. Обновление уже это соблюдает (`Updater.IsGameRunning`); запись профиля и
  управление сборками — должны тоже.
- **Одна игра на установку за раз.** Вторая игра той же установки запишет в общий
  `openxcom.log`, `user/reports/` и, на одном мастере, в общую папку сейвов. Лаунчер не
  запускает вторую копию и объясняет почему.
- Конфиги пишутся атомарно и с `.bak` — как уже делает `ProfileWriter`.
- **Обновление общего мода проверяется против всех сборок установки** (§5.5) до начала
  установки. Сломает какую-то сборку — лаунчер называет её и спрашивает.
- **Ошибка установки откатывается:** журнал операций (`Journal` в состоянии лаунчера) уже
  есть для выпусков. Он должен покрывать и компоненты сборок, и правку конфигов.

### 3.7 Одна версия мода на установку

Id мода в `user/mods` уникален, вторая копия с тем же id молча пропускается (грабли R-074).
Поэтому **разные версии одного мода для разных сборок в одной папке держать нельзя.**
Закрепить версию можно только отдельной установкой. Обходить это переименованием id
нельзя: сейв запоминает id мода.

## 4. Модель данных

### 4.1 Каталог, схема 2 — моды, игры и требования

```json
"games": [
  { "id": "piratez", "engineMaster": "piratez", "requires": ["piratez"] },
  { "id": "rosigma", "engineMaster": "<из metadata.yml, этап 0>", "requires": ["40k?", "rosigma"] },
  { "id": "xcf",     "engineMaster": "<из metadata.yml, этап 0>", "requires": ["xcf"] }
],
"mods": [
  { "id": "piratez", "kind": "master", "source": "repo", "lines": ["oxce", "oxce-hd"] },
  { "id": "rosigma", "kind": "game-core", "source": "upstream",
    "upstream": { "url": "…", "sha256": "…", "size": 0, "extract": { "ROSIGMA/": "user/mods/ROSIGMA/" } } },
  { "id": "piratez_tank_turret", "kind": "addon", "targetGames": ["piratez"], "engine": "OXCE-HD" },
  { "id": "hd_core", "kind": "art", "targetGames": "*", "provides": ["hdFonts"] },
  { "id": "hd_piratez", "kind": "art", "targetGames": ["piratez"], "requires": ["hd_core"],
    "provides": ["terrainHd", "unitsHd", "baseAnim", "craftLights", "craftOutlines", "hdFx", "hdUiSkin"] }
]
```

- `games` — целевые игры. `engineMaster` — что запускать ключом `-master` и где сейвы.
  `requires` — без чего игра не собирается (у RoSigma, возможно, 40k).
- `targetGames` у мода — для каких игр он сделан: список или `"*"`. Это главное поле
  совместимости. `master` из `metadata.yml` проверяется отдельно, как факт движка: мод,
  который движок не включит, каталог предложить не может, что бы ни было в `targetGames`.
- Общее дополнение для нескольких игр пишется так же: `"targetGames": ["piratez", "rosigma"]`.
  Конкретного мода-примера в рабочем каталоге нет, пока он не выбран (§13).
- **Лаунчер запрещает несовместимое сочетание по `targetGames`. При изменении состава через
  игровое меню результат проверки теряет силу. Защиту от подмены HD-кадров при фактической
  загрузке обеспечивает проверка подписи ресурса** (§5.4 п.3). `targetGames` — правило
  лаунчера, а не движка: движок включит `hd_rosigma` в X-Com Files, если игрок сам
  поставит галочку в меню модов, и мастер движка у них общий. Поэтому лаунчер перечитывает
  состав перед каждым запуском (§3.3), а движок не верит имени набора без подписи.
- `source`: `repo`, `upstream` или `repo+upstream` (EDITIONS §12.2).
- `provides` — что мод обещает (§6). Обещание не равно факту: факт подтверждает движок.

### 4.2 Сборка на машине игрока

```json
{ "id": "rosigma-hd", "title": "RoSigma + HD", "template": "rosigma-hd", "line": "oxce-hd",
  "targetGame": "rosigma", "engineMaster": "<из каталога>",
  "cfg": "user/builds/rosigma-hd/", "created": "2026-10-02", "lastPlayed": "…" }
```

Моды и опции сборки в `builds.json` не дублируются: правда одна — её `options.cfg`.
Иначе меню модов в игре и лаунчер разойдутся (семья граблей R-087).

`targetGame` в `builds.json` — **заявка**, а не факт. Лаунчер сверяет её с фактическим
составом перед каждым запуском (§3.3) и показывает как недостоверную, если выключен
хоть один обязательный компонент игры.

## 5. Совместимость — четыре слоя

| Слой | Вопрос | Откуда правда | Кто проверяет | При нарушении |
|---|---|---|---|---|
| 1. движок | пойдёт ли мод на этом exe | `requiredExtendedEngine`, `requiredExtendedVersion` | движок и лаунчер заранее | строка серая, с причиной |
| 2. игра | для какой игры мод | `targetGames` в каталоге; `master` из `metadata.yml` как ограничение движка | лаунчер; движок (`canActivate`) | мод не предлагается в этой сборке |
| 3. мод с модом | уживается ли мод с этой сборкой | каталог: `requires`, `conflicts`, `loadAfter` | автоматическая проверка (§5.3) | предупреждение или запрет |
| 4. арт с ресурсом | рисует ли HD-кадр то, что под ним | **сейчас ничто** | движок при загрузке ресурса (§5.4 п.3) | классический кадр и строка в логе |

### 5.1 Результаты проверки

«Успешно загрузилось» и «совместимо» — разные вещи. Невидимый запуск не увидит неверную
картинку, сдвиг баланса или конфликт, который проявится после исследования. Поэтому у
проверки три **независимых** результата, и каждый называет свой объём:

| Результат | Что подтверждено | Чем |
|---|---|---|
| **Загрузка пройдена** | сборка дошла до главного меню без ошибок загрузки в логе | `mod_compat.py load` |
| **Смоук-тест пройден** | выполнен конкретный сценарий: новая кампания, переход на геоскейп, один бой ботом до конца, сохранение и загрузка | `mod_compat.py smoke`, сценарий назван в результате |
| **Графика проверена** | **полный охват подписей**: проверено = ожидалось, отвергнуто = 0, не проверено = 0 (§5.3); контрольные кадры сняты и сравнены — они подтверждают только перечисленные сцены | `mod_compat.py art` + дампы |

У каждого из трёх результатов одно из значений:

| Значение | Когда |
|---|---|
| **пройдено** | проверка выполнена до конца, ошибок нет |
| **провалено** | проверка выполнена и нашла ошибку: падение, строка лога из §5.3 п.3, бой не доигран, отказы подписи |
| **не завершено** | только графика: отказов нет, но охват неполный (не проверено > 0). Показывается свой охват, зелёного не даёт |
| **не запускалось** | проверку не проводили для этого отпечатка |
| **результат не получен** | проверку начали, но стенд не дал ответа: таймаут без признаков игры, нет места на диске, сбой запускателя. Причина пишется отдельным полем и **ничего не говорит о сборке** |
| **не требуется** | только для графики: в сборке нет HD-модов, проверять нечего |

Статус сборки выводится из трёх результатов:

| Статус | Условие | Что видит игрок |
|---|---|---|
| **зелёный** | загрузка и смоук пройдены, графика пройдена **или не требуется** | можно играть; подсказка называет сценарий и дату |
| **жёлтый** | загрузка пройдена, смоук или графика не запускались, графика не завершена (или результат не получен) | подсказка называет, что именно пройдено, и охват графики |
| **красный** | загрузка или смоук провалены; слово автора «несовместимо» | заблокировано в обычном режиме, причина видна |
| **отказ графики** | загрузка и смоук пройдены, графика провалена | не зелёный; лаунчер **прямо предлагает** «запустить с классической графикой» — один раз, настройки сборки не меняются (ниже) |
| **не проверялось** | ничего не запускалось, слои 1–2 пройдены; **так же — любой новый отпечаток без результатов** | серая метка «не проверено» |

**Одноразовый запуск с классической графикой.** Передать `-oxceHdMode 0` недостаточно.
По коду значение из командной строки ложится в те же опции, что и прочитанные из конфига
(`Options.cpp:1306`), а `Options::save` при выходе пишет все опции (`Options.cpp:1377`) —
режим 0 останется в `options.cfg` сборки навсегда. Ещё и F9 в игре меняет `oxceHdMode`.
Способ временного переопределения выбирается **опытом**, кандидаты:

- запуск на временной копии папки конфига, после выхода в конфиг сборки переносятся все
  изменения, кроме переопределённого ключа; незавершённый перенос доделывается при
  следующем старте лаунчера по журналу (§3.6);
- ключ движка «не сохранять значения из командной строки» — правка движка, только если
  первый способ не годится.

Требования специалиста к временному конфигу (02.10, обязательны для любого способа):

- после выхода изменения игрока **переносятся обратно** в конфиг сборки, а ключи графики,
  которые переопределял запуск, получают **исходные значения сборки** — те, что были до
  запуска, а не те, с которыми игра вышла;
- если игра или лаунчер **закрылись аварийно**, временный конфиг не удаляется: он остаётся
  на диске, лаунчер при следующем старте предлагает восстановление (перенос по тем же
  правилам), и до решения игрока ничего не теряется.

Приёмка опытом: сборка с `oxceHdMode 2` → запуск с классикой → в игре меняется другая
настройка → выход. После выхода `oxceHdMode` = 2, другая настройка сохранилась.
Контроль: голый `-oxceHdMode 0` даёт после выхода 0. Второй опыт: игра снята
`taskkill /F` посреди сессии → временный конфиг на месте → следующий старт лаунчера
переносит его по тем же правилам.

«Результат не получен» — забота стенда, а не игрока: у игрока такой результат показывается
как «не запускалось», а у нас уходит в отчёт стенда с причиной и в повтор. Красным сборку он
не делает никогда.

Ни один результат не утверждает, что баланс не сдвинут и что сборка доживёт до конца
кампании. Это пишется прямо в подсказке зелёного статуса.

**Ключ результата — отпечаток сборки**, а не номера версий:

- хэш exe;
- хэши компонентов (содержимое каждого мода, а не его `version` из `metadata.yml`);
- порядок активных модов;
- значимые настройки — те, что меняют загрузку или картинку: язык, `oxceHdMode`,
  `oxceHdScale`, ключи из `fixedUserOptions` профиля;
- версия теста (`mod_compat.py` и сценария).

Изменилось хоть что-то — прежний результат недействителен, сборка становится «не
проверялось» до новой проверки. Сюда входит и смена состава через игровое меню модов
(§3.3). Отпечаток считает лаунчер у игрока так же, как сборщик, — поэтому зелёный статус
у игрока означает ровно ту комбинацию, которую мы проверили.

### 5.2 Порядок загрузки

Порядок выводится **стабильной топологической сортировкой** по `requires` и `loadAfter`:
при равенстве — порядок из шаблона, затем по id. Цикл в зависимостях — явная ошибка
каталога, сборщик его не публикует. Ручная перестановка разрешена, если не нарушает
`requires` / `loadAfter`; кнопка «рекомендованный порядок» её отменяет.

### 5.3 Как проводится проверка

Новый инструмент `tools/mod_compat.py`:

1. Каждый прогон — в **своей** временной папке: свои `-user` и `-cfg`, моды из установки
   (соединение папки, как у `tools/game_hidden.py`; снимать только `rmdir`, R-047). Так у
   каждого прогона свой `openxcom.log`, и параллельные проверки не мешают друг другу.
2. Игра запускается невидимо (`game_hidden.py` / `ai_probe.Hidden`: свой рабочий стол,
   SDL dummy — R-124).
3. `load`: до главного меню и выход. Ошибка — любая строка `ERROR`, `not found in` (R-036),
   `already mapped in` (R-074), `is far from` (R-033), битые ссылки рулсета.
4. `smoke`: сценарий из §5.1, бой — ботом стенда ИИ.
5. `art`: отказы проверки ресурсов (§5.4 п.3) и контрольные кадры по точкам сценария.
   **Охват — четыре числа** по HD-кадрам, которые сборка должна использовать:
   - **ожидалось** — кадры активных HD-модов, чьи наборы есть в итоговых ресурсах сборки;
   - **проверено** — подпись сверена и совпала;
   - **отвергнуто** — подпись не совпала, движок рисует классику;
   - **не проверено** — набор не загружался за прогон (сцены, куда сценарий не дошёл).

   **«Пройдено» — только при полном охвате:** проверено = ожидалось, отвергнуто = 0,
   не проверено = 0. Частичный прогон показывает свой охват и даёт «не завершено».
   Подпись можно сверить и без сцены — для всех наборов при загрузке, тогда «не проверено»
   обнуляется. **Контрольные кадры подтверждают только названные сцены** (геоскейп,
   база, бой на карте сценария) — результат перечисляет их и не обобщает на остальные.
   Сборка без HD-модов получает `art = не требуется`, и это не мешает зелёному.
6. Пишет `compat.tsv`: отпечаток, три результата, причину «не получен», сценарий и
   названные сцены, охват графики (четыре числа), версию теста, строки лога. Сборщик
   каталога берёт оттуда статусы, сайт строит матрицу.

### 5.4 Арт с ресурсом — главный риск

Проверено по коду: HD-кадры ищутся **по имени набора** (`HdSprites::loadPack`,
`hd/TERRAIN/<имя>.PCK/<кадр>.png`), картинки интерфейса — **по имени файла без мода**
(`Mod.cpp` → `HdUiArt::addLazy`, R-033). Сверки с классическим кадром нет. Мод `hd`
объявлен `master: "*"`. Значит, в чужой игре одноимённые наборы (ванильные `CULTIVAT`,
`BARN`, `BASEBITS` и другие) получат кадры Пираток без единой ошибки.

Три шага:

1. **Разделить `hd` по зависимости от исходного ресурса, а не по виду графики.** Граница —
   «нарисовано под конкретный ресурс игры или независимо»:
   - `hd_core` (`targetGames: "*"`): **только то, что подтверждено универсальным** —
     TTF-шрифты и курсоры, нарисованные независимо от кадров `CURSOR.PCK`. Подтверждение —
     отдельная проверка: ресурс не опирается на кадр, палитру или рулсет конкретной игры;
   - `hd_piratez` (`targetGames: ["piratez"]`): **всё остальное**, включая скин интерфейса,
     прицелы, глобус и боевые эффекты. Чужая игра может переопределять тот же ресурс
     (свой `CURSOR.PCK`, свои цвета интерфейса, свои `SMOKE.PCK`), поэтому без проверки
     они считаются зависимыми;
   - ресурс переезжает из `hd_piratez` в `hd_core` только после проверки на второй игре;
   - позже `hd_rosigma`, `hd_xcf`.

   Арт читается через виртуальную ФС движка (`FileMap`), куда попадают только активные
   моды, поэтому раздел — перенос папок и правка сборщика. Проверка: режим 0 при k=1 и k=4 —
   IDENTICAL; Пиратки с `hd_core` + `hd_piratez` — тот же кадр, что с прежним `hd`
   (контрольный опыт: без `hd_piratez` — DIFFERENT, R-086).
2. **`targetGames`** в каталоге не даёт лаунчеру включить `hd_piratez` вне Пираток (§4.1).
3. **Подпись исходного ресурса** (движок). Имя набора и номер кадра остаются ключом,
   к ним добавляется подпись классического ресурса, под который нарисован HD-кадр:
   - сверяется **итоговый** классический ресурс — после применения всех активных модов, а не
     файл одного мода;
   - в подпись палитрового кадра входят: размеры, индексы пикселей, прозрачность (индекс 0
     и tRNS, как читает `Surface::FixTransparent`, R-043) и **значимая палитра** — записи
     палитры, которые реально встречаются в кадре. Точный состав — решение этапа 6, с
     замером: перекраска палитрой мода не должна молча проходить;
   - проверка — **вне цикла отрисовки**: при загрузке набора или при первом обращении к
     кадру; результат кэшируется на кадр до смены набора модов;
   - не совпало — классический кадр (через обычный путь режима 1/2) и одна диагностическая
     строка в логе на набор, с числом отказов;
   - подписи пишет сборщик пака рядом с кадрами (`<кадр>.src` или таблица на набор).
   Переход на ключ «только хэш содержимого» сейчас не нужен.

### 5.5 Какие комбинации проверяются

1. Каждый официальный шаблон сборки целиком.
2. Шаблон плюс одно дополнение из каталога для этой игры.
3. Известные конфликтные сочетания — список в каталоге, пополняется по отчётам.
4. Перед обновлением общего мода — все сборки, где он включён, по отпечаткам из
   `compat.tsv` (у игрока — его собственные сборки, проверка слоёв 1–3 по каталогу).

Пары модов сами по себе ничего не доказывают о сборке целиком и отдельно не гоняются.

## 6. Опции движка — по возможностям контента

### 6.1 Принцип

Строка HD-меню (`OptionsHdState`) видна, если её возможность **подтверждена** в активной
сборке. Подтверждение идёт в два шага:

1. **Объявление** — мод говорит, что даёт: `hdProvides: [...]` в `metadata.yml` арт-мода
   (в каталоге — `provides`). Это ожидание, на нём строится карточка в лаунчере и на сайте.
2. **Подтверждение движком** — ресурс есть и пригоден:
   - `craftOutlines`: в `hd/OUTLINE/index.txt` есть хоть один тип корабля или НЛО из
     загруженного рулсета (`HdOutline` и так ищет по типу рулсета);
   - `hdFx`: в `hd/FX/weapons.txt` есть хоть один тип предмета из рулсета;
   - `baseAnim`, `craftLights`: в `hd/BASEBITS.PCK` есть фазы `.vN` или `.lights.txt` для
     кадров построек и кораблей рулсета, **и** эти кадры прошли подпись ресурса (§5.4 п.3);
   - `groundVariants`: в паках террейна есть `<кадр>.v1.png`, прошедшие подпись.

Объявлено, но не подтверждено — строки нет, а в логе одна запись «мод X обещает baseAnim,
пригодных кадров 0». Это же расхождение `mod_compat.py` пишет в `compat.tsv`. Подтверждено,
но не объявлено — строка есть, а сборщик предупреждает, что объявление надо дописать.

Скрытая опция **не сбрасывается**: значение остаётся в конфиге сборки и вернётся, когда
арт появится.

### 6.2 Раскладка нынешних опций (из `Options.inc.h`, требует сверки)

| Опция | Нужен контент? | Возможность |
|---|---|---|
| `oxceHdScale`, `oxceHdMode` 0, `oxceHdThreads`, `oxceHdFrameSkip` | нет | всегда |
| `oxceHdHoverBob`, `oxceHdEnemyNumber`, `oxceHdKillCam`, `oxceHdLight` | нет | всегда |
| `oxceHdUi`, `oxceHdUiSmooth`, `oxceHdGlobeScale` | нет | всегда |
| `oxceHdUiFont` | TTF | `hdFonts` |
| `oxceHdUiSkin` | скин под цвета интерфейса игры | `hdUiSkin` |
| `oxceHdMode` 1–2 | паки | `terrainHd` / `unitsHd` |
| `oxceHdPictures` | картинки интерфейса этой игры | `hdPictures` |
| `oxceHdGroundVariants` | варианты кадров | `groundVariants` |
| `oxceHdBaseAnim` | фазы BASEBITS | `baseAnim` |
| `oxceHdCraftLights` | `.lights.txt` | `craftLights` |
| `oxceHdCraftOutlines` | `hd/OUTLINE` | `craftOutlines` |
| `oxceHdFx`, `oxceHdFire` | `hd/FX`, варианты SMOKE | `hdFx`, `hdFire` |
| `oxceHdReticle` 2+ | стили прицела | `reticleStyles` |

### 6.3 Те же возможности — в лаунчере и на сайте

Карточка сборки: «HD в этой сборке: шрифты; террейн и анимация базы — нет». До первой
проверки показывается объявление с пометкой «ожидается», после — подтверждённое из
`compat.tsv`.

## 7. Лаунчер: что видит игрок

- **Главная:** большая «Играть» и над ней переключатель сборки — карточка с обложкой
  игры, именем и статусом (§5.1). Недостающие моды докачиваются при первом выборе, дальше
  переключение мгновенное.
- **Сборки:** создать из шаблона, копировать, переименовать, удалить (§3.5). Удаление
  сборки не удаляет моды, которыми пользуется другая сборка.
- **Экран сборки:** игра, моды с порядком и статусами, строка возможностей HD, кнопки
  «рекомендованный порядок» и «сбросить настройки к профилю».
- **Сейвы:** у сейва — список подходящих сборок, а не «чей он» (§3.4).
- **Свои моды игрока:** видны, не трогаются, проходят слои 1–2. Перетащил zip — лаунчер
  читает `metadata.yml`, кладёт мод в `user/mods` и сразу ловит дубль zip и папки.
- **Перед «Играть»** лаунчер перечитывает `options.cfg` сборки и проверяет состав (§3.3).
  Изменение состава в игровом меню видно в карточке: «состав изменён в игре — проверка не
  относится к нему».
- **Статусы видны все** (§5.1). Красные и несовместимые строки показаны с причиной и
  заблокированы в обычном режиме; в режиме для опытных — запуск с явным подтверждением.
- **Пока игра идёт**, экраны сборок только для чтения (§3.6).
- **Невидимый помощник** (EDITIONS §7) не меняется. Игра, запущенная с `-cfg`, сообщает
  лаунчеру id сборки, и строка обновления в меню касается её модов.

- **Каталог** строится из `catalog.json`: игры, их обязательные моды, дополнения, общие
  моды, автор, источник и права.
- **Матрица совместимости** из `compat.tsv`: строки — моды и шаблоны, столбцы — игры и
  линии движка. В клетке три результата (§5.1), охват графики, сценарий и дата проверки.
- **«Поставить в лаунчере»** — ссылка `xpl://build/new?template=rosigma-hd`, этап 7.
  Регистрация схемы в `HKCU\Software\Classes` — **отдельная галочка в установке**, по
  умолчанию выключена. Ссылка только **выбирает известный шаблон** из подписанного
  каталога: по ней нельзя передать ни URL загрузки, ни путь, ни список модов. Неизвестный
  id шаблона — лаунчер открывается и говорит, что такого шаблона нет.
- Разделы на сайте уже есть (`portal/deploy/seed/community.json`, `CommunitySeed`).

## 9. Права на раздачу

- Пиратки и RU-патч — разрешение есть (DECISIONS 2026-09-25).
- RoSigma, 40k, X-Com Files и другие — у каждого свой автор, разрешения нет. Без него —
  источник `upstream` (ссылка и sha256 на файл автора; ModDB отдаёт 403 не браузеру,
  EDITIONS §12.7) или «укажите скачанный архив».
- Наши слои поверх чужого мода — только отдельным модом, не правкой его файлов.

## 14. Что изменилось против редакции 1

- Введены `engineMaster` и `targetGame`; совместимость пишется на игру (§2, §4.1).
- `hd_ui` больше не универсален целиком: `hd_core` — только подтверждённое (шрифты,
  независимые курсоры); скин, прицелы, глобус и эффекты — в пакете игры (§5.4).
- «Проверено» разбито на три результата с отпечатком сборки; смоук-тест больше не
  «по желанию» — это отдельный результат (§5.1).
- Сейв не определяет сборку — только список подходящих (§3.4).
- Аудит записываемых файлов по коду (§3.2); правила безопасной записи, одна игра на
  установку, проверка обновлений против всех сборок, откат (§3.6); поведение рекомендаций
  при копии сборки (§3.5).
- Подпись ресурса: итоговый ресурс, состав подписи, вне цикла отрисовки, кэш, откат на
  классику (§5.4 п.3).
- Порядок загрузки — стабильная топологическая сортировка (§5.2); объём проверок (§5.5).
- Этапы перестроены (§11).

## 15. Что изменилось против редакции 2

- `targetGames` защищает только выбор в лаунчере; смена состава в игровом меню обнуляет
  проверку; от подмены HD-кадров при загрузке защищает подпись ресурса (§4.1).
- Лаунчер перед каждым запуском перечитывает `options.cfg` сборки и проверяет состав;
  `targetGame` — заявка, недостоверная при выключенных обязательных компонентах (§3.3, §4.2, §7).
- Результаты проверки: пройдено / провалено / не запускалось / результат не получен /
  не требуется. Провал смоука — красный, сбой стенда — не результат, отказ графики — не
  зелёный, но с предложением классической графики; сборка без HD может быть зелёной (§5.1).
- Охват графики — ожидалось / проверено / отвергнуто / не проверено; контрольные кадры
  подтверждают только названные сцены (§5.3).
- `xpl:` — отдельная галочка, только известный шаблон из подписанного каталога (§8).
- Видны все статусы, несовместимые заблокированы с причиной (§7).
- Раздел `hd` — выпуск до первой чужой игры, проверка удаления старых файлов (§11).
- «Яблоки» заменены на «пример общего дополнения», из примера каталога убраны (§2, §3.1, §4.1).
- §13 — рекомендации специалиста, ждут решения Vitali.

## 16. Правки приёмки после редакции 3

Специалист принял редакцию 3 как основу реализации; новая редакция не заводилась.

- «Графика пройдена» — только при полном охвате подписей; частичный прогон — новое
  значение «не завершено», зелёного не даёт (§5.1, §5.3).
- Одноразовый запуск с классической графикой: голый `-oxceHdMode 0` перезапишет конфиг
  сборки при выходе (проверено по коду); способ выбирается опытом, приёмка — опытом с
  контролем (§5.1, §11 этап 6).
- Новый отпечаток без результатов — «не проверялось» по таблице §5.1 и в §3.3 (раньше в
  §3.3 стоял «жёлтый»).
- Приёмка этапа 1 перечислена: миграция, независимость настроек двух сборок, сохранность
  сейвов, запрет записи под работающей игрой (§11).
- §13: RoSigma — после проверки связки с 40k; общее дополнение — выбор отложен; пункты
  §13 этап 1 не задерживают.
