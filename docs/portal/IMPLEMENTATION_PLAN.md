# Портал, лаунчер и обратная связь — план реализации

Версия 0.1 · 2026-09-22. Архитектура — `ARCHITECTURE.md`. Сложность: S — дни, M — неделя-две
работы агента с проверкой, L — больше. Сроков нет намеренно.

## Раскладка в репозитории

Предложение, окончательно — после ответа на OPEN_QUESTIONS, вопрос 4:

```
portal/                          — отдельное решение .NET 10, в CMake движка не входит
  Portal.sln
  src/Xp.Manifest/               — схема manifest, правила пути, подпись (общая для всех)
  src/Xp.Launcher/               — лаунчер
  src/Xp.Bootstrapper/
  src/Xp.ReleaseBuilder/
  src/Xp.Portal/                 — API + Portal + Admin
  tests/…                        — xUnit на каждый проект
  web/tools/                     — графические утилиты (статичные JS + Worker)
  deploy/                        — docker-compose (Postgres, MinIO, ClamAV), .env.example
src/Engine/Feedback.{h,cpp}      — единственная новая единица в движке
docs/portal/                     — эта папка, плюс руководства пользователя и команды
```

Новые каталоги не пересекаются с файлами апстрима, поэтому слияние с MeridianOXC (`tools/merge`)
их не задевает. Правка движка — один новый файл и несколько строк в `Game.cpp`, `main.cpp`,
`CrossPlatform.cpp`, `Options.*`.

## Этап 0 — аудит и проектирование (этот документ) · S

Готово: карта проекта, архитектура, модель угроз, схема manifest, модель данных, набросок API,
вопросы, риски. **Не готово**: макеты экранов и OpenAPI — они делаются в начале этапов 1 и 2,
когда подтверждён стек.

## Этап 1 — updater, работающий без сервера · L

Сервер для этого этапа не нужен: manifest и блобы лежат в любом статическом хранилище, в
разработке — в локальной папке или MinIO.

1. `Xp.Manifest`: схема, сериализация, правила пути, Ed25519 (библиотека NSec или
   BouncyCastle — выбрать по поддержке .NET 10), генерация ключей.
2. `Xp.ReleaseBuilder`: `dist/_stage` → блобы по хэшу + manifest + подпись; выгрузка в папку или
   S3; реестр релизов пока — JSON-файл каналов.
3. Прототип оболочки лаунчера: Avalonia/NativeAOT против WinForms — замер размера и холодного
   старта, решение записывается в `docs/DECISIONS.md`.
4. `Xp.Launcher`: выбор каталога, канал, проверка, докачка, staging, откат, блокировка при
   запущенной игре, лог, запуск игры.
5. `Xp.Bootstrapper` и самообновление.

**Приёмка**: автотесты на все 12 сценариев раздела 15 ТЗ «Launcher/updater» (временный каталог,
локальный HTTP-сервер с обрывом и докачкой, поддельная подпись, path traversal, падение посреди
установки); ручной прогон на реальной установке Пираток: сейвы и `options.cfg` побайтно те же до и
после.

## Этап 2 — тикеты на сайте · L

1. Каркас `Xp.Portal`: Identity (Argon2id, TOTP, подтверждение email), роли и permissions, CLI
   первого SuperAdmin, миграции, `docker-compose` для разработки.
2. OpenAPI-контракт `/api/v1`, клиент в лаунчере генерируется из него.
3. Тикеты: форма гостя и пользователя, вложения потоком в S3, magic bytes, лимиты, ClamAV →
   карантин, кабинет, секретная ссылка гостя, переписка, внутренние заметки, история.
4. Админка: очередь по разрешённым категориям, статусы, ответственный, дубликаты, аудит.
5. Telegram: `TelegramRoute`, фоновая очередь, retry/backoff, dead-letter, экранирование.
6. Минимальный публичный сайт: главная, текущая версия, changelog, «Скачать launcher».

**Приёмка**: интеграционные тесты на Postgres в контейнере: матрица ролей, Admin code не видит
graphics, IDOR, повтор `Idempotency-Key`, XSS в заголовке, подделка MIME, текст сообщения
Telegram сверяется с шаблоном.

## Этап 3 — F8 в игре · M

1. Движок: `Feedback.*`, `FeedbackState`, запуск лаунчера, папка `user/reports/<uuid>/`.
   Клавиша — по решению OPEN_QUESTIONS, вопрос 2.
2. Лаунчер в режиме `--report`: форма, предпросмотр скриншота, галочки лога и сейва с именем и
   размером, вычистка лога, черновик, офлайн-очередь, номер тикета.
3. Проверка движка по Definition of Done проекта: сборка без новых предупреждений, IDENTICAL при
   `k = 1` и `k = 4`, `drawMs`/`flipMs` не хуже, ванильный UFO и Пиратки.

**Приёмка**: матрица «экран × режим окна × пауза до F8» (геоскейп, база, бой, инвентарь,
уфопедия; окно и полный экран; пауза была и не было). Геоскейп-время до и после отмены формы
сравнивается по сейву.

## Этап 4 — отчёт после краша · M

Маркер сессии в движке, обнаружение в лаунчере (с учётом кода выхода и штатного закрытия
на время обновления), вычистка, выбор файлов, очередь, тикет с источником `crash`, ротация
`launcher/logs` и `launcher/queue`.

**Приёмка**: принудительное падение отладочной клавишей в debug-сборке → при следующем
запуске есть предложение; штатный выход и закрытие лаунчером — нет.

## Этап 5 — документация, roadmap, донаты, утилиты · M

Статьи с версией и датой, roadmap с журналом и проверкой 0–100, две раздельные карточки донатов
с allowlist доменов, все десять графических утилит в Web Worker. Руководства по разделу 9 ТЗ —
и на сайте, и в `docs/portal/`.

## Этап 6 — укрепление продакшена · M

CI (GitHub Actions: сборка и тесты на каждый push в `portal/`, выпуск ReleaseBuilder с ключом из
секрета), бэкап Postgres и хранилища с проверенным восстановлением, метрики и страница очередей
в админке, нагрузочный прогон manifest и загрузок, проверка заголовков (CSP, HSTS), runbook.

## Порядок коммитов

`portal: …`, `launcher: …`, `feedback: …` — одно логическое изменение на коммит, как в остальном
проекте. После каждого этапа — короткий отчёт в формате раздела 18 ТЗ и запись в `CHANGELOG.md`
на языке игрока.
