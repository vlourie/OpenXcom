## 2026-09-18 — цвет мода задаёт оригинал, яркость — художник
Контекст: X-Piratez заменяет боевую палитру целиком (PAL_DGOOD_NORMAL -> PAL_BATTLESCAPE, delicious_regular.pal). Художник считал насыщенные цвета ошибкой и перекрашивал: рампа 192-207 (розовый -> фиолетовый) уходила в бежевый, цветность падала с 36 до 4. Старый color_match не помогал: он двигает среднее и разброс по каналу для всего кадра, а розовая область - 8 % пикселей.
Решение: в build_pack добавлен chroma_lock (ключ --chroma-lock, по умолчанию 1.0). В CIELAB яркость берётся от художника, цветность - от оригинала. Привязка тем жёстче, чем насыщеннее цвет оригинала (0.25 для спокойного, 0.92 для яркого); оригинал берётся размытым, потому что цветность низкочастотна.
Причина: яркость - это работа художника (объём, фактура, светотень), цветность - замысел автора мода. Их надо разделять, а не усреднять.
Последствия: отличие по цвету упало вдвое (LIGHTNIN 18.1 -> 8.9, DESERT 23.5 -> 10.5). Художник больше не может осознанно перекрасить объект - если это когда-то понадобится, ключ выключается нулём. Меряем отличие только по a/b: обычный dE штрафует за светотень, которую мы как раз хотим.

## 2026-09-18 — полы и объекты красим разной силой
Контекст: при общей strength 0.8 мелкие объекты модель рисует заново по-своему: кактус раздувался, уезжал из силуэта, и обрезка оставляла бежевый огрызок (DESERT кадр 10). На полах та же 0.8 даёт хорошую фактуру.
Решение: gen_all.ps1 красит набор двумя проходами - полы обычной силой, объекты с -ObjectStrength (0.55). Второй проход берёт полы из листа первого (gen_hd --only objects). В негатив добавлены горшок, кашпо, подставка, пьедестал, столешница, продуктовое фото.
Причина: проверено перебором. Опыт показал, что усиление ControlNet (tile 0.6 -> 1.1) делает хуже: модель крепче держится за оранжевые пиксели песка и дорисовывает горшок всё убедительнее. Работает именно снижение силы.
Последствия: два прохода вместо одного (на CORP.PCK 155 кадров - 3 минуты). Объекты стали скромнее по фактуре, зато остаются на своём месте.

## 2026-09-18 — объём работы считаем по непустым кадрам, но экономии почти нет
Контекст: hd_coverage считал кадры по числу записей в .tab. У CORP.PCK 155 записей, а непустых 52 - build_pack пустые пропускает.
Решение: hd_coverage декодирует PCK и считает только непустые (8 мс на набор, ~5 с на все 625); в таблицу добавлена колонка total. Если разобралось меньше половины кадров - пишем "?", а не число.
Причина: считать пустые кадры работой - завышать план.
Последствия: гипотеза о трёхкратном сокращении НЕ подтвердилась. По всем 625 наборам пустых всего 312 кадров (0.8 %): CORP оказался исключением, у FREIGHTER_COMMAND и SEAURBAN пустых нет вовсе. Объём остался прежним - около 39 000 кадров.
